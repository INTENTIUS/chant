# Composed stacks demo

chant's own composed-stacks run, as a tree a demo host can drive. It is a stock
chant project: three CloudFormation stacks, `network`, `app` and `edge`, each a
`*.component.ts` and a source directory under `src/`. There is no hand-built
pipeline.

```
network  <-  app  <-  edge
```

Each stack reads the one before it through CloudFormation parameters. A
component names the edge twice: `dependsOn` orders the run, and a
`stackOutput` input fills the parameter the stack's `params.ts` declares from
the other stack's output. There are no exports (floci gets those wrong).

The base is a running set of stacks. network holds a VPC, `subnetA`
(10.0.1.0/24) and the SSM parameter `httpProxyPort` (8080), and publishes
`VpcId`, `SubnetAId` and `HttpProxyPort`. app holds a security group, a
network interface in subnet a and the SSM parameter `listenerPort`, which takes
the proxy port, and publishes `ListenerPort`. edge holds the SSM parameters
`allowlist` (`10.0.1.0/24`) and `upstream` (`http://app:<ListenerPort>`).
Every value that stands in for a setting is an SSM parameter, a resource floci
creates at once. The VPC, the subnets, the security group and the network
interfaces are the only resources with an id, and none of them boots anything.
No scenario replaces or deletes a resource.

## What runs where

`.forgejo/workflows/chant-pr.yml` is the pipeline chant generates for the
project, byte for byte:

```
chant build --components --generate forgejo --pr-loop --env demo \
  --image demo-chant-compose:local --events-json \
  --report-url 's3://demo-reports/demo/chant/${{ github.repository }}' \
  --pr-build-command 'ln -s /opt/demo-chant-compose/node_modules node_modules && npm run build'
```

On each pull request `chant components pr-plan` plans the stacks the change
reaches and posts one note with one digest. On each push to main
`chant components pr-apply --require-review` plans them again, checks that the
digest is the approved one and applies network, app and edge in that order.
The demo host runs both in Forgejo, in a job image tagged
`demo-chant-compose:local`, against a floci. The loop that does so lives
outside this directory and fetches it. The driver is two people: the author
opens and merges the pull request, and the reviewer approves with
`chant approve` and its own key.

One approval covers the apply's second plan when that plan only fills in what
the first marked unknown. The pipeline is generated by chant 0.124.30 (the
`package.json` pin, as in `fan-out-estate`), and the job image carries chant
and its aws lexicon built from a commit of INTENTIUS/chant, because covered
rounds (chant#4419) are in no release yet.

`scenarios/` is the part of the tree the base does not get: the demo host
leaves it out of the base and overlays one scenario's `pull/` onto main for its
pull request. A scenario's `pull/` carries `*.component.ts` files of its own,
so the pipeline is generated from a copy of the tree without `scenarios/`.

## The scenarios

Each has `about.json` (the kiosk's card), `pull/` (the pull request) and
`ask.json`, the prompts and replies the demo's prompt pane plays (the tips are
objects with a title, a body and an optional link).

- `chant-compose-edit`: network's proxy port goes from 8080 to 8090 and it
  gains an `adminPort` of 9000. app adds `adminListenerPort`, and edge
  `adminUpstream`. The plan is 3 to create, 3 to change and 0 to delete, and
  every value is known at plan. A network output whose value is a string in the
  source, or a parameter the plan has a value for, is known at that value, so
  app and edge are planned on 8090 and 9000.
- `chant-compose-create`: network adds `subnetB` (10.0.2.0/24) and publishes
  `SubnetBId`, unknown at plan. app adds `workerInterface` in it, reading
  `SubnetBId` through a parameter of its own. edge's `allowlist` becomes
  `10.0.1.0/24,10.0.2.0/24`, a known value. app publishes the worker's subnet
  as `WorkerSubnetId`, and edge records it in `workerSubnet`. The plan is 3 to
  create, 1 to change and 0 to delete. Two values are known after apply: the
  worker's `SubnetId` and edge's `WorkerSubnetId`. After network applies, the apply plans app and edge again, and
  the first approval covers that round.

## The base and the reset

The demo host applies the base with `chant run --components all` in the job
image, outside the pipeline, and pushes it with `[skip ci]`. Each reset applies
the base tree's templates again, which brings every stack back to its base
template (`stacks_back`). Nothing in CloudFormation is left locked: each
stack's update has ended before the next step starts.
