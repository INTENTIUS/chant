## Synopsis

```
chant release cut [<label>|auto [--pre <id>]] [--at <sha>] [--yes] [--build <command>] [--param <name=value>]... [--params-file <file>]
                  [--src <dir>] [-o <file>] [--lexicon <name>] [--actor <name>] [--sign [<key file>]] [--channel <tag>] [--lane <name>] [--override-green]
                  [--image <component>=<repository>@sha256:<hex>]... [--json]
chant release next [--at <sha>] [--pre <id>] [--json]
chant release changed [--at <sha>] [--bump-member <member>=<level>]... [--json]
chant release candidates [--env <env>] [--branch <branch>] [--lane <name>] [--forge-issues] [--json]
chant release compose <name> [--base <label|sha>] (--pr <n> | --work <id>)... [--yes] [--json]
chant release doctor [--json]
chant release publish <label|digest> [--yes] [--allow-unsigned] [--require-provenance] [--json]
chant release verify <label|digest> [--sigstore [--assets <dir>]] [--json]
chant release stamp <label> [--json]
chant release tag <label|digest|tag> [--json]
chant release artifacts <label|digest> [--no-build] [--from <dir>] [-o <dir>] [--json]
chant release init [--yes] [--force] [--forge github|gitlab|forgejo] [--json]
chant release workflow [--forge github|gitlab|forgejo] [--install <command>] [--build <command>] [--chant <command>] [--output <file>]
chant release deprecate <label|digest> [--yes] [--reason <text>] [--replacement <label>] [--actor <name>] [--sign [<key file>]] [--json]
chant release yank <label|digest> [--yes] [--reason <text>] [--replacement <label>] [--forge-release prerelease|draft|delete]
                  [--actor <name>] [--sign [<key file>]] [--json]
chant release restore <label|digest> [--yes] [--actor <name>] [--sign [<key file>]] [--json]
chant release list [--json]
chant release export <label|digest> --env <env> [-o <dir>] [--json]
```

A release is the compiled output of one green commit of one member ([#4026](https://github.com/INTENTIUS/chant/issues/4026), [ws-104](https://github.com/INTENTIUS/chant/blob/main/docs/design/decisions/ws-104-the-release-model.md)). The commit is the source, and the release is what moves through the environments. A release holds the commit, the artifacts built once from it, and one target per environment. A target lists the templates compiled for that environment and the build parameters they were compiled with.

This is a separate object from a deploy record. A deploy record is a line of `<env>/releases.jsonl` that `chant run --components` and `chant components promote` append when they deploy a component. [`chant components promote --release`](/chant/cli/components/#components-promote) deploys one target and names its digest on the deploy record it writes.

## release init

Sets up `chant release` in a project that has never used chant. It reads the project, writes a `release` block into `chant.config.ts`, writes the release workflow with [`release workflow`](#release-workflow), and lists what has to be set up by hand on the registries.

```bash
chant release init          # a dry run: prints the block and why
chant release init --yes    # writes it
```

| Flag | Description |
|---|---|
| `--yes` | Write the config, the workflow and the goreleaser change. Without it nothing is written |
| `--force` | Replace an existing `release` block, and a release workflow file chant did not write |
| `--forge <forge>` | The forge the workflow is written for. Default: the repository's workflow directory (`.github/workflows`, `.forgejo/workflows`, `.gitlab-ci.yml`), else the forge `origin` names, else `github` |
| `--json` | Print the plan as JSON: `release`, `reasons`, `notes`, `registry`, `workflow`, `goreleaser` and `next` |

What it reads, from the directory it runs in, and what each sets:

| Found | Sets |
|---|---|
| The repository's tags | `release.tag`: the prefix most version tags share, such as `v{version}` for `v1.2.0` or `cli-v{version}` for `cli-v0.4.1`; `v{version}` when no tag names a version, or `{path}/v{version}` for a Go module in a subdirectory. A release of more than one package keeps `v{version}` unless its tags are `v<version>` already. `release.legacyTags` lists the prefixes the existing tags use, so [`release changed`](#release-changed) reads them as earlier releases |
| `ci.green` in `chant.workspace.json`, or `ci/green/` tags | `release.green: "chant"`; otherwise `"forge-checks"`. A repository with no CI workflow is told that a cut refuses a commit with no checks |
| `package.json`, with npm `workspaces` (a list or `{ packages }`) or `pnpm-workspace.yaml` | An `npm` target for every package not marked `private`, in dependency order, with `access: "public"` when a scoped package has no `publishConfig.access`. `release.version` stamps the same packages, with `ranges: "exact"` when one depends on another |
| `engines.vscode` in a `package.json` | `marketplace` targets for the VS Code Marketplace and Open VSX (trusted publishing) from `dist/<name>.vsix`, and `VSCE_PAT` from the repository's secrets in `release.workflow.env` |
| `Dockerfile` or `Containerfile`, at the root or up to two directories down | A `release.images` entry each, and an `oci` target on the registry of the forge `origin` names: `ghcr.io/<owner>/<repo>`, `registry.gitlab.com/<path>`, or the Forgejo host |
| `.goreleaser.yaml` (or `.yml`, or without the dot) | A [`release.artifacts`](#files-the-release-builds) entry `{ name: "goreleaser", goreleaser: {} }`, so the cut runs `goreleaser release --snapshot` once and records the files it writes, and a `forge` release of the `origin` repository with generated notes that uploads them (`assets: ["artifact:goreleaser"]`). The release workflow installs the goreleaser version chant pins. With `--yes`, a config with no `snapshot` section gets `snapshot.version_template: "{{ .Env.CHANT_RELEASE_LABEL }}"`, so its snapshot build carries the release's label; a config with its own `snapshot` section is told to set it. A goreleaser config that builds images (`dockers`, `kos`) leaves the Dockerfiles out of `release.images` |
| `go.mod`, `Cargo.toml`, `pyproject.toml` | Nothing to publish: the release's tag is what the Go module proxy reads, and chant release has no crates.io or PyPI target, which the output says |

`release.workflow` is `trigger: "dispatch"`, so a release is one run started by hand with its label. With pnpm or yarn it installs with `corepack enable` and the lockfile's tool, and builds with that tool when the root `package.json` has a `build` script; with npm and no `package-lock.json` it installs with `npm install`. A `package.json` that does not depend on `@intentius/chant` runs chant in the jobs as `npx --yes @intentius/chant@<version>`, the version that wrote the config.

A project with no `chant.config.ts` gets one holding the block alone. One that has a config gets the block added to the object its default export names: `export default { ... }`, `export default defineConfig({ ... })`, or `export default config` with `const config = { ... }`. A `chant.config.json` is rewritten with the block added. A config that already has a `release` block is refused with `release-init-release-exists` unless `--force`, and one whose default export is not an object literal with `release-init-config-unreadable`; both print the block to add by hand. A release workflow file that chant did not generate is refused with `release-init-workflow-exists` unless `--force`.

The output ends with the steps to take by hand, such as an npm trusted publisher that names the workflow file (`chant-release.yml`) with npm dist-tag allowed, the Open VSX trusted publisher, `VSCE_PAT`, a GHCR package's visibility, and on GitLab the include and `CHANT_RELEASE_TOKEN`. Then it prints the commands to commit and push, to run [`release doctor`](#release-doctor) once those steps are done, and to start the first release with a label: a patch after the newest version tag, or `0.1.0`. Each later release can be started with the label `auto` (`gh workflow run chant-release.yml -f label=auto`), which takes the label from the commits since the previous release with [`release next`](#release-next); the first release has no previous chant release to bump from. The dispatched workflow runs `release doctor` in its cut job too, before the cut.

## release cut

Cuts a release of the member in the current directory from the checkout's `HEAD`. A release is only ever cut by this command; [`chant ci tick`](/chant/cli/ci/#ci-tick) never cuts one ([ws-105](https://github.com/INTENTIUS/chant/blob/main/docs/design/decisions/ws-105-release-trigger-and-revocation.md), proposed). See [Cutting on green](#cutting-on-green) for a pipeline that cuts every green commit, and [Release from your workstation](/chant/guide/release-from-workstation/) for a cut made on a laptop and published from CI.

```bash
git fetch origin --tags
git checkout "$(chant ci last-green)"
chant release cut v1.4.0 --build "npm run build"         # a dry run: prints the plan
chant release cut v1.4.0 --build "npm run build" --yes   # cuts, records and tags
```

Without `--yes` the cut is a dry run ([#4027](https://github.com/INTENTIUS/chant/issues/4027)). It makes every check below and compiles every environment, then prints what the cut would record and tag, and what will be published where. Nothing is built or signed, and nothing is written to `chant/lifecycle` or tagged. Run the same command again with `--yes` to cut. The same command runs unchanged in CI, where it needs `--yes` as well.

The cut refuses before it writes anything when:

| Code | When |
|---|---|
| `release-worktree-dirty` | A tracked file has uncommitted changes, or a file git does not ignore is untracked, so the compile would not be the commit's. A new `*.component.ts` left untracked would otherwise be compiled into the release. |
| `release-commit-not-on-trunk` | `HEAD` is not reachable from `origin/<trunk>` or from any further branch listed in `ci.green.branch` ([#4325](https://github.com/INTENTIUS/chant/issues/4325)), and is not a first-parent commit of a pushed `chant/compose/<name>` branch (see [Cutting a composed commit](#cutting-a-composed-commit)). Trunk is the branch `ci.green.branch` names in the declaration at base, else the branch `origin/HEAD` names, else `main`. |
| `release-commit-not-pushed` | `HEAD` is on the local trunk branch but not on `origin/<trunk>`, or this clone has no `origin/<trunk>`. The check reads the remote-tracking branch as this clone last fetched it and fetches nothing, so a commit pushed from elsewhere needs a `git fetch origin <trunk>` first. |
| `release-commit-not-green` | The [green gate](#the-green-gate) does not pass. Under `chant`, `HEAD` has no `ci/green/<sha>` tag, or with a lane no `ci/green-<lane>/<sha>` tag (see [Cutting from a lane](#cutting-from-a-lane)). [`chant ci`](/chant/cli/ci/) makes the tags; only local tags are read, so fetch them first. With [signed tags](/chant/cli/ci/#signed-tags), a tag without a valid statement doesn't count, and the message names it. Under `forge-checks`, a check on the forge failed or has not finished, a check the branch requires is missing, or there is no check at all, and the message names them. With `--override-green`, an override can let it through (see [Cutting a commit that is not green](#cutting-a-commit-that-is-not-green)). |
| `release-forge-checks-unavailable` | `release.green` is `forge-checks`, and the forge can't be asked: the origin remote names no GitHub, GitLab or Forgejo repository, no token is set, or the forge answered with an error. |
| `release-green-none-refused` | `release.green` is `none`, and the declaration at base turns on the `supply-chain` or `verified-releases` security group, or names a `release` gate in `identity.gates`. |
| `release-commit-revoked` | `HEAD` has a `ci/revoked/<sha>` tag, or with a lane a `ci/revoked-<lane>/<sha>` tag. |
| `release-tag-taken` | The tag the release would get (see [The release's tag](#the-releases-tag)) already names another commit. |
| `release-tag-invalid` | The label makes a tag name git refuses. |
| `release-tag-template-invalid` | `release.tag` is not a template: it names no `{version}` or `{label}`, names one twice, names a placeholder there is none of, holds a character a tag can't, or names `{member}` or `{path}` where there is no member or the project is at the repository root. |
| `release-tag-collision` | `release.tag` can make a tag another `chant` member of the workspace can make, so one member's release could take the other's tag. |
| `release-no-environments` | The member's `chant.config.ts` declares no `environments` and no `release.publish` target or `release.images`, so there is nothing to release. With targets and no environments the cut is an [artifact release](#a-release-with-no-environments). |
| `release-no-components` | The member declares environments and components, none is enabled in any environment, and nothing was compiled. A project that declares no component is released from its build output instead, see [a project with no components](#a-project-with-no-components). A project that only publishes packages or files declares no environments. |
| `release-unsigned` | The declaration at base names a `release` gate in `identity.gates`, and the cut is not signed. See [Who may cut](#who-may-cut). |
| `release-signer-refused` | The cut's signature does not verify for the actor against the signers file at base, or the actor is not in the `release` gate's class. Nothing is written. |
| `declaration-invalid` | The cut names a lane, and the declaration at base has no `ci.green` or declares no such lane, or `release.green` is not `chant`, which is the only gate with lanes. The message lists the lanes it declares. |
| `release-build-inputs-differ` | A component's build steps differ between environments, for example a `docker-build` whose `buildArgs` read a parameter that is set per environment. Its artifact can't be built once for every environment. |
| `publish-npm-carries-image` | An `npm` target in `release.publish` would pack an image archive the cut just built ([#4941](https://github.com/INTENTIUS/chant/issues/4941)). The cut runs the npm target's own check (see [Images the package pins](#images-the-package-pins)) once the images are built, so the label is not spent on a release the publish would refuse. `publish-npm-pack-failed` when `npm pack --dry-run` can't list the package. |

The code is printed in square brackets at the end of the message. The dry run refuses with the same codes, and also with `release-label-taken` when the label already names a release of another commit.

`auto` in place of the label cuts the label [`release next`](#release-next) computes for the commit being cut, and refuses with its codes. `--pre <id>` goes with `auto` only. Every cut with a label, `auto` or typed, consumes the [intent files](#intent-files) at the commit that name the member: its cut line lists them, and the dry run prints them.

### Cutting a chosen commit

`--at <sha>` cuts that commit instead of `HEAD` ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). The cut checks the commit out in a temporary detached worktree, runs the compile and the artifact builds there, and removes the worktree when it ends. The checkout you run it from can be at any commit and can have uncommitted changes, so `release-worktree-dirty` does not apply. Every other check in the table above does: the commit must be on `origin/<trunk>`, carry a `ci/green` tag that counts and no `ci/revoked` tag. `--at` takes anything git resolves to a commit, and refuses a name this clone does not know with `release-at-unknown`.

```bash
git fetch origin --tags
chant release candidates
chant release cut v1.4.0 --at 3f2a9c1e0b7d --build "npm run build" --yes
```

The worktree shares the repository's refs, so the release and the cut go to the repository's `chant/lifecycle` and the `release/<label>` tag names the commit. The checkout's `node_modules` are linked into the worktree at the top and in each directory down to the member, so the compile resolves the packages already installed. A commit whose lockfile differs from the checkout's needs its own install.

### Cutting a composed commit

A commit of a pushed `chant/compose/<name>` branch, as [`release compose`](#release-compose) makes it, is cut like a trunk commit ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). The branch is read as this clone last fetched it from `origin`. Green and revoked tags decide as they do on trunk. With [signed tags](/chant/cli/ci/#signed-tags) the tag's statement names the compose branch the tick walked.

The cut line's `composed` field names the branch and the base it was composed on. It also lists the trunk commits its `Chant-Composed-From` trailers name, oldest first. The walk goes back along first parents to the first commit on trunk, past any commit made on the branch by hand. `--channel <tag>` records `channel` on the cut line, and [`release publish`](#release-publish) then moves that tag in place of `latest`. The dry run and `--json` print both as `composed` and `channel`, and print `prerelease` too: true when the label is a semver prerelease such as `1.4.0-rc.1`, which a publish treats as one without a channel.

```bash
git fetch origin --tags
chant release cut v1.4.1 --at "$(git rev-parse origin/chant/compose/hotfix-1-4)" --channel hotfix --yes
```

### Cutting from a lane

A workspace whose `ci.green` declares [lanes](/chant/cli/ci/#green-lanes) tags a commit `ci/green-<lane>/<sha>` once that lane's phases pass, without waiting for the rest. `--lane <name>` cuts from that tag ([#4692](https://github.com/INTENTIUS/chant/issues/4692)): the commit must carry `ci/green-<lane>/<sha>` that counts and no `ci/revoked-<lane>/<sha>`, and `ci/green/<sha>` is not needed. A member that is always released from one lane sets it in its config, and `--lane` on the command line wins over it:

```ts
// chant.config.ts
export default {
  environments: ["staging", "prod"],
  release: { lane: "server" },
};
```

```bash
git fetch origin --tags
chant release cut v2.3.0 --at "$(chant ci last-green --lane server)" --lane server --yes
```

The lane must be one the declaration at base declares under `ci.green.lanes`, and with [signed tags](/chant/cli/ci/#signed-tags) the tag's statement must name that lane. The cut line records `lane`, and the dry run and `--json` print it, as does `release list`. Without a lane, nothing changes.

A release cut from a lane is revoked as any other is, by a `ci/revoked/<sha>` tag on its commit. A `ci/revoked-<lane>/<sha>` tag made after the cut does not revoke it yet: it refuses the next cut of that commit in that lane.

### Cutting a commit that is not green

Sometimes a release has to go out from a commit that is not green: a red phase that is known to be unrelated, or CI that is down. `--override-green` cuts such a commit under a person's override ([#4693](https://github.com/INTENTIUS/chant/issues/4693)). The override is the one [the override gate](/chant/guide/ops/#overriding-a-denied-plan) records for a denied plan, on `_gates/policy-override.jsonl` on `chant/lifecycle`, so the same people may write it, it needs a reason, and it is spent once used. It takes three steps:

```bash
# 1. The cut is refused, and records the request for an override of release-3f2a9c1e0b7d.
chant release cut v1.4.1 --at 3f2a9c1e0b7d --override-green --yes
# 2. A person the overriders file lists overrides it, with the reason.
git fetch origin chant/lifecycle:chant/lifecycle
chant approve policy-override release-3f2a9c1e0b7d --rule ci-green --reason "windows runners are down; server phases passed" --actor github:alice
# 3. The same cut, now under the override.
chant release cut v1.4.1 --at 3f2a9c1e0b7d --override-green --yes
```

The subject is `release-<sha12>`, the plan the commit's full sha, and the rule `ci-green`, or `ci-green-<lane>` for a cut [from a lane](#cutting-from-a-lane). The refusal prints the exact `chant approve` line. An override counts when:

- a person wrote it: a line an agent, an MCP or ACP session, a job (`via`) or a forge review wrote does not count;
- `.chant/overriders` at base lists that person, one principal per line, and without the file nobody may override;
- it gives a reason;
- under a `release` gate in `identity.gates`, it is sealed (`chant approve ... --sign`) by a key the signers file at base lists for that person;
- no earlier cut spent it.

The cut that counts it writes the applied record to `_gates/policy-override/applied.jsonl` before its cut line, so one override lets one cut through. Another label, or the same commit cut again, needs its own. The cut line records the override, and says the commit was not green:

```json
"override": { "green": false, "tag": "ci/green/3f2a9c1e0b7d...", "by": "github:alice", "at": "2026-11-01T09:12:00.000Z", "reason": "windows runners are down; server phases passed", "digest": "sha256:...", "sealed": false }
```

Only a cut with `--yes` records the request, and it pushes `chant/lifecycle` so the person who answers it can fetch it. A dry run with `--override-green` decides the same way and writes nothing: it prints the override it would spend, or refuses with the command to run. The request stands for 48 hours. An override written after it lapses still counts for the same commit. `--reason` on the cut is refused, since the reason is the overrider's. A commit with a revoked tag is never cut, with or without an override. Without `--override-green` a standing override is not used.

The dry run prints `not green: no ci/green tag` where it would print `green`, and the override it would spend. `release list` marks such a release `not green`, and prints who overrode it and why on stderr. The [`releases`](/chant/reference/workspace-read-contract/) document carries `override` on the cut. The request, the override and its applied record are ordinary override gate lines, so `chant approve` and the gate audit reader (`lifecycle/gate-audit.ts`) read them as they read any override.

### The green gate

What says a commit may be released is `release.green` in the member's `chant.config.ts`:

```ts
release: {
  green: "forge-checks",
  publish: [{ type: "npm", packages: ["."] }],
},
```

| Value | The commit may be released when |
|---|---|
| `chant` | It carries a `ci/green/<sha>` tag that counts and no `ci/revoked/<sha>` tag, as [`chant ci`](/chant/cli/ci/) writes them from `ci.green`. The default when `chant.workspace.json` declares `ci.green`, or when the repository holds any `ci/green/` tag. |
| `forge-checks` | Its checks on the forge passed. The default otherwise. |
| `none` | Always. The cut prints a warning and records that it had no gate. |

Under `forge-checks` the cut asks the forge the CI job runs on, or, outside CI, the one the `origin` remote names, with the token from `CHANT_GITHUB_TOKEN`, `GH_TOKEN` or `GITHUB_TOKEN` on GitHub, `CHANT_FORGEJO_TOKEN`, `FORGEJO_TOKEN`, `GH_TOKEN` or `GITHUB_TOKEN` on Forgejo, and `CHANT_GITLAB_TOKEN`, `GITLAB_TOKEN` or `CI_JOB_TOKEN` on GitLab. On a workstation, `GH_TOKEN=$(gh auth token) chant release cut 1.4.0` is enough for GitHub. What counts as a check:

| Forge | Checks | Required |
|---|---|---|
| GitHub | Every check run and commit status on the commit, by name. A run that passed, was skipped or was neutral counts as passed. | The checks a branch rule (ruleset) of trunk requires. A required check that is not reported refuses the cut. |
| Forgejo | Every commit status on the commit. | The status contexts trunk's branch protection requires, when the token can read it. |
| GitLab | The newest pipeline of each source (`push`, `merge_request_event`, `schedule`, ...) on the commit. | |

A check that failed or has not finished refuses the cut, and so does a commit with no check at all. The release workflow's own runs are left out: on GitHub every run of the workflow file the cut runs in (`GITHUB_WORKFLOW_REF`), on Forgejo the cut's own run, and on GitLab the pipelines started the way the cut's was, from the web or the API. The token needs read access to checks and statuses (`checks: read` and `statuses: read` on GitHub), which a [dispatched release workflow](#the-whole-release-from-the-config) grants its cut job.

`none` is refused with `release-green-none-refused` when the declaration at base turns on the `supply-chain` or `verified-releases` [security group](/chant/reference/security-features/), or names a `release` gate in `identity.gates`: those ask for releases a green gate passed.

The cut line records the gate the commit passed as `green`: `{ "source": "chant", "tag": "ci/green/<sha>" }`, `{ "source": "forge-checks", "forge": "github", "checks": ["build", "test"] }`, or `{ "source": "none" }`. A cut under an override records the override instead. The dry run and the cut print it, [`release verify`](#release-verify) shows it for each cut, and the publish's [provenance statement](/chant/reference/publish-targets/#the-provenance-statement) carries it. `--override-green` works under `forge-checks` as under `chant`: the override's `tag` is then `forge-checks/<sha>`.

### The label in the build

When the cut has a label, every compile and artifact build runs with `CHANT_RELEASE_LABEL` set to it. The version reaches the build without a commit that bumps it ([#4168](https://github.com/INTENTIUS/chant/issues/4168), decision 5). A [build-time parameter](/chant/concepts/build-time-parameters/) reads it by declaring the variable:

```ts
// chant.config.ts
export default {
  environments: ["staging", "prod"],
  buildParams: { version: { type: "string", env: "CHANT_RELEASE_LABEL", required: false } },
};
```

A build step's own tool reads the variable directly. A Cargo crate takes it at compile time with `option_env!("CHANT_RELEASE_LABEL")`, which is `None` for a build outside a cut, or a `build.rs` passes it on with `println!("cargo:rustc-env=APP_VERSION={}", std::env::var("CHANT_RELEASE_LABEL").unwrap_or_default())` and `println!("cargo:rerun-if-env-changed=CHANT_RELEASE_LABEL")`. An npm build reads `process.env.CHANT_RELEASE_LABEL` in its bundler config. A label in the caller's shell is never passed through: only the cut sets the variable, and a cut with no label leaves it unset. A parameter that reads the label is recorded on each target like any other, so two labels of one commit are two releases.

### The label as the package version

A package published by an npm target carries the version in its `package.json`, and a bundle that imports `version` from that file carries it too. Without `release.version` the label must already be that version, so a release needs a commit that bumps it first. `release.version` names the package directories whose `package.json` the release stamps with the label instead ([#4840](https://github.com/INTENTIUS/chant/issues/4840)):

```ts
release: {
  version: { packages: ["packages/cli"] },
  images: [/* ... */],
  publish: [{ type: "npm", packages: ["packages/cli"], pins: "dist/image-digests.json" }],
},
```

| Field | Meaning |
|---|---|
| `packages` | Package directories relative to the member, `"."` for the member's own. Each `package.json` gets the label as its `version`. With the default `ranges`, no other field changes |
| `lockfile` | The lockfile whose entries for those packages follow, with the root entry and the top-level `version` for `"."`. Default `package-lock.json` when the member has one; `false` for none |
| `ranges` | What happens to the ranges of workspace dependencies: `keep` (the default), `exact`, `caret` or `train`. See [Workspace dependency ranges](#workspace-dependency-ranges) |

The cut stamps the files once it has found the tree clean, before it builds the images and before any compile or `--build`, and puts them back byte for byte when it is done, whether it cut or failed. Every image build, `prepare` and build then reads the label as the package's version, so `releaseImagePins` accepts the label and the bundle carries it. A Dockerfile entry in `release.images` also gets the label as the build argument `CHANT_RELEASE_LABEL`. The publish job runs [`chant release stamp <label>`](#release-stamp) before its images and its build, and `chant release publish` takes those files as the commit's when each is exactly the commit's file stamped with the release's label. Any other change still makes the tree dirty. A label that is not a version npm takes (`1.4.0`, `1.4.0-rc.1`, not `v1.4.0`) is refused with `release-version-label-invalid`, a cut with no label with `release-version-no-label`, and a directory with no `package.json` with `release-version-no-package`. `RELEASE_VERSION_FLOOR` in `@intentius/chant/lifecycle/release-version` is the first chant with the setting.

#### Workspace dependency ranges

A package that depends on another package of the same workspace carries a range for it, and that range names a version the release may not publish. `ranges` rewrites it to the label the release gives that package. It applies to `dependencies`, `peerDependencies` and `optionalDependencies` in each stamped `package.json` and in the lockfile's entry for it; `devDependencies` and a range of `*` stay as committed, and so does a dependency on a package the release has no label for.

| `ranges` | A dependency on a package the release stamps becomes | A dependency on another member's package |
|---|---|---|
| `keep` | its committed range | its committed range |
| `exact` | the label, `1.4.0` | its committed range |
| `caret` | `^1.4.0` | its committed range |
| `train` | `^1.4.0` | `^` and the label the [release train](/chant/cli/workspace-train/) pins for the member that owns the package |

```ts
release: { version: { packages: ["packages/conformance", "packages/reference"], ranges: "exact" } },
```

With two packages released in lockstep, `reference` then publishes depending on exactly the `conformance` published beside it. With `train`, members release at their own labels and each package's ranges name the labels of the train it ships in. The cut runs before any train is recorded, so it stamps only the packages of its own release, and the pack step stamps the rest from the train:

```bash
chant release stamp 0.125.3 --train train-2f6c   # in the member's directory
```

`--train` takes a train's id or digest, found in the environments the member's `chant.config.ts` declares. A member owns the packages its `release.version.packages` names; a member with no `release.version` owns none, so dependencies on it keep their ranges. `chant release publish` takes a tree stamped from a train that pins the release's label as the commit's. A package of a member the train pins with no label is refused with `release-ranges-unpinned`, a train that pins none of the member's packages at the release's label with `release-train-not-pinned`, an unknown train with `release-train-unknown`, and `--train` under any other `ranges` with `release-ranges-not-train`.

#### Files that embed the version

A project on `release.version` follows one rule: the committed tree never holds the version being released. Only the release's build writes that version, from the stamped `package.json` or from `CHANT_RELEASE_LABEL`. In practice:

- The `version` in each stamped `package.json` stays where it is on the default branch and no longer moves. chant's own packages do the same: their versions are older than the releases on npm.
- A committed file rendered from the package version, such as a golden, an example pipeline or a generated Dockerfile, is rendered from that committed version. It no longer changes when a release is made, so no release needs a commit to regenerate it.
- A Dockerfile reads the version from a build argument, never from text rendered into it: `ARG CHANT_RELEASE_LABEL` with `LABEL org.opencontainers.image.version="${CHANT_RELEASE_LABEL}"`, and the same argument for a file name that carries the version, such as the tarball `npm pack` writes. A command entry passes `--build-arg CHANT_RELEASE_LABEL="$CHANT_RELEASE_LABEL"` itself, and a Dockerfile entry gets the argument from chant. A build outside a release passes the committed version.
- A committed file that must name a published release, such as an example that runs the newest image, pins that release as it would pin a dependency, in a change of its own, not as part of a release.

The version-bump script and its recipe can then go, and a release is one dispatched run with the new label.

### What the dry run prints

```
Dry run: cut v1.4.0 from commit 3f2a9c1d0b7e (on origin/main, green)
  actor alice@example.com (from git user.email)
  run minted on this machine at the cut (local)
  not signed
  tag release/v1.4.0, made here and not pushed
  dev: 1 template(s)
  prod: 1 template(s)
  api: artifacts built in dev
  digest decided when the artifacts are built
What will be published where:
  api: publish-image to $env.registry in dev, prod, by that environment's deploy (chant components promote --release v1.4.0)
  chant release publish v1.4.0: npm (2 packages) to npm the registry npm's config names
  a publish from here would carry no OIDC provenance: this run is not in CI, and a workstation has no OIDC token
```

The digest is printed when no artifact needs building, since it is then known without a build. `--json` prints the same as a document with `dryRun: true`: the commit, `label`, `releaseDigest` (or null), `alreadyCut`, `targets`, `build`, `reused`, `handed`, `publishSteps`, `signatureRequired`, `actor` and `actorSource`, `run`, `trunk`, `sign`, `tag`, `publish` and `next`.

### What --yes records

With `--yes` the cut builds the artifacts and stores the release. It then appends the cut line, signed when `--sign` is given. The line names who cut and the run it ran in:

| Field | On a workstation | In CI |
|---|---|---|
| `actor` | `--actor`, else the principal the signers file at base lists for the `--sign` key, else git's `user.email`, else `USER` | `--actor`, else the signer, else `GITHUB_ACTOR` or `GITLAB_USER_LOGIN` |
| `runId` | `local-<epoch ms>`, minted from the cut's time | `GITHUB_RUN_ID` or `CI_PIPELINE_ID` |
| `runOrigin` | `{ "forge": "local" }` | `github` or `gitlab`, with the repository and a link to the run |

The line also records the [green gate](#the-green-gate) the commit passed, as `green`.

Everything else in the line, and the whole release, is the same wherever the cut runs. A cut of one commit on a workstation and in CI stores byte-identical release files, and cut lines that differ only in `runId`, `runOrigin`, `actor` and `timestamp`, and in `signature` when two keys signed.

The cut then tags the commit with the [release's tag](#the-releases-tag), `release/<label>` (or `release/<member>/<label>` in a workspace member) unless `release.tag` names another, as an annotated tag whose message names the release digest. The tag is made in this clone only. chant pushes `chant/lifecycle` when there is a remote and never pushes the tag, so pushing it is a step you take, and a CI workflow can publish on it. A release cut without a label gets no tag.

The record is pushed before the tag is made ([#4965](https://github.com/INTENTIUS/chant/issues/4965)). A push the remote refuses is tried again, up to three pushes, after a fetch and a replay onto the remote's tip when another writer pushed first. When none lands, the cut makes no tag and exits 1 with `release-record-not-pushed`, naming what git said. The release workflow pushes the tag only after the cut succeeds, so a tag never names a release the publish job can't find, and the label is not spent: run the cut, or the workflow, again. `RELEASE_CUT_RECORD_FLOOR` is the first chant that does this; before it, the cut printed a warning and tagged. Cutting a release that is already cut is a no-op, and makes the tag if it is missing.

The last lines name the next command. In CI that is `chant release publish <label>`. On a workstation it is `git push origin <tag>`, so that CI publishes. After that it names the publish command and the deploy of the first environment as other choices.

### The release's tag

`release.tag` in the member's `chant.config.ts` names the tag a cut makes, as a template ([#5150](https://github.com/INTENTIUS/chant/issues/5150)):

```ts
release: {
  tag: "v{version}",                               // v1.4.0
  // tag: "cli-v{version}",                        // a prefix of the member's own
  // tag: "{path}/v{version}",                     // a Go module in a subdirectory: tools/v1.4.0
  // tag: { name: "v{version}", floating: "v{major}" },  // and v1, moved at each release
},
```

| Placeholder | Value |
|---|---|
| `{version}` | The label, with one leading `v` dropped when a digit follows it: `v{version}` gives `v1.4.0` for the label `1.4.0` and for `v1.4.0` |
| `{label}` | The label as given |
| `{member}` | The workspace member's ledger name, outer names first and joined by `/`, such as `npm/core` |
| `{path}` | The member's directory from the repository root |
| `{major}` | In `floating` only: the major version of a `MAJOR.MINOR.PATCH` label |

A template names `{version}` or `{label}` once, and holds letters, digits and `. _ + - /` around its placeholders. A member that sets no `release.tag` gets `release/<label>`, or `release/<member>/<label>` in a workspace member, as it always has, so an existing release workflow, script or trusted publisher that reads those tags is unchanged. Setting `release.tag: "release/{label}"` names the same tag in a project with no members.

The cut refuses a template another `chant` member of the workspace could render to the same tag (`release-tag-collision`), reading each member's own `chant.config.ts`. `v{version}` in two members collides, and so do `v{version}` and `v{version}-cli`; `{member}-v{version}`, `{path}/v{version}`, or a prefix per member keeps them apart. A member that sets no `release.tag` never collides with another that sets none, since its tag holds its name.

The ledger names a release by its record, not by its tag. A tag is the template's rendering of the label, and chant reads a release back from its tag by rendering the template for each label the member's ledger holds, with [`release tag`](#release-tag). Changing `release.tag` changes the tags of later cuts; a release cut before keeps the tag it got, and `release tag` and the publish job then render the new template for it.

`floating` names a tag that [`release publish`](#release-publish) moves to the release's commit, here and on `origin`, once every target has revealed: `v1` for an action or a Go major version that consumers pin. The cut never makes it. It moves only for a `MAJOR.MINOR.PATCH` label cut with no `--channel`, never for a [prerelease label](/chant/reference/publish-targets/#prereleases) such as `1.5.0-rc.1` (the publish says it left the tag where it was), and only when no cut of the member has a later version of the same major, so a fix to `1.3` after `1.4` leaves `v1` on `1.4`. A publish that can't move or push it publishes anyway, and warns with the commands to run.

### What the cut compiles

The environments are the entries of the member's [`environments`](/chant/configuration/config-file/#promotion-order-and-canary) array, in order. A pattern entry such as `pr-*` is not compiled. Each environment is compiled in a child process with `CHANT_ENV` set to it, since a template is synthesized for one environment per process. In each one the cut:

1. runs `--build <command>` in the member's directory, when given, with `CHANT_ENV` set;
2. resolves the build parameters the way `chant build --env <env>` does, with `{env}` in a `--params-file` path replaced by the environment's name;
3. discovers the components enabled under those parameters;
4. reads each template their deploys name.

A template is a file named by a literal path in a deploy step's `template`, `manifest` or `values` field, such as `cfn-deploy`'s `template: "dist/api.template.json"`. A path with the `archive:` prefix names the file after the prefix. Build and publish steps are not read. A template that does not exist after the build stops the cut.

Since [#4155](https://github.com/INTENTIUS/chant/issues/4155) the cut also records the other local paths a deploy step names, from the fields [Plan previews](/chant/components/plan-previews/#a-capability-without-plan) lists: a `helm-upgrade` chart, a `kustomize-apply` directory, an `s3-sync` source. A directory is recorded file by file. Each file is a template at its path under the directory, and the target names the directory in `trees`. A directory git ignores, such as a build's `dist`, is recorded whole, since the release is what the build wrote. A file that is not UTF-8, such as a packaged subchart, is recorded as base64 with `encoding: "base64"`. A chart named from a repository is not a local path. Such a path is not recorded and does not stop the cut.

A promote under the release points each recorded path at its copy. A directory is written under `.chant/release-templates/<digest>/<name>/`, where the digest is taken over its files. The deploy reads the tree the cut recorded and not the checkout's. A target cut before #4155 has no `trees`, and a promote of it reads charts and the other directories from the checkout, as it did.

A step that names its files through a key gets them from its capability ([#4542](https://github.com/INTENTIUS/chant/issues/4542)). A `terraform-apply` step names its root by key, and the terraform lexicon answers with the files a pull request's plan counts as the root's change. Those are the root's directory and each local module it reaches through a `./` or `../` source. Its var files and backend-config files are recorded with them. The cut records each of them for the component, directories in `trees`. A root whose state is a file in its own directory (the `local` backend) is left out, and the cut prints why, since a plan of a copy would read no state; such a root rolls back with [`chant lifecycle rollback --to`](/chant/cli/lifecycle/). A path outside the member's directory leaves its step out the same way. The dry run lists each recorded directory under its environment, and `release list --json` shows them in each target's `trees`.

Under the release, a promote or rollback writes every file the target records for the component under `.chant/release-templates/<digest>/`, each at its path from the member's directory, so a root's `../modules/vpc` still resolves. The step's `dir` is set to the copy of the root. `terraform-apply` plans that copy against the environment's state, keeping the rest of the root's entry in `terraform.roots`. The release gate binds that plan, so rolling a root back is a new plan of the old configuration under its own approval. With `terraform.compose.enabled`, a root deployed from a copy plans on its own and never in a composed group.

A `pulumi-up` step records the stack's directory. When `main` points outside it, the program's entry file is recorded too. A stack whose backend is a `file://` path relative to its directory is left out. The cut records tracked files only, so a Node program's copy has no `node_modules`. Before the copy's first preview, `pulumi-up` runs `pulumi install` in the copy (`plunge install` on plunge). That installs the dependencies the recorded lockfile pins and the plugins the program uses. It does the same for a Python program whose virtualenv or `poetry` or `uv` toolchain needs building. A Node copy with no lockfile is refused by name, since an install there would take today's versions rather than the release's. Programs in the other runtimes fetch what they need on the run.

The artifacts are built once. Each component's `docker-build`, `zip-package` and `jvm-build` steps run, and nothing else, in the first environment the component is enabled in. `docker-build` gives an `image` entry and the other two an `asset` entry, each with the archive path and the digest. When a component's source did not change since the release cut from the nearest earlier commit, its entries are carried from that release and nothing is built. Unchanged means git sees no change between the two commits in the component's file, the member's `chant.config.ts`, and the paths the build steps read (`context` and the Dockerfile, `source`, `path`). A commit that only changes a flag or a parameter then gets a release of its own with the same artifact digests.

### An image built elsewhere

Some images can't be built where the cut runs, such as static binaries a CI job builds with a toolchain the cut's machine lacks. The job that built and pushed the image hands it to the cut by digest with `--image <component>=<repository>@sha256:<hex>`, once per component ([#4694](https://github.com/INTENTIUS/chant/issues/4694)):

```bash
digest=$(crane digest registry.fly.io/illogical-control:ci-$GITHUB_SHA)
chant release cut v1.4.0 --image control=registry.fly.io/illogical-control@$digest --yes
```

The release records the image as the component's `image` entry, with its reference in `ref` and an empty `path`, since no build step wrote an archive. The cut builds nothing for that component, and carries nothing for it from an earlier release. The reference must name the repository and the digest, and no tag, since a tag can move after the cut. A reference that does not is refused with `release-image-invalid`, and a component that is not enabled in any environment with `release-image-unknown-component`. The dry run lists each handed image, and `--json` lists them in `handed`.

A deploy under the release runs that image. The component's composition says where it goes with a `release-image` step, which stands where a publish step would ([Running a release](/chant/cli/run/#running-a-release---release)):

```ts
export const control: Component = {
  name: "control",
  dependsOn: [],
  deploy: [
    phase("Approve", [gate("prod-release")]),
    phase("Image", [{ kind: "release-image" }]),
    phase("Release", [{ kind: "fly-release", plan: "dist/fly.json", machine: "controlMachine", image: "@Image.uri", digest: "@Image.digest" }]),
  ],
};
```

`fly-release`'s `image` is the serving Machine's, and its `images` names the plan's other Machines, such as a scheduled one. A Machine built from the same image takes it the same way, `images: { controlCron: "@Image.uri" }`. A release records one image per component, so a Machine that runs another image belongs to the component that image is handed for, or takes it by a literal reference.

The `ref` is in the release digest, so a release that records one is read by chant 0.124.65 and newer. An older chant reads it as a release that does not match its digest.

### Images the package pins

A package that pins container images by digest needs the digests when it is packed. `release.images` in `chant.config.ts` names images the cut builds before anything else ([#4657](https://github.com/INTENTIUS/chant/issues/4657)):

```ts
release: {
  images: [
    { name: "tofu", build: "docker buildx build --provenance=false --sbom=false --output type=oci,dest=dist/tofu.tar,rewrite-timestamp=true -f images/Dockerfile.tofu .", archive: "dist/tofu.tar" },
  ],
  publish: [
    { type: "oci", image: "dist/tofu.tar", repository: "ghcr.io/acme/tofu" },
    { type: "npm", packages: ["packages/cli"], pins: "dist/image-digests.json" },
  ],
},
```

Each `build` runs in the member's directory with `SOURCE_DATE_EPOCH` set to the commit's time and `CHANT_RELEASE_LABEL` to the label, and writes the OCI archive at `archive`, a layout directory or a tar file of one. The cut records the archive's top manifest digest, which is the digest a registry serves once the `oci` target pushes it, as an image artifact named after the image. It writes `{ "<name>": "sha256:..." }` to a file and runs `--build` with `CHANT_RELEASE_DIGESTS` naming that file, so the build that packs the package can copy the digests into it. A name that is also a component's is refused (`release-image-name-taken`). The dry run builds the images too, since its compile runs the build command.

An entry may name a Dockerfile instead of a command, and chant runs the reproducible build itself ([#4819](https://github.com/INTENTIUS/chant/issues/4819)):

```ts
images: [
  { name: "pulumi", dockerfile: "images/plywood-pulumi/Dockerfile", prepare: "npm run build && npm pack -w @intentius/plywood --pack-destination images/pack" },
],
```

chant creates a `docker-container` buildx builder named `chant-release` when there is none. It runs `docker buildx build --no-cache --provenance=false --sbom=false --build-arg SOURCE_DATE_EPOCH=...` for every platform in `platforms` (default `linux/amd64` and `linux/arm64`, one image index) and writes `type=oci,dest=<archive>,rewrite-timestamp=true`. `context` defaults to `.`, and `archive` to `dist/images/<name>.tar`. `prepare` runs once, before any build and with `CHANT_RELEASE_DIGESTS` unset, so whatever the image copies in, such as a bundle or a packed package, is the same in the cut and the publish job. Building arm64 on amd64 needs QEMU's binfmt handlers, which the jobs `chant release workflow` writes set up (see [release workflow](#release-workflow)). A `build` entry may name `platforms` too: chant does not pass them to the command, and the workflow sets up QEMU from them ([#4876](https://github.com/INTENTIUS/chant/issues/4876)). An entry with both `build` and `dockerfile` is refused (`release-image-invalid`). `args` gives more build arguments, `{ NAME: "value" }`, passed as `--build-arg NAME=value` after the two chant passes, which it cannot set ([#4908](https://github.com/INTENTIUS/chant/issues/4908), `RELEASE_IMAGE_ARGS_FLOOR`). The config computes the values, such as the file `npm pack` writes into the context and the chant packages the lockfile holds, so a product whose image takes them needs no build script of its own.

The build that packs the package turns the digests into the table it bakes in with `releaseImagePins` from `@intentius/chant/lifecycle/release-images`. That module loads under plain Node, so a `.mjs` build script can import it. Pass each image's name and its reference at this version, and the package's version:

```js
const table = releaseImagePins({ images: { pulumi: `ghcr.io/intentius/plywood-pulumi:${version}-pulumi3.272.0` }, version });
// ... bundle with the table baked in ...
writeReleaseImagePins(table, { out: "dist/image-digests.json", bundles: ["dist/plywood.mjs"] });
```

Outside a release build the table is `undefined` and `writeReleaseImagePins` removes the pins file. A `CHANT_RELEASE_LABEL` that is not the version is refused (`release-label-not-version`). Under [`release.version`](#the-label-as-the-package-version) the cut and the publish job have stamped the label into `package.json` by then, so a build that reads the version from that file passes it. A name the digests file has no digest for is refused too (`release-image-digest-missing`), and so is a bundle that does not carry every digest (`release-pin-not-bundled`). `RELEASE_IMAGE_DOCKERFILE_FLOOR` is the first chant with them.

The publish job checks out the release's commit and runs `chant release images <label>` before the build that packs the package. It builds each image again, refuses one whose digest is not the recorded one (`release-image-digest-mismatch`), and writes the recorded digests to `.chant/release-digests.json` (or `-o <file>`), printing `CHANT_RELEASE_DIGESTS=<file>` for the job to export. The publish job `chant release workflow` writes passes `-o` a file in the runner's temp directory (`$RUNNER_TEMP` on GitHub and Forgejo, `/tmp` on GitLab), so `chant release publish` finds the checkout as the cut left it, and a repository that commits files under `.chant/` doesn't need to ignore the digests. The `oci` target then refuses an archive that is not the recorded one, so the image pushed is the one the package pins. This needs a build that writes the same archive from the same commit: timestamps rewritten from `SOURCE_DATE_EPOCH`, no logs or caches in the layers, and no attestations built into the archive. #4657's thread has the check against terragucci's Dockerfiles.

An npm target's `pins` names the file in the package that carries the digests. The publish plan refuses a package whose file holds a `sha256:` digest the release does not record as an image (`publish-npm-pin-unknown`), and a target none of whose packages has the file (`publish-npm-pins-missing`). `chant release verify` makes the same check on a package built in the checkout (`release-pin-unknown`).

The archives sit in the checkout when the publish runs: the cut or `chant release images` wrote them there, or the dispatched publish job took the cut's into the same paths. A package directory that an archive the release records lies inside is listed with `npm pack --dry-run --json --ignore-scripts` at the plan, and one that would carry the archive is refused before any target publishes (`publish-npm-carries-image`, [#4934](https://github.com/INTENTIUS/chant/issues/4934)). The message names the file, and the fix names the `files` entry that leaves it out, such as `"!dist/images/app.tar"` for a package whose `files` lists `dist`. `NPM_CARRIES_IMAGE_FLOOR` is the first chant with the check. The cut runs the same check once it has built the images, before it records the release or tags it, and refuses with the same code ([#4941](https://github.com/INTENTIUS/chant/issues/4941), `RELEASE_CUT_CARRIES_IMAGE_FLOOR`), so the label is not spent on a release the publish would refuse.

### Files the release builds

`release.artifacts` lists files the cut builds once and records: binaries, archives of them, a checksums file, what goreleaser writes, or files a job on another runner built before the cut. Each entry has a `name` and one of `outputs` (with or without `build`), `goreleaser` and `checksums`, and the cut builds them in order, after the images and before `--build`.

```ts
export default {
  release: {
    artifacts: [
      {
        name: "tool",
        build: 'go build -trimpath -ldflags "-X main.version=$CHANT_RELEASE_LABEL" -o "dist/${CHANT_RELEASE_OS}_${CHANT_RELEASE_ARCH}/tool${CHANT_RELEASE_EXT}" ./cmd/tool',
        outputs: ["dist/{os}_{arch}/tool{ext}"],
        platforms: ["linux/amd64", "linux/arm64", "darwin/arm64", "windows/amd64"],
        archive: { files: ["README.md", "LICENSE"] },
      },
      { name: "sums", checksums: "dist/SHA256SUMS" },
    ],
    publish: [{ type: "forge", forge: "github", repo: "acme/tool", assets: ["artifact:tool", "artifact:sums"] }],
  },
};
```

A `build` entry runs its command in the member's directory with `SOURCE_DATE_EPOCH` set to the commit's time and `CHANT_RELEASE_LABEL` to the label. With `platforms`, it runs once per platform with `CHANT_RELEASE_OS`, `CHANT_RELEASE_ARCH` and `CHANT_RELEASE_EXT` (`.exe` on Windows, empty otherwise) set; the command passes them to its compiler, as `GOOS=$CHANT_RELEASE_OS GOARCH=$CHANT_RELEASE_ARCH` does for Go. `outputs` names the files it writes, relative to the member. An output may hold `{os}`, `{arch}`, `{ext}`, `{label}` and `{version}` (the label from its first digit), and `*` or `?` within a path segment. An output the build did not write stops the cut (`release-artifact-no-output`), and so does a command that fails (`release-artifact-build-failed`).

An entry with `outputs` and no `build` records files something else built before the cut, such as a [build job on another runner](#builds-on-other-runners): the cut runs nothing for it and records the files at `outputs` as it finds them, per platform when the entry has `platforms`. `builtBy` names the `release.workflow.builds` jobs that write them, and `outputs` then defaults to those jobs' outputs; an entry with `platforms` names its outputs itself. A `builtBy` that names no job of `release.workflow.builds` is refused (`release-artifact-invalid`), by the cut and by `chant release workflow`. A declared output that is not there stops the cut (`release-artifact-not-built`). Under `--at` the cut reads these files from the checkout it runs in, which must be at the commit it cuts (`release-artifact-wrong-commit`), and packs and checksums them in the commit's worktree like any other entry's.

```ts
release: {
  workflow: {
    trigger: "dispatch",
    builds: [
      { name: "linux-arm64", runner: "ubuntu-24.04-arm", build: "GOOS=linux GOARCH=arm64 go build -trimpath -o dist/linux_arm64/tool .", outputs: ["dist/linux_arm64/tool"] },
      { name: "darwin-arm64", runner: "macos-15", build: "GOOS=darwin GOARCH=arm64 go build -trimpath -o dist/darwin_arm64/tool .", outputs: ["dist/darwin_arm64/tool"] },
    ],
  },
  artifacts: [
    { name: "tool", builtBy: ["linux-arm64", "darwin-arm64"], outputs: ["dist/{os}_{arch}/tool"], platforms: ["linux/arm64", "darwin/arm64"], archive: true },
    { name: "sums", checksums: "dist/SHA256SUMS" },
  ],
},
```

With `archive`, each platform's outputs are packed, beside the files `archive.files` names, into one archive per platform, and the release records the archives in place of the outputs. An archive is a tar.gz, or a zip for a Windows platform, unless `archive.format` names one. It is written to `archive.dir` (default `dist`) as `archive.name` (default `{name}_{os}_{arch}`, or `{name}` with no platforms) plus the extension. chant writes the archives itself: every entry is dated `SOURCE_DATE_EPOCH`, owned by root, and mode 0755 when executable, else 0644, so the same files pack to the same bytes. `archive: true` takes every default.

A `checksums` entry writes a file of `<sha256>  <file name>` lines, sorted by name, as `sha256sum` writes them and `sha256sum -c` checks them. It covers the files of the entries `of` names, or of every entry before it. Two covered files with one name are refused (`release-artifact-checksums-name-taken`).

A `goreleaser` entry runs `goreleaser release --snapshot --clean --skip=publish` in the member's directory, with `--config` when `goreleaser.config` names one, so goreleaser builds and publishes nothing. The run is `CHANT_GORELEASER` when set, else `goreleaser` on the `PATH`. The config's snapshot version must be the label chant passes, so the binaries carry the release's version:

```yaml
snapshot:
  version_template: "{{ .Env.CHANT_RELEASE_LABEL }}"
```

chant reads `metadata.json` in goreleaser's `dist` (`goreleaser.dist`, default `dist`) and refuses a version that is neither the label nor the label from its first digit (`release-artifact-version-mismatch`). It records the files `artifacts.json` lists whose `type` is in `goreleaser.types`: by default `Archive`, `Checksum`, `File`, `Linux Package`, `SBOM`, `Source`, and a `Binary` at the top of `dist`, which are the files goreleaser's own release would upload. chant's targets publish them. A goreleaser entry needs a label (`release-artifact-no-label`), and so does an output or archive name that holds `{label}` or `{version}`.

Each file is recorded in the release as an `asset` artifact whose `component` is the entry's name. Two entries, or two platforms, writing one path are refused (`release-artifact-output-taken`), and so is a name that an image or a component also has (`release-artifact-name-taken`). A forge or homebrew target names an entry's files with `artifact:<name>` in its `assets`; a name the release records no file for is refused at the publish (`publish-artifact-not-recorded`). Every target that reads a recorded file refuses one whose digest differs (`publish-artifact-digest-mismatch`), and the signing, provenance and SBOM checks of the security groups apply to these files as to any other. `RELEASE_ARTIFACTS_FLOOR` is the first chant with `release.artifacts`.

The files sit in the checkout when the publish runs, so their directory belongs in `.gitignore`: the publish refuses an untracked file (`release-worktree-dirty`). The publish job of a dispatched release gets them from the cut job (see [release artifacts](#release-artifacts)), and on a release tag it builds them again with `chant release artifacts <label>`, which needs builds that write the same bytes twice, such as `go build -trimpath` and archives dated from `SOURCE_DATE_EPOCH`. An entry with no `build` is not built again there: the files must be in the checkout by then, written by the workflow's build step.

### A project with no components

A project with no `*.component.ts` file is cut from what `chant build` writes ([#4046](https://github.com/INTENTIUS/chant/issues/4046)). For each environment the child process builds the project as `chant build <src> --env <env> -o <output>` would, with the environment's build parameters, and every file that build writes becomes a template with `component: null`. The target's `params` are the build's resolved parameters, and `artifactDigests` is empty.

| Flag | Meaning |
|---|---|
| `--src <dir>` | The build root, relative to the member's directory. Defaults to `chant.config.ts` `sourceDir`, then the member's directory, as [`chant lifecycle`](/chant/cli/lifecycle/) resolves it. A project that declares `stacks` must name one. |
| `-o <file>` | The build's output file, relative to the member's directory. Defaults to `dist/build.yaml`. As with `chant build -o`, a `.yaml` or `.yml` name writes YAML and any other name JSON, a lexicon whose output is YAML (k8s, helm) writes YAML whatever the name, and the extra files a lexicon emits are written beside it. |
| `--lexicon <name>` | Build only this lexicon. |

An Op's IR is written under the build root, so a project with `sourceDir: "src"` and an Op records `src/dist/ops/<op>/op.json` as well. The files are kept in memory and nothing is written to the checkout, so a file an earlier build left there is never recorded.

A build is deterministic. Two cuts of one commit record the same bytes for each environment and get one digest, whichever clone or directory they run in.

### A release with no environments

A project that only publishes packages, binaries or images needs no chant sources and no environments. Its `chant.config.ts` names what the release publishes, and nothing else:

```ts
export default {
  release: {
    version: { packages: ["."] },
    publish: [{ type: "npm", packages: ["."] }],
  },
};
```

[`chant release init`](#release-init) writes such a block from what it finds in the project.

With no `environments`, the cut compiles nothing. It records the release as the commit, the artifacts the cut built or was handed (`release.images`, `release.artifacts`, `--image`), and `publishes`: each `release.publish` target's key, type and destination, in the declared order. `targets` is empty. The release digest covers `publishes`, so a release with them is read by chant `RELEASE_PUBLISHES_FLOOR` and newer. A `--build` command runs once the gate has passed and the images are built, with `CHANT_RELEASE_LABEL` set, and a build that fails cuts nothing. No `sourceDir` and no `chant.workspace.json` are needed; without `ci.green`, the [green gate](#the-green-gate) is the forge's checks.

The publish is the same as for any release. Each target checks the files it uploads against the artifacts the release records at their paths, and the signature, provenance and SBOM checks of the security groups apply unchanged, see [release publish](#release-publish).

### The release digest and the label

The release is stored on `chant/lifecycle` under its digest, and a cut is a line appended to the cut log:

| Path | Holds |
|---|---|
| `_releases/<releaseDigest>.json` | The release, written once and never rewritten. `:` is written as `_`. |
| `_releases/cuts.jsonl` | One line per cut: `{ version, releaseDigest, label, actor, timestamp, runId, runOrigin, signature }`. |
| `_releases/templates/<digest>.txt` | Each template's bytes, by content digest, for a promote to deploy. |
| `_releases/templates/<digest>.b64` | The base64 of a template that is not UTF-8, by the digest of its bytes. |

A workspace member's copies sit under `_members/<member>/`. The cut writes the local branch and pushes it when there is a remote.

`releaseDigest` is `computePlanDigest("release", subject)`. The subject is what deploys:

| In the digest | Outside it |
|---|---|
| `member`, `commit` and `artifactDigests` | each parameter's `source` |
| each target's `env`, `templates` (with each one's `encoding`) and `trees` | the cut line's `label`, `actor`, `timestamp`, `runId`, `runOrigin` and `signature` |
| each parameter's `name` and `value` | the chant version |

So two cuts of one commit give the same digest.

The label is a human name such as `v1.4.0`. It starts with a letter or digit, and after that it may also hold `.`, `_`, `+` and `-`. Within a member, a label names one digest and a digest takes at most one label. Cutting the same digest again is a no-op that prints its label. Cutting it under another label is refused with `release-already-labelled`, and a label that already names another digest is refused with `release-label-taken`. A digest cut without a label can be given one by a later cut. `signature` holds the cut's signature, or `null` for an unsigned cut. `runId` and `runOrigin` name the run, as [What --yes records](#what-yes-records) lists. A cut line written before 0.124.29 has no `runId`, which reads as `null`, and its `runOrigin` is `null` outside CI.

### Who may cut

Who may cut a release is an `identity.gates` entry for a gate named `release` ([#4031](https://github.com/INTENTIUS/chant/issues/4031)), read from the declaration at base like every [identity gate](/chant/reference/workspace-declaration/#identity):

```json
"identity": {
  "gates": {
    "release": { "class": "releaser" }
  }
}
```

With the entry, a cut must be signed with `--sign`, by a key `.chant/allowed_signers` at base lists for the actor. With `class`, the role grants in `.chant/trust.json` at base must also put the actor in that class. A class no pinned package supplies lets nothing through. Without the entry anyone may cut, and a signature is optional.

`--sign <key file>` signs with that ssh key, and `--sign` alone uses git's `user.signingkey` when `gpg.format` is `ssh`, as `chant approve --sign` does for a [signed gate](/chant/reference/workspace-declaration/#identity). When `--actor` is not given, the actor is the principal the signers file at base lists for that key, if it lists exactly one. `--actor` names the signer otherwise, as in the cut below.

```bash
chant release cut v1.4.0 --actor github:alice --sign ~/.ssh/id_ed25519 --yes
```

Under the gate the dry run reads the key's public half and refuses with `release-signer-refused` when the signers file at base lists it for someone other than the actor. A key whose public half can't be read without its passphrase is checked when it signs.

The signature is `ssh-keygen -Y sign` in the `chant-release` namespace over four lines. They hold the release digest and the label (empty for none), then the actor and the cut's time. Changing any of them in the cut line stops it verifying. The cut checks the signature and the class before it stores anything.

`release list` and [`workspace status`](/chant/cli/workspace-status/) check each cut's signature again on every read, against the signers file and the role grants at base. A key removed from the signers file makes the cuts it signed read as `unverified` from then on.

| Flag | Meaning |
|---|---|
| `<label>` or `--label <label>` | The release's label, such as a version. Optional; a release with no label gets no tag. |
| `--yes` | Cut. Without it the command is a dry run. |
| `--build <command>` | A shell command run in the member's directory before each environment's templates are read, with `CHANT_ENV` set to the environment. |
| `--param <name=value>` | A build parameter for every environment. Repeatable. |
| `--params-file <file>` | A JSON file of build parameters. `{env}` in the path is replaced by each environment's name, as in `params.{env}.json`. |
| `--image <component>=<repository>@sha256:<hex>` | An image built elsewhere, handed to the cut by digest: the release records it for the component, and the cut builds nothing for it. Repeatable, one per component. See [An image built elsewhere](#an-image-built-elsewhere). |
| `--actor <name>` | Who made the cut. Defaults to the signer of `--sign`'s key, then `GITHUB_ACTOR` or `GITLAB_USER_LOGIN`, then git's `user.email`, then `USER`. |
| `--sign [<key file>]` | Sign the cut with an ssh key, or with git's `user.signingkey` when no file is given. See [Who may cut](#who-may-cut). |
| `--json` | With `--yes`, print the release, its label, the cut line written (`null` when the release was already cut), whether the release file was written now, the components whose artifacts were carried from an earlier release, and the images handed to the cut (`handed`), with `dryRun: false`, `actor`, `actorSource`, `tag` (`{ name, created }`, or `null`) and `next`. Without `--yes`, print the dry run's document. |

### Cutting on green

A project that wants a release for every green commit runs the cut in its own pipeline, after the tick. Cutting a digest that is already cut does nothing, so the step can run on every tick:

```bash
git fetch origin --tags
git checkout "$(chant ci last-green)"
chant release cut --build "npm run build" --yes
```

The checkout must have `origin/<trunk>` for the trunk check, so fetch the branch with the tags (`fetch-depth: 0` with `actions/checkout`). The step needs only git, the tags and the member's build, so it runs on any runner, including one whose tick reads [chant runs](/chant/cli/ci/#chant-runs-as-the-status-source). Under a `release` gate in `identity.gates` the cut must be signed by a signer in the gate's class. The job then needs that signer's key, so the declaration decides whether CI may cut.

### Revoked releases

A release is revoked when the commit it was cut from gets a `ci/revoked/<sha>` tag that counts, after the cut ([#4033](https://github.com/INTENTIUS/chant/issues/4033)). Nothing is written when that happens: every reader joins the release's `commit` to the local tags, judged as the cut judges them, so with [signed tags](/chant/cli/ci/#signed-tags) a revoked tag without a valid statement revokes nothing. Fetch the tags before reading.

| Command | With a revoked release |
|---|---|
| `release list` | Marks it, see [release list](#release-list). |
| [`chant components promote --release`](/chant/cli/components/#promoting-a-release) | Refuses it with `release-revoked` before anything runs. |
| [`chant approve`](/chant/cli/operator/#approve-op-gate) on its release gate | Refuses with `release-revoked`, so a gate pending for it never passes. `chant approve release <gate> --expire` clears the pending fact. |
| [`chant workspace status`](/chant/cli/workspace-status/#revoked-releases) | Flags each component of an environment that runs it, with the `chant components rollback` line, and reads its pending gate as `superseded`. |

## release doctor

Asks each target `release.publish` declares whether a publish from this environment can succeed, before anything is cut ([#5161](https://github.com/INTENTIUS/chant/issues/5161)). It needs no release and changes nothing on any registry. Run it on a workstation to read what the registries show anyone, and in the release workflow to test what only that workflow can.

```bash
chant release doctor
```

```
Release doctor, from a workstation: OIDC no; the release workflow is .github/workflows/chant-release.yml in acme/app
npm @acme/core
  ok          npm-registry: @acme/core is on https://registry.npmjs.org, latest 1.3.0
  warn        npm-last-publisher: @acme/core@1.3.0 was published by trusted publishing from acme/app, .github/workflows/publish.yml, by its provenance, and this release publishes from acme/app, .github/workflows/chant-release.yml. ...
              fix: On npmjs.com, the package's Settings, Trusted Publisher, name acme/app and the workflow file chant-release.yml.
  can't tell  npm-trusted-publisher: whether @acme/core's trusted publisher names this workflow can only be tested by a run of .github/workflows/chant-release.yml ...
  can't tell  npm-dist-tag: the reveal moves latest with npm dist-tag add; over trusted publishing that needs "Allow npm dist-tag" on @acme/core's record, which npm does not show ...
1 ok, 1 warning(s), 0 failed, 2 can't be observed from here
```

Each check ends `ok`, `warn`, `FAIL` or `can't tell`. A credential the publish needs and this environment lacks fails in CI and is a warning on a workstation, where the release job's environment is not the one being checked. `can't tell` is what can't be observed from where the doctor runs, and the line says why. The doctor exits 1 when a check fails and 0 otherwise.

| Target | Checks | What it can't tell |
|---|---|---|
| `npm` | Each package's `package.json` names a package that is not `private`. The registry has the package (`npm-registry`). The workflow the latest version was published from, read from its provenance (`npm-last-publisher`). In the release workflow, npm's OIDC exchange for the package (`npm-trusted-publisher`). A token in npm's config, and whether its user may write the package (`npm-token`) | The trusted-publisher record itself, which npm shows only to the package's owners, so `npm-last-publisher` is evidence of the last publish and nothing more. The exchange outside a run of the release workflow, since npm matches the record against the workflow file whose token asks. Whether the record allows `npm dist-tag`, which the reveal needs unless the target says `stage: false` |
| `oci` | Credentials from the declared variables or the docker config. The registry's token service, asked for `pull,push` on the repository (`oci-push`) | Whether the credentials may push, when the registry's token does not list what it grants, or the registry takes Basic credentials |
| `forge` | The token is set, and what it may do on the repository: `permissions.push` on GitHub and Forgejo, a classic token's scopes, a GitLab token's `api` scope and Developer role | What a GitHub job token or a GitLab `CI_JOB_TOKEN` may do, which their APIs do not say |
| `homebrew`, `tauri-updater` | The token is set and may write the repository, as for `forge` | Whether an SSH deploy key has write access, which shows when it pushes |
| `marketplace` | The extension's publisher and name, from the `.vsix` or the member's `package.json`. Open VSX: the namespace exists, and under `trusted-publishing` the exchange for a publishing token in CI. VS Code Marketplace: `vsce verify-pat` for the token or the Entra identity | Whether an Open VSX token may publish, which has no read-only check |
| `pypi` | The project's name, from a built distribution or `[project] name` in `pyproject.toml`, and whether the index has it (`pypi-project`; a project not there yet is a warning, since trusted publishing then needs a pending publisher). The token is set (`pypi-token`). Under trusted publishing in CI, the exchange for an upload token (`pypi-trusted-publisher`) | Whether a token may upload, which PyPI has no read-only check for. The exchange outside CI |
| `cargo` | The crates `cargo metadata` gives and the order they publish in (`cargo-crates`), with the plan's refusals. Which crates the registry's index does not have yet (`cargo-new-crates`, a warning: a first version needs a token that may publish new crates). The token is set (`cargo-token`). Under trusted publishing in CI, crates.io's token exchange, whose token is revoked at once (`cargo-trusted-publisher`) | Whether a token may publish, which a registry has no read-only check for. The exchange outside CI |

Under the `forge-checks` [green gate](#the-green-gate), the default without `ci.green`, the doctor also finds the forge and the token the cut would ask, and reads the checks and statuses of the commit checked out (`green-forge-checks`). It fails when no token is set in CI, or when the forge refuses the token, which on GitHub needs `checks: read` and `statuses: read`. Whether the commit's checks passed is the cut's question, and the line only reports it. A member with no `environments`, which releases only what `release.publish` names, is checked the same way.

When the publish signs with [Sigstore](/chant/reference/publish-targets/#sigstore-signatures) and declares an `oci`, `forge` or `pypi` target, the doctor also checks what signing needs from the job it runs in: an OIDC token cosign can sign with (`signing-oidc`, which names the identity the certificate will carry) and cosign 3 (`signing-cosign`). Either one missing fails in CI. The generated release workflow installs cosign in the cut job as well as the publish job, and on GitLab gives the cut job `SIGSTORE_ID_TOKEN`, so the doctor there sees what the publish will.

Four checks hand back a short-lived publishing token, which the doctor masks and drops: npm's OIDC exchange, Open VSX's, PyPI's and crates.io's trusted-publishing exchanges. They are the requests a publish makes first, and crates.io's token is revoked straight away. No other check sends a request that changes anything. Every line and the `--json` document go through the publish's redactor.

The release workflow file is `release.workflow.file` in the workspace root's `chant.config.ts`, else the forge's default (`.gitlab-ci.yml` on GitLab, whose trusted publishers name the top-level file). In GitHub Actions, the run's own file comes from `GITHUB_WORKFLOW_REF`.

`--json` prints `environment` (`ci`, `oidc`, `workflow`, `repository`, `releaseWorkflow`), `targets` (each `kind`, `name` and `checks`, each with `check`, `status`, `message` and `fix`) and `counts`. A config that does not load exits 1 with `doctor-config-invalid`.

A dispatched release runs it in the cut job before the cut (see [The whole release from the config](#the-whole-release-from-the-config)).

## release publish

Publishes a cut release to the targets its member declares under `release.publish` in `chant.config.ts` ([#4027](https://github.com/INTENTIUS/chant/issues/4027), [#4047](https://github.com/INTENTIUS/chant/issues/4047)): npm packages, an image in an OCI registry such as GHCR or Docker Hub, release assets on GitHub, GitLab or Forgejo, a Homebrew tap, an editor marketplace, a Tauri updater feed, Python distributions on PyPI and Rust crates on crates.io. [Publish Targets](/chant/reference/publish-targets/) lists the declaration, each target and its credentials. It is meant to run in CI, where the job's OIDC token gives what it publishes provenance, as npm trusted publishing needs.

```bash
chant release publish v1.4.0          # a dry run: prints what would be published where
chant release publish v1.4.0 --yes    # publishes
```

After a best-effort fetch of `chant/lifecycle`, it refuses before it publishes anything when:

| Code | When |
|---|---|
| `release-not-found` | No cut names the label or digest in this member. |
| `release-revoked` | The release's commit is [revoked](#revoked-releases). |
| `release-unsigned` | No cut of the release is signed, and the workspace names a `release` gate in `identity.gates` or opts into `verified-releases` ([#4049](https://github.com/INTENTIUS/chant/issues/4049), [#4168](https://github.com/INTENTIUS/chant/issues/4168)). |
| `release-signature-unverified` | Under the same settings, no cut's signature verifies for its actor against `.chant/allowed_signers` at base, or, under a `release` gate, the signer is not in the gate's class. |
| `publish-provenance-missing` | `--require-provenance` is given, and the run has no OIDC token. |
| `publish-signing-no-oidc` | The publish signs with Sigstore (`release.signing`, or the `supply-chain` group), an `oci` or `forge` target is declared, and the run has no OIDC token cosign can sign with: a GitHub Actions job without `id-token: write`, a GitLab CI job without `SIGSTORE_ID_TOKEN`, or a workstation. |
| `publish-signing-tool-missing` | Under the same settings, cosign 3 is not on `PATH` and `CHANT_COSIGN` does not name it. |
| `publish-config-invalid` | `release.publish` in `chant.config.ts` does not validate. |
| `release-head-mismatch` | A target is declared, and the checkout's `HEAD` is not the release's commit. |
| `release-worktree-dirty` | A target is declared, and the tree has a change or an untracked file git does not ignore. Under `release.version`, a file it names that is exactly the commit's stamped with this release's label is not a change ([#4840](https://github.com/INTENTIUS/chant/issues/4840)). |

A release whose cut names a `channel` moves that tag instead of `latest`: the npm target's dist-tag and the OCI target's image tag. The newest cut that names one decides.

A release whose label is a semver prerelease (`1.4.0-rc.1`) needs no channel. npm reveals under a dist-tag named for the prerelease id (`rc`, `beta`, or `next` when there is none) and never moves `latest`, GitHub and Forgejo mark the release a prerelease, and OCI keeps no `latest` tag. A channel on the cut still wins for npm and OCI. The publish prints `prerelease` and, with `--json`, `prerelease: true` and `distTag`. See [Prereleases](/chant/reference/publish-targets/#prereleases).

The last two hold because a target uploads files from the checkout it runs in, which are the release's only at its commit. A CI job on the release's tag passes both. A publish with no target reads nothing and checks neither.

Signing is opt-in ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). With no `release` gate and no `security` group in `chant.workspace.json`, an unsigned release publishes without a word, and the `--json` document's `signature.status` says `unsigned` or `unverified`. A workspace that sets `"security": ["verified-releases"]` publishes only a release signed by a key the signers file lists, so cut it with `--sign` (see [Who may cut](#who-may-cut)). There `--allow-unsigned` publishes a release with no signature that verifies anyway. It prints a warning first, and `release verify` then fails for what was published. Under a `release` gate in `identity.gates`, `--allow-unsigned` changes nothing: the gate publishes only a signed release.

It then checks whether the run has an OIDC token. In GitHub Actions that means `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, which a job with `permissions: id-token: write` gets. In GitLab CI it means an ID token named `SIGSTORE_ID_TOKEN` or `NPM_ID_TOKEN` under the job's `id_tokens`. Without one, as on a workstation, the `--json` document's `provenance.oidc` is false. A workspace that opts into `supply-chain` also gets a warning on stderr before anything is published: what it publishes carries no OIDC provenance. Without that group nothing is printed. `--require-provenance` refuses such a run with `publish-provenance-missing`, with or without the group. With a token, the npm target passes `--provenance`, and after the reveal runs `npm audit signatures` over what it published.

When the publish signs ([#5164](https://github.com/INTENTIUS/chant/issues/5164)), the OCI and forge targets sign what they stage with Sigstore, keylessly with the job's OIDC token: an image gets a cosign signature and SLSA provenance as referrers, and a forge release gets a `.sigstore.json` bundle beside each file and `release.slsa.sigstore.json`. Signing is off unless `release.signing` in `chant.config.ts` turns it on or the workspace opts into `supply-chain`. [Sigstore signatures](/chant/reference/publish-targets/#sigstore-signatures) has the details.

Next it plans every target: each reads the files it would upload, checks a file the release records as an artifact against the release's digest, and finds its credentials. A target that can't stops the publish with its own code, such as `publish-file-missing`, `publish-artifact-digest-mismatch` or `publish-credentials-missing`, before anything is sent.

Without `--yes` the publish is a dry run. It prints what each target would publish and where, and uploads nothing:

```
Dry run: publish v1.4.0 (jcs1-sha256:...) from commit 3f2a9c1d0b7e
  signed by alice@example.com
What would be published where:
  npm (2 packages), with --provenance:
    @acme/core@1.4.0 to the registry npm's config names, dist-tag next, then latest, carrying sbom.spdx.json
    @acme/cli@1.4.0 to the registry npm's config names, dist-tag next, then latest, carrying sbom.spdx.json
  oci ghcr.io/acme/api:
    dist/api.oci.tar (tag v1.4.0) to ghcr.io/acme/api@sha256:...
    sbom.spdx.json (SBOM) to ghcr.io/acme/api@sha256:..., a referrer of the image
    release.intoto.json (provenance) to ghcr.io/acme/api@sha256:..., a referrer of the image
Dry run: nothing was published. Run again with --yes to publish: chant release publish v1.4.0 --yes
```

With `--yes` it publishes in two passes ([#4048](https://github.com/INTENTIUS/chant/issues/4048)). First it stages every target in the order declared, where no consumer resolves it yet: npm packages under the `next` dist-tag, images by digest, forge assets on a draft release. Only when every target has staged does it reveal them in the same order. Revealing moves npm's `latest` with the first package declared going first. It also moves the OCI tags and publishes the forge release. It prints each item it published. Each step is appended to `_releases/publishes.jsonl` on `chant/lifecycle` and pushed.

A target that fails stops the publish. The error says whether anything is visible yet and which targets staged, and ends with the same command to run again. Run again, the publish reads the record and skips what an earlier run staged or revealed, and a stage asks its registry first and sends nothing that is there. So a resume publishes nothing twice, from the same checkout or from a fresh CI clone of the release's commit. The dry run says which targets an earlier run staged or published. [Staging and resuming](/chant/reference/publish-targets/#staging-and-resuming) has the details. Every line a publish prints, its `--json` document and its record have their credentials masked.

Each target attaches the release's provenance statement when it stages, and an SBOM when it has a source for one, so nothing is visible before they are attached ([#4049](https://github.com/INTENTIUS/chant/issues/4049)). A target with no SBOM source publishes without one, except under the `supply-chain` group, which refuses it with `publish-sbom-missing` ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). An npm package carries its SBOM in the package. An image gets both as OCI referrers, and a forge release gets both as assets. The provenance statement names the release and carries the cut's signature. [SBOMs and provenance](/chant/reference/publish-targets/#sboms-and-provenance) has the details.

With no target declared it makes its checks and prints any warning. It then says that nothing was published and exits 0. The publish steps a component declares (`publish-image`, `publish-artifact`, `publish-asset`, `load-image-on-host`) are deploy steps. They run in each environment's deploy of the release, [`chant components promote --release`](/chant/cli/components/#promoting-a-release), and not here.

The document `--json` gives for a publish holds `dryRun` and the release's digest, label and commit. Beside them sit `signature` (`status`, `actor`, `key`, `reason`), `provenance` (`oidc`, `ci`, `reason`), `signing` (the `identity` the certificate names and the `signer`, or `null` when the publish does not sign), the `warnings`, the `targets` (each `kind`, `name`, `destination`, its `progress` from earlier runs, `none`, `staged` or `revealed`, and its planned `items`), what was `published` (each `target`, `destination` and `items`; empty in a dry run) and the release's `environments`. A dry run adds `next`, and a publish adds `resumed`, the targets an earlier run had staged or revealed, each with its `target` and `step`. The warning is printed on stderr in either form.

| Flag | Meaning |
|---|---|
| `--yes` | Publish. Without it the command is a dry run. |
| `--allow-unsigned` | Under `verified-releases`, publish a release with no signature that verifies, with a warning. Never overrides a `release` gate. Without either it changes nothing. |
| `--require-provenance` | Refuse a run with no OIDC token. A CI job that must give npm provenance passes it, so a misconfigured job fails instead of publishing without. |
| `--json` | Print the document described above. |

To publish the releases a [release train](/chant/cli/workspace-train/#publish) pins as one set, each member's packages after the packages they depend on, run `chant workspace train publish <env>` in the workspace root instead. It records each member's steps in the same publish record, so either command resumes the other.

## release workflow

Writes the publish workflow, the job that runs `chant release publish` for the release a `release/**` tag names, or a tag `release.tag` makes ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). It is generated the way [`chant ci workflow`](/chant/cli/ci/#ci-workflow) writes the tick, with a header naming the command that regenerates it.

```bash
chant release workflow
```

| Forge | File |
|---|---|
| `github` | `.github/workflows/chant-release.yml` |
| `forgejo` | `.forgejo/workflows/chant-release.yml` |
| `gitlab` | `.gitlab/chant-release.yml`, which `.gitlab-ci.yml` includes |

The job checks out the tag and builds what the targets upload. Then it fetches the ci tags and `chant/lifecycle` and publishes with `--yes`. It always has the OIDC permission, so what it uploads carries provenance when the token is there. The workspace's security groups add the rest: `supply-chain` adds `--require-provenance`, and `verified-releases` adds a `chant release verify` step before the publish. With neither, nothing refuses a run that lacks them.

When the publish signs with Sigstore (`release.signing`, or `supply-chain` with an `oci` or `forge` target), the jobs download cosign pinned by SHA-256 for the runner's platform and set `CHANT_COSIGN` to it, unless `release.workflow` sets `CHANT_COSIGN` itself.

| Flag | Description |
|---|---|
| `--forge <forge>` | Inferred from the repository's pipeline files, `github` when there are none. |
| `--install <command>` | The install step. Default `npm ci` in a project with a `package.json`, none otherwise. |
| `--build <command>` | What builds the files the targets upload. Default `npm run build` when the `package.json` has a `build` script, none otherwise. |
| `--chant <command>` | What runs chant. Default `npx chant` in a project with a `package.json`; otherwise `npx --yes @intentius/chant@<version>`, the version that wrote the file. |
| `--output <file>` | Write somewhere else. |

A flag wins over the `release.workflow` field it names. With no `--build` and no `release.workflow.build`, a project whose `package.json` has no `build` script, or that has no `package.json`, gets no build step.

Each job sets up the toolchains the project builds with, found from the files at the project's root, beside the Node that chant runs on:

| File | Toolchain | Action | Version |
|---|---|---|---|
| `package.json` | node | `actions/setup-node` | 24 |
| `go.mod` | go | `actions/setup-go` | `go-version-file: go.mod` |
| `pyproject.toml`, `setup.py`, `requirements.txt` | python | `actions/setup-python` | `.python-version` when there is one, otherwise `3.x` |
| `Cargo.toml` | rust | `actions-rust-lang/setup-rust-toolchain` | `rust-toolchain.toml` when there is one, otherwise stable |
| `pom.xml`, `build.gradle`, `build.gradle.kts` | java | `actions/setup-java` (Temurin) | `.java-version`, `.sdkmanrc` or `.tool-versions` when there is one, otherwise 21 |

Every action is pinned by commit, as in the other workflows chant writes, and none caches, so a release build starts from the commit and the toolchain alone. The gate job, which only runs chant, sets up Node alone. A Go project with no `package.json` gets Node and Go, no install step and no build step, and runs chant with `npx --yes @intentius/chant@<version>`. `release.workflow.toolchains` names them instead (see below). On GitLab a job runs in its runner's image, which brings the toolchain: the file sets nothing up, `chant release workflow` says which toolchains the project's files name, and a `toolchains` field that names anything but `node` is refused.

A project with no `chant.workspace.json` renders its workflow from the `chant.config.ts` in the current directory, and needs no `chant ci` setup: with no `ci.green` its cut is gated on the forge's checks (see [The green gate](#the-green-gate)).

### The whole release from the config

`release.workflow` in the workspace root's `chant.config.ts` renders the rest of the release into the same file ([#4656](https://github.com/INTENTIUS/chant/issues/4656)):

```ts
release: {
  workflow: {
    trigger: "dispatch",
    gate: "last-green",
    build: "npm run build",
    after: ["npm run announce"],
  },
  publish: [/* the targets, as before */],
},
```

| Field | Meaning |
|---|---|
| `trigger` | `tag` (default) publishes on the release's tag, as above. `dispatch` starts the release by hand with its label |
| `gate` | For `dispatch`: `last-green` (default) cuts the newest green commit at or below the dispatched one; `head` cuts the dispatched commit and refuses it when it is not green |
| `install`, `build`, `chant` | As the flags. `install: false` installs nothing and `build: false` builds nothing. The cut runs `build` as its `--build`, and so does the publish job |
| `toolchains` | The toolchains the jobs set up, in place of those the files name: `"node"`, `"go"`, `"python"`, `"rust"`, `"java"`, or `{ name, version }` for a version, such as `[{ name: "go", version: "1.24" }]`. Jobs that run chant get Node as well. `false` sets up nothing and leaves the runner's own. GitHub and Forgejo |
| `builds` | Per-platform build jobs for `trigger: "dispatch"`, see [Builds on other runners](#builds-on-other-runners) |
| `after` | Shell lines run once the release is published, with `CHANT_RELEASE_LABEL` set |
| `permissions` | Scopes added to the workflow's `contents: write` and `id-token: write`, such as `{ actions: "read" }`. GitHub and Forgejo only ([#4751](https://github.com/INTENTIUS/chant/issues/4751)) |
| `env` | Variables for the cut and publish jobs. A forge expression stays in the job's `env:` (GitLab: `variables:`), off every `run:` line |
| `setup` | Steps the cut and publish jobs run after the install: `{ run }`, or `{ uses, with }` on GitHub and Forgejo, such as a newer npm. GitLab refuses `uses` |
| `file` | Where the workflow is written, from the repository root, such as `.github/workflows/publish.yml` when npm's trusted publisher names that file |
| `doctor` | [`chant release doctor`](#release-doctor) before anything is published. With `trigger: "dispatch"` the cut job runs it before the cut, unless `doctor: false`. With `trigger: "tag"` the cut already happened, and `doctor: true` runs it in the publish job before the build |

On GitHub the targets in `release.publish` add what they need, so the config names none of it ([#4786](https://github.com/INTENTIUS/chant/issues/4786)). An `oci` target on `ghcr.io` with no `usernameEnv` or `passwordEnv` pushes with the run's token: the workflow gets `packages: write`, and the cut and publish jobs get `OCI_USERNAME: "${{ github.actor }}"` and `OCI_PASSWORD: "${{ github.token }}"`. An `npm` target on npmjs publishes with trusted publishing, which needs npm 11.5.1 or later, so the cut and publish jobs install a newer npm after `setup` when the runner's is older. A scope or variable `release.workflow` sets wins over the one the targets add.

When `release.images` builds a platform the runner can't run, such as `linux/arm64` on an amd64 runner, the cut and publish jobs set up QEMU's binfmt handlers for it after the install and before `setup` ([#4876](https://github.com/INTENTIUS/chant/issues/4876)). The platforms are a Dockerfile entry's `platforms` (default `linux/amd64` and `linux/arm64`) and a `build` entry's `platforms`. GitHub and Forgejo run `docker/setup-qemu-action` at chant's pin with `platforms: arm64`; GitLab runs `docker run --privileged --rm tonistiigi/binfmt:<tag>@sha256:<digest> --install arm64`, the image pinned by the digest `IMAGE_PINS.binfmt` in `@intentius/chant/image-pins` records ([#4941](https://github.com/INTENTIUS/chant/issues/4941)), and `chant release workflow` notes that the runner's executor must run privileged containers, or have the handlers installed on its host. A `setup` that names the action or the binfmt image already gets no second one, and a release whose images build only `linux/amd64` gets none. `RELEASE_WORKFLOW_QEMU_FLOOR` is the first chant that does this.

With `trigger: "dispatch"` the file has four jobs, and the label is an input of the run (a pipeline variable, `CHANT_RELEASE_LABEL`, on GitLab):

| Job | What it does |
|---|---|
| gate | `chant ci last-green --from <dispatched commit>`, honouring `release.lane`, and hands the commit on. When `release.green` is `forge-checks` or `none`, it hands on the dispatched commit, which the cut then checks. It hands on the label too, computed by `release next` for `auto` |
| cut | Checks the commit out, runs `chant release doctor` (with the run's `GITHUB_TOKEN` when a GitHub forge target or `forge-checks` needs it), then `chant release cut <label> --at <commit> --yes`, which pushes `chant/lifecycle`, and pushes the tag the cut made; a cut whose record did not land exits 1 and the tag is not pushed |
| publish | Checks the commit out, builds, and publishes, with the security groups' `--require-provenance` and `release verify` as above |
| after-release | Runs `after`, when there is any |

The label input takes `auto` (on GitLab, `CHANT_RELEASE_LABEL=auto`): the gate fetches `chant/lifecycle` and runs `chant release next --at <commit>` at the commit it chose, stops when that refuses, and hands the label on, so every later job, the build jobs among them, sees the computed label in `CHANT_RELEASE_LABEL`. A label typed in is handed on as it is. On GitLab a pipeline variable outranks the gate's dotenv, so the gate hands the label on as `CHANT_RELEASE_NEXT` and each later job exports it as `CHANT_RELEASE_LABEL` first.

No tag exists until the gate has passed and the cut has run. Under `forge-checks` the cut job gets the run's token as `GITHUB_TOKEN`, and on GitHub the workflow gets `checks: read` and `statuses: read`; on GitLab the cut reads pipelines with `CHANT_RELEASE_TOKEN` unless `CHANT_GITLAB_TOKEN` is set. On GitLab the jobs follow each other by `needs` in the default stage, so `.gitlab-ci.yml` keeps its own `stages`, and the cut and publish jobs push with `CHANT_RELEASE_TOKEN`, a project access token with `write_repository`, since a job token cannot push.

With `release.images` (see [Images the package pins](#images-the-package-pins)), the publish job runs `chant release images <label>` after fetching `chant/lifecycle` and before the build, and exports `CHANT_RELEASE_DIGESTS`. In a dispatched release the cut job hands the archives it built to the publish job as a workflow artifact (`chant-release-images`; on GitLab, the cut job's `artifacts:`), and the publish job checks them with `chant release images <label> --no-build`, which reads the archives on disk and refuses one whose digest is not the recorded one. The images published are then the ones the cut built, even when the package mirror an image installs from moved between the two jobs. This holds for either trigger. `after` with the tag trigger adds an after-release job that follows the publish. A config with only `publish` renders the file it always did.

With `release.tag` (see [The release's tag](#the-releases-tag)), the tag trigger runs on the tags the template makes, with `{member}` and `{path}` filled in: `v{version}` runs on `v*`. A `floating` tag is left out with a negated pattern (`!v[0-9]+`), so moving it starts nothing; on GitLab the rule is a regular expression with the same effect. The publish job fetches `chant/lifecycle` right after the install, reads the label with `chant release tag "$GITHUB_REF_NAME" --json`, and exits 1 for a tag that names no release of the member. Every later step uses `CHANT_RELEASE_LABEL`, and the after-release job gets it from the publish job. Under `doctor: true` the publish job runs `chant release doctor` once the label is read. A floating tag is pushed by the publish job with git: GitHub and Forgejo jobs can, with `contents: write`; a GitLab job token can't, so `chant release workflow` says so, and a dispatched release on GitLab pushes it with `CHANT_RELEASE_TOKEN`. A dispatched release pushes whatever tag the cut made. A member with no `release.tag` renders the `release/**` file it did.

### Builds on other runners

`release.workflow.builds` adds a job per platform that builds on its own runner, such as a native arm64 runner, macOS or Windows, after the gate and before the cut:

```ts
release: {
  workflow: {
    trigger: "dispatch",
    builds: [
      { name: "linux-arm64", runner: "ubuntu-24.04-arm", build: "go build -o dist/acme-linux-arm64 .", outputs: ["dist/acme-linux-arm64"] },
      { name: "darwin-arm64", runner: "macos-15", build: "go build -o dist/acme-darwin-arm64 .", outputs: ["dist/acme-darwin-arm64"] },
      { name: "windows-amd64", runner: "windows-latest", build: "go build -o dist/acme.exe .", outputs: ["dist/acme.exe"] },
    ],
  },
  publish: [{ type: "forge", forge: "github", repo: "acme/acme", assets: ["dist/acme-linux-arm64", "dist/acme-darwin-arm64", "dist/acme.exe"] }],
},
```

| Field | Meaning |
|---|---|
| `name` | The job is `build-<name>` (`chant-release-build-<name>` on GitLab): lowercase letters, digits and dashes |
| `runner` | GitHub's and Forgejo's `runs-on` label, or labels; on GitLab, the runner's `tags` |
| `build` | Run with bash from the project root, with `CHANT_RELEASE_LABEL` set, so a version can be built in |
| `outputs` | The files the job hands on, from the project root. Shell globs such as `dist/acme-*` are allowed; a path with `..` or a leading `/` is refused |
| `install` | The install before the build. Default the workflow's; `false` for none |
| `toolchains` | In place of the workflow's toolchains, as above. Node is not added: a build job doesn't run chant |
| `env` | Variables for this job only |

On GitHub and Forgejo a build job checks out the gate's commit without the job token's credentials, reads with `contents: read` and nothing more, and gets none of the cut and publish jobs' `env`, so a build cannot push, mint an OIDC token or read the publish credentials. On GitLab it gets none of the release file's variables or ID tokens, and the project's CI/CD variables reach it as they reach any job, so keep publish credentials protected and the release on a protected ref. A build job packs its outputs with `tar`, which keeps each file's path and mode, and hands the archive on as a workflow artifact (`chant-release-build-<name>`; on GitLab, the job's `artifacts:`). The cut job waits for every build, so `chant release doctor` runs there after the builds, with the cut job's toolchains and credentials; a build job has neither and never runs it. The cut job unpacks each archive into the project root before `chant release cut` runs, with `tar -k`, so a build cannot replace a file of the commit and two builds cannot write the same path. The cut then finds the files where its own build would have left them, and a `release.artifacts` entry with no `build` (see [Files the release builds](#files-the-release-builds)) records them as they are, so the cut job builds nothing a build job built. The publish job unpacks them too, before the stamp, the images and the build, so the targets upload the files the runners built, under the same signing, provenance and SBOM checks as any other release. Build outputs belong in `.gitignore`, as for any build, or the publish refuses the tree as changed.

`builds` needs `trigger: "dispatch"`: with the tag trigger the release was cut before the workflow ran, and `chant release workflow` refuses it.

With `release.artifacts` (see [Files the release builds](#files-the-release-builds)), a dispatched release's cut job stages the files it built with `chant release artifacts <label> --no-build -o <dir>` and hands them to the publish job as the workflow artifact `chant-release-artifacts`, from the runner's temp directory. The publish job downloads them to its temp directory and runs `chant release artifacts <label> --from <dir>` after the build and before the publish, which puts each file at its path and refuses one whose digest is not the recorded one. On GitLab the cut job keeps them as `.chant-release-artifacts/` in its `artifacts:`, and the publish job moves that directory out of the checkout first. With the tag trigger the publish job runs `chant release artifacts <label>` after fetching `chant/lifecycle`, which builds them again and checks them. A `goreleaser` entry adds two steps to the job that builds: `actions/setup-go` with the member's `go.mod` on GitHub and Forgejo, unless `setup` names `actions/setup-go`, and the goreleaser chant pins, downloaded, checked against its SHA-256 and named by `CHANT_GORELEASER`, unless `release.workflow.env` sets `CHANT_GORELEASER`. A GitLab job uses its image's Go.


With `release.version` (see [The label as the package version](#the-label-as-the-package-version)), the publish job runs `chant release stamp <label>` after the install and the setup steps and before the images and the build, under either trigger. The cut job is unchanged: the cut stamps on its own. A config without `release.version` renders the file it did.

## release stamp

Writes the label as the `version` of each `package.json` that `release.version` names, and into the lockfile's entries for them, as the cut does before its build ([#4840](https://github.com/INTENTIUS/chant/issues/4840)). It leaves the files stamped. The publish job runs it before its build, and `chant release publish` takes the stamped files as the commit's. `git checkout -- <files>` puts them back on a workstation.

```bash
chant release stamp 1.4.0   # Stamped 1.4.0 into packages/cli/package.json, package-lock.json
```

With `ranges` set, the workspace dependencies' ranges follow the label too. `--train <id|digest>` gives a `ranges: "train"` member the labels of the other members' packages from a recorded train (see [Workspace dependency ranges](#workspace-dependency-ranges)).

It refuses a member with no `release.version` (`release-version-not-declared`), and the label and package problems the cut refuses.

## release tag

Prints the tag `release.tag` gives a release of the member here, found by its label, its digest, or the tag itself ([#5150](https://github.com/INTENTIUS/chant/issues/5150)). It fetches `chant/lifecycle` first, as `release publish` does. A tag is matched by rendering the template for each label in the member's ledger, never parsed.

```bash
chant release tag 1.4.0            # v1.4.0
chant release tag v1.4.0 --json    # { "releaseDigest": "sha256:…", "label": "1.4.0", "commit": "…", "tag": "v1.4.0", "floating": "v1", "template": "v{version}" }
```

`floating` is the floating tag the release would move, or null. It exits 1 with `release-not-found` when no release of the member has that label, digest or tag, `release-no-label` for a release with no label (`--json` prints `tag: null` instead), and `release-tag-template-invalid` as the cut does. The publish job of [`release workflow`](#release-workflow) reads the label of the tag that started it this way.

## release artifacts

Checks the files `release.artifacts` declares against the digests the release records, from the release's commit checked out here ([#5151](https://github.com/INTENTIUS/chant/issues/5151)). With no flag it builds them again, as the cut did; an entry with no `build` is checked as it is found. `--no-build` checks the files on disk, and `--from <dir>` first copies them from a directory where a cut job staged them. `-o <dir>` then stages the checked files in `<dir>` at their paths in the member, for the next job.

```bash
chant release artifacts v1.4.0 --no-build -o "$RUNNER_TEMP/chant-release-artifacts"   # in the cut job
chant release artifacts v1.4.0 --from "$RUNNER_TEMP/chant-release-artifacts"          # in the publish job
```

It refuses a checkout at another commit (`release-artifacts-wrong-commit`), a member with no `release.artifacts` (`release-artifacts-not-declared`), an entry the release does not record (`release-artifact-not-recorded`), a file that is not there (`release-artifact-missing`), and a file whose digest is not the recorded one, or a build that writes a file the release does not record (`release-artifact-digest-mismatch`). `--json` prints `releaseDigest`, `label`, `files` (each `name`, `path` and `digest`) and `staged`.

## release verify

Checks that a release was signed by a key `.chant/allowed_signers` lists ([#4049](https://github.com/INTENTIUS/chant/issues/4049)). It reads the release and its cuts from the local `chant/lifecycle` branch, and the signers file at the release's own commit, with its signed history, as [`chant workspace evidence verify`](/chant/cli/workspace-evidence/) reads the policy at a revision. It fetches nothing and needs no key, so fetch `chant/lifecycle` and the release's commit first.

```bash
git fetch origin chant/lifecycle:chant/lifecycle
chant release verify v1.4.0
```

A release verifies when its stored file is the digest of what it holds, and a cut of it carries a signature in the `chant-release` namespace that verifies for the cut's actor. When the declaration at the release's commit names a `release` gate with a class, the actor must be in it too. Because the signers file is read at the release's commit, a key added later does not make an older release verify, and a key removed later does not unmake it. [`release list`](#release-list) judges cuts against the signers file at base instead, which is the policy now.

It exits 0 when the release verifies and prints the signer on stderr:

```
  cut by alice at 2026-10-17T10:00:00.000Z: verified (SHA256:...)
    green by ci/green tag
Verified v1.4.0 (jcs1-sha256:...): signed by alice, checked against .chant/allowed_signers at 3f2a9c1d0b7e
```

It exits 1 with one of these codes:

| Code | When |
|---|---|
| `release-unsigned` | No cut of the release is signed. |
| `release-signature-unverified` | No cut's signature verifies against the signers file at the release's commit, such as one signed by a key the file does not list. |
| `release-digest-mismatch` | The stored release is not the digest of what it holds, so it was changed after the cut. |
| `release-not-found` | No cut names the label or digest in this member. |
| `release-commit-missing` | The release's commit is not in this clone. |
| `trust-policy-unreadable` | The signers file or its history at the commit can't be read. |

`--json` prints `releaseDigest`, `label`, `member`, `commit`, `signers` (`path`, `at`, `active`), `digestMatches`, `status` (`verified`, `unsigned` or `unverified`), `verifiedBy` (`actor`, `key`, or `null`), `reason` and each cut with its `signatureCheck`, and its `green` gate or `override` when the cut recorded one (see [The green gate](#the-green-gate)). A release that does not verify adds `error` with its `code` and `message`. Without `--sigstore`, `sigstore.recorded` counts the Sigstore bundles the publish record holds.

### Checking the Sigstore signatures

A release published with [Sigstore signing](/chant/reference/publish-targets/#sigstore-signatures) has its bundles named in the publish record on `chant/lifecycle`. `--sigstore` checks each with cosign 3 (`CHANT_COSIGN`, else `cosign` on `PATH`), against the certificate identity and issuer `release.signing` names in `chant.config.ts`, else the ones the publish recorded: a workflow of the repository it ran in, and its CI's issuer. An image's signature and provenance are read from its registry, with docker's credentials. A forge release's bundles are read from the directory `--assets` names, where its assets were downloaded. Each bundle must be the bytes the publish uploaded, and an asset beside it must be the digest it signs.

```bash
gh release download release/v1.4.0 -D /tmp/v1.4.0
chant release verify v1.4.0 --sigstore --assets /tmp/v1.4.0
```

This check reads the registry and Sigstore's trust root, so it is not offline. It exits 1 with:

| Code | When |
|---|---|
| `release-sigstore-unsigned` | The publish record holds no Sigstore bundle for the release. |
| `release-sigstore-unverified` | A bundle does not verify for the identity, differs from what was uploaded, or can't be checked (no cosign, or a forge bundle not in `--assets`). |

`--json` adds `sigstore`: its `status` (`verified`, `failed` or `none`), `reason` and each check with its `name`, `kind`, `target`, `attachment` (`signature` or `attestation`), `signs`, `identity`, `status` (`verified`, `failed` or `unchecked`) and `reason`.

## release export

Writes the files a cut recorded for one environment, each at the path it was compiled to, under `-o <dir>` (the member's directory by default). Each file's bytes are read from `chant/lifecycle`, after a best-effort fetch, and checked against the target's digest first. A missing or changed file stops the export before anything is written.

```bash
chant release export v1.4.0 --env prod
kubectl apply -f dist/build.yaml
```

This is how a project with no components deploys what it cut. [`chant components promote --release`](/chant/cli/components/#components-promote) deploys components, and refuses such a cut with a pointer to this command. The project's own deploy, an Op such as `chant run deploy` or a CI job, then reads the exported files. An Op whose first phase runs the build again would overwrite them, so drop that phase when it deploys exported files. `--json` prints the digest and label with the environment and the directory written to. It also prints the target's templates and params.

## release candidates

Lists the green commits of trunk a release can be cut from, newest first ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). Trunk is the branch `release cut` checks, and the walk follows its first-parent line from the tip back to the oldest commit an environment of the member runs. When some environment runs no release yet, it reads the newest 50 commits. `--env <env>` gives one environment's view, so the walk stops at what that environment runs.

With several branches in [`ci.green.branch`](/chant/guide/branch-routing/#give-a-routed-target-a-green-verdict), `--branch <branch>` walks that one instead of the first ([#4325](https://github.com/INTENTIUS/chant/issues/4325)).

`--lane <name>`, or `release.lane` in the member's `chant.config.ts`, reads a lane's tags as [`release cut --lane`](#cutting-from-a-lane) checks them ([#4692](https://github.com/INTENTIUS/chant/issues/4692)). A candidate is then a commit with `ci/green-<lane>/<sha>` and no `ci/revoked-<lane>/<sha>`, and a commit with `ci/revoked-<lane>/<sha>` is skipped. The document's `lane` names the lane, or is `null` for `ci/green/<sha>`.

```bash
git fetch origin --tags
git fetch origin chant/lifecycle:chant/lifecycle
chant release candidates --env prod
```

Each candidate is a commit with a `ci/green` tag that counts and no `ci/revoked` tag. Under it are the first-parent commits since the previous candidate, so each commit appears under exactly one candidate. Its pull request is the one its merge record names. Without a merge record it is the one the subject names, `(#123)` at the end as a forge's squash merge writes it. Its work items are the ones its `Chant-Record: work:<id>` trailers name. The list is grouped by work item and then by pull request ([#4168](https://github.com/INTENTIUS/chant/issues/4168) 4.4). Changes with two work items show under both, and those with none come last, under "no work item". Within a group, the ones that landed without a pull request show under "no pull request". A candidate also lists the flags whose record files those commits change. It says which environments run neither it nor a later commit, and which labels were already cut from it. A revoked commit is listed as skipped, and its changes stay with the next candidate. Commits after the newest candidate are counted as not green yet.

With `--forge-issues`, each pull request's closing issues are read from the forge and become work items ([#4649](https://github.com/INTENTIUS/chant/issues/4649)). A change that no `Chant-Record` trailer gives a work item shows under each issue its pull request closes, as "issue #70", after the work ids and before "no work item". A change with a work id stays under it. When the forge can't be read, the changes stay where they were, and the reason is printed once on stderr. [Issues a pull request closes](/chant/cli/workspace-graph/#issues-a-pull-request-closes) says which forge and token are used, and what each forge answers from. Without the flag nothing reaches the network.

```bash
GH_TOKEN=$(gh auth token) chant release candidates --forge-issues --json
```

With `--json` the output is the [read contract](/chant/reference/workspace-read-contract/)'s `release-candidates.schema.json` document. Its `environments` field lists what each one runs, `since` is the commit the walk stopped at (or `null`), `candidates` and `skipped` are newest first, and `pending` holds the commits after the newest candidate. Each change has `commit`, `subject`, `date`, `work`, `records` (every `Chant-Record` trailer as `<kind>:<id>`), `pr` and `merge`, the merge record `_merges/<sha>.json` on `chant/lifecycle` when one exists. Each change also has `closes`: `null` without `--forge-issues` or a pull request, else what the forge says the pull request closes, `{ resolved, issues, reason }`. Each candidate's `groups` holds the same changes as `{ work, issue, pullRequests: [{ pr, commits }] }`, with `null` for no work item, no issue and no pull request, in the order the text output prints them. Outside git the command exits 1 with `not-a-git-repository`. When the ledger or the tags can't be read it exits 1 with `ledger-unreadable`. Nothing is fetched, so fetch the tags and `chant/lifecycle` first. `--forge-issues` reads the forge's API and fetches no git ref.

## release next

```
chant release next [--at <sha>] [--pre <id>] [--json]
```

Prints the label of the member's next release, from the conventional commits and the [intent files](#intent-files) since its previous release. The label alone goes to stdout, so a script can read it, and why goes to stderr. `--at` reads another commit than `HEAD`. It fetches `chant/lifecycle` first, as `release tag` does.

```bash
chant release next          # 1.5.0
                            #   minor from 1.4.2 (3f2a9c1e0b7d): 4 commits, 1 intent file
                            #     minor  9b1c2d4 feat(api): stream responses
                            #     minor  .chant/release/streaming.md
                            #   tag v1.5.0
chant release cut auto --yes
```

The previous release is found in the member's ledger, never from a tag: the release cut from the nearest ancestor of the commit whose label is a version without a prerelease part and that is not [yanked](#release-deprecate-yank-and-restore). The commits counted are the ones after it that touch the member's directory, merges left out. A release member that sits in a nested workspace, such as `release/core` beside a package at `packages/core`, counts the directory of the outer workspace's member of its name, as `release changed` maps paths. Each commit gives a level: a `type!:` subject or a `BREAKING CHANGE:` footer a major, `feat` a minor, anything else a patch. The pending intent files give theirs, and the highest of all is applied to the previous label. A label with a leading `v` gives labels with one, and a `0.x` version becomes `1.0.0` on a breaking change.

Prereleases cut since the previous release count too. When one has a higher version than the bumped one, the next label is that version, so `2.0.0-rc.1` is followed by `2.0.0` even when only fixes landed after it. With `--pre <id>` the label is a prerelease of the computed version, `<version>-<id>.<n>`, with `n` one past the highest that version and id have in the member's ledger: `1.5.0-rc.0`, then `1.5.0-rc.1`.

A yanked release passed over keeps its version, since no registry takes a version twice, so a next label at or below it becomes its next patch. After `1.0.0`, and `1.1.0` yanked, a fix gives `1.1.1`, and the commits counted start at `1.0.0`.

A commit the member already has a labelled release of answers that label (`alreadyCut: true`), so a release workflow run again at the same commit cuts nothing new.

| Code | When |
|---|---|
| `release-next-no-previous` | The member has no release with a version label before the commit. Cut the first release with the label you choose |
| `release-next-unchanged` | No commit since the previous release touches the member, and no intent file names it |
| `release-next-pre-invalid` | `--pre` is not a letter followed by letters, digits and `-` |
| `release-next-history-shallow` | The clone is shallow, so the commits since the previous release can't be listed |
| `release-intent-invalid` | An intent file can't be read |
| `not-a-git-repository`, `revision-unknown` | No git repository here, or `--at` names no commit |

`--json` prints `{ label, at, bump, alreadyCut, from: { label, commit }, commits: [{ sha, subject, bump }], intents: [{ path, added, bump, summary }], tag }`, where `tag` is the one `release.tag` gives the label, or `{ error: { code, message, fix } }` with exit 1.

### Intent files

An intent file says what a change releases, for a change whose commits don't say it, or to write the summary the release notes show. It is a Markdown file under `.chant/release/` at the repository root, committed with the change. Its front matter names members and the level each takes, and the text after it is the summary:

```md
---
core: minor
lexicon-aws: patch
---
The core reads its config once, at start.
```

A key is a member's name as `release changed` lists it (a full ledger name such as `npm/core` also works), or `*` for every member, which is the key a project that is no workspace member uses. A level is `major`, `minor` or `patch`. `README.md` in the directory is not an intent file, and any other `.md` file directly in it is one.

Intent files are read from the commit's tree. A cut of a member records each intent file at its commit that names the member and that no earlier cut of the member consumed, by its path and the commit that added it, on its cut line in `chant/lifecycle`. The file stays in the tree, and no commit to the branch is needed when releasing, since the next release of the member skips what a cut consumed. Delete consumed files whenever it suits; a file deleted and written again under the same name is a new intent. Each member consumes a file once, so one file naming two members applies to both releases.

[Generated notes](/chant/reference/publish-targets/#generated-notes) from commits lead with the summaries of the intent files the release's cut consumed.

## release changed

```
chant release changed [--at <sha>] [--bump-member <member>=major|minor|patch]... [--json]
```

Run in the root of a workspace whose `chant` members are released separately, it lists the members a release at a commit has to cut, in the order to publish them. `--at` names the commit; without it the tip of trunk is read, as [`release candidates`](#release-candidates) walks it.

For each `chant` member the command finds its last release: the newest cut in the member's ledger, else the newest legacy tag. Legacy tags are the prefixes `release.legacyTags` names in the workspace root's `chant.config.ts`, each followed by a version: with `legacyTags: ["release/npm/", "chant-v"]`, `release/npm/0.124.44` and `chant-v0.124.44` count, and `release/npm/core/0.125.0` does not. It lists the paths changed from that commit to `--at` and maps each to the member of the outermost workspace that holds it. That member has the release member's name. Paths that `changes.ignore` matches and generated files count for nothing. A member with paths left, or with no release yet, is `paths-changed`.

Dependencies then pull in more members, until nothing changes. The edges are the `dependencies`, `peerDependencies` and `optionalDependencies` of each member's `package.json` at the commit.

- A member of the release also releases each workspace dependency of it, direct or transitive, that has changes since its own last release (`needed-by <member>`; a changed member no other member needs keeps `paths-changed`).
- A dependent is added when the range its last release's `package.json` gives a dependency does not admit that dependency's next label (`range-broken-by <member>`). Under `^0.124.34`, a patch of the dependency forces nothing and a minor forces the dependent.

A member that an [intent file](#intent-files) names, which no cut of it consumed, is in the release too (`intent-pending`), when no path of its own changed. Its next label is the last label bumped by the highest of its commits over the changed paths, classified as [`release next`](#release-next) does, and its pending intent files, a patch when neither gives one. `--bump-member` sets a member's level outright.

```
chant release changed --bump-member core=minor
layer 0  core  0.124.44 -> 0.125.0  (paths-changed)
layer 1  lexicon-aws  0.124.44 -> 0.124.45  (range-broken-by core)
```

Members come in dependency layers: a member publishes after every member of the release it depends on, and layer 0 needs none. Within a layer they are sorted by name. A commit range that touches only `lexicons/aws/` lists `lexicon-aws`, and `core` only when core has changes of its own since its last release.

`--json` prints a [read contract](/chant/reference/workspace-read-contract/) document, `release-changed.schema.json`, a read contract at version 1, written by chant 0.124.100 and newer. Each member has `member`, `layer`, `reason` (`{ code, member }`, with `code` one of `paths-changed`, `needed-by`, `range-broken-by` and `intent-pending`), `last` (`{ label, commit, source }`, or `null`), `bump`, `bumpFrom` (`flag`, `commits`, `intents`, or `default` for a patch neither gave), `next`, `paths` and `intents`, the paths of its pending intent files. A failure exits 1 with `not-a-git-repository`, `declaration-missing`, `revision-unknown`, `bump-invalid`, `ledger-unreadable` or `intent-invalid`, an intent file that can't be read or that names a member the declaration does not have. The read uses local refs and tags and never fetches.

## release compose

Picks chosen changes from trunk onto a base, on the branch `chant/compose/<name>` ([#4168](https://github.com/INTENTIUS/chant/issues/4168), mode b). [Compose a Release](/chant/guide/compose-a-release/) walks through it.

```bash
chant release compose hotfix-1-4 --base v1.4.0 --pr 412 --work fix-cache        # a dry run
chant release compose hotfix-1-4 --base v1.4.0 --pr 412 --work fix-cache --yes  # composes and pushes
```

`--base` takes a release label or digest of the member, or anything git resolves to a commit. `--pr <n>` and `--work <id>` can each be given more than once. A pull request matches a first-parent commit of trunk after the base by its merge record `_merges/<sha>.json` on `chant/lifecycle`, or by `(#n)` at the end of its subject. A work item matches by a `Chant-Record: work:<id>` trailer or a merge record whose source names it. Every matching commit is cherry-picked in trunk order, a merge commit against its first parent, and each gets a `Chant-Composed-From: <sha>` trailer.

The picks are made in a temporary detached worktree, so the checkout is never touched and a dry run finds a conflict too. With `--yes` the local branch moves and is pushed to `origin`, never forced.

A branch that exists is only appended to. It keeps the base it has, read by walking back from its tip to the first commit on trunk, and a chosen change it already carries is listed as carried and not picked again. It refuses before any ref moves when:

| Code | When |
|---|---|
| `compose-name-invalid` | The name is not letters, digits, dots, dashes and underscores starting with a letter or digit. |
| `compose-nothing-chosen` | No `--pr` or `--work` is given. |
| `compose-base-unknown` | `--base` names no release and no commit, or the branch is new and `--base` is missing. |
| `compose-base-differs` | The branch exists on another base than `--base` names. |
| `compose-branch-diverged` | The local branch and `origin`'s have diverged. |
| `compose-source-unknown` | A `--pr` or `--work` matches no commit on trunk after the base. |
| `compose-conflict` | A pick does not apply. The message names the change, its pull request and work items, and the conflicting files. |
| `compose-push-refused` | `origin` refused the push. The local branch has moved, so push it by hand. |

The `--json` document has the compose's `name` and `branch`, its `base`, and `from`, the tip before it ran or `null`. `picked` and `already` list sources, each with `commit`, `subject`, `pr`, `work` and `chosenBy`. Then come `tip`, `written`, `pushed`, `dryRun` and `next`. A refusal prints `{ "error": { "code", "message", "conflict" } }`, with `conflict` only for `compose-conflict`.

[`chant ci tick`](/chant/cli/ci/#ci-tick) walks each pushed compose branch as it walks trunk, judging the composed commits in the window and tagging them. Each tag's record names the compose branch. When the tick revokes a trunk commit that a composed commit carries, it warns and names the composed commit. That commit's own tags decide its releases.

## release deprecate, yank and restore

Changes what consumers get from a published release, on each target `release.publish` declares that can do it, and records the change on `chant/lifecycle`.

```bash
chant release deprecate v1.4.0 --reason "slow startup" --replacement v1.4.1   # a dry run
chant release yank v1.4.0 --reason "corrupts the cache" --yes
chant release restore v1.4.0 --yes
```

| Command | Status recorded | What it is for |
|---|---|---|
| `deprecate` | `deprecated` | The release still installs, and consumers are warned. |
| `yank` | `yanked` | New consumers stop getting the release: every moving tag goes back to the previous good release. |
| `restore` | `active` | Undoes a deprecation or a yank, as far as each target can. |

The words match the statuses the record already used. A rollback of what an environment runs is a different thing, [`chant components rollback`](/chant/cli/components/), so these commands are not called that.

What each target does:

| Target | `deprecate` | `yank` | `restore` |
|---|---|---|---|
| `npm` | `npm deprecate <name>@<version> "<message>"` for each package | The same, then the dist-tag the publish moved (`latest`, the release's channel, or a prerelease's tag such as `rc`) moves to the previous good release's version where it names this one. The version stays on the registry. | Clears the message with `npm deprecate <name>@<version> ""`, and moves the dist-tag back when this release is the newest good one |
| `oci` | Nothing: a registry has no deprecation | Each moving tag that names this release's digest is pointed at the previous good release's. A moving tag is a declared tag without `{label}`, such as `latest`, or the channel. A prerelease never moved `latest`, so its yank leaves it. The label's own tag stays | Points the moving tags back when this release is the newest good one |
| `forge` | Nothing: a forge release has no deprecation | `--forge-release prerelease` (the default) marks the release a prerelease, `draft` makes it a draft again, and `delete` deletes it. The tag stays. On GitHub, unless the declaration sets `latest: false`, the previous good release becomes the latest. GitLab has no prerelease or draft, so only `delete` works there. A release with a prerelease label is a prerelease already, so `prerelease` is refused for it with `release-status-forge-prerelease` | Clears the prerelease mark, except on a release with a prerelease label, or publishes the draft. A deleted release is refused with `release-status-forge-deleted` |
| `homebrew` | Nothing: a formula has no deprecation | When the tap branch still holds this release's formula, it is replaced by the formula the previous good release published. That formula is found by its digest among the last 100 commits of the branch that touch it. One commit, over the API or over SSH | Puts this release's formula back when it is the newest good one |
| `cargo` | Nothing: a crate version has no deprecation | `cargo yank --version <version> <crate>` for each crate, with `--registry` when the target names one. The version stays downloadable for lockfiles that name it, and new resolutions skip it. It needs a token in the target's token variable that may yank the crates | `cargo yank --undo` for each crate |
| `pypi`, `marketplace`, `tauri-updater` | Refused with `release-status-unsupported` | Refused | Refused |

The previous good release, for a target, is the newest release of the member on the same line that has the status `active`, is not [revoked](#revoked-releases) and was published to that target. Order is the order the releases were first cut. A yank of a release with no such earlier release can't move what npm, the OCI tags and the formula point at, and those actions are refused with `release-status-no-previous`. The rest still run. The line is the channel the release was cut for. Without one, it is the npm tag of a [prerelease](/chant/reference/publish-targets/#prereleases) label, such as `rc`, or the stable line for every other label. A yanked `1.4.0-rc.2` moves `rc` back to `1.4.0-rc.1`, and a yanked stable release never moves `latest` onto a prerelease.

When `release.tag` declares a [floating tag](#the-releases-tag) such as `v{major}`, a yank of a stable release moves that tag back to the highest version of the same major that is active, not revoked, cut without a channel and published, when the tag names the yanked release's commit. A restore moves it to the restored release when that release is the highest of its major again. The tag is moved here and force-pushed to `origin`, as `release publish` moves it. With no other release of the major to move back to, the move is refused with `release-status-no-previous`. A release's forge release is found by the tag `release.tag` renders for its label.

A yank never unpublishes from npm. npm's rules allow an unpublish only within 72 hours and only when no other package depends on the version, and the version can never be published again after it. The yank deprecates the version instead and says so. Run `npm unpublish` yourself if the version must go and npm's rules allow it.

What went out to each target is read from the publish record, `_releases/publishes.jsonl`, and not from the checkout, so the commands run from any checkout of the member. A target the release was never published to is left alone. A release published to a target that `release.publish` no longer declares gets a warning naming it.

Without `--yes` the command is a dry run. It prints the status record it would write and what each target would do, and asks no registry. A move is printed with its condition, such as `npm dist-tag add @acme/core@1.3.0 latest, if latest is 1.4.0`. With `--yes` it first appends the status record to `_releases/release-status.jsonl`, then acts on each target and appends what it did to `_releases/status-actions.jsonl`. Both files sit on `chant/lifecycle`, and each line is pushed as it is written. A yank acts on the targets last declared first, so a formula stops naming a forge release's assets before that release is withdrawn. The other two go in the order declared. Each action that is already so is reported and sends nothing. An action a target can't do is printed as a warning with its code, the other targets still run, and the command exits 0.

A run that stops part way resumes. Run the same command again: the latest status record already sets that status, so no new record is written, and a target that has a line for the record in `status-actions.jsonl` is skipped. The reason and replacement of the record being resumed are the ones used.

| Code | When |
|---|---|
| `release-not-found` | No cut names the label or digest in this member. |
| `release-status-unchanged` | `restore` of a release that was never deprecated or yanked. |
| `release-status-yanked` | `deprecate` of a yanked release. Restore it first. |
| `release-status-flag-invalid` | `--forge-release` on anything but `yank`, or `--replacement` on `restore`. |
| `release-unsigned` | The workspace names a `release` gate in `identity.gates`, and `--sign` is not given. |
| `release-signer-refused` | Under that gate, the signature does not verify for the actor against `.chant/allowed_signers` at base, or the actor is not in the gate's class. |
| `publish-config-invalid` | `release.publish` in `chant.config.ts` does not validate. |

A target that fails part way stops the run with its own code, such as `release-status-npm-failed`, `release-status-oci-failed`, `release-status-homebrew-history`, `release-status-cargo-failed`, `release-status-tag-failed` (the floating tag could not be moved or pushed) or `publish-credentials-missing`, and names the targets already done. The credentials are the ones the target publishes with.

Who may change a release's status follows [Who may cut](#who-may-cut). Without a `release` gate anyone who can push to `chant/lifecycle` and holds the targets' credentials may. With the gate, the change must be signed with `--sign` by a key the signers file at base lists for the actor, and the actor must be in the gate's class when it names one. The signature covers the release digest, the label, the actor, the time and the status, in the `chant-release` namespace. It goes in the record's `signature` field, and its bytes are never those of a cut's signature. `--actor` and `--sign` resolve the actor as `release cut` does.

The status record is the one [`chant query`](/chant/cli/query/) loads into the `release_status` table, with `env` `_releases` and the member as `component` (`.` outside a workspace). `release list` ends a deprecated or yanked release's line with its status and prints who set it and why on stderr.

| Flag | Meaning |
|---|---|
| `--yes` | Change the status. Without it the command is a dry run. |
| `--reason <text>` | Why. It goes in the record and in npm's deprecation message. |
| `--replacement <label>` | The release to use instead. It goes in the record, and npm's message says `use <label>`. |
| `--forge-release prerelease\|draft\|delete` | How `yank` leaves a forge release. Default `prerelease`. |
| `--actor <name>` | Who made the change, found as `release cut` finds it when not given. |
| `--sign [<key file>]` | Sign the change with an ssh key, or with git's `user.signingkey`. Required under a `release` gate. |
| `--json` | Print the plan, and with `--yes` the record written (`written`) and each target's `results`, as one document. |

## release list

Lists every release of the member, newest cut first. Each line starts with the label and the digest. The commit comes next, then the newest cut's signature (`signed by <actor>`, `unsigned` or `unverified`), then where the release runs. An `unverified` signature's reason goes to stderr. A [revoked](#revoked-releases) release's line ends with `revoked`. Why it was revoked goes to stderr. A [deprecated or yanked](#release-deprecate-yank-and-restore) release's line ends with its status, and who set it, when and why go to stderr.

`--json` prints a [read contract](/chant/reference/workspace-read-contract/#releases) document, `releases.schema.json`. Each entry holds the fields of the stored file. It adds `label` and `cuts`, and `environments` says where it runs: for each environment, the components whose latest deploy record there names its digest in `releaseDigest`. Each entry has `revoked`, which is `null` unless the release's commit is revoked. When it is, `revoked` holds the commit and the revoked tag as [`chant ci list`](/chant/cli/ci/#ci-list) shows it. It is also `null` when the tags can't be judged. Each cut carries `signatureCheck`, `{ status, key, reason }`. Its `status` is `verified`, `unsigned` or `unverified`, and `key` is the fingerprint in the signature. An environment shows up once `chant components promote --release` has deployed to it. A stored file or a cut line that can't be read is left out and counted under `reason`, with the code `ledger-malformed`. A read that fails outright exits 1 with `ledger-unreadable`, or `not-a-git-repository` outside git. The list reads the local branch and never fetches.

## Joining a release to its commit, gates and deploys

The records name one another through the release digest ([#4043](https://github.com/INTENTIUS/chant/issues/4043)). From a commit, a release, a release gate or a deploy record, the others are one lookup away:

| From | To | Through |
|---|---|---|
| commit | releases | the `commit` of each `_releases/<releaseDigest>.json` |
| release | gates | `releaseDigest` on the facts of `_gates/release.jsonl` |
| release | deploy records | `releaseDigest` on the records of every `<env>/releases.jsonl`, or for a record with none, the release gate resolution its `admission` names |
| deploy record | release | its `releaseDigest`, or for a record with none but an `admission` of op `release`, the resolution that admission names |

A deploy record's `env` with its `releaseDigest` names the target. `components promote --release` and [`run --components --release`](/chant/cli/run/#running-a-release---release) write the field, and `components rollback` and `components redeploy` copy it from the record they restore. [`workspace status`](/chant/cli/workspace-status/) lists it on each item as `releaseDigest`, with `releaseLabel`, the label the cut gave.

`joinRelease` in `lifecycle/release-join.ts` does the walk for a library reader. It takes `{ commit }`, `{ commits }`, `{ release }`, `{ deploy }` or `{ gate }` and returns what it found, each with its `label`, `commit`, `cuts`, `gates` and `deploys`. A commit can have several. `{ commits }` joins every release cut from any of several commits and reads the ledgers once ([#4023](https://github.com/INTENTIUS/chant/issues/4023)). A starting point that names nothing returns an empty list and a `reason`. [`workspace graph --intent`](/chant/cli/workspace-graph/#the-why-chain) uses it for the why chain, from a piece of code to the releases and deploys that shipped it.
