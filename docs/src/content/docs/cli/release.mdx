## Synopsis

```
chant release cut [<label>] [--at <sha>] [--yes] [--build <command>] [--param <name=value>]... [--params-file <file>]
                  [--src <dir>] [-o <file>] [--lexicon <name>] [--actor <name>] [--sign [<key file>]] [--channel <tag>] [--lane <name>] [--json]
chant release candidates [--env <env>] [--branch <branch>] [--lane <name>] [--forge-issues] [--json]
chant release compose <name> [--base <label|sha>] (--pr <n> | --work <id>)... [--yes] [--json]
chant release publish <label|digest> [--yes] [--allow-unsigned] [--require-provenance] [--json]
chant release verify <label|digest> [--json]
chant release workflow [--forge github|gitlab|forgejo] [--install <command>] [--build <command>] [--chant <command>] [--output <file>]
chant release list [--json]
chant release export <label|digest> --env <env> [-o <dir>] [--json]
```

A release is the compiled output of one green commit of one member ([#4026](https://github.com/INTENTIUS/chant/issues/4026), [ws-104](https://github.com/INTENTIUS/chant/blob/main/docs/design/decisions/ws-104-the-release-model.md)). The commit is the source, and the release is what moves through the environments. A release holds the commit, the artifacts built once from it, and one target per environment. A target lists the templates compiled for that environment and the build parameters they were compiled with.

This is a separate object from a deploy record. A deploy record is a line of `<env>/releases.jsonl` that `chant run --components` and `chant components promote` append when they deploy a component. [`chant components promote --release`](/chant/cli/components/#components-promote) deploys one target and names its digest on the deploy record it writes.

## release cut

Cuts a release of the member in the current directory from the checkout's `HEAD`. A release is only ever cut by this command; [`chant ci tick`](/chant/cli/ci/#ci-tick) never cuts one ([ws-105](https://github.com/INTENTIUS/chant/blob/main/docs/design/decisions/ws-105-release-trigger-and-revocation.md), proposed). See [Cutting on green](#cutting-on-green) for a pipeline that cuts every green commit, and [Release from your workstation](/chant/guide/release-from-workstation/) for a cut made on a laptop and published from CI.

```bash
git fetch origin --tags
git checkout "$(chant ci last-green)"
chant release cut v1.4.0 --build "npm run build"         # a dry run: prints the plan
chant release cut v1.4.0 --build "npm run build" --yes   # cuts, records and tags
```

Without `--yes` the cut is a dry run ([#4027](https://github.com/INTENTIUS/chant/issues/4027)). It makes every check below and compiles every environment, then prints what the cut would record and tag, and what will be published where. Nothing is built or signed, and nothing is written to `chant/lifecycle` or tagged. Run the same command again with `--yes` to cut. The same command runs unchanged in CI, where it needs `--yes` as well.

The cut refuses before it writes anything when:

| Code | When |
|---|---|
| `release-worktree-dirty` | A tracked file has uncommitted changes, or a file git does not ignore is untracked, so the compile would not be the commit's. A new `*.component.ts` left untracked would otherwise be compiled into the release. |
| `release-commit-not-on-trunk` | `HEAD` is not reachable from `origin/<trunk>` or from any further branch listed in `ci.green.branch` ([#4325](https://github.com/INTENTIUS/chant/issues/4325)), and is not a first-parent commit of a pushed `chant/compose/<name>` branch (see [Cutting a composed commit](#cutting-a-composed-commit)). Trunk is the branch `ci.green.branch` names in the declaration at base, else the branch `origin/HEAD` names, else `main`. |
| `release-commit-not-pushed` | `HEAD` is on the local trunk branch but not on `origin/<trunk>`, or this clone has no `origin/<trunk>`. The check reads the remote-tracking branch as this clone last fetched it and fetches nothing, so a commit pushed from elsewhere needs a `git fetch origin <trunk>` first. |
| `release-commit-not-green` | `HEAD` has no `ci/green/<sha>` tag, or with a lane no `ci/green-<lane>/<sha>` tag (see [Cutting from a lane](#cutting-from-a-lane)). [`chant ci`](/chant/cli/ci/) makes the tags; only local tags are read, so fetch them first. With [signed tags](/chant/cli/ci/#signed-tags), a tag without a valid statement doesn't count, and the message names it. |
| `release-commit-revoked` | `HEAD` has a `ci/revoked/<sha>` tag, or with a lane a `ci/revoked-<lane>/<sha>` tag. |
| `release-tag-taken` | The tag the release would get, `release/<label>`, already names another commit. |
| `release-tag-invalid` | The label makes a tag name git refuses. |
| `release-no-environments` | The member's `chant.config.ts` declares no `environments`. |
| `release-no-components` | The member declares components, none is enabled in any environment, and nothing was compiled. A project that declares no component is released from its build output instead, see [a project with no components](#a-project-with-no-components). |
| `release-unsigned` | The declaration at base names a `release` gate in `identity.gates`, and the cut is not signed. See [Who may cut](#who-may-cut). |
| `release-signer-refused` | The cut's signature does not verify for the actor against the signers file at base, or the actor is not in the `release` gate's class. Nothing is written. |
| `declaration-invalid` | The cut names a lane, and the declaration at base has no `ci.green` or declares no such lane. The message lists the lanes it declares. |
| `release-build-inputs-differ` | A component's build steps differ between environments, for example a `docker-build` whose `buildArgs` read a parameter that is set per environment. Its artifact can't be built once for every environment. |

The code is printed in square brackets at the end of the message. The dry run refuses with the same codes, and also with `release-label-taken` when the label already names a release of another commit.

### Cutting a chosen commit

`--at <sha>` cuts that commit instead of `HEAD` ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). The cut checks the commit out in a temporary detached worktree, runs the compile and the artifact builds there, and removes the worktree when it ends. The checkout you run it from can be at any commit and can have uncommitted changes, so `release-worktree-dirty` does not apply. Every other check in the table above does: the commit must be on `origin/<trunk>`, carry a `ci/green` tag that counts and no `ci/revoked` tag. `--at` takes anything git resolves to a commit, and refuses a name this clone does not know with `release-at-unknown`.

```bash
git fetch origin --tags
chant release candidates
chant release cut v1.4.0 --at 3f2a9c1e0b7d --build "npm run build" --yes
```

The worktree shares the repository's refs, so the release and the cut go to the repository's `chant/lifecycle` and the `release/<label>` tag names the commit. The checkout's `node_modules` are linked into the worktree at the top and in each directory down to the member, so the compile resolves the packages already installed. A commit whose lockfile differs from the checkout's needs its own install.

### Cutting a composed commit

A commit of a pushed `chant/compose/<name>` branch, as [`release compose`](#release-compose) makes it, is cut like a trunk commit ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). The branch is read as this clone last fetched it from `origin`. Green and revoked tags decide as they do on trunk. With [signed tags](/chant/cli/ci/#signed-tags) the tag's statement names the compose branch the tick walked.

The cut line's `composed` field names the branch and the base it was composed on. It also lists the trunk commits its `Chant-Composed-From` trailers name, oldest first. The walk goes back along first parents to the first commit on trunk, past any commit made on the branch by hand. `--channel <tag>` records `channel` on the cut line, and [`release publish`](#release-publish) then moves that tag in place of `latest`. The dry run and `--json` print both as `composed` and `channel`.

```bash
git fetch origin --tags
chant release cut v1.4.1 --at "$(git rev-parse origin/chant/compose/hotfix-1-4)" --channel hotfix --yes
```

### Cutting from a lane

A workspace whose `ci.green` declares [lanes](/chant/cli/ci/#green-lanes) tags a commit `ci/green-<lane>/<sha>` once that lane's phases pass, without waiting for the rest. `--lane <name>` cuts from that tag ([#4692](https://github.com/INTENTIUS/chant/issues/4692)): the commit must carry `ci/green-<lane>/<sha>` that counts and no `ci/revoked-<lane>/<sha>`, and `ci/green/<sha>` is not needed. A member that is always released from one lane sets it in its config, and `--lane` on the command line wins over it:

```ts
// chant.config.ts
export default {
  environments: ["staging", "prod"],
  release: { lane: "server" },
};
```

```bash
git fetch origin --tags
chant release cut v2.3.0 --at "$(chant ci last-green --lane server)" --lane server --yes
```

The lane must be one the declaration at base declares under `ci.green.lanes`, and with [signed tags](/chant/cli/ci/#signed-tags) the tag's statement must name that lane. The cut line records `lane`, and the dry run and `--json` print it, as does `release list`. Without a lane, nothing changes.

A release cut from a lane is revoked as any other is, by a `ci/revoked/<sha>` tag on its commit. A `ci/revoked-<lane>/<sha>` tag made after the cut does not revoke it yet: it refuses the next cut of that commit in that lane.

### The label in the build

When the cut has a label, every compile and artifact build runs with `CHANT_RELEASE_LABEL` set to it. The version reaches the build without a commit that bumps it ([#4168](https://github.com/INTENTIUS/chant/issues/4168), decision 5). A [build-time parameter](/chant/concepts/build-time-parameters/) reads it by declaring the variable:

```ts
// chant.config.ts
export default {
  environments: ["staging", "prod"],
  buildParams: { version: { type: "string", env: "CHANT_RELEASE_LABEL", required: false } },
};
```

A build step's own tool reads the variable directly. A Cargo crate takes it at compile time with `option_env!("CHANT_RELEASE_LABEL")`, which is `None` for a build outside a cut, or a `build.rs` passes it on with `println!("cargo:rustc-env=APP_VERSION={}", std::env::var("CHANT_RELEASE_LABEL").unwrap_or_default())` and `println!("cargo:rerun-if-env-changed=CHANT_RELEASE_LABEL")`. An npm build reads `process.env.CHANT_RELEASE_LABEL` in its bundler config. A label in the caller's shell is never passed through: only the cut sets the variable, and a cut with no label leaves it unset. A parameter that reads the label is recorded on each target like any other, so two labels of one commit are two releases.

### What the dry run prints

```
Dry run: cut v1.4.0 from commit 3f2a9c1d0b7e (on origin/main, green)
  actor alice@example.com (from git user.email)
  run minted on this machine at the cut (local)
  not signed
  tag release/v1.4.0, made here and not pushed
  dev: 1 template(s)
  prod: 1 template(s)
  api: artifacts built in dev
  digest decided when the artifacts are built
What will be published where:
  api: publish-image to $env.registry in dev, prod, by that environment's deploy (chant components promote --release v1.4.0)
  chant release publish v1.4.0: npm (2 packages) to npm the registry npm's config names
  a publish from here would carry no OIDC provenance: this run is not in CI, and a workstation has no OIDC token
```

The digest is printed when no artifact needs building, since it is then known without a build. `--json` prints the same as a document with `dryRun: true`: the commit, `label`, `releaseDigest` (or null), `alreadyCut`, `targets`, `build`, `reused`, `publishSteps`, `signatureRequired`, `actor` and `actorSource`, `run`, `trunk`, `sign`, `tag`, `publish` and `next`.

### What --yes records

With `--yes` the cut builds the artifacts and stores the release. It then appends the cut line, signed when `--sign` is given. The line names who cut and the run it ran in:

| Field | On a workstation | In CI |
|---|---|---|
| `actor` | `--actor`, else the principal the signers file at base lists for the `--sign` key, else git's `user.email`, else `USER` | `--actor`, else the signer, else `GITHUB_ACTOR` or `GITLAB_USER_LOGIN` |
| `runId` | `local-<epoch ms>`, minted from the cut's time | `GITHUB_RUN_ID` or `CI_PIPELINE_ID` |
| `runOrigin` | `{ "forge": "local" }` | `github` or `gitlab`, with the repository and a link to the run |

Everything else in the line, and the whole release, is the same wherever the cut runs. A cut of one commit on a workstation and in CI stores byte-identical release files, and cut lines that differ only in `runId`, `runOrigin`, `actor` and `timestamp`, and in `signature` when two keys signed.

The cut then tags the commit `release/<label>`, or `release/<member>/<label>` in a workspace member, as an annotated tag whose message names the release digest. The tag is made in this clone only. chant pushes `chant/lifecycle` when there is a remote and never pushes the tag, so pushing it is a step you take, and a CI workflow can publish on it. A release cut without a label gets no tag. Cutting a release that is already cut is a no-op, and makes the tag if it is missing.

The last lines name the next command. In CI that is `chant release publish <label>`. On a workstation it is `git push origin release/<label>`, so that CI publishes. After that it names the publish command and the deploy of the first environment as other choices.

### What the cut compiles

The environments are the entries of the member's [`environments`](/chant/configuration/config-file/#promotion-order-and-canary) array, in order. A pattern entry such as `pr-*` is not compiled. Each environment is compiled in a child process with `CHANT_ENV` set to it, since a template is synthesized for one environment per process. In each one the cut:

1. runs `--build <command>` in the member's directory, when given, with `CHANT_ENV` set;
2. resolves the build parameters the way `chant build --env <env>` does, with `{env}` in a `--params-file` path replaced by the environment's name;
3. discovers the components enabled under those parameters;
4. reads each template their deploys name.

A template is a file named by a literal path in a deploy step's `template`, `manifest` or `values` field, such as `cfn-deploy`'s `template: "dist/api.template.json"`. A path with the `archive:` prefix names the file after the prefix. Build and publish steps are not read. A template that does not exist after the build stops the cut.

Since [#4155](https://github.com/INTENTIUS/chant/issues/4155) the cut also records the other local paths a deploy step names, from the fields [Plan previews](/chant/components/plan-previews/#a-capability-without-plan) lists: a `helm-upgrade` chart, a `kustomize-apply` directory, an `s3-sync` source. A directory is recorded file by file. Each file is a template at its path under the directory, and the target names the directory in `trees`. A directory git ignores, such as a build's `dist`, is recorded whole, since the release is what the build wrote. A file that is not UTF-8, such as a packaged subchart, is recorded as base64 with `encoding: "base64"`. A chart named from a repository is not a local path. Such a path is not recorded and does not stop the cut.

A promote under the release points each recorded path at its copy. A directory is written under `.chant/release-templates/<digest>/<name>/`, where the digest is taken over its files. The deploy reads the tree the cut recorded and not the checkout's. A target cut before #4155 has no `trees`, and a promote of it reads charts and the other directories from the checkout, as it did.

A step that names its files through a key gets them from its capability ([#4542](https://github.com/INTENTIUS/chant/issues/4542)). A `terraform-apply` step names its root by key, and the terraform lexicon answers with the files a pull request's plan counts as the root's change. Those are the root's directory and each local module it reaches through a `./` or `../` source. Its var files and backend-config files are recorded with them. The cut records each of them for the component, directories in `trees`. A root whose state is a file in its own directory (the `local` backend) is left out, and the cut prints why, since a plan of a copy would read no state; such a root rolls back with [`chant lifecycle rollback --to`](/chant/cli/lifecycle/). A path outside the member's directory leaves its step out the same way. The dry run lists each recorded directory under its environment, and `release list --json` shows them in each target's `trees`.

Under the release, a promote or rollback writes every file the target records for the component under `.chant/release-templates/<digest>/`, each at its path from the member's directory, so a root's `../modules/vpc` still resolves. The step's `dir` is set to the copy of the root. `terraform-apply` plans that copy against the environment's state, keeping the rest of the root's entry in `terraform.roots`. The release gate binds that plan, so rolling a root back is a new plan of the old configuration under its own approval. With `terraform.compose.enabled`, a root deployed from a copy plans on its own and never in a composed group.

A `pulumi-up` step records the stack's directory. When `main` points outside it, the program's entry file is recorded too. A stack whose backend is a `file://` path relative to its directory is left out. The cut records tracked files only, so a Node program's copy has no `node_modules`. Before the copy's first preview, `pulumi-up` runs `pulumi install` in the copy (`plunge install` on plunge). That installs the dependencies the recorded lockfile pins and the plugins the program uses. It does the same for a Python program whose virtualenv or `poetry` or `uv` toolchain needs building. A Node copy with no lockfile is refused by name, since an install there would take today's versions rather than the release's. Programs in the other runtimes fetch what they need on the run.

The artifacts are built once. Each component's `docker-build`, `zip-package` and `jvm-build` steps run, and nothing else, in the first environment the component is enabled in. `docker-build` gives an `image` entry and the other two an `asset` entry, each with the archive path and the digest. When a component's source did not change since the release cut from the nearest earlier commit, its entries are carried from that release and nothing is built. Unchanged means git sees no change between the two commits in the component's file, the member's `chant.config.ts`, and the paths the build steps read (`context` and the Dockerfile, `source`, `path`). A commit that only changes a flag or a parameter then gets a release of its own with the same artifact digests.

### A project with no components

A project with no `*.component.ts` file is cut from what `chant build` writes ([#4046](https://github.com/INTENTIUS/chant/issues/4046)). For each environment the child process builds the project as `chant build <src> --env <env> -o <output>` would, with the environment's build parameters, and every file that build writes becomes a template with `component: null`. The target's `params` are the build's resolved parameters, and `artifactDigests` is empty.

| Flag | Meaning |
|---|---|
| `--src <dir>` | The build root, relative to the member's directory. Defaults to `chant.config.ts` `sourceDir`, then the member's directory, as [`chant lifecycle`](/chant/cli/lifecycle/) resolves it. A project that declares `stacks` must name one. |
| `-o <file>` | The build's output file, relative to the member's directory. Defaults to `dist/build.yaml`. As with `chant build -o`, a `.yaml` or `.yml` name writes YAML and any other name JSON, a lexicon whose output is YAML (k8s, helm) writes YAML whatever the name, and the extra files a lexicon emits are written beside it. |
| `--lexicon <name>` | Build only this lexicon. |

An Op's IR is written under the build root, so a project with `sourceDir: "src"` and an Op records `src/dist/ops/<op>/op.json` as well. The files are kept in memory and nothing is written to the checkout, so a file an earlier build left there is never recorded.

A build is deterministic. Two cuts of one commit record the same bytes for each environment and get one digest, whichever clone or directory they run in.

### The release digest and the label

The release is stored on `chant/lifecycle` under its digest, and a cut is a line appended to the cut log:

| Path | Holds |
|---|---|
| `_releases/<releaseDigest>.json` | The release, written once and never rewritten. `:` is written as `_`. |
| `_releases/cuts.jsonl` | One line per cut: `{ version, releaseDigest, label, actor, timestamp, runId, runOrigin, signature }`. |
| `_releases/templates/<digest>.txt` | Each template's bytes, by content digest, for a promote to deploy. |
| `_releases/templates/<digest>.b64` | The base64 of a template that is not UTF-8, by the digest of its bytes. |

A workspace member's copies sit under `_members/<member>/`. The cut writes the local branch and pushes it when there is a remote.

`releaseDigest` is `computePlanDigest("release", subject)`. The subject is what deploys:

| In the digest | Outside it |
|---|---|
| `member`, `commit` and `artifactDigests` | each parameter's `source` |
| each target's `env`, `templates` (with each one's `encoding`) and `trees` | the cut line's `label`, `actor`, `timestamp`, `runId`, `runOrigin` and `signature` |
| each parameter's `name` and `value` | the chant version |

So two cuts of one commit give the same digest.

The label is a human name such as `v1.4.0`. It starts with a letter or digit, and after that it may also hold `.`, `_`, `+` and `-`. Within a member, a label names one digest and a digest takes at most one label. Cutting the same digest again is a no-op that prints its label. Cutting it under another label is refused with `release-already-labelled`, and a label that already names another digest is refused with `release-label-taken`. A digest cut without a label can be given one by a later cut. `signature` holds the cut's signature, or `null` for an unsigned cut. `runId` and `runOrigin` name the run, as [What --yes records](#what-yes-records) lists. A cut line written before 0.124.29 has no `runId`, which reads as `null`, and its `runOrigin` is `null` outside CI.

### Who may cut

Who may cut a release is an `identity.gates` entry for a gate named `release` ([#4031](https://github.com/INTENTIUS/chant/issues/4031)), read from the declaration at base like every [identity gate](/chant/reference/workspace-declaration/#identity):

```json
"identity": {
  "gates": {
    "release": { "class": "releaser" }
  }
}
```

With the entry, a cut must be signed with `--sign`, by a key `.chant/allowed_signers` at base lists for the actor. With `class`, the role grants in `.chant/trust.json` at base must also put the actor in that class. A class no pinned package supplies lets nothing through. Without the entry anyone may cut, and a signature is optional.

`--sign <key file>` signs with that ssh key, and `--sign` alone uses git's `user.signingkey` when `gpg.format` is `ssh`, as `chant approve --sign` does for a [signed gate](/chant/reference/workspace-declaration/#identity). When `--actor` is not given, the actor is the principal the signers file at base lists for that key, if it lists exactly one. `--actor` names the signer otherwise, as in the cut below.

```bash
chant release cut v1.4.0 --actor github:alice --sign ~/.ssh/id_ed25519 --yes
```

Under the gate the dry run reads the key's public half and refuses with `release-signer-refused` when the signers file at base lists it for someone other than the actor. A key whose public half can't be read without its passphrase is checked when it signs.

The signature is `ssh-keygen -Y sign` in the `chant-release` namespace over four lines. They hold the release digest and the label (empty for none), then the actor and the cut's time. Changing any of them in the cut line stops it verifying. The cut checks the signature and the class before it stores anything.

`release list` and [`workspace status`](/chant/cli/workspace-status/) check each cut's signature again on every read, against the signers file and the role grants at base. A key removed from the signers file makes the cuts it signed read as `unverified` from then on.

| Flag | Meaning |
|---|---|
| `<label>` or `--label <label>` | The release's label, such as a version. Optional; a release with no label gets no tag. |
| `--yes` | Cut. Without it the command is a dry run. |
| `--build <command>` | A shell command run in the member's directory before each environment's templates are read, with `CHANT_ENV` set to the environment. |
| `--param <name=value>` | A build parameter for every environment. Repeatable. |
| `--params-file <file>` | A JSON file of build parameters. `{env}` in the path is replaced by each environment's name, as in `params.{env}.json`. |
| `--actor <name>` | Who made the cut. Defaults to the signer of `--sign`'s key, then `GITHUB_ACTOR` or `GITLAB_USER_LOGIN`, then git's `user.email`, then `USER`. |
| `--sign [<key file>]` | Sign the cut with an ssh key, or with git's `user.signingkey` when no file is given. See [Who may cut](#who-may-cut). |
| `--json` | With `--yes`, print the release, its label, the cut line written (`null` when the release was already cut), whether the release file was written now, and the components whose artifacts were carried from an earlier release, with `dryRun: false`, `actor`, `actorSource`, `tag` (`{ name, created }`, or `null`) and `next`. Without `--yes`, print the dry run's document. |

### Cutting on green

A project that wants a release for every green commit runs the cut in its own pipeline, after the tick. Cutting a digest that is already cut does nothing, so the step can run on every tick:

```bash
git fetch origin --tags
git checkout "$(chant ci last-green)"
chant release cut --build "npm run build" --yes
```

The checkout must have `origin/<trunk>` for the trunk check, so fetch the branch with the tags (`fetch-depth: 0` with `actions/checkout`). The step needs only git, the tags and the member's build, so it runs on any runner, including one whose tick reads [chant runs](/chant/cli/ci/#chant-runs-as-the-status-source). Under a `release` gate in `identity.gates` the cut must be signed by a signer in the gate's class. The job then needs that signer's key, so the declaration decides whether CI may cut.

### Revoked releases

A release is revoked when the commit it was cut from gets a `ci/revoked/<sha>` tag that counts, after the cut ([#4033](https://github.com/INTENTIUS/chant/issues/4033)). Nothing is written when that happens: every reader joins the release's `commit` to the local tags, judged as the cut judges them, so with [signed tags](/chant/cli/ci/#signed-tags) a revoked tag without a valid statement revokes nothing. Fetch the tags before reading.

| Command | With a revoked release |
|---|---|
| `release list` | Marks it, see [release list](#release-list). |
| [`chant components promote --release`](/chant/cli/components/#promoting-a-release) | Refuses it with `release-revoked` before anything runs. |
| [`chant approve`](/chant/cli/operator/#approve-op-gate) on its release gate | Refuses with `release-revoked`, so a gate pending for it never passes. `chant approve release <gate> --expire` clears the pending fact. |
| [`chant workspace status`](/chant/cli/workspace-status/#revoked-releases) | Flags each component of an environment that runs it, with the `chant components rollback` line, and reads its pending gate as `superseded`. |

## release publish

Publishes a cut release to the targets its member declares under `release.publish` in `chant.config.ts` ([#4027](https://github.com/INTENTIUS/chant/issues/4027), [#4047](https://github.com/INTENTIUS/chant/issues/4047)): npm packages, an image in an OCI registry such as GHCR or Docker Hub, and release assets on GitHub, GitLab or Forgejo. [Publish Targets](/chant/reference/publish-targets/) lists the declaration, each target and its credentials. It is meant to run in CI, where the job's OIDC token gives what it publishes provenance, as npm trusted publishing needs.

```bash
chant release publish v1.4.0          # a dry run: prints what would be published where
chant release publish v1.4.0 --yes    # publishes
```

After a best-effort fetch of `chant/lifecycle`, it refuses before it publishes anything when:

| Code | When |
|---|---|
| `release-not-found` | No cut names the label or digest in this member. |
| `release-revoked` | The release's commit is [revoked](#revoked-releases). |
| `release-unsigned` | No cut of the release is signed, and the workspace names a `release` gate in `identity.gates` or opts into `verified-releases` ([#4049](https://github.com/INTENTIUS/chant/issues/4049), [#4168](https://github.com/INTENTIUS/chant/issues/4168)). |
| `release-signature-unverified` | Under the same settings, no cut's signature verifies for its actor against `.chant/allowed_signers` at base, or, under a `release` gate, the signer is not in the gate's class. |
| `publish-provenance-missing` | `--require-provenance` is given, and the run has no OIDC token. |
| `publish-config-invalid` | `release.publish` in `chant.config.ts` does not validate. |
| `release-head-mismatch` | A target is declared, and the checkout's `HEAD` is not the release's commit. |
| `release-worktree-dirty` | A target is declared, and the tree has a change or an untracked file git does not ignore. |

A release whose cut names a `channel` moves that tag instead of `latest`: the npm target's dist-tag and the OCI target's image tag. The newest cut that names one decides.

The last two hold because a target uploads files from the checkout it runs in, which are the release's only at its commit. A CI job on the release's tag passes both. A publish with no target reads nothing and checks neither.

Signing is opt-in ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). With no `release` gate and no `security` group in `chant.workspace.json`, an unsigned release publishes without a word, and the `--json` document's `signature.status` says `unsigned` or `unverified`. A workspace that sets `"security": ["verified-releases"]` publishes only a release signed by a key the signers file lists, so cut it with `--sign` (see [Who may cut](#who-may-cut)). There `--allow-unsigned` publishes a release with no signature that verifies anyway. It prints a warning first, and `release verify` then fails for what was published. Under a `release` gate in `identity.gates`, `--allow-unsigned` changes nothing: the gate publishes only a signed release.

It then checks whether the run has an OIDC token. In GitHub Actions that means `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, which a job with `permissions: id-token: write` gets. In GitLab CI it means an ID token named `SIGSTORE_ID_TOKEN` or `NPM_ID_TOKEN` under the job's `id_tokens`. Without one, as on a workstation, the `--json` document's `provenance.oidc` is false. A workspace that opts into `supply-chain` also gets a warning on stderr before anything is published: what it publishes carries no OIDC provenance. Without that group nothing is printed. `--require-provenance` refuses such a run with `publish-provenance-missing`, with or without the group. With a token, the npm target passes `--provenance`, and after the reveal runs `npm audit signatures` over what it published.

Next it plans every target: each reads the files it would upload, checks a file the release records as an artifact against the release's digest, and finds its credentials. A target that can't stops the publish with its own code, such as `publish-file-missing`, `publish-artifact-digest-mismatch` or `publish-credentials-missing`, before anything is sent.

Without `--yes` the publish is a dry run. It prints what each target would publish and where, and uploads nothing:

```
Dry run: publish v1.4.0 (jcs1-sha256:...) from commit 3f2a9c1d0b7e
  signed by alice@example.com
What would be published where:
  npm (2 packages), with --provenance:
    @acme/core@1.4.0 to the registry npm's config names, dist-tag next, then latest, carrying sbom.spdx.json
    @acme/cli@1.4.0 to the registry npm's config names, dist-tag next, then latest, carrying sbom.spdx.json
  oci ghcr.io/acme/api:
    dist/api.oci.tar (tag v1.4.0) to ghcr.io/acme/api@sha256:...
    sbom.spdx.json (SBOM) to ghcr.io/acme/api@sha256:..., a referrer of the image
    release.intoto.json (provenance) to ghcr.io/acme/api@sha256:..., a referrer of the image
Dry run: nothing was published. Run again with --yes to publish: chant release publish v1.4.0 --yes
```

With `--yes` it publishes in two passes ([#4048](https://github.com/INTENTIUS/chant/issues/4048)). First it stages every target in the order declared, where no consumer resolves it yet: npm packages under the `next` dist-tag, images by digest, forge assets on a draft release. Only when every target has staged does it reveal them in the same order. Revealing moves npm's `latest` with the first package declared going first. It also moves the OCI tags and publishes the forge release. It prints each item it published. Each step is appended to `_releases/publishes.jsonl` on `chant/lifecycle` and pushed.

A target that fails stops the publish. The error says whether anything is visible yet and which targets staged, and ends with the same command to run again. Run again, the publish reads the record and skips what an earlier run staged or revealed, and a stage asks its registry first and sends nothing that is there. So a resume publishes nothing twice, from the same checkout or from a fresh CI clone of the release's commit. The dry run says which targets an earlier run staged or published. [Staging and resuming](/chant/reference/publish-targets/#staging-and-resuming) has the details. Every line a publish prints, its `--json` document and its record have their credentials masked.

Each target attaches the release's provenance statement when it stages, and an SBOM when it has a source for one, so nothing is visible before they are attached ([#4049](https://github.com/INTENTIUS/chant/issues/4049)). A target with no SBOM source publishes without one, except under the `supply-chain` group, which refuses it with `publish-sbom-missing` ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). An npm package carries its SBOM in the package. An image gets both as OCI referrers, and a forge release gets both as assets. The provenance statement names the release and carries the cut's signature. [SBOMs and provenance](/chant/reference/publish-targets/#sboms-and-provenance) has the details.

With no target declared it makes its checks and prints any warning. It then says that nothing was published and exits 0. The publish steps a component declares (`publish-image`, `publish-artifact`, `publish-asset`, `load-image-on-host`) are deploy steps. They run in each environment's deploy of the release, [`chant components promote --release`](/chant/cli/components/#promoting-a-release), and not here.

The document `--json` gives for a publish holds `dryRun` and the release's digest, label and commit. Beside them sit `signature` (`status`, `actor`, `key`, `reason`), `provenance` (`oidc`, `ci`, `reason`), the `warnings`, the `targets` (each `kind`, `name`, `destination`, its `progress` from earlier runs, `none`, `staged` or `revealed`, and its planned `items`), what was `published` (each `target`, `destination` and `items`; empty in a dry run) and the release's `environments`. A dry run adds `next`, and a publish adds `resumed`, the targets an earlier run had staged or revealed, each with its `target` and `step`. The warning is printed on stderr in either form.

| Flag | Meaning |
|---|---|
| `--yes` | Publish. Without it the command is a dry run. |
| `--allow-unsigned` | Under `verified-releases`, publish a release with no signature that verifies, with a warning. Never overrides a `release` gate. Without either it changes nothing. |
| `--require-provenance` | Refuse a run with no OIDC token. A CI job that must give npm provenance passes it, so a misconfigured job fails instead of publishing without. |
| `--json` | Print the document described above. |

## release workflow

Writes the publish workflow, the job that runs `chant release publish` for the release a `release/**` tag names ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). It is generated the way [`chant ci workflow`](/chant/cli/ci/#ci-workflow) writes the tick, with a header naming the command that regenerates it.

```bash
chant release workflow
```

| Forge | File |
|---|---|
| `github` | `.github/workflows/chant-release.yml` |
| `forgejo` | `.forgejo/workflows/chant-release.yml` |
| `gitlab` | `.gitlab/chant-release.yml`, which `.gitlab-ci.yml` includes |

The job checks out the tag and builds what the targets upload. Then it fetches the ci tags and `chant/lifecycle` and publishes with `--yes`. It always has the OIDC permission, so what it uploads carries provenance when the token is there. The workspace's security groups add the rest: `supply-chain` adds `--require-provenance`, and `verified-releases` adds a `chant release verify` step before the publish. With neither, nothing refuses a run that lacks them.

| Flag | Description |
|---|---|
| `--forge <forge>` | Inferred from the repository's pipeline files, `github` when there are none. |
| `--install <command>` | The install step. Default `npm ci`. |
| `--build <command>` | What builds the files the targets upload. Default `npm run build`. |
| `--chant <command>` | What runs chant. Default `npx chant`. |
| `--output <file>` | Write somewhere else. |

## release verify

Checks that a release was signed by a key `.chant/allowed_signers` lists ([#4049](https://github.com/INTENTIUS/chant/issues/4049)). It reads the release and its cuts from the local `chant/lifecycle` branch, and the signers file at the release's own commit, with its signed history, as [`chant workspace evidence verify`](/chant/cli/workspace-evidence/) reads the policy at a revision. It fetches nothing and needs no key, so fetch `chant/lifecycle` and the release's commit first.

```bash
git fetch origin chant/lifecycle:chant/lifecycle
chant release verify v1.4.0
```

A release verifies when its stored file is the digest of what it holds, and a cut of it carries a signature in the `chant-release` namespace that verifies for the cut's actor. When the declaration at the release's commit names a `release` gate with a class, the actor must be in it too. Because the signers file is read at the release's commit, a key added later does not make an older release verify, and a key removed later does not unmake it. [`release list`](#release-list) judges cuts against the signers file at base instead, which is the policy now.

It exits 0 when the release verifies and prints the signer on stderr:

```
  cut by alice at 2026-10-17T10:00:00.000Z: verified (SHA256:...)
Verified v1.4.0 (jcs1-sha256:...): signed by alice, checked against .chant/allowed_signers at 3f2a9c1d0b7e
```

It exits 1 with one of these codes:

| Code | When |
|---|---|
| `release-unsigned` | No cut of the release is signed. |
| `release-signature-unverified` | No cut's signature verifies against the signers file at the release's commit, such as one signed by a key the file does not list. |
| `release-digest-mismatch` | The stored release is not the digest of what it holds, so it was changed after the cut. |
| `release-not-found` | No cut names the label or digest in this member. |
| `release-commit-missing` | The release's commit is not in this clone. |
| `trust-policy-unreadable` | The signers file or its history at the commit can't be read. |

`--json` prints `releaseDigest`, `label`, `member`, `commit`, `signers` (`path`, `at`, `active`), `digestMatches`, `status` (`verified`, `unsigned` or `unverified`), `verifiedBy` (`actor`, `key`, or `null`), `reason` and each cut with its `signatureCheck`. A release that does not verify adds `error` with its `code` and `message`.

## release export

Writes the files a cut recorded for one environment, each at the path it was compiled to, under `-o <dir>` (the member's directory by default). Each file's bytes are read from `chant/lifecycle`, after a best-effort fetch, and checked against the target's digest first. A missing or changed file stops the export before anything is written.

```bash
chant release export v1.4.0 --env prod
kubectl apply -f dist/build.yaml
```

This is how a project with no components deploys what it cut. [`chant components promote --release`](/chant/cli/components/#components-promote) deploys components, and refuses such a cut with a pointer to this command. The project's own deploy, an Op such as `chant run deploy` or a CI job, then reads the exported files. An Op whose first phase runs the build again would overwrite them, so drop that phase when it deploys exported files. `--json` prints the digest and label with the environment and the directory written to. It also prints the target's templates and params.

## release candidates

Lists the green commits of trunk a release can be cut from, newest first ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). Trunk is the branch `release cut` checks, and the walk follows its first-parent line from the tip back to the oldest commit an environment of the member runs. When some environment runs no release yet, it reads the newest 50 commits. `--env <env>` gives one environment's view, so the walk stops at what that environment runs.

With several branches in [`ci.green.branch`](/chant/guide/branch-routing/#give-a-routed-target-a-green-verdict), `--branch <branch>` walks that one instead of the first ([#4325](https://github.com/INTENTIUS/chant/issues/4325)).

`--lane <name>`, or `release.lane` in the member's `chant.config.ts`, reads a lane's tags as [`release cut --lane`](#cutting-from-a-lane) checks them ([#4692](https://github.com/INTENTIUS/chant/issues/4692)). A candidate is then a commit with `ci/green-<lane>/<sha>` and no `ci/revoked-<lane>/<sha>`, and a commit with `ci/revoked-<lane>/<sha>` is skipped. The document's `lane` names the lane, or is `null` for `ci/green/<sha>`.

```bash
git fetch origin --tags
git fetch origin chant/lifecycle:chant/lifecycle
chant release candidates --env prod
```

Each candidate is a commit with a `ci/green` tag that counts and no `ci/revoked` tag. Under it are the first-parent commits since the previous candidate, so each commit appears under exactly one candidate. Its pull request is the one its merge record names. Without a merge record it is the one the subject names, `(#123)` at the end as a forge's squash merge writes it. Its work items are the ones its `Chant-Record: work:<id>` trailers name. The list is grouped by work item and then by pull request ([#4168](https://github.com/INTENTIUS/chant/issues/4168) 4.4). Changes with two work items show under both, and those with none come last, under "no work item". Within a group, the ones that landed without a pull request show under "no pull request". A candidate also lists the flags whose record files those commits change. It says which environments run neither it nor a later commit, and which labels were already cut from it. A revoked commit is listed as skipped, and its changes stay with the next candidate. Commits after the newest candidate are counted as not green yet.

With `--forge-issues`, each pull request's closing issues are read from the forge and become work items ([#4649](https://github.com/INTENTIUS/chant/issues/4649)). A change that no `Chant-Record` trailer gives a work item shows under each issue its pull request closes, as "issue #70", after the work ids and before "no work item". A change with a work id stays under it. When the forge can't be read, the changes stay where they were, and the reason is printed once on stderr. [Issues a pull request closes](/chant/cli/workspace-graph/#issues-a-pull-request-closes) says which forge and token are used, and what each forge answers from. Without the flag nothing reaches the network.

```bash
GH_TOKEN=$(gh auth token) chant release candidates --forge-issues --json
```

With `--json` the output is the [read contract](/chant/reference/workspace-read-contract/)'s `release-candidates.schema.json` document. Its `environments` field lists what each one runs, `since` is the commit the walk stopped at (or `null`), `candidates` and `skipped` are newest first, and `pending` holds the commits after the newest candidate. Each change has `commit`, `subject`, `date`, `work`, `records` (every `Chant-Record` trailer as `<kind>:<id>`), `pr` and `merge`, the merge record `_merges/<sha>.json` on `chant/lifecycle` when one exists. Each change also has `closes`: `null` without `--forge-issues` or a pull request, else what the forge says the pull request closes, `{ resolved, issues, reason }`. Each candidate's `groups` holds the same changes as `{ work, issue, pullRequests: [{ pr, commits }] }`, with `null` for no work item, no issue and no pull request, in the order the text output prints them. Outside git the command exits 1 with `not-a-git-repository`. When the ledger or the tags can't be read it exits 1 with `ledger-unreadable`. Nothing is fetched, so fetch the tags and `chant/lifecycle` first. `--forge-issues` reads the forge's API and fetches no git ref.

## release compose

Picks chosen changes from trunk onto a base, on the branch `chant/compose/<name>` ([#4168](https://github.com/INTENTIUS/chant/issues/4168), mode b). [Compose a Release](/chant/guide/compose-a-release/) walks through it.

```bash
chant release compose hotfix-1-4 --base v1.4.0 --pr 412 --work fix-cache        # a dry run
chant release compose hotfix-1-4 --base v1.4.0 --pr 412 --work fix-cache --yes  # composes and pushes
```

`--base` takes a release label or digest of the member, or anything git resolves to a commit. `--pr <n>` and `--work <id>` can each be given more than once. A pull request matches a first-parent commit of trunk after the base by its merge record `_merges/<sha>.json` on `chant/lifecycle`, or by `(#n)` at the end of its subject. A work item matches by a `Chant-Record: work:<id>` trailer or a merge record whose source names it. Every matching commit is cherry-picked in trunk order, a merge commit against its first parent, and each gets a `Chant-Composed-From: <sha>` trailer.

The picks are made in a temporary detached worktree, so the checkout is never touched and a dry run finds a conflict too. With `--yes` the local branch moves and is pushed to `origin`, never forced.

A branch that exists is only appended to. It keeps the base it has, read by walking back from its tip to the first commit on trunk, and a chosen change it already carries is listed as carried and not picked again. It refuses before any ref moves when:

| Code | When |
|---|---|
| `compose-name-invalid` | The name is not letters, digits, dots, dashes and underscores starting with a letter or digit. |
| `compose-nothing-chosen` | No `--pr` or `--work` is given. |
| `compose-base-unknown` | `--base` names no release and no commit, or the branch is new and `--base` is missing. |
| `compose-base-differs` | The branch exists on another base than `--base` names. |
| `compose-branch-diverged` | The local branch and `origin`'s have diverged. |
| `compose-source-unknown` | A `--pr` or `--work` matches no commit on trunk after the base. |
| `compose-conflict` | A pick does not apply. The message names the change, its pull request and work items, and the conflicting files. |
| `compose-push-refused` | `origin` refused the push. The local branch has moved, so push it by hand. |

The `--json` document has the compose's `name` and `branch`, its `base`, and `from`, the tip before it ran or `null`. `picked` and `already` list sources, each with `commit`, `subject`, `pr`, `work` and `chosenBy`. Then come `tip`, `written`, `pushed`, `dryRun` and `next`. A refusal prints `{ "error": { "code", "message", "conflict" } }`, with `conflict` only for `compose-conflict`.

[`chant ci tick`](/chant/cli/ci/#ci-tick) walks each pushed compose branch as it walks trunk, judging the composed commits in the window and tagging them. Each tag's record names the compose branch. When the tick revokes a trunk commit that a composed commit carries, it warns and names the composed commit. That commit's own tags decide its releases.

## release list

Lists every release of the member, newest cut first. Each line starts with the label and the digest. The commit comes next, then the newest cut's signature (`signed by <actor>`, `unsigned` or `unverified`), then where the release runs. An `unverified` signature's reason goes to stderr. A [revoked](#revoked-releases) release's line ends with `revoked`. Why it was revoked goes to stderr.

`--json` prints a [read contract](/chant/reference/workspace-read-contract/#releases) document, `releases.schema.json`. Each entry holds the fields of the stored file. It adds `label` and `cuts`, and `environments` says where it runs: for each environment, the components whose latest deploy record there names its digest in `releaseDigest`. Each entry has `revoked`, which is `null` unless the release's commit is revoked. When it is, `revoked` holds the commit and the revoked tag as [`chant ci list`](/chant/cli/ci/#ci-list) shows it. It is also `null` when the tags can't be judged. Each cut carries `signatureCheck`, `{ status, key, reason }`. Its `status` is `verified`, `unsigned` or `unverified`, and `key` is the fingerprint in the signature. An environment shows up once `chant components promote --release` has deployed to it. A stored file or a cut line that can't be read is left out and counted under `reason`, with the code `ledger-malformed`. A read that fails outright exits 1 with `ledger-unreadable`, or `not-a-git-repository` outside git. The list reads the local branch and never fetches.

## Joining a release to its commit, gates and deploys

The records name one another through the release digest ([#4043](https://github.com/INTENTIUS/chant/issues/4043)). From a commit, a release, a release gate or a deploy record, the others are one lookup away:

| From | To | Through |
|---|---|---|
| commit | releases | the `commit` of each `_releases/<releaseDigest>.json` |
| release | gates | `releaseDigest` on the facts of `_gates/release.jsonl` |
| release | deploy records | `releaseDigest` on the records of every `<env>/releases.jsonl`, or for a record with none, the release gate resolution its `admission` names |
| deploy record | release | its `releaseDigest`, or for a record with none but an `admission` of op `release`, the resolution that admission names |

A deploy record's `env` with its `releaseDigest` names the target. `components promote --release` and [`run --components --release`](/chant/cli/run/#running-a-release---release) write the field, and `components rollback` and `components redeploy` copy it from the record they restore. [`workspace status`](/chant/cli/workspace-status/) lists it on each item as `releaseDigest`, with `releaseLabel`, the label the cut gave.

`joinRelease` in `lifecycle/release-join.ts` does the walk for a library reader. It takes `{ commit }`, `{ commits }`, `{ release }`, `{ deploy }` or `{ gate }` and returns what it found, each with its `label`, `commit`, `cuts`, `gates` and `deploys`. A commit can have several. `{ commits }` joins every release cut from any of several commits and reads the ledgers once ([#4023](https://github.com/INTENTIUS/chant/issues/4023)). A starting point that names nothing returns an empty list and a `reason`. [`workspace graph --intent`](/chant/cli/workspace-graph/#the-why-chain) uses it for the why chain, from a piece of code to the releases and deploys that shipped it.
