## Synopsis

```
chant workspace train <env> [--pin <member>=<label|digest>]... [--dry-run] [--json]
chant workspace train list <env> [--json]
chant workspace train promote <env> [<train id|digest>] [--gate <name>] [--continue] [--dry-run] [--json]
chant workspace train cut <env> [--at <sha>] [--levels <levels>] [--yes] [--no-push] [--json]
chant workspace train prepare <env> [<train id|digest>] [--json]
chant workspace train publish <env> [<train id|digest>] [--yes] [--allow-unsigned] [--require-provenance] [--json]
```

## Description

Releases stay per member. Each one is a digest over its artifacts and a git commit, cut with [`chant release cut`](/chant/cli/release/) in the member's directory and kept in its own ledger (ws-043). A release train is one record that pins a release of every `chant` member, so several members can move together ([#2554](https://github.com/INTENTIUS/chant/issues/2554), [#4037](https://github.com/INTENTIUS/chant/issues/4037)). It names each one by digest and never changes it.

`chant workspace train <env>` picks each `chant` member's newest cut, or the one `--pin <member>=<label|digest>` names, and appends the record to `_members/_workspace/<env>/trains.jsonl` on `chant/lifecycle`. In a nested workspace, a member of kind `workspace`, the record goes inside the outer member's ledger, as the nested members' ledgers do: the nested workspace in the outer member `npm` writes `_members/npm/_members/_workspace/<env>/trains.jsonl`, and its members' releases are read from `_members/npm/_members/<member>/`. So two nested workspaces never share a train file, nor does a nested one with the outer one, and the same holds for their runs and gates. It refuses and writes nothing when a member has nothing cut or a pin names nothing. A workspace with no `chant` or `repo` member is refused too, so the record never leaves a member out and never pins nothing.

A [`repo` member](/chant/cli/workspace-graph/) names another repository by URL and pinned `rev` ([#5119](https://github.com/INTENTIUS/chant/issues/5119)). Its releases are read the way its graph is: chant fetches the revision into the user's cache, fetches that repository's `chant/lifecycle` into the same cache clone, and runs `chant release list --json` in the workspace root at the revision. Nothing is written in the other repository. The ledger is fetched again on every read, since releases are cut after the revision a declaration pins. A member whose repository can't be read refuses the train with the reason. The pinned member also carries `repo: { url, rev }`, the URL with any credential removed. An org workspace, which holds only `repo` members, records its trains this way.

```
$ chant workspace train prod --pin api=v1.4.0
Recorded release train train-8a2c… for prod, digest jcs1-sha256:5d1e…:
  api                      v1.4.0  sha256:3f…  9b1c0d2e4f6a
  web                      v2.0.1  sha256:c7…  9b1c0d2e4f6a
```

Each pinned member carries `member`, `releaseDigest`, `commit` and `label`. Beside them sit `env`, `timestamp`, `actor` and `trainDigest`.

`trainDigest` is `computePlanDigest("release-train", { members })` over each member's `member` and `releaseDigest`, sorted by member. Each `releaseDigest` already covers its commit, and the label is the cut's own, so neither is hashed again. Nor is anything about when, where or by whom the record was made. The same picks therefore always give the same digest, and a staging record and a prod record with the same picks share it. A line written by an older chant has no `trainDigest`, and the reader computes it.

`chant workspace train list <env>` prints what is recorded for `<env>`, oldest first. With `--json`, each entry also carries `promotions`: every [`train promote`](#promote) run for it, oldest first, as `{ run, started, ended, status, gate, members[{ member, status, memberRun }] }`. That is enough for a lane to draw one row per train that opens to its members. A step of a promote across repositories also carries `repo`, the member's `outcome` once it answered, and a `reason` when it did not pass. A run of that kind is written again as each member answers, and `promotions` lists the newest line of each run.

## Promote

`chant workspace train promote <env>` takes the newest record for `<env>`, or the one named by id or digest. It runs [`chant components promote --to <env> --release <releaseDigest>`](/chant/cli/components/#components-promote) in each member's directory under the member's own chant, one member at a time. The composed graph's member links set the order, so a producer goes before the members that read it. Unlinked members keep the order they were pinned in. The first member that fails or stops at a gate stops the rest. `--dry-run` prints the order and runs nothing.

A member's promote binds its own gate to what it deploys and to its change set for `<env>`. Without `--gate`, those gates apply as they would to a promote run by hand.

With `--gate <name>`, one approval covers every member:

1. Every member plans first with `components promote --plan-only` and deploys nothing. The workspace gate `<name>` records one pending fact under `_members/_workspace/_gates/<name>.jsonl`. It holds one cover per member release gate, naming the gate, the environment and `releaseDigest`, with the member's change set as `planDigest`. The fact also names the train as `train: { id, digest }`. A member whose change set is empty needs no cover, since its gate passes without an approval. The command exits 3.
2. `chant workspace run approve <name> --plan <digest>` approves the fact. The approval copies the covers and the train.
3. Run the same command again. Now an approval of exactly those covers stands, so each member is promoted in turn under `CHANT_WORKSPACE_GATE`. A member's gate counts the workspace approval only when a cover names that gate with the member's `releaseDigest` and change set for `<env>`. The member must also set `acceptWorkspaceGates: true` at base. A member that doesn't opt in still needs its own approval.

A member's plan can move between the approval and the promote, for example when a producer's apply changed what the member reads. Its change set then differs from the approved one. If the move shows up while every member plans, the covers hash to a new digest and a new fact is recorded before anything deploys. If it shows up only during the deploy, that member stops at its own gate.

```
$ chant workspace train promote prod --gate train-prod
release train train-8a2c… to prod: gated
  api                      gated  gate prod-release
  web                      gated  gate prod-release
Workspace gate "train-prod" is pending over 2 release gate(s) of 2 member(s), digest sha256:41c0…. Nothing was deployed.
  Approve: chant workspace run approve train-prod --plan sha256:41c0…
$ chant workspace run approve train-prod --plan sha256:41c0…
$ chant workspace train promote prod --gate train-prod
release train train-8a2c… to prod: ok (workspace gate "train-prod" approved sha256:41c0…)
  api                      ok  (run 9001)
  web                      ok  (run 9001)
```

Each promote is recorded as a workspace run in `_members/_workspace/<env>/runs.jsonl`, with `train: { id, digest }`. It has one step per member, `<member>/components promote`, which keeps the step's status and exit code and the member's run id. The deploy records each member writes name its release as usual. The command exits 0 when every member promoted and 3 when it waits on a gate. Any other stop exits 1.

## Promote across repositories

A train whose members are `repo` members is promoted from the control repository, one member repository at a time ([#5119](https://github.com/INTENTIUS/chant/issues/5119)). Each member repository runs its own release under its own identity. The control repository holds one dispatch-only token per member repository, in the secret `CHANT_TRAIN_TOKEN_<MEMBER>` (the member's name upper-cased, every other character `_`), and no cloud credentials.

1. `chant workspace train promote <env>` writes a workspace run citing the train. It sends one `<product>-train` dispatch into the first member repository in link order, producers first, and marks that step `dispatched`. The dispatch carries the member, `env`, the train id, the run id, the release digest and the release's commit. The order comes from the links the declaration states.
2. The member repository's `<product>-train.yml` checks out the release's commit and runs `chant run --components all --env <env> --release <digest>`. Each deploy record it writes names the release. Its last step tells the control repository how the run ended with the member's usual `<product>-applied` dispatch. That dispatch also carries `train`, `run`, `env` and `release`. The outcome is `applied`, `waiting` when the run stopped at the member's own gate, or `failed`.
3. The control repository's `<product>-dependents.yml` records the answer in `_control/applied.jsonl` with its train fields. In place of the member's dependents, it runs `chant workspace train promote <env> <train> --continue` and pushes `chant/lifecycle`. `--continue` reads the answer for the member the run waits on. After `applied` or `unchanged`, that step is `ok` and the next member is dispatched, or the run ends `ok`. `waiting` ends the run `gated` at that member, and `failed` or `partial` ends it `fail`. The step says why. An answer for another release digest or environment fails the step. Until the member answers, `--continue` writes nothing.

Each member keeps its own gate. A workspace gate covers members of one repository only, so `--gate` is refused for such a train. A promote is refused while another promote of the same train is in flight. Once the run has stopped, promote the train again: the new run starts from the first member, and a member whose release is already deployed runs nothing new. A train that pins both `chant` and `repo` members is refused at promote.

The two `<product>-train.yml` workflows are written by the GitHub lexicon (`generateTrainMemberPipeline` and `generateTrainControlPipeline` in `@intentius/chant-lexicon-github/components/train-pipeline`). The pieces come from `@intentius/chant/control/train`. The member's workflow takes the product's cloud login steps before the run. The control repository's job has one step after the checkout, which holds the dispatch tokens and nothing else. `generateControlPipeline({ trainMembers })` maps the same tokens into the dependents workflow, so an answer can dispatch the next member. A GitLab member repository takes no train dispatch yet.

## Cut

`chant workspace train cut <env>` releases every member that changed, in one run, at the commit `--at` names (the trunk's tip without it). It runs in the root of a workspace whose `chant` members are the units released separately, such as one member per package of a monorepo, and needs `release.train` in the root's `chant.config.ts`:

```ts
// release/chant.config.ts, the root of the workspace of release members
export default {
  release: {
    train: { env: "npm" },
  },
};
```

| Field | Meaning |
|---|---|
| `env` | The environment the train is recorded for, and the middle of its tag `release-train/<env>/<id>`. The command's `<env>` must name it |
| `first` | `each` (default) labels every member from its own versions. `together` makes the environment's first train cut every member at one label, one past the highest version any of them has, for packages that shipped at one shared version until now |
| `check` | Shell lines run in the root once the labels are known and before any member is cut, with `CHANT_RELEASE_COMMIT`, `CHANT_TRAIN_ENV` and `CHANT_TRAIN_PLAN`, a JSON file of `{ env, commit, members: [{ member, label }] }`. One that fails stops the train with nothing cut. What a line prints goes to stderr |
| `buildDependencies` | The command [`prepare`](#prepare) runs in a package the train's members build against. Default: the package's `prepack` script, else its `build` script. `false` builds nothing |

The cut, in order:

1. A commit a `release-train/<env>/*` tag already names is released: it says so and does nothing.
2. The members are those [`chant release changed`](/chant/cli/release/changed/) lists at the commit, with its dependency closure, in publish order. `--levels` types levels: `auto` (the default: each member's conventional commits and intent files decide), a level for every member (`minor`), `<member>=<level>`, or several separated by spaces or commas (`minor core=major`). A member already cut from this commit, by a run that stopped part way, is taken at its label and is not cut again.
3. Each member's label is its bumped label, floored past every version it already has: the labels in its ledger, its release tags (as `release.tag` renders them, default `release/<workspace>/<member>/<label>`), the `release.legacyTags` tags, the `version` of each package its `release.version` names at the commit, and every version npm lists for the packages it stamps or publishes (`npm view <name> versions`, at the target's `registry`). A label is never one the registry already holds. A registry that can't answer stops the cut with `train-registry-unreadable`; one that has never heard of a package adds nothing.
4. Each member the train cuts has its npm packages looked up on the registry, at the target's `registry`. A package that has never been published refuses the train with `publish-npm-never-published` before any member is cut, since npm trusted publishing can't create a package and its first publish would otherwise fail part way through the train. The message names the package. Publish one placeholder version of it by hand (`npm login`, then `npm publish`), add the trusted publisher on npmjs.com under the package's Settings, and cut again. A registry that can't answer refuses with `publish-npm-registry-unreadable`. [`chant release doctor`](/chant/cli/release/doctor/) reports the same package before a cut.
5. `release.train.check` runs.
6. [`chant release cut <label> --at <commit> --yes`](/chant/cli/release/cut/) runs in each member's directory. Each cut pushes its record and tags the commit locally.
7. The train is recorded, every member cut here at its new release and every other member at its newest, and `chant/lifecycle` is pushed.
8. The member tags and `release-train/<env>/<id>` on the commit go to `origin` in one atomic push. A workflow on that tag publishes the train.

Without `--yes` it prints the members, their labels and why, runs each cut's dry run, and writes nothing. `--no-push` records and tags locally and pushes no tag. `--json` prints the plan, the tags and the train. Under `--json` stdout holds that document and nothing else: what the `release.train.check` lines and the member cuts print goes to stderr.

```
$ chant workspace train cut npm --levels "lex=minor"
Release train for npm from 3c9f58c44300:
  core                     1.0.4        paths-changed; patch from default; floor 1.0.3
  lex                      1.1.0        paths-changed; minor from typed; floor 1.0.0
Dry run: nothing was cut, recorded, tagged or pushed. Run again with --yes to cut the train.
```

| Code | Why the cut stopped |
|---|---|
| `train-not-declared` | The root's `chant.config.ts` declares no `release.train` |
| `train-env-mismatch` | `<env>` is not the one `release.train.env` names |
| `train-levels-invalid` | `--levels` has a word that is not a level or `<member>=<level>`, names a member the workspace does not have, or gives per-member levels to a `first: "together"` train |
| `train-registry-unreadable` | npm could not say which versions a package has |
| `publish-npm-never-published` | A member's npm target names a package the registry has never published. Nothing was cut |
| `publish-npm-registry-unreadable` | The registry could not say whether a package of a member's npm target exists. Nothing was cut |
| `train-check-failed` | A `release.train.check` line failed. Nothing was cut |
| `train-cut-failed` | A member's cut failed. Run the train again: members already cut from the commit are taken as they are |
| `train-member-unreleased` | A member the train does not cut has no release to pin |
| `train-record-not-pushed` | The train was recorded and `chant/lifecycle` did not reach the remote, so no tag was pushed |
| `train-tags-not-pushed` | The atomic tag push failed; the message names the push to run |

## Prepare

`chant workspace train prepare <env> [<train>]` readies a checkout of the train's commit for `train publish`, as the generated workflow's publish job does before it. For each member the train cut from this commit:

- its `release.version` files take the member's label, and under `ranges: "train"` each workspace dependency's range takes `^` and the label the train gives the member that owns that package. `train publish` takes these files, every member's, as the commit's.
- the workspace packages it depends on, directly or not, that this run does not publish are built once each, dependencies first, with `release.train.buildDependencies` or the package's `prepack` (else `build`) script. A workspace package is one a member's `release.version.packages` or npm target names, or one the repository root declares in `workspaces` (npm, yarn) or `pnpm-workspace.yaml`. The members this run publishes build when npm packs them, in the train's layer order. A member cut from this commit whose package an earlier run of the publish already revealed is not packed again, so when a member still to publish depends on it, prepare builds it like any other dependency: a resumed publish finds the packages it builds against built.

The builds print to stderr, so `--json` prints only the train, what was stamped and what was built. It refuses a train that is not recorded (`train-unknown`), a checkout whose commit the train cut no member from (`train-nothing-cut-here`), and a build that fails (`train-build-failed`).

## Publish

`chant workspace train publish <env>` publishes the newest train for `<env>`, or the one named by id or digest, as one set: every member's [publish targets](/chant/reference/publish-targets/#publishing-a-release-train) stage before any reveals, each member's [`release.verify`](/chant/cli/release/publish/#verifying-the-staged-release) commands run after the whole train has staged and before the first layer reveals, and the members reveal in dependency layers, each layer waiting until the one before it is served to a consumer. The layers come from what each member's targets publish and need, across kinds: an npm package after the packages it depends on, a crate after the crates it depends on, an MCP Registry entry after the packages and images its `server.json` lists. `release.dependsOn` in a member's `chant.config.ts` names members it comes after that no manifest shows, such as the member whose package an image bundles. It runs in a checkout of the commit the train's new releases were cut from, as a CI job on the train's tag does, and publishes each member whose release was cut there. A member pinned at a release from another commit is not published again, and must already be: its publish record or its registry says so, or nothing stages.

Without `--yes` it prints the members in their layers, each with the members it comes after and what it would publish where, and sends nothing. With `--yes` it publishes. A failure prints what is staged and what is revealed, and running the same command again resumes from each member's publish record. `--allow-unsigned` and `--require-provenance` apply to every member as they do to [`chant release publish`](/chant/cli/release/publish/). A train of `repo` members is refused, since each one publishes in its own repository.

```
$ chant workspace train publish npm
Dry run: publish release train train-3c1e… (jcs1-sha256:9f0a…) for npm
  lexicon-sql 0.125.0: pinned at commit 4d2c9a0b1e7f, already published
  layer 0: core 0.125.1
    npm (1 package):
      @intentius/chant@0.125.1 to the registry npm's config names, dist-tag latest
  layer 1: lexicon-aws 0.125.1, after core
    npm (1 package):
      @intentius/chant-lexicon-aws@0.125.1 to the registry npm's config names, dist-tag latest
```

### Resuming a train

A train that was cut and recorded and did not publish is finished by dispatching the release workflow with its `train` input, the train's id as `chant workspace train list <env>` prints it (see [release workflow](/chant/cli/release/workflow/)). The gate and the cut are skipped. The publish job checks out the commit `release-train/<env>/<id>` names and runs `train prepare` and `train publish` for that train, and the publish picks up from each member's publish record.

Two things come from different places. The workflow file is the one on the branch the dispatch runs from, the default branch unless you pick another, so a fix to the workflow merged since the cut applies to the resumed run. The chant code a step runs, such as `npx tsx packages/core/src/cli/main.ts`, is the cut commit's. A change to the release tooling merged after the cut does not reach the resumed run, and a step the workflow file now has that the cut commit's chant lacks fails there.

## Options

| Option | Effect |
|---|---|
| `--pin <member>=<label\|digest>` | The release to pin for that member instead of its newest. Repeatable. |
| `--gate <name>` | (`promote`) Plan every member first and wait on one workspace gate over their release gates. Refused for a train of `repo` members. |
| `--continue` | (`promote`) For a train of `repo` members: move the promote in flight on from the answer the control repository recorded, and start nothing new. |
| `--dry-run` | Pick the releases and print the train without writing it. With `promote`, print the order and run nothing. |
| `--yes` | (`cut`) Cut, record, tag and push. (`publish`) Publish. Without it each prints its plan and sends nothing. |
| `--dry-run` | Plan only, as without `--yes`. With `--yes` too, `cut` and `publish` stay a dry run. |
| `--at <sha>` | (`cut`) The commit to release. Default: the trunk's tip. |
| `--levels <levels>` | (`cut`) `auto`, a level for every member, `<member>=<level>`, or several of them separated by spaces or commas. |
| `--no-push` | (`cut`) Record the train and tag locally, and push no tag. |
| `--allow-unsigned`, `--require-provenance` | (`publish`) As for `chant release publish`, for every member. |
| `--json` | Print the train, or the list, as JSON. |
| `--actor <principal>` | Who records the train; else the CI or shell identity. |
