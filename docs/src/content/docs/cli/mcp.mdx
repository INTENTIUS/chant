## Synopsis

```
chant serve mcp [path]
```

## Description

`chant serve mcp` starts an MCP (Model Context Protocol) server over stdio. This allows AI agents that support MCP — such as Claude Code, Cursor, and Windsurf — to interact with your chant project programmatically.

Typically you don't run this directly. `chant init` detects your IDE and writes the MCP config to the appropriate global config file — `~/.claude/mcp.json` for Claude Code, `~/.cursor/mcp.json` for Cursor, or `~/.config/mcp/mcp.json` otherwise. Your agent picks it up automatically. See [Agent Integration](/chant/guide/agent-integration/).

### At a workspace root

A project with no lexicon refuses to start with "No lexicon detected". The root of a declared workspace (`chant.workspace.json`) with no lexicon of its own is the exception, as in a repo made from chud's template, whose lexicons are all in `delivery/`. There the server starts and serves the core tools and resources below, with the lexicons of the workspace's members of kind `chant`, each read from that member's own `chant.config.ts`. A member whose config does not load, or a lexicon this chant cannot import, is left out and the rest are served, down to core alone.

The `initialize` result then carries `instructions`. They say which lexicons loaded and which did not, and that the tools taking a `path` want a member's directory.

## Tools

These are the core tools the server registers. Lexicon plugins contribute more.

A test ties this list to the server's own registrations, so a tool added or removed in `packages/core/src/cli/mcp/server.ts` fails the build until this page names it.

### `build`

Build chant infrastructure code and generate output for the target lexicon.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `path` | `string` | Yes | Path to the infrastructure directory or file |
| `output` | `string` | No | Accepted by the schema and currently ignored; the built output always comes back in the response |
| `format` | `"json" \| "yaml"` | No | Output format (default: `json`) |

Returns `{ success, resourceCount, output, format }`. A build that reports errors fails the call instead of returning them.

### `lint`

Lint chant infrastructure code and report issues.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `path` | `string` | Yes | Path to the infrastructure directory or file |
| `fix` | `boolean` | No | Auto-fix fixable issues (default: `false`) |

Returns `{ success, errorCount, warningCount, diagnostics, output }`.

### `import`

Import external templates and convert them to chant TypeScript.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `source` | `string` | Yes | Path to the template file to import |
| `output` | `string` | No | Output directory (default: `./infra/`) |

The response is `{ success, lexicon, generatedFiles, warnings }`. A failed import fails the call.

### `explain`

Summarize the resources in a chant project.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `path` | `string` | Yes | Path to the infrastructure directory |
| `format` | `"markdown" \| "json" \| "okf"` | No | Output format (default: `markdown`) |

`markdown` returns a prose summary. `json` returns `{ sourceFiles, totalEntities, lexicons, dependencies, errors }`, carrying an extra `knowledge` key when the project's OKF bundle bound a concept to a discovered entity, and omitting that key entirely when nothing bound. `okf` returns `{ okf_version, files, errors }`, where `files` maps each bundle-relative path to its content, which is the same bundle `chant explain --format okf` writes to a directory.

### `scaffold`

Generate starter files for a chant project.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `pattern` | `string` | Yes | Resource pattern to scaffold (e.g. `"s3-bucket"`, `"pipeline"`) |
| `lexicon` | `string` | No | Lexicon to use for templates. Auto-detected if omitted |
| `template` | `string` | No | Named init template (e.g. `"node-pipeline"`). Given one, the template's own source files come back instead of a pattern match |

Returns `{ lexicon, pattern, files }`, where `files` is `[{ filename, content }]`. A named template that matched adds `template`. When no lexicon template matched at all, the response is a generic skeleton with a `note` saying so.

### `search`

Search the resource types and the composites of the loaded lexicons.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `query` | `string` | Yes | Search query (case-insensitive substring match) |
| `lexicon` | `string` | No | Filter to a specific lexicon |
| `limit` | `number` | No | Maximum results (default: `20`) |

The response is `{ query, total, results }`, with prefix matches ahead of substring matches and `total` counting the matches before `limit` was applied. A resource type matches on its type, class name or kind and comes back as `{ className, resourceType, kind, lexicon }`. A composite matches on its name, its description or a resource kind it bundles, and comes back as `{ kind: "composite", name, description, bundles, lexicon }`, so a query for `queue` returns the `Queue` resource and the `LambdaSqs` composite that bundles one. Among matches of equal rank, composites come before resource types. The `composites` tool has the composite's parameters.

### `composites`

List the composites the loaded lexicons export. "What composites do you have for aws?" is a call with `lexicon: "aws"`.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `lexicon` | `string` | No | Only composites from this lexicon |
| `query` | `string` | No | Keyword matched against the name, description, bundled resource kinds and parameter names |
| `limit` | `number` | No | Maximum composites (default: `50`) |

Returns `{ lexicons, total, composites }`, plus the `lexicon` and `query` that were given. `lexicons` names every loaded lexicon, so an empty list for a lexicon it names means that lexicon exports no composites. Each composite is `{ name, lexicon, description, bundles, params }`. Its `bundles` are the resource kinds it creates, nested composites included, and each entry in `params` is `{ name, type, required, description }`. With a `query`, name matches come first. The data is the catalog each lexicon ships in its package. Reading it loads no composite and calls no provider.

### `lifecycle-snapshot`

Capture deployed state for an environment, reading every loaded lexicon that implements `describeResources`.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `environment` | `string` | Yes | Target environment |
| `lexicon` | `string` | No | Restrict to one lexicon; snapshots all of them if omitted |

Returns `{ snapshots, warnings, errors }`, where `snapshots` is how many were captured. Two conditions come back as a plain string rather than that object: `No plugins implement describeResources` when nothing loaded can describe live state, and `Build failed` when the project did not build.

### `lifecycle-diff`

Compare the current build's digest against the digest stored in an environment's last snapshot.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `environment` | `string` | Yes | Target environment |
| `lexicon` | `string` | No | Restrict to one lexicon; diffs all of them if omitted |

The response is an object keyed by lexicon name, each value that lexicon's digest diff. A lexicon with no stored snapshot for the environment diffs against nothing, which reads as everything being new. `Build failed` comes back as a plain string when the project did not build.

Every Op tool takes an optional `runtime`, the same choice [`chant run --on`](/chant/cli/run/#choosing-a-runtime-with---on) makes on the command line. Omitted, it is the built-in local runtime, which executes the Op in this process.

### `op-list`

List every Op discovered from `*.op.ts` files with the run state the runtime reports.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `runtime` | `string` | No | Runtime to address: a lexicon name with an `opRuntime`, or `local` (the default) |

Returns `{ ops, errors }`. Each entry carries `{ name, overview, phases, labels, depends, runState }`, and an unreachable runtime leaves `runState` as a dash rather than failing the call.

### `op-run`

Run an Op on a runtime and return its result.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `name` | `string` | Yes | Op name (must match an `*.op.ts` file) |
| `runtime` | `string` | No | Runtime to address: a lexicon name with an `opRuntime`, or `local` (the default) |

A finished run comes back as `{ op, runId, state, startedAt, endedAt }`, plus `records` and `gate` when the run produced them.

### `op-status`

Show the state the runtime reports for an Op's latest run.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `name` | `string` | Yes | Op name |
| `runtime` | `string` | No | Runtime to address: a lexicon name with an `opRuntime`, or `local` (the default) |

Returns `{ op, runtime, runId, state, startedAt, endedAt, records, gate }`. `records` is the per-phase `StepRecord[]` array (present when the Op's `*.op.ts` is discoverable; see [Progress and gate state](/chant/guide/ops-reference/#progress-and-gate-state)) — the same shape `--progress-json` streams. `gate` is the pending gate (`{ name, since }`), null when none is standing.

### `op-approve`

Record a gate's resolution on the gate ledger, then wake the runtime hosting the gated run. This is the rename of `op-signal`, and a different act: a gate is resolved by recording the fact, not by sending a message to a waiting workflow.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `name` | `string` | Yes | Op name |
| `gate` | `string` | Yes | Gate name (must match the gate's name in the Op) |
| `note` | `string` | No | Free-text context recorded on the resolution |
| `url` | `string` | No | Absolute http/https URL this resolution happened at |
| `runtime` | `string` | No | Runtime to address: a lexicon name with an `opRuntime`, or `local` (the default) |

Returns `{ op, gate, resolvedBy, origin, timestamp, runtimeNotified }`.

#### A gate reached over MCP cannot be resolved over MCP

Every gate fact records the channel it came through, one of `cli`, `mcp` or `acp`. When a run reaches a gate over MCP, the pending fact says `mcp`, and this tool then refuses to answer it. `op-run` wrote the first half and `op-approve` would write the second, so one caller in one session would have written both, and the gate would have no second party in it.

The refusal names the way through. Approve from a channel the run did not arrive on, which is normally `chant approve <op> <gate>` at a shell. A gate reached at a shell or over ACP is resolvable here, because that is the separation the gate exists for. `chant approve` carries an `--allow-same-origin` override for the operator who genuinely wants both halves in one session; this tool deliberately has no equivalent.

There is no `approver` parameter, and the resolution records `resolvedBy` as `unattested`. MCP cannot verify a name, so a name supplied here would sit on the ledger looking exactly like a name a person gave. A shell approval takes `--actor` and can be believed.

The approval is for the plan the gated run recorded, so a gate with no pending fact standing has nothing for this tool to approve and the call fails. Naming a plan digest by hand is a shell-only affordance, `chant approve --plan <digest>`.

### `op-report`

Return a markdown report for an Op's latest run.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `name` | `string` | Yes | Op name |
| `runtime` | `string` | No | Runtime to address: a lexicon name with an `opRuntime`, or `local` (the default) |

### Plugin Tools

Lexicon plugins can contribute additional tools. Plugin tools are namespaced as `{pluginName}:{toolName}` to avoid conflicts with core tools.

## Workspace tools

Started at or inside a declared workspace (`chant.workspace.json` in the directory or above it, up to the git root), the server also serves the workspace's read contract and its record writes ([#2707](https://github.com/INTENTIUS/chant/issues/2707)). A harness that speaks MCP but has no shell can then read decisions and propose them. The same test ties these sections to the tools a server inside a workspace registers.

Each tool is a thin call into what the CLI runs. A read runs `chant workspace <command> ... --json` with the chant the server runs as, in the server's directory, and returns the document it printed, unchanged. The document follows that command's output schema in the [read contract](/chant/reference/workspace-read-contract/), reason codes included, and an error document is returned as a document. A read handed to the workspace root's pinned chant by the CLI is handed on the same way. The [reader conformance suite](/chant/reference/workspace-read-contract/#testing-a-reader) runs over MCP as well, and requires each tool's document to equal the command's.

A write calls the function `chant workspace records new`, `amend`, `review` or `close` calls, and returns the same JSON result, refusals included. It keeps the CLI's rules. The kind's schema judges the record, and a closed record never changes. An approved record changes only in its state, evidence and reviews, and a dissent needs a note. Through MCP, two things are added. A new record opens in the kind's first state, `proposed` for a decision, and any other state is refused with `record-state-not-initial`. The record's [source block](/chant/cli/workspace-records/#where-a-proposal-came-from) gets `via: "mcp"` and `client`, the client's `clientInfo` from `initialize` or from the request's `_meta`. An amendment gets them only when its fields set the source block, since the block says where the proposal came from. Computed provenance, from git, is unchanged. `sign: true` seals with this host's configured key, git's `user.signingkey` with `gpg.format ssh`, and is refused with the CLI's remedy when none is set.

`points-answer` calls what `chant workspace points answer` calls ([ws-058](/chant/guide/decision-points/)). It records people's answer to an open decision point question once the point's quorum is met. The quorum never counts anyone holding the agent role. No tool asks a point's deciders: chant calls no model, so an ask runs in the operations layer.

Records are proposals until they are reviewed, and `by` must name the person or agent that actually decided. Each write tool's description says so, for the model that reads it. The server listens on no port and authenticates nobody: it speaks over stdio, and `by` is recorded as given, as `--by` is.

A value that starts with `-` is refused before any command runs, so no argument can be read as a flag.

| Tool | Parameters | Returns |
|---|---|---|
| `workspace-ls` | `at` | the document of `chant workspace ls --json` (`ls.schema.json`) |
| `workspace-status` | `env` (required), `compareTo` | the document of `chant workspace status <env> --json` (`status.schema.json`) |
| `workspace-graph` | `kind` (a list), `intent`, `composites`, `at` | the document of `chant workspace graph --json` (`graph.schema.json`); with `intent`, the intent graph over that region (`intent.schema.json`); with `composites`, the composites joined to components (`composites.schema.json`) |
| `workspace-points` | `open`, `kind`, `at` | the document of `chant workspace points --json` (`points.schema.json`): the decision points and the questions asked of them, each open one with any model's answer and confidence ([ws-058](/chant/guide/decision-points/)) |
| `workspace-records` | `kind`, `current`, `since`, `id`, `at` | the document of `chant workspace records --json` (`records.schema.json`), or with `since` the changes since a revision or session (`records-since.schema.json`); with `id`, only that record is kept in `records`, and `summary` stays the command's |
| `records-new` | `record` (required), `kind`, `prefix`, `by`, `sign`, `dryRun` | the result of `chant workspace records new` (`records-new.schema.json`) |
| `records-amend` | `id` and `fields` (required), `kind`, `by`, `sign`, `dryRun` | the result of `chant workspace records amend` (`records-amend.schema.json`) |
| `records-review` | `id`, `verdict` and `by` (required), `kind`, `note`, `session`, `sign`, `dryRun` | the result of `chant workspace records review` (`records-review.schema.json`), whose verdict moves the record's quorum |
| `records-close` | `id` (required), `kind`, `dryRun` | the result of `chant workspace records close` (`records-close.schema.json`) |
| `points-answer` | `id`, `answer`, `by` (all required), `kind`, `dryRun` | the result of `chant workspace points answer` (`points-write.schema.json`): people's answer to an open question, refused with `quorum-not-met` until the point's quorum is met |

Each parameter stands for the CLI flag of the same name, written in camel case, so `compareTo` is `--compare-to`. `kind` names a kind file from the server's directory or a kind the declaration names. Without `kind`, a write goes through the one kind the declaration names, as the CLI's does. `record` and `fields` are JSON objects, the text `--from` and `--set` would read. `by` on `records-new` and `records-amend` is written to the kind's decider field, `decided_by` for a decision, and signing needs it. Without `state`, `records-new` gives the record the kind's first.

## Resources

The server provides resources that agents can read for context:

| URI | MIME Type | Description |
|-----|-----------|-------------|
| `chant://context` | `text/markdown` | Lexicon-specific instructions, patterns, and best practices |
| `chant://examples/list` | `application/json` | JSON array of available examples (`[{ name, description }]`) |
| `chant://ops` | `application/json` | Every Op discovered from `*.op.ts`, with overview, phase count, labels and dependencies |
| `chant://ops/{name}/runs` | `application/json` | Run history for a named Op, newest first |
| `chant://ops/{name}/runs/latest` | `application/json` | Latest run state for a named Op |
| `chant://composites` | `application/json` | Every composite the loaded lexicons export, the same entries the `composites` tool returns, unfiltered |
| `chant://knowledge` | `application/json` | The project's OKF knowledge bundle as `{ dir, index, concepts }`, empty when the project has authored none |
| `chant://state/{environment}` | `application/json` | Every lexicon's snapshot for an environment, keyed by lexicon |
| `chant://state/{environment}/{lexicon}` | `application/json` | One lexicon's snapshot for an environment |

`chant://examples/{name}` reads too, although `resources/list` does not advertise it. It resolves to whichever plugin resource has a URI ending in `/examples/{name}`.

### Plugin Resources

Lexicon plugins can contribute additional resources, namespaced as `chant://{pluginName}/{path}`. Plugin resources with `/examples/` in their URI are automatically included in the examples list.

## Configuration

### Automatic Setup

`chant init` detects your IDE and adds the MCP server to the appropriate global config file:

| IDE | Config path |
|-----|------------|
| Claude Code | `~/.claude/mcp.json` |
| Cursor | `~/.cursor/mcp.json` |
| Other | `~/.config/mcp/mcp.json` |

The config looks like:

```json
{
  "mcpServers": {
    "chant": {
      "command": "npx",
      "args": ["chant", "serve", "mcp"]
    }
  }
}
```

### Manual Setup

If your agent doesn't auto-detect the MCP config, configure the server manually. The command is:

```bash
chant serve mcp
```

The server communicates over stdin/stdout using JSON-RPC 2.0 with line-based framing (one JSON object per line).

## Protocol Details

The MCP server implements the [Model Context Protocol](https://modelcontextprotocol.io/). It negotiates a revision rather than assuming the client's, and understands two:

| Version | Role |
|---------|------|
| `2026-07-28` | Preferred. Answered to a client that asks for it, and to one that names no version at all |
| `2024-11-05` | Answered to a client that asks for it by name |

On the 2026-07-28 revision the requested version and the client identity travel in a `_meta` envelope on every request, and the server falls back to the top-level `protocolVersion` and `clientInfo` fields a prior-revision client sends on `initialize`.

### Supported Methods

| Method | Description |
|--------|-------------|
| `initialize` | Handshake — returns the negotiated protocol version, capabilities, and server info: `name` is `chant`, and `version` is the installed chant's version, the one `chant --version` prints. At a workspace root with no lexicon of its own it also returns `instructions` |
| `server/discover` | The `initialize` result merged with the tool and resource listings, so a client can discover everything in one call |
| `tools/list` | List all available tools (core + plugin-contributed) |
| `tools/call` | Invoke a tool by name with parameters |
| `resources/list` | List all available resources (core + plugin-contributed) |
| `resources/read` | Read a resource by URI |

A message with no `id` is a notification, `notifications/initialized` being the one every client sends, and gets no response at all. A tool whose handler returns an object is answered with both a text block and a `structuredContent` field holding the parsed shape.
