## Synopsis

```
chant ci last-green [--json] [--from <rev>]
chant ci list [--json] [--limit <n>] [--since <rev>] [--forge github] [--source checks|runs]
chant ci tick [--dry-run] [--forge github] [--source checks|runs] [--key <runner key.pem>]
chant ci workflow [--workflow <name>]... [--output <file>] [--chant <command>] [--install <command>]
                  [--token-secret <NAME> | --app-id-var <VAR> --app-key-secret <NAME>]
                  [--runner-key-secret <NAME>]
```

`chant ci` records which commits of a branch passed CI as git tags, from the [`ci.green`](/chant/reference/workspace-declaration/#ci) block of the workspace declaration ([#3573](https://github.com/INTENTIUS/chant/issues/3573), [ws-103](https://github.com/INTENTIUS/chant/blob/main/docs/design/decisions/ws-103-ci-green-and-revoked-tags.md)). A commit that passes every required phase gets `ci/green/<sha>`. A green commit that later fails one gets `ci/revoked/<sha>`. Anyone with a clone can then find the newest commit that passed, for example to freeze it and release from it.

## ci last-green

Prints the full id of the newest first-parent commit of the branch that has a green tag and no revoked tag. The walk follows `refs/remotes/origin/<branch>` when the checkout has it, else the local branch. Only local tags are read, so fetch them first:

```bash
git fetch origin --tags
git checkout "$(chant ci last-green)"
```

When no commit qualifies, a message goes to stderr and the exit code is 1. `--from <rev>` walks the first-parent commits of `rev` instead of the branch, so `chant ci last-green --from <sha>` prints `<sha>` exactly when that commit counts as green. With [signed tags](#signed-tags), each tag the walk ignores is printed on stderr as a warning.

`--json` prints a [read contract](/chant/reference/workspace-read-contract/) document, `ci-last-green.schema.json`, whose `commit` is `{ sha, tag, tagged, committed }` or `null`, and exits 0 in both cases. `ignored` lists the tags the walk passed over for want of a valid statement, newest first, each with `tag`, `status` and `reason`. A failure has an `error` and exits 1. Its code is `ci-green-undeclared` for a declaration with no `ci.green`, `ci-branch-unknown` when the branch has no ref in this checkout, or the code of a declaration that can't be read.

## ci list

Prints what happened to the branch's recent history: the first-parent commits inside `ci.green.window`, newest first. Each has a state and the result of every required phase ([#4021](https://github.com/INTENTIUS/chant/issues/4021)). It follows the same ref as `ci last-green` and reads local tags only, so fetch them first with `git fetch origin --tags`.

| State | Meaning |
|---|---|
| `green` | The commit has `ci/green/<sha>` and no revoked tag. |
| `revoked` | The commit has `ci/revoked/<sha>`. |
| `undecided` | The commit has neither tag. |

A phase's result comes from the tags. A green tag's annotation records the runs of each phase that passed, so a green commit lists every required phase as `pass` with its runs. A revoked one keeps those and shows the phase its revoked tag names as `fail`, with the failed run. An undecided commit has no tag to read, so its phases are `unrecorded` and have no runs. Add `--forge github` to read the check runs of undecided commits from the forge, as `ci tick` does, and each phase becomes `pass`, `fail` or `pending`. The forge is asked about nothing else, and without `--forge` the command reaches no network. When the source is [chant runs](#chant-runs-as-the-status-source), an undecided commit's phases are judged from the signed Op runs on the local `chant/lifecycle` instead, still with no network, and `--forge` is refused. Each run then has an `opRun` object naming the run, and each commit has `ignoredRuns`, listing the runs that do not count.

A line for an `unlinked` or `wrong` commit ends with `; why unknown:` and the reason. [Link commits to work items](/chant/guide/work-items/#link-commits-to-work-items) says how a commit names one.

With [signed tags](#signed-tags), the state counts only the tags that carry a valid statement. A tag that does not is listed on its own line under the commit, as `ignored <tag> (<status>): <reason>`, and in `--json` under the commit's `ignored`. The `green` and `revoked` objects name the runner that signed the tag in `signer`, which is `null` for a tag that counts unsigned.

`--limit <n>` keeps the newest `n`. `--since <rev>` lists what came after `rev` and replaces the window, so a reader holding the last sha it saw can ask for what is new.

`--json` prints a [read contract](/chant/reference/workspace-read-contract/) document, `ci-list.schema.json`, with `window`, `since`, `require` and a `commits` array. Each entry has `sha`, `committed`, `state`, `phases`, and a `green` and a `revoked` object holding the tag and the time it was made, plus the failed phase and run for a revoked tag. Either object is `null` when the tag is absent. Each entry also has `work` ([#4029](https://github.com/INTENTIUS/chant/issues/4029)), `{ state, ids, problems }`, where `state` says whether the commit names its work item. The judgement is the one [`workspace check --changes`](/chant/cli/workspace-check/#commits-that-name-no-work-item) makes, against the work records at the listed ref. `work` is `null` when the workspace declares no work kind. chant 0.124.28 added it within contract 1, and a reader ignores fields it does not know. A failure uses the codes of `ci last-green`, and `revision-unknown` when `--since` names no commit, with exit code 1.

## ci tick

One pass over the branch. It fetches the branch and the `ci/*` tags from `origin`, and the fetch prunes a `ci/*` tag deleted there by hand. It reads the check runs of each first-parent commit within `window`, then makes the tags that are due and pushes them, never forced:

| A commit with | that now | gets |
|---|---|---|
| no green tag | passes every required phase | `ci/green/<sha>` |
| a green tag and no revoked tag | fails a required phase | `ci/revoked/<sha>` |
| a revoked tag | anything | nothing, and its check runs are not read |

Running it again over the same check runs changes nothing. `--dry-run` prints what it would tag and makes no tag. With [signed tags](#signed-tags), the tick signs each tag it makes and judges the tags already there as every other reader does, so a hand-pushed tag doesn't count. Since chant never moves or deletes a tag, a hand-pushed tag that holds the name of a tag the tick would make stops it, and the tick says which tag to delete. A commit that names no work item, or a wrong one, has `; why unknown:` and the reason at the end of its line, as in `ci list`.

By default the check runs come from the forge. GitHub is the only forge with a check-run reader: the tick reads `GITHUB_REPOSITORY`, a token from `CHANT_FORGE_TOKEN`, `GITHUB_TOKEN` or `GH_TOKEN` with `checks: read`, and `GITHUB_API_URL` for GitHub Enterprise Server. `--forge gitlab` and `--forge forgejo` are refused. GitLab and Forgejo get no status reader, and are covered through the results of chant's own runs instead ([#4044](https://github.com/INTENTIUS/chant/issues/4044)). Mapping pipeline jobs and commit statuses to check runs would need rules for retries and skips per forge, since GitLab reports jobs per pipeline and Forgejo reports statuses per context. An Op run's result is the same on every forge. Pushing the tags needs `contents: write` on the remote.

## Chant runs as the status source

A project whose pipelines run as chant Ops can take its phase results from those runs in place of a forge's check runs ([#4044](https://github.com/INTENTIUS/chant/issues/4044)). This is how a project on GitLab or Forgejo gets green and revoked tags. Set `source` to `runs` in `ci.green`, or pass `--source runs` to `ci tick` and `ci list`, which overrides the declaration either way. `checks` is the default.

```json
"ci": {
  "green": {
    "branch": "main",
    "phases": { "lint": ["lint"], "test": ["test", "e2e-*"] },
    "require": ["lint", "test"],
    "source": "runs"
  }
}
```

With `runs`, a phase's patterns match Op names, with `*` standing for any run of characters, as they match check-run names otherwise. Each Op run's record on `chant/lifecycle` (`<env>/runs__<op>.jsonl`, see [chant run](/chant/cli/run/)) names the commit it built from as `gitSha`, and counts for that commit. For each Op on a commit, the latest record by end time decides, so a re-run replaces the run before it. Status `ok` passes, `fail` fails, and a stop at a gate or a decision point leaves the phase undecided. Records from every environment count alike.

A run counts only when its record carries a statement signed by a runner key. Without that, anyone who can write to `chant/lifecycle` could write a passing run. The runner signs at the end of the run when `chant run <op>` is given a key, with `--key <file>` or the PEM in `CHANT_RUNNER_KEY`. The key and its principal follow the rules for the [tick's own key](#the-runner-key): `.chant/trust.json` at the checkout's `HEAD` must list it under `runners`, and the principal must hold the `runner` role. `chant run --key` refuses any other key before the run starts. A key from `CHANT_RUNNER_KEY` that is not a runner key only prints a warning, and the run is recorded unsigned.

The envelope format matches the tag's, with its own predicate type, `https://intentius.io/chant/op-run/v1`, over the run's commit. The predicate names the signer and the run, with the run's status and the SHA-256 of its record without the statement. Stored on the record as `statement`, it makes the record and its signature one ledger line. Every run is checked against `.chant/trust.json` at the branch's tip, and one whose statement fails is ignored with the statuses a tag uses. Such a run neither greens nor revokes its commit, and appears under the commit as `ignored run <id> of <op> in <env> (<status>): <reason>`.

| Status | When |
|---|---|
| `unsigned` | The record carries no statement. |
| `invalid` | The envelope or its payload is not an op-run statement, or it names another signer than the key's. |
| `untrusted` | No key that `.chant/trust.json` lists under `runners` signed it, or its principal holds no `runner` role. |
| `mismatch` | It signs another run, Op, env, status or commit, or the record changed after it was signed. |

A tick from runs fetches `chant/lifecycle` before it reads, without forcing it, and stops when the local branch and the remote's have diverged. It needs no forge token. It signs every tag it makes, so it needs a runner key even without `signedSince`, apart from `--dry-run`. A tag made from runs has `source: "runs"` in its record. Each run in it has `id: null` and an `opRun` object holding the Op run's `id`, `env`, the runner that signed it and the run's statement, so the tag carries the signed word of every run behind it.

A pipeline on GitLab or Forgejo runs its Ops with the key and then the tick. `chant run` appends each run's record to the local `chant/lifecycle` and does not push it, so push the branch for later ticks and other checkouts to see the runs:

```bash
chant run lint --key "$RUNNER_KEY_FILE"
chant run test --key "$RUNNER_KEY_FILE"
git push origin chant/lifecycle
chant ci tick --source runs --key "$RUNNER_KEY_FILE"
```

`ci workflow` writes only a GitHub Actions file, so on another forge the tick goes in the pipeline by hand, or in a scheduled job that runs it every few minutes.

## Signed tags

The tags are plain git tags, so anyone who may push a tag could make `ci/green/<sha>` by hand and go around CI ([#4031](https://github.com/INTENTIUS/chant/issues/4031)). Setting `ci.green.signedSince` in the [declaration](/chant/reference/workspace-declaration/#ci) closes that. It names the full sha of the first commit on the branch whose tags must be signed, and a tag on that commit or any later one counts only when its annotation carries a statement signed by a runner key. Without `signedSince`, every tag counts, as before.

```json
"ci": {
  "green": {
    "branch": "main",
    "phases": { "test": ["test"] },
    "require": ["test"],
    "signedSince": "8b045980cf9cd1351dd4f60c9c46ee69d45ec0d7"
  }
}
```

The statement is the one [runner evidence](/chant/cli/workspace-evidence/) and [agent-run statements](/chant/cli/workspace-runs/#signed-statements) use: an in-toto statement in a DSSE envelope, signed with an Ed25519 key. Its subject is the tagged commit, and its predicate (`https://intentius.io/chant/ci-tag/v1`) holds the signer and the tag's JSON record. The envelope sits in that record as `statement`, so a reader that doesn't know it reads the record as before.

A reader counts such a tag when all of these hold, and otherwise ignores it with one of four statuses:

| Status | When |
|---|---|
| `unsigned` | The annotation carries no statement, as with a lightweight tag or one made by hand. |
| `invalid` | The envelope or its payload is not a ci-tag statement, or it names another signer than the key's. |
| `untrusted` | No key that `.chant/trust.json` lists under `runners` signed it, or its principal holds no `runner` role there. Both are read where the branch is, at `refs/remotes/origin/<branch>` or the local branch. |
| `mismatch` | It signs another commit, another kind of tag or another branch, the annotation's record is not the one signed, or the tag points at another commit than its name gives. |

A tag on a strict first-parent ancestor of `signedSince` counts without a statement, so the tags a workspace already has keep working. Position in history decides, never a date: whoever makes a commit or a tag sets its time, so a backdated commit or tag outside that ancestry gains nothing. A `signedSince` that names no commit in the clone is refused with `declaration-invalid`, so fetch the branch before reading the tags. Every reader judges the tags the same way: `ci tick`, `ci list`, `ci last-green`, [`release cut`](/chant/cli/release/#release-cut) and chant's own `scripts/release-preflight.sh`.

### The runner key

The tick signs with an Ed25519 private key in PEM, from `--key <file>` or from the `CHANT_RUNNER_KEY` environment variable. `.chant/trust.json` lists its public half under `runners`, and the principal it names holds the `runner` role:

```json
{
  "schema": 1,
  "runners": [{ "principal": "ci:acme/app", "class": "runner", "key": "ssh-ed25519 AAAA..." }],
  "roles": { "runner": ["ci:acme/app"] }
}
```

The tick refuses a key the file doesn't list, a principal without the role and a key the signers file lists, before it makes any tag. A person's key never signs a tag. With `signedSince` set, the tick refuses to run without a key, apart from `--dry-run`. Both files are read at the branch's tip, and changing either is a protected write, as for [runner evidence](/chant/cli/workspace-evidence/). Make the key as for runner evidence:

```bash
openssl genpkey -algorithm ed25519 -out runner.pem
```

A tick given a key the file doesn't list yet refuses it and prints the key's `ssh-ed25519` line to add under `runners`. Keep `runner.pem` out of the repository.

On GitHub the key lives in a repository secret, and `chant ci workflow --runner-key-secret <NAME>` hands it to the tick as `CHANT_RUNNER_KEY`. Turn signing on in this order: add the key to `runners` and the principal to `roles.runner`, store the secret and regenerate the workflow, then set `signedSince` to the sha of the branch's current tip. A commit can't name its own sha, so the commit that sets `signedSince` comes after it, and its tags and every later commit's must be signed. A chant older than 0.124.28 refuses a declaration with `signedSince`, so set `minReader` to `0.124.28` with it.

## ci workflow

Writes `.github/workflows/chant-ci-green.yml` (or `--output`), the root CI file that runs the tick. A tick starts when a workflow holding a required check run completes on the branch, so a result or a re-run is acted on within seconds. A cron every 15 minutes covers an event that was dropped or late. All ticks share one concurrency group that never cancels, so they run one at a time.

It finds the workflows to listen to by reading the other files in `.github/workflows/`. A job reports its `name` or its id as its check run, followed by ` (<matrix values>)` for a matrix job, and a workflow is kept when one of its jobs can report a check run that a required phase's pattern matches. It warns about each required pattern no job matches. `--workflow <name>` adds a workflow the scan can't see, such as one whose job names are built from expressions, and it is repeatable.

The tick runs in the workspace root as `npx --yes @intentius/chant@<version> ci tick`, at the version that wrote the file. `--chant <command>` runs chant with another command instead, and `ci tick` is put after it. `--install <command>` adds a step before the tick that installs what that command needs, in the same directory. When the workspace root has a `package-lock.json`, the install step also gets setup-node's npm cache. Both flags go into the regenerate command in the header. The file's first line is the generated-file header naming the command. When the command runs in a member's directory, that member records the file as one it generates ([ws-042](https://github.com/INTENTIUS/chant/blob/main/docs/design/decisions/ws-042-root-ci-files.md)). Regenerate it after changing `ci.green` or the workflows it listens to.

## Pushing tags to commits that change workflows

By default the tick pushes its tags with the Actions token, `GITHUB_TOKEN`, which actions/checkout leaves in the clone. GitHub treats a new ref to a commit whose files under `.github/workflows/` differ from the default branch's as an update to those workflows. That needs the `workflows` permission, and the Actions token can never have it. So on a branch where a commit changes a workflow file, every push of that commit's tag fails with `refusing to allow a GitHub App to create or update workflow ... without workflows permission`, and `chant ci tick` says so in its error.

Give the push a token that may update workflows, kept in a repository secret, and regenerate the workflow with it:

```bash
chant ci workflow --token-secret CI_GREEN_TOKEN
```

The checkout then uses `${{ secrets.CI_GREEN_TOKEN || github.token }}`, so the push does too. Where the secret is unset, as in a fork or a fresh repository, the checkout falls back to the Actions token: the tick still runs, and only the tags for commits that change `.github/workflows/` fail to push, which `ci tick` reports. A fine-grained personal access token for the repository needs Contents read and write and Workflows read and write. The tick still reads check runs with the Actions token and the job's `checks: read`, because a fine-grained token can't call the Checks API.

A GitHub App with Contents and Workflows write works too. Put its id in an Actions variable and its private key in a secret, and the workflow mints an installation token with actions/create-github-app-token before the checkout:

```bash
chant ci workflow --app-id-var CI_GREEN_APP_ID --app-key-secret CI_GREEN_APP_KEY
```

`--runner-key-secret <NAME>` passes the repository secret `NAME` to the tick step as `CHANT_RUNNER_KEY`, so the tick [signs its tags](#signed-tags). The secret holds the runner key as PEM, and the key's principal needs the `runner` role in `.chant/trust.json`. When the declaration sets `ci.green.signedSince` and the flag is missing, `ci workflow` warns, since every tick would fail.

Regenerating keeps the token flags you passed, since the header records them. Leave them out and the file comes out byte for byte as 0.108.0 wrote it.

## chant's own repository

chant declares `ci.green` for its own `main` in its `chant.workspace.json`. The phases are `check`, `test`, `validate` and `suites`. The first three are the checks branch protection requires, each one check run of the same name from the `chant` workflow, where `test` is the job that passes only when the unit shards passed. That workflow holds the fast checks, and it is all that runs on a push or a pull request. Those checks are the unit tests and typechecks, plus lint and some small guards. `suites` is the job of the same name in `release-suites.yml`. It runs the end-to-end project on `main` every three hours and when a person starts it. That project is every `*.e2e.test.ts`, which covers the CLI goldens and the corpus differentials as well as the reference workspace. A commit is green only when all four passed, so a release never tags a commit the long suites have not passed, and a commit `release-suites.yml` never ran on stays undecided. The other large suites live in `large-suites.yml` and `helm-survey.yml`, which run only when a person dispatches them; no phase and no release waits on those. Other workflows can run on main's commits too, so none of their jobs is named `check`, `test`, `validate` or `suites`, which keeps their runs out of those phases.

Its tick runs the source at the commit it checks out, so a change to `chant ci` is tested on main before it ships:

```bash
chant ci workflow --chant 'npx tsx packages/core/src/cli/main.ts' --install 'npm install --ignore-scripts'
```

The install skips the lexicon builds, and the tick needs none of them. `just release` picks the commit it tags from these tags: `scripts/release-preflight.sh` reads them whenever the declaration on `origin/main` sets `ci.green` for `main`. When no commit has a green tag, it refuses to release. It doesn't fall back to asking GitHub, and `CHANT_RELEASE_SKIP_PREFLIGHT=1` skips the check. chant does not set `signedSince` yet, so its tags are unsigned and the script checks that they exist. Once the declaration on `origin/main` sets it, the script asks chant instead. It runs `ci last-green --from <commit>` through `$CHANT_CLI`, which defaults to this checkout's source through tsx. Each tag chant ignored is printed as it goes. Turning signing on for chant itself waits on a runner key in its secrets ([#4040](https://github.com/INTENTIUS/chant/issues/4040)). The publish workflow has a second gate, `release-gate`, that waits for a green run on the released commit. A tag push skips that gate and publishes. To get it, start `publish.yml` by hand with `verify_ci` checked. The repository variable `CHANT_RELEASE_SKIP_CI_GATE` that used to skip it is no longer read.
