Sets up `chant release` in a project that has never used chant. It reads the project, writes a `release` block into `chant.config.ts`, writes the release workflow with [`release workflow`](/chant/cli/release/workflow/), and lists what has to be set up by hand on the registries.

```bash
chant release init          # a dry run: prints the block and why
chant release init --yes    # writes it
```

| Flag | Description |
|---|---|
| `--yes` | Write the config, the workflow and the goreleaser change. Without it nothing is written |
| `--force` | Replace an existing `release` block, and a release workflow file chant did not write |
| `--forge <forge>` | The forge the workflow is written for. Default: the repository's workflow directory (`.github/workflows`, `.forgejo/workflows`, `.gitlab-ci.yml`), else the forge `origin` names, else `github` |
| `--json` | Print the plan as JSON: `release`, `reasons`, `notes`, `registry`, `workflow`, `goreleaser` and `next` |

What it reads, from the directory it runs in, and what each sets:

| Found | Sets |
|---|---|
| The repository's tags | `release.tag`: the prefix most version tags share, such as `v{version}` for `v1.2.0` or `cli-v{version}` for `cli-v0.4.1`; `v{version}` when no tag names a version, or `{path}/v{version}` for a Go module in a subdirectory. A release of more than one package keeps `v{version}` unless its tags are `v<version>` already. `release.legacyTags` lists the prefixes the existing tags use, so [`release next`](/chant/cli/release/next/) and [`release changed`](/chant/cli/release/changed/) read them as earlier releases |
| `ci.green` in `chant.workspace.json`, or `ci/green/` tags | `release.green: "chant"`; otherwise `"forge-checks"`. A repository with no CI workflow is told that a cut refuses a commit with no checks |
| `package.json`, with npm `workspaces` (a list or `{ packages }`) or `pnpm-workspace.yaml` | An `npm` target for every package not marked `private`, in dependency order, with `access: "public"` when a scoped package has no `publishConfig.access`. `release.version` stamps the same packages, with `ranges: "exact"` when one depends on another |
| `engines.vscode` in a `package.json` | `marketplace` targets for the VS Code Marketplace and Open VSX (trusted publishing) from `dist/<name>.vsix`, and `VSCE_PAT` from the repository's secrets in `release.workflow.env` |
| `Dockerfile` or `Containerfile`, at the root or up to two directories down | A `release.images` entry each, and an `oci` target on the registry of the forge `origin` names: `ghcr.io/<owner>/<repo>`, `registry.gitlab.com/<path>`, or the Forgejo host |
| `.goreleaser.yaml` (or `.yml`, or without the dot) | A [`release.artifacts`](/chant/cli/release/cut/#files-the-release-builds) entry `{ name: "goreleaser", goreleaser: {} }`, so the cut runs `goreleaser release --snapshot` once and records the files it writes, and a `forge` release of the `origin` repository with generated notes that uploads them (`assets: ["artifact:goreleaser"]`). The release workflow installs the goreleaser version chant pins. With `--yes`, a config with no `snapshot` section gets `snapshot.version_template: "{{ .Env.CHANT_RELEASE_LABEL }}"`, so its snapshot build carries the release's label; a config with its own `snapshot` section is told to set it. A goreleaser config that builds images (`dockers`, `kos`) leaves the Dockerfiles out of `release.images` |
| `pyproject.toml` with a `[project]` (or `[tool.poetry]`) name | A `release.artifacts` entry `{ name: "python", build: "python -m pip install build && python -m build", outputs: ["dist/*"] }`, so the cut builds the sdist and wheel once and records them, and a `pypi` target for `artifact:python` with `auth: "trusted-publishing"` (`"token"` on Forgejo, with `PYPI_TOKEN` from the repository's secrets in `release.workflow.env`). A `pyproject.toml` whose version is static is added to `release.version.files`; one whose version is dynamic is left to the build, which the output says |
| `Cargo.toml` with a `[package]` name or a `[workspace]` | A `cargo` target, which publishes each crate that allows crates.io in dependency order. A `Cargo.toml` with a `version` in `[package]` or `[workspace.package]` is added to `release.version.files`; a workspace root without one is told to name its member crates. A crate with `publish = false` gets no target |
| `go.mod` | Nothing to publish: the release's tag is what the Go module proxy reads |

`release.workflow` is `trigger: "dispatch"`, so a release is one run started by hand with its label. With pnpm or yarn it installs with `corepack enable` and the lockfile's tool, and builds with that tool when the root `package.json` has a `build` script; with npm and no `package-lock.json` it installs with `npm install`. A `package.json` that does not depend on `@intentius/chant` runs chant in the jobs as `npx --yes @intentius/chant@<version>`, the version that wrote the config.

A project with no `chant.config.ts` gets one holding the block alone. One that has a config gets the block added to the object its default export names: `export default { ... }`, `export default defineConfig({ ... })`, or `export default config` with `const config = { ... }`. A `chant.config.json` is rewritten with the block added. A config that already has a `release` block is refused with `release-init-release-exists` unless `--force`, and one whose default export is not an object literal with `release-init-config-unreadable`; both print the block to add by hand. A release workflow file that chant did not generate is refused with `release-init-workflow-exists` unless `--force`.

The output ends with the steps to take by hand, such as an npm trusted publisher that names the workflow file (`chant-release.yml`) with npm dist-tag allowed, a PyPI trusted publisher that names the same file (on GitLab, the top-level pipeline file `.gitlab-ci.yml`), crates.io trusted publishing or a `CARGO_REGISTRY_TOKEN` (a crate's first version needs the token), the Open VSX trusted publisher, `VSCE_PAT`, a GHCR package's visibility, and on GitLab the include and `CHANT_RELEASE_TOKEN`. Then it prints the commands to commit and push, to run [`release doctor`](/chant/cli/release/doctor/) once those steps are done, and to start the first release. When the repository has version tags that `release.tag` or `release.legacyTags` matches, that is the label `auto` (`gh workflow run chant-release.yml -f label=auto`), which takes the label from the commits since the newest of those tags with [`release next`](/chant/cli/release/next/). Otherwise it is a label: a patch after the newest version tag, or `0.1.0`. Each later release can be started with `auto`, which then reads the previous release from chant's ledger. The dispatched workflow runs `release doctor` in its cut job too, before the cut.
