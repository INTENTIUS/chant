A pull request's plan ([`chant components pr-plan`](/chant/cli/components/#components-pr-plan-and-components-pr-apply)) and a [gated wave](/chant/cli/components/#one-gate-per-wave) ask each step of each component what it would change. Only a capability with `plan` can answer. This page lists every capability chant registers, says which of them plan, and says what the note shows for a component in each case.

## Every capability

The table is generated from the capability plugins that core and the lexicons register. `plan` says the capability can describe what its `run` would change. `outputs` says it can read the outputs it left when it last ran, which a dependent's `stackOutput()` resolves to when the change does not plan the dependency. When it does, the dependent reads what the dependency's plan says it will expose instead ([Outputs](#outputs)).

## What every note has

The note has a row per member with its status and its counts of creates, updates, replaces and deletes. Below the rows come the plan digest and the approve command. The grouped plan summary comes last and lists destroys, failures and holes before its groups. Entries with the action `no-op` or `read` are kept in the change set and left out of the counts.

The digest a reviewer approves is the [change-set](/chant/reference/change-set/) document's digest. It covers each member's plan digest, status and holes. It also covers every entry with its attributes and every side effect. On merge, `pr-apply` plans every member again before it applies any. When the digest it gets is not the approved one, it applies nothing and exits 3.

A step whose `plan` throws makes its component's members `plan failed`, with the error in the summary's failed list. A plan with a failed member applies nothing.

A component's members come from its steps that have `plan`, one member per such step. Its other steps are not members. A component that builds an image with `docker-build` and deploys it with `cfn-deploy` has one member, the stack. The note says nothing about the image. [A capability without `plan`](#a-capability-without-plan) covers the component none of whose steps can plan.

## Capabilities with plan

Six capabilities have `plan`. Each section below says what the plan reads and what the note shows. It also says what holds the apply to the approved plan. A step that finds its target moved since the approved plan applies nothing, and the command exits 4 ([#3997](https://github.com/INTENTIUS/chant/issues/3997)).

### `arm-deploy`

`lexicons/azure/src/components/arm-deploy.ts` holds the plan and the apply. Its `run` hands the template to `azApply`. `ApplyOp`'s `arm` target calls the same applier, so a component step and an Op share one code path. One resource group is one member. A step without `resourceGroup` deploys into a group named for its component. The step reaches `endpoint` when it sets one and `AZURE_ENDPOINT_URL` otherwise, which is how it targets floci-az. `subscriptionId` and `AZURE_SUBSCRIPTION_ID` pick the subscription the same way.

ARM offers no change set, so the plan GETs each declared resource by its id at the template's `apiVersion`. It compares the answer with the body `azApply` would PUT. Both sides go through the noise rules in `lexicons/azure/src/deep-observe.ts` first. A 404 makes the resource a create that lists every property it declares. Matching properties make it a `no-op`, and any difference makes it an update listing the paths that moved with both values. The ownership tags `azApply` stamps are never compared, since floci-az drops tags. A value read from `reference()` or `listKeys()` is shown as known after apply, and the plan never calls `listKeys`.

With `prune: true` the plan adds a delete for each resource in the group that carries chant's ownership tag and that the template no longer declares. That is the set `azApply` would prune. Without `prune` the plan proposes no deletes.

A read that fails for any reason but a 404 leaves a hole naming the reason, and such a plan gives `run` nothing to hold it to. A step waiting on an upstream output reads nothing and gets a hole naming that upstream.

The digest binds the environment and the template's bytes. It binds where the step deploys too, meaning the group and its location under one endpoint and subscription. The prune setting and every entry with its attributes are in it as well. On apply, `run` plans again first. A digest other than the approved one stops it before any PUT, with `refusing to apply`.

The template's own `outputs` section is evaluated against a live read of its resources, by `outputs` and at the end of `run`, and an output that comes to nothing is skipped. Before apply, the plan gives the value of an output whose every resource read is planned as `no-op`, or which reads none.

### `cfn-deploy`

The plan is `planCfnDeploy` in `lexicons/aws/src/components/apply.ts`.

The plan creates a change set for the stack's template and resolved parameters, reads the changes it proposes and deletes it without executing it. The member is the stack's name, taken from `stack` or else from the component. A stack that does not exist yet gets a CREATE change set, and the plan deletes the empty `REVIEW_IN_PROGRESS` stack CloudFormation made to hold it.

Each resource change is one entry, addressed by its logical id, or `<nested stack>/<logical id>` inside a nested stack. `Add` is a create, `Modify` an update, or a replace when CloudFormation marks it `Replacement: True` or `Conditional`, and `Remove` a delete. An entry's attributes are the property names from the change's details, with no values before or after, since a change set gives none. A change set with nothing to apply gives a member with no entries.

A change CloudFormation marks `Replacement: True` fails the member's plan when `onReplace` is `"block"`, which is the default. The error names the resources.

When a parameter reads another component's output that has no value yet, such as an output of a stack that does not exist or one its upstream's plan knows only after apply, the stack is previewed with placeholders ([#4423](https://github.com/INTENTIUS/chant/issues/4423)). The plan creates the change set with a stand-in for each such parameter, typed from the template's `Parameters`.

| Parameter type | Stand-in |
|---|---|
| An EC2 id type | `subnet-00000000known-after-apply` and the like |
| `Number` | `0` |
| An SSM parameter type | `/known-after-apply` |
| Anything else | `known-after-apply` |

Its entries are the change set's changes as above. Each property a stand-in drives is marked known after apply, so no stand-in value is in the note or the digest. The plan keeps the change set's shape. For each change that is its logical id and action, its replacement and its properties. That shape's digest goes in the plan's digest. Then the plan deletes the change set and any empty stack it made. A parameter that reads an earlier step of the same component is previewed the same way.

No preview is possible when CloudFormation refuses the change set with the stand-ins, as real CloudFormation does for an id type naming a resource that does not exist, or when the upstream is unresolved but no parameter is left without a value. Then the member is a hole saying `inputs from <component>; re-checked on apply` (or `inputs <names> are known only at apply; re-checked on apply` for an earlier step), followed by `; no preview: <why>` when the preview was refused, and the note shows `?` for its counts.

The plan's digest covers the environment and the stack. It also covers the template's path and bytes, the resolved parameters, the components whose outputs were missing and, for a previewed member, its shape. The plan also hands `run` a digest of the changes it read. On apply, `run` creates a new change set and executes it only when its changes have that digest. Otherwise it deletes the change set and fails with `refusing to apply`. For a previewed member `run` gets the shape instead: the change set made once the upstream applied must have the same shape, differing only in what the stand-ins drove, or `run` deletes it and refuses it as a moved plan. A member with a hole hands `run` nothing to compare, so its change set is executed as created.

`outputs` reads the stack's outputs with `describe-stacks`, and gives none for a stack that does not exist. The plan also says which outputs the stack keeps: all of them when the change set has nothing to apply, and otherwise each output whose template `Value` reads only resources the change set modifies in place. Every other output is known only after apply.

### `gcp-apply`

The plan is `planGcpApply` in `lexicons/gcp/src/components/gcp-apply.ts`, and it decides each resource with `decideResource` in `lexicons/gcp/src/op/activities/gcp-apply.ts`, the function the applier acts on.

The step applies a built Config Connector manifest (`manifest`) through the `gcpApply` activity, the same REST mappers an Op and the floci-gcp path use. Its member takes the step's `stack`, falling back to the component. `GCP_ENDPOINT_URL`, or the step's `endpoint`, points the reads and the writes at floci-gcp. Each resource's project is the step's `project`, else its `spec.projectRef.external`, its `cnrm.cloud.google.com/project-id` annotation, `GCP_PROJECT_ID`, then `GOOGLE_CLOUD_PROJECT`.

The plan reads each declared resource with a GET on the applier's own URL, or through its target's `getIamPolicy` for an `IAMPolicyMember`, and writes nothing. A 404 makes a create entry. A resource whose live body already holds every field the manifest sets gets a `no-op`, as does one whose kind has no in-place update. Otherwise the entry is an update whose attributes are the top-level fields that differ, live value as `before` and manifest value as `after`. Apply sends an update only in that last case, so its report matches the plan. Setting `prune: true` also lists as deletes the live resources of a manifested kind labelled `managed-by: chant` that the manifest dropped.

Three cases get a hole instead of an entry. Apply skips a kind with no REST mapper. A read that answers neither 200 nor 404 can't say whether the resource exists. When a compute field can't change in place, apply reports `replace required` and leaves the resource alone.

A step whose inputs wait on another component's outputs reads nothing, and its hole says `inputs from <component>; re-checked on apply`.

A `gcp-apply` plan's digest is taken over its member in that environment. The manifest's path and bytes go in too. So do the endpoint and the project override. The prune mode is included, as are the components whose outputs were missing. `run` gets a digest of the planned entries, new values included. On apply it plans again and refuses with `refusing to apply` when the two differ, and the command exits 3.

`outputs` reads what the API reports for the applied resources: `<name>Uri` for a `RunService` (its `uri`), `<name>Address` for a `ComputeAddress` and `<name>IpAddress` for a `ComputeForwardingRule`. `run` returns them once it applied. The plan knows the value of each resource that stays, and a resource it creates has its output known only after apply.

### `kubectl-apply`

The plan and its entries are in `lexicons/k8s/src/components/kubectl-apply.ts`, in `plan` and `changeSetPartOf`.

Each document of the manifest goes to the API server as a server-side apply with `dryRun=All`, under the field manager `chant:<stack>` and with the release attributes the apply would set. It compares what the dry run returns with each live object. The member is named after the step's `stack`, and after the component when the step has none.

An object with no live counterpart is a create, with every field the manifest declares. One whose dry run equals the live object is a `no-op`. One that differs is an update, with each changed field path and its value before and after. Server bookkeeping such as `managedFields`, `resourceVersion` and `status` is dropped before the comparison. A Secret's `data` and `stringData` are marked sensitive and carry no values. An update under `spec.template` of a workload whose pods roll on such a change has the disruption `rolling`.

With `delete: "owned-only"` the plan adds a delete for each object carrying chant's marker and the stack's label that the manifest no longer declares. With the default `delete: "never"` there are no deletes.

When the API server refuses a change in the dry run, as it does for a Deployment's `spec.selector`, the object is an update with unknown disruption. Its hole carries the server's message, and the apply would fail the same way.

Nothing is read or dry-run for a step waiting on another component's outputs, since its `manifest` or `context` may be one of them. Its member gets one hole, `inputs from <component>; re-checked on apply`, and no artifact. That plan's digest is taken over the environment and the member, plus the step's `manifest`, `context` and `delete` and the components whose outputs were missing.

The digest covers the documents sent, the target they are sent to and the delete mode. For each object it also covers the action and the new value of every changed field. On apply, `run` dry-runs the approved documents again. It applies them only when that dry run gives the approved digest. Otherwise it fails before the cluster changes and names both digests.

`kubectl-apply` has outputs only when the step names them: `outputs: { host: { object: "Service/prod/web", field: "status.loadBalancer.ingress.0.hostname" } }`, each a field of an object the manifest declares. `outputs` reads those fields from the cluster, and `run` returns them once it applied. The plan knows a field the manifest sets, and any field of an object the dry run leaves unchanged.

### `member-outputs`

The capability is in `packages/core/src/components/verbs/member-outputs.ts` ([#4455](https://github.com/INTENTIUS/chant/issues/4455)). Its step names another member of the workspace, and the member's declared kind picks the engine output source that reads it. A lexicon contributes a source through `CapabilityPlugin.engineOutputSources()`. The terraform lexicon's reads a `choudoufu` member.

The plan asks the source for the member's planned outputs. For a choudoufu member that is `live-plan-set -json` over the member's root: its `planned_values.outputs`, less each output whose `output_changes` entry is unknown after apply. The member in the consumer's change set is `<member>#outputs`. It has no entries, since the member's own pipeline plans and applies its changes. Each output known only after apply is a hole, `<member>.<output>`, and a step that reads one is planned again once the member applied.

The digest covers the environment, the member, its kind, the digest of the member's own plan and the known and unknown outputs, so a member's plan that moves after review moves the consumer's digest too. `run` applies nothing. It plans the member again and refuses while the member has changes left to apply, then answers the member's applied outputs.

`outputs` answers the member's outputs as applied now, for a choudoufu member from `choudoufu output -json` in its directory.

### `pulumi-up`

`lexicons/pulumi/src/pulumi-up.ts` holds the capability ([#4541](https://github.com/INTENTIUS/chant/issues/4541)), and `lexicons/pulumi/src/change-set.ts` maps its steps to entries. The step is `{ kind: "pulumi-up", dir, stack }`, and the member is `<project>/<stack>`, where the project is `Pulumi.yaml`'s `name` unless the step names a `member`. One kind covers stock Pulumi and plunge. The engine is the one the member's config, `plywood.yml`, `PULUMI_BACKEND_URL` or `Pulumi.yaml` names, in that order ([#4559](https://github.com/INTENTIUS/chant/issues/4559)).

Before the first engine run in a process, the step makes the program runnable in its directory ([plywood#22](https://github.com/INTENTIUS/plywood/issues/22)). A job's checkout holds the files git tracks, so a Node program there has no `node_modules`. When neither the directory nor any directory above it has `node_modules` (or Yarn's `.pnp.cjs`), and a lockfile sits beside `package.json`, the step runs `pulumi install` there (`plunge install` on plunge), once per directory. A Node program with no lockfile is refused by name, since an install would take whatever versions resolve today. A Python program gets the install when its virtualenv is missing or its toolchain is `poetry` or `uv`. A release's copy follows the same rule ([chant release](/chant/cli/release/)).

The plan runs `preview --json --show-sames --stack <stack>` in the stack's directory with `PULUMI_ENABLE_STREAMING_JSON_PREVIEW=true`, so the preview prints its engine events. The steps give the entries, read as the printed preview document reads them, and the policy events give CrossGuard's findings. On plunge the preview also saves its plan with `--save-plan` into a scratch directory outside the working tree. The step's `config` is written into a scratch copy of `Pulumi.<stack>.yaml` and passed with `--config-file`, and `policyPacks` pass as `--policy-pack`. Under a pull request or an Op wave the packs, and the declaration's `ci.policy.packs`, are copies read at base ([CrossGuard packs at base](/chant/guide/gate-policy/#crossguard-packs-at-base)).

Each URN is one entry with its action. A replace is one entry, and it is marked `destroy` when the delete comes before the create. Each top-level input the change writes is listed with its old and new value. An input holding Pulumi's unknown value shows as known after apply, and a secret carries no value. A resource a program may register inside an `apply()` is a `mayAppear` entry. A mandatory CrossGuard violation denies the plan before any gate opens, and an advisory one is kept with the plan.

The digest is the one a workspace plan of the member binds (`pulumiPreviewDigest`). For a member on the resource lock grain, the default on plunge, `same` and `read` steps are left out, so a pull request that changes other resources of the stack does not move it. A stack whose `config` reads an output not known yet is a hole naming that output, with no preview.

On plunge, `run` applies the saved plan with `plunge up --plan <file> --yes --json --stack <stack>`. plunge refuses a plan whose records moved since it was saved, and the command exits 4. On stock Pulumi, `run` previews again and exits 4 when that preview goes beyond the approved shape. Then it runs `pulumi up --yes --json --stack <stack>` and compares the steps in its event stream with the approved shape. A step the approval did not hold fails the apply, with exit 1, since the update has run. With no approved plan, `run` previews and applies in one go.

Its `outputs` runs `stack output --json --show-secrets=false`. The plan reads the stack's future outputs from the stack step of the preview.

### `terraform-apply`

The capability is in `lexicons/terraform/src/components/capability-plugin.ts`, and its entries come from `lexicons/terraform/src/change-set.ts`.

The plan runs `init`, then `plan -input=false -detailed-exitcode -out=<plan file>` in the root with its var files and the step's `vars`, then `show -json` over the plan file. The binary is the one `terraform.binary` names: terraform, tofu or choudoufu. The member is the root's name.

Every `resource_changes` entry is an entry with its address and action. `create`, `update` and `delete` keep their names, and a delete with a create in either order is a replace. Attributes are the top-level attributes the change writes, each with its value before and after. A value terraform knows only after apply shows as `<known after apply>`. A sensitive attribute carries no value. An attribute that forces the replacement is marked. Imports, forgets, deposed objects and, from Terraform 1.14, action invocations as side effects are kept too.

A root outside a composed group whose `vars` read an upstream output with no value yet is previewed with placeholders ([#4463](https://github.com/INTENTIUS/chant/issues/4463)), since terraform takes no unknown variable. Each variable that holds no value gets a stand-in typed from the root's `variable` block.

| Variable type | Stand-in |
|---|---|
| string | `known-after-apply` |
| number | `0` |
| bool | `false` |
| list or map | an empty one |
| object or tuple | one made of stand-ins |

The preview covers every resource change the root plans with those values. Each change has its action and type and the attributes it writes. An attribute or root output a stand-in drives, through `var.<name>` in the attribute's expression (module inputs included) or by carrying the `known-after-apply` string, shows as known after apply, so no stand-in value is in the note or the digest. The member lists the variables under `placeholders`, and its row in the note says `previewed with placeholders for var.<name>`. The plan file is deleted, and `run` gets the preview's shape instead of a plan file.

On merge the apply plans the root again once its upstream applied. That round is covered by the first approval when its shape is within the preview's ([covered rounds](/chant/guide/apply-on-merge/#a-round-the-first-approval-covers)), and asks for an approval of its own otherwise. A `run` handed the shape itself plans with the real values and refuses, with exit 3, a plan that goes beyond it. The preview cannot see a stand-in that reaches an attribute another way, such as a number through a `local`, so the attribute shows the stand-in. The real plan then differs from the preview and asks for its own approval.

No preview is possible when a variable holding the unknown read is not declared, when the unknown sits inside a larger value, when a `count` or `for_each` reads a stand-in, or when the placeholder plan fails, for example on a `validation` block. Then the member stays a hole saying `inputs from <component>; planned again once they apply; no preview: <why>`, with no plan file. Otherwise the plan has no holes.

The digest covers the plan's resource changes, output changes and action invocations. Timestamps, versions and prior state are left out. `run` applies the plan file the plan wrote with `apply <plan file>`. When choudoufu refuses that plan file, the step fails as a moved plan and the command exits 4. Plain terraform and tofu refuse a stale plan file too, and the command exits 1, because chant does not tell that error from others.

A live choudoufu root that `live-plan-set` can plan as chant would, one with no var files, no `vars` and no backend config, is planned as a one-root set instead. `run` hands choudoufu that set and its digest with `live-wave-apply`, and choudoufu's refusal of a moved set exits 4.

Its `outputs` runs `output -json` in the root after an `init`. The plan reads the root's future outputs from `show -json`, in the same way as for a choudoufu member above.

### `sql-apply`

A declarative SQL member applies through this capability of the sql lexicon, `lexicons/sql/src/capability-plugin.ts` ([#4569](https://github.com/INTENTIUS/chant/issues/4569)). The step names an `environment` and a `build`, the chant build output to apply.

The plan reads the build's dialect and diffs the build against the environment's server with that dialect's planner, Postgres or ClickHouse. Each change becomes an entry of the member's part. A change the applier does not make in place fails the plan and names the Op to run instead. A column rename is one. An object the planner cannot read fails it too. The member is the environment.

`run` applies only a plan that was planned and decided first. It plans again just before the apply, and a plan that moved since the decision applies nothing and exits 4.

### `sql-migrate`

The capability is in `lexicons/sql/src/capability-plugin.ts` ([#4569](https://github.com/INTENTIUS/chant/issues/4569)), and runs sql-yodeler's `yodel` through a fixed argument list.

The plan runs `yodel plan <env> --part <file>`, one entry per object the pending migrations touch. In an op wave (the step names `spec`) it also runs `yodel apply <env> --wave-plan <file> --spec <spec>`, and the wave plan's digest is the member's. The wave plan's destructive steps come back as the plan's destructive classes, so `on-destructive` waits on what the engine calls destructive. A plan the engine would refuse fails the plan.

`run` applies only the plan an op wave decided, with `yodel apply <env> --wave-apply <file>`. The engine plans again under its lock, and its refusal of a moved plan exits 4.

### `terraform-copy`

An ephemeral copy of a root plans through this capability, in `lexicons/terraform/src/state-ops.ts` ([#4618](https://github.com/INTENTIUS/chant/issues/4618)). It initialises the root under the copy's backend settings with `init -reconfigure -backend-config=<k>=<v>`.

With `destroy` set, the step asks for a destroy plan instead. Entries come from the saved plan file through the same change-set reader `terraform-apply` uses, and the apply hands that same file to `apply`. A copy waits at chant's `pr-env` gate and takes no request of its own.

### `terraform-action`

A day-2 action runs through this capability, in `lexicons/terraform/src/action-ops.ts`. Its plan is `plan -invoke=<address> -out`, read with `show -json`. The invocation shows as a side effect, and the plan has no resource changes, since `-invoke` plans in refresh-only mode.

`run` plans again and asks for a gated request whose digest binds the address, the commit and the plan's `action_invocations`. It applies the saved plan once an approval counts.

### `terraform-state-push`

A standalone state migration writes through this capability, declared beside the copy. Nothing is read from the backend at plan time, and the note shows no entries for the member.

Its digest covers the roots whose state files the step pushes. `run` pushes each file with `state push`, under one gated request whose attachment is the migration's proof.

### `terraform-state-unlock`

Releasing a stuck state lock is the third operation in that file. At plan time the step's facts are all there is: the lock ID and its location, which the digest covers.

`run` releases that one lock with `force-unlock -force`, under a gated request.

## A capability without `plan`

A component with no step that has `plan` is one member under the component's name. Its row reads `planned` with a count of 0 in every column, and its group in the plan summary says `no changes`. That row says nothing about what the component will change, since the plan had nothing to ask.

The member's plan digest is the component's composition digest, the one its own gates bind. It is computed over the component's declaration and the environment with its vars. Every step's input goes in as written, and since [#4155](https://github.com/INTENTIUS/chant/issues/4155) so does the content of each local file or directory a step deploys from. A commit pushed after review that changes a chart, a values file or a site's tree moves the digest, and `pr-apply` exits 4 as it does for a moved cfn or k8s plan.

These are the paths the digest reads, from the step's literal input (`packages/core/src/components/deploy-inputs.ts`):

| Steps | Fields |
|---|---|
| any step | `template`, `manifest`, `values` |
| `helm-upgrade` | `chart` |
| `kustomize-apply` | `dir` |
| `fly-release`, `fly-rollback` | `plan` |
| `s3-sync`, `r2-sync`, `copy-to-host` | `from` |
| `wrangler-deploy`, `wrangler-versions-promote` | `config` |
| `docker-build` | `context`, and `dockerfile` under it |
| `zip-package` | `source` |
| `jvm-build` | `path` |

A file is hashed by its bytes. A directory is hashed over the files under it that git does not ignore, each by its path and bytes, so a Docker context leaves out `node_modules` and `dist`. A value wired from another step, such as `codeRef: "@Build.uri"`, and an `archive:` path are build outputs and are not read. A `lambda-deploy` is bound through its bundle step's `source` instead, so a build that is not reproducible still applies under its approval. A path that does not exist is left out, and one that appears later moves the digest.

Some steps deploy what the digest can't name. A `shell` or `run-agent` step runs content its input does not list, and a directory git ignores as a whole is a build output, such as `s3-sync` from `dist`. The member then has a hole for each such step, with a reason that starts `unbound:`, and the plan note lists it under Holes. A reviewer of such a member has to read the change itself.

- Read what the step deploys in the pull request's diff: the script a `shell` step runs, or the sources of the build that writes the synced directory.
- Approve the pull request only once its head is the commit you read.
- Turn on the forge's setting that drops approvals when commits are pushed: "Dismiss stale pull request approvals when new commits are pushed" on GitHub, "Dismiss stale approvals" on Forgejo, "Remove all approvals when commits are added to the source branch" on GitLab. With the default `requireReview`, `pr-apply` counts only an approving review that still stands on the forge, so a push after your review needs a new one.

A gated wave treats such a component the same way: one member, the composition digest, and no entries.

A component that has a step with `plan` beside steps without one, such as a `lambda-deploy` beside a `cfn-deploy`, gets one more member, `<component>#inputs`. Its digest is taken over the files the steps without `plan` deploy from, and its holes are those steps' unbound ones. The member is there only when those steps name a file or have a hole.

## Outputs

`arm-deploy`, `cfn-deploy`, `gcp-apply`, `terraform-apply` and `kubectl-apply` have `outputs`. A pull request's plan reads them for each dependency of a planned member that the change does not plan, so a `stackOutput()` reference resolves to the value deployed now (`deployedOutputs` in the report). For a dependency the change plans too, it reads what that dependency's plan says it will expose (`plannedOutputs`, [#3999](https://github.com/INTENTIUS/chant/issues/3999)).

A reference neither can answer stays unresolved. `arm-deploy`, `gcp-apply` and `kubectl-apply` report a hole for it. `cfn-deploy` previews the stack with placeholders for it ([`cfn-deploy`](#cfn-deploy)), and `terraform-apply` previews a root outside a group the same way ([`terraform-apply`](#terraform-apply)); each keeps the hole only when no preview is possible. When the upstream is in the change, the member lists the reference under `unknownInputs`. The apply holds that member back until its upstream applied and plans it again. When that plan does only what the first one showed, the first approval covers it ([covered rounds](/chant/guide/apply-on-merge/#a-round-the-first-approval-covers)); otherwise it asks for an approval of that plan at `pr-apply-round-<n>`. An artifact a build in the same change publishes, read as `@<component>.publish.*`, is listed under `buildInputs` instead. The build's provenance binds it, so the member applies with it without a second approval. `--seed-outputs <file>` supplies values instead of either read.
