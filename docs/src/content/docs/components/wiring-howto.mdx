This is how to wire one component's data into another. The composition grammar these patterns build on — phases, steps, gate, onFailure — lives in [Composition & Wiring](/chant/components/composition-and-wiring/).

## Cross-stack outputs

When one component's stack exports a value another needs, the consumer imports it. The graph resolves it, replacing the `describe-stacks | jq` glue a pipeline would otherwise carry.

```ts
export const searchService: Component = {
  name: "search-service",
  dependsOn: ["shared-alb"],
  deploy: [
    phase("Apply", [cfnDeploy({ template: "archive:search.template.json", inputs: { ...sharedAlb.outputs } })]),   // listener ARN, cluster ARN, subnets, …
  ],
};
```

`chant graph --stacks` orders `shared-alb` before the service and wires its outputs. See [Multi-Stack Projects](/chant/guide/multi-stack/) for the underlying `stackOutput` mechanism.

[`examples/adopt-alb-services`](https://github.com/INTENTIUS/chant/tree/main/examples/adopt-alb-services) is the runnable version of this exact pattern: a bespoke two-service ALB pipeline — `describe-stacks | jq` glue and all, kept as `before/.gitlab-ci.yml` — adopted as three `build.json` components a single driver runs.

## Cross-component outputs

Components also wire by **artifact**, not just by stack output. A [producer](/chant/components/component-contract/#archetypes) publishes an artifact; a consumer references it as `@<component>.publish.uri` (or `.digest` / `.key`). `dependsOn` orders the producer first; the graph resolves the reference into the consumer's step.

The example illustrates the wiring — its `jvm-build` and `publish-artifact` verbs are [not yet implemented](/chant/components/capabilities/#the-families) (the cross-component reference resolution is what ships today):

```ts
// producer — a JAR published to S3, publish-only deploy
export const jarLib: Component = {
  name: "jar-lib",
  build: jvmBuild({ tool: "maven", path: ".", into: "archive" }),
  deploy: [phase("Publish", [publishArtifact({ from: "archive", to: "$env.s3" })])],   // → @jar-lib.publish.uri
};

// consumer — an EMR job that reads the JAR
export const emrJob: Component = {
  name: "emr-job",
  dependsOn: ["jar-lib"],
  deploy: [
    phase("Submit", [emrStartJobRun({ jar: "@jar-lib.publish.uri", args: [/* … */] })]),
    phase("Verify", [waitJob({ runId: "@Submit.runId" })]),
  ],
};
```

## Another member's outputs

A member of a workspace can read another member's outputs as its parameters when that member runs on another engine, such as a choudoufu estate ([#4455](https://github.com/INTENTIUS/chant/issues/4455)). The consumer adds a component named after the member, whose one step is `member-outputs`, and reads it with `stackOutput()` like any upstream component. In the three-cloud demo, `dns` reads the `azureEndpoint` the Azure site publishes:

```ts
import { memberOutputsComponent } from "@intentius/chant/components/verbs/member-outputs";

// The azure member of chant.workspace.json, whatever engine it runs on.
export const azure = memberOutputsComponent("azure");

export const records: Component = {
  name: "records",
  dependsOn: ["azure"],
  deploy: [
    phase("Apply", [cfnDeploy({ template: "dist/dns.json", inputs: { azureEndpoint: stackOutput("azure", "azureEndpoint") } })]),
  ],
};
```

The member's `kind` in `chant.workspace.json` picks how its outputs are read. A lexicon that drives an engine contributes a source for it through `CapabilityPlugin.engineOutputSources()`. The terraform lexicon contributes the one for `choudoufu` members, so the consumer lists `terraform` among its lexicons. A Pulumi source, for `pulumi` members, is still to come. It plugs in behind the same verb, so the consumer's components stay as they are.

The values are read the way a pull request reads any upstream ([plan previews](/chant/components/plan-previews/)):

- When the change does not touch the member, the consumer is planned against the outputs it has now.
- When the change touches it, the consumer is planned against the outputs the member's own plan says it will have. An output known only after the member applies has no value yet. The consumer's step is planned without it, the pull request's report lists `azure.azureEndpoint` under the consumer's `unknownInputs`, and the change set has a hole on `azure#outputs` that names the output. On merge, the consumer is held back until the member applied, then planned again against the value it applied as. That round is gated like any other.

The member applies through its own pipeline, never through the consumer's. The step only reads. While the member's plan still has changes to apply, the step refuses, and the consumer is blocked behind it. The member's component is in a change when the change signal names the member as a changed unit. The terraform lexicon does this for a `terraform.roots` entry of the same name. `--from-affected` can name it too.

<Aside type="note" title="Both wirings, one resolver">
Cross-stack outputs and cross-component artifact outputs are resolved the same way — by the graph, never by orchestrator code. That is what keeps the driver generic across an unbounded set of components.
</Aside>
