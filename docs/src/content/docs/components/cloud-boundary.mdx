The component model is agnostic in **structure and orchestration**, and spec-true in the **leaves**. This applies chant's [spec-true, not cloud-abstract](/chant/concepts/philosophy/#spec-true-not-cloud-abstract) stance to release: each cloud's real API surface, typed and linted, with no invented cross-cloud resource model.

## The seam is the lexicon boundary

A [component](/chant/components/component-contract/) composes over [capability](/chant/components/capabilities/) *families*. Those family interfaces are cloud-agnostic. The concrete verb behind each family is the cloud-specific leaf, contributed by that cloud's [lexicon](/chant/lexicons/overview/) — the same seam that already provides synthesis, `describeResources`, ownership markers, and the [`ApplyOp`](/chant/guide/ops/#apply-code--cloud) `target`. The release layer invents no new per-cloud plugin system.

Core ships only the agnostic verbs (`docker-build`, `sign`, `wait-endpoint`, …). The AWS leaves — `cfn-deploy`, `ecs-update-service`, `emr-*`, `code-deploy`, the SSM host verbs, the CloudFormation/ECS/EMR waits — live in `@intentius/chant-lexicon-aws` and register through the [`CapabilityPlugin`](/chant/components/capabilities/) contract when a project's `chant.config.ts` lists `lexicons: ["aws"]`. A component's `cfn-deploy` step resolves only when that lexicon is active; core has no AWS in it.

## Where each family falls

| Family | Where it sits | AWS leaf | Azure | GCP | k8s / generic |
|---|---|---|---|---|---|
| **build** | fully agnostic | docker / zip / jvm | same | same | same |
| **publish-image** | agnostic (endpoint + auth is env config) | ECR | ACR (`az acr login` backend) | Artifact Registry (`gcloud auth configure-docker` backend) | any OCI |
| **apply infra** | cloud-shaped | `cfn-deploy` | `arm-deploy` | `gcp-apply` (Config Connector objects over the REST API) | `kubectl` (leveler) / Terraform |
| **job submission** | cloud-shaped | EMR / Glue / Batch | Synapse / Batch / ADF | Dataproc / Dataflow | Job / Argo / Spark operator |
| **host / code delivery** | split | SSM + CodeDeploy | Run Command / Arc (no CodeDeploy peer) | OS Config / MIG rolling | SSH (agnostic) |
| **wait / verify** | split | `wait-for-stack` | `wait-for-deployment`, `wait-container-app` | `wait-for-operation`, `wait-cloud-run-ready` | rollout status; `health-gate` agnostic |
| **safety / rollback** | coupled to apply | CFN rollback / CodeDeploy auto | none yet: `arm-deploy` is `needs-opt-out` | none yet: `gcp-apply` is `needs-opt-out` | rollout undo; saga *mechanism* agnostic |
| **observe / drift** | lexicon seam | tags | tags | labels | labels |

Only the AWS, k8s and generic leaves are complete. In the Azure and GCP columns, `arm-deploy` and `gcp-apply` ship ([#4273](https://github.com/INTENTIUS/chant/issues/4273)), each with a plan read live from the cloud. A cell marked *planned* names a leaf that doesn't exist yet, so a component can't compose it. The job-submission and host-delivery cells name the cloud's own services, for which chant has no leaf on any cloud but AWS. A step whose verb has no rollback declares `noRollback` with a reason, which COMP003 asks for.

`build`, `publish-image`, `remote-exec` over SSH, and `health-gate` / `wait-endpoint` port almost unchanged. `apply` is the most cloud-shaped. Managed `code-deploy` is nearly AWS-only — there is no clean Azure or GCP peer, so the portable fallback is `copy-to-host` + `remote-exec`.

## Two kinds of agnostic, only one is free

- **Structural agnosticism (always).** Every component and every cloud shares the contract, the grammar, and one orchestrator. A GCP component and an AWS component are both build -> publish -> apply -> verify, differing only in leaf verbs. Uniform orchestration, one driver, one lint envelope, no per-cloud special-casing. This is most of the value.
- **Portable component (write once, any cloud).** Only for the subset composed entirely of agnostic capabilities. The clean path is Kubernetes: a `kubectl`-apply component runs on EKS, AKS, and GKE because k8s levels the apply family to a single verb. Off-cluster a component is structurally uniform but cloud-bound, because `cfn-deploy` is AWS by definition. This is why standardizing pipelines was easier inside k8s and harder outside it.

<Aside type="note" title="The honest claim">
Trying to make a `cfn-deploy` component "just run on GCP" would be exactly the cross-cloud abstraction chant exists to avoid. The agnostic win is that a hundred components across three clouds look identical to the driver, the lint, and the human, while each still deploys the real thing for its cloud.
</Aside>
