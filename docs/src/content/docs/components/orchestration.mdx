The orchestrator runs a set of [components](/chant/components/component-contract/) in dependency order, dispatching each step to its [capability](/chant/components/capabilities/). It contains no per-component code. There are two modes, and both make pipeline count independent of component count.

<Diagram name="orchestrator-modes" alt="Two modes side by side: interpret mode runs one Op over the component graph on the local executor or a fountain steward; generate mode synthesizes plain CI YAML from the same declarations." caption="Interpret mode runs the declarations directly; generate mode synthesizes CI YAML from them. Same contract underneath." />

## Interpret mode

chant generates one orchestrator Op that reads the declarations, orders them with `chant graph --components` (dependency order from each component's `dependsOn`, plus parallel-safe waves), and drives each composition. No per-component pipeline files exist.

The orchestrator is an [Op](/chant/guide/ops/), so it runs **local by default** on the in-process executor. Phase sequencing, retries, activity profiles, and `onFailure` saga rollback all work locally with nothing installed.

<Aside type="note" title="A hosted runtime is optional">
A `gate` in a composition needs no hosted runtime. The run reads the gate ledger, walks through on a resolution someone already recorded, or writes the pending fact and exits 3 — nothing is parked, so nothing has to survive being parked. Schedules do not need one either. A schedule rides on the Op's own `schedule` field, or externalizes to whatever native scheduler the platform already runs. What a hosted runtime buys is a machine of its own and a standing record of what ran there, and `chant run --on <lexicon>` is how a component asks for one; the component definition does not change. See [`chant run`](/chant/cli/run/) and [Ops as teammates](/chant/concepts/durable-workflows/).
</Aside>

<Aside type="note" title="Release recording stays outside the composition">
On a successful deploy, `chant run --components` auto-emits a [release-ledger](/chant/components/observability/) record, always as a CLI post-run step and never as a step of the composition itself. The run returns its final phase outputs so the CLI can read the published digest once the run reports success; a ledger write is a side effect on git and the network, and a composition that carried it would be re-running it on every retry.
</Aside>

## Generate mode

The same declarations synthesize plain CI YAML through the [GitHub](/chant/lexicons/github/), [GitLab](/chant/lexicons/gitlab/), or [Forgejo](/chant/lexicons/forgejo/) lexicon. Pipeline files still exist, but nobody maintains them by hand, and a cross-cutting change is one edit to the generator. The generated YAML is a thin trigger and runner; the deploy logic stays in the component, not the YAML.

The two compose: interpret mode behind a thin generated CI trigger.

Generate mode has an Op counterpart too, see [Scheduling an Op](/chant/guide/ops/#scheduling-an-op). A scheduled Op's CI trigger is not limited to cron: `pull_request` and `push` triggers are generic beyond the cron case, for an Op whose natural trigger is a PR or a push to a branch rather than a clock.

See [Execution Backends](/chant/components/backends-reference/) for the backend interface and the general-consumption default profile.

## Rollback comes free

Because each capability declares its own compensation, the orchestrator gets saga rollback without a hand-written rollback pipeline: on failure it unwinds executed steps in reverse and calls each `rollback`. Native rollbacks are reused where the platform provides them — `cfn-deploy` triggers CloudFormation's own `rollback-stack`, `code-deploy` triggers CodeDeploy's own automatic rollback to the last known-good revision. Where a capability has no native rollback (`ecs-update-service`, `lambda-deploy`), it declares a best-effort compensation instead (re-apply the prior state); where a component needs a truer restore than that best-effort re-apply gives, it supplies its own component-level `rollback` phase (the ALB/ECS pilot does this with `rollback-previous`). Non-auto, non-compensable cases opt out with a stated reason (`noRollback: "<reason>"` on the step) rather than failing silently — the [COMP003 lint rule](/chant/lint-rules/composition/) requires the reason at author time, and the driver reports the same fact at run time: a step whose capability has no rollback gets its own `rollback-opted-out` record in the run result, carrying that reason, rather than being passed over without a trace.

<Aside type="caution" title="The unwind itself is not durable">
The saga mechanism — reverse-order unwind, calling each executed step's `rollback` — is capability-agnostic and runs the same wherever the run is hosted. What it does not do is survive a crash *during* the unwind. Rollback state lives in the driver's in-memory call stack: if the process dies mid-unwind, nothing resumes it, and whichever steps had not yet been rolled back stay in whatever partial state they were left in. The same boundary already applies to forward `onFailure` compensation on a plain Op. Running on a [fountain steward](/chant/concepts/durable-workflows/) does not change that; what it changes is that the machine is not your laptop and the thread records how far the unwind got, so the next run starts from something you can read rather than something you have to reconstruct. A capability whose rollback cannot be re-run safely is the real problem, and the apply contract is what fixes it.
</Aside>

## What chant adds over hand-driving it

- **Semantic lint on the composition.** Publishes-but-never-applies, an `imageRef` to a phase that does not exist, a mutating capability with no rollback and no opt-out, an unacknowledged gate, a capability named after a component. These are the long-term entropy guards a plain JSON contract cannot enforce — see the [Composition lint rules](/chant/lint-rules/composition/) (COMP001–COMP007).
- **The graph and the generated driver.** `chant graph` / `describe` over components; `chant build` emits the orchestrator Op.
