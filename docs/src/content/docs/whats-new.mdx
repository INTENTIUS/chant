## Ops run on the local runtime and on a fountain steward

Temporal is gone. An Op no longer compiles to workflow code for an engine you have to run: `chant run <op>` executes the phases in this process, and `chant run <op> --on fountain` hands the same declaration to a [steward](/chant/lexicons/fountain/steward/), one teammate on a persistent sandbox whose thread becomes that environment's operational history. The `temporal` lexicon, the `--temporal` flag and the generated worker are all removed. The bridge that caught `--temporal` ahead of the parser and exited **2** with a line pointing at `--on fountain` shipped in 0.58.0 only, and [#2204](https://github.com/INTENTIUS/chant/issues/2204) took it back out for 0.59.0, so the flag now fails as an unknown flag like any other.

What used to need a workflow engine now lives in three places nothing has to host. A gate is a **fact** on the gate ledger: a run that reaches an unapproved one records that it is waiting and exits **3**, `chant approve <op> <gate>` writes the resolution, and the next run reads both and walks through. Nothing is suspended, so nothing has to survive being suspended. The field naming a gate is `gate`, the same word `chant approve` takes on the command line, renamed from `signalName` by [#2202](https://github.com/INTENTIUS/chant/issues/2202) once `0.58.0` had shipped with the old spelling; the old key is still read and warns once at build, and it goes away in `0.60.0`. A cadence is `schedule` on the Op itself, plain data that the github generator, [`chant operator`](/chant/guide/operator/) and a fountain `Steward` each render their own way. And a machine is a steward, declared alongside the ops it runs. See [Ops as teammates](/chant/concepts/durable-workflows/) for where each half belongs, and [Choosing Your Deployment Model](/chant/concepts/deployment-paths/) for which to reach for.

## Op pipelines behave the same on GitHub, Forgejo and GitLab

One chant project generates the Op pipelines for all three forges, and since 0.60.0 each forge has received every job with the same triggers and the same names. What a job could *do* still varied by generator rather than by what the forge actually supports. That gap is now closed, and a first real execution of the generated pipelines closed a second one nobody had seen.

`ScheduledOpSpec` now takes `variables`, so a per-Op secret lands on that Op's own job instead of the whole file. A project with no OIDC no longer puts the apply key on every pull-request job.

Posting now works off github.com too. `gh api` resolves a relative path against `/api/v3` for any host but github.com, and Forgejo serves `/api/v1`, so every sticky-comment call built from a bare path answered 404 there. Calls are now built from `GITHUB_API_URL`, which GitHub Actions and Forgejo Actions both already set correctly. The `issue` finding mode gained a GitLab path and a sticky GitHub one, so a nightly Op edits the issue it owns rather than opening a new one each run.

The generated GitLab file and stage are named `ops` rather than `scheduled-ops`, which is a **breaking rename** of the file a consuming project includes.

Four failures came from running the pipelines rather than reading them. A gated job could not start under `container:`, whose default shell is `sh`, because the generated script opens with `set -o pipefail`. `TerraformAdoptOp` had no Init phase, so its Ledger step found no provider schema on any fresh checkout. A CI clone has no committer identity, so the gate's own commit failed, and the run reported no error at all. A CI clone also fetches only the pipeline ref, so an absent `chant/lifecycle` read as a ledger where nothing had been approved. A retried job then recorded a second pending fact, and `chant approve` force-wrote the branch over the record it should have appended to.

## Exploitability-aware vulnerability gating

`vuln-gate` can now gate on whether a CVE is actually being exploited, not just how bad it would be: **KEV** catalog membership (CISA's list of vulnerabilities exploited in the wild) and the **EPSS** score (likelihood of exploitation in the next 30 days). Four new `vulnPolicy` fields — `failOnKev`, `failEpssAtOrAbove`, `warnEpssAtOrAbove`, `exploitabilityFixableOnly` — work project-wide from `chant.config.ts` or per-step. All default to off, so upgrading blocks nothing new; the one change every gate sees is that `VulnGateFailedError` now names the rule that fired per finding (`in CISA KEV since 2024-03-11, known ransomware use` instead of a bare CVE list). VEX suppression still outranks everything, KEV included. grype reports the data; trivy (v0.73) reports none of it, in which case the gate behaves exactly as before. See [Exploitability gating](/chant/components/attestation-reference/#exploitability-gating-kev-and-epss).

## A Kubernetes runtime surface

The k8s lexicon had chant's strongest authoring surface and its weakest runtime one: `describeResources()` shelled `kubectl get` once per declared entity, serially, through a hardcoded twenty-entry map that warn-skipped every CRD. `lifecycle diff --live`, `lifecycle plan` and behold's overlay all inherited that cap. It now reads through a typed API client in its own package — coverage from the same codegen pass that emits the declarable classes (180-odd types, CRDs included) confirmed against the cluster's own API discovery, concurrent reads, and failures carrying the API server's `code` and `reason` instead of a parsed stderr line. A run that calls `kubectlApply` or `waitForReady` no longer needs a `kubectl` binary.

Writes went the same way. Every Kubernetes apply — including `ApplyOp({ target: "kubectl" })`, which used to shell `kubectl apply -f` — is now a **server-side apply** as the field manager `chant:<stack>`, so the API server records per field which of your tools wrote it. When another manager already owns a field the apply would set, chant names the owner and the contested paths and stops; it never forces a conflict on your behalf. See [The Kubernetes API client](/chant/lexicons/k8s/api-client/).

## Provisioned infrastructure diagrams

The newest thread. `chant graph` gained a **live** data source: `chant graph --live --env <name>` graphs the *actually-provisioned* infrastructure, not the declared source — nodes from each lexicon's observation, **edges reconstructed** from the live references between resources (a subnet's VPC, an ALB's target group), and **containment** (VPC ⊃ subnet ⊃ resource) as boundary structure. `--overlay` classifies each resource against declared source — managed / foreign / pending — so the diagram shows drift. The companion painter, [pinhole](https://github.com/INTENTIUS/pinhole), renders the result as an AWS-style architecture diagram. AWS is enriched from the deployed CloudFormation template, so a managed AWS stack draws its real topology. Scope is managed-only (owned resources); a full-account scan is the natural next phase. See [`chant graph --live`](/chant/cli/graph/) and [Implementing Observation](/chant/lexicon-authoring/observation/) for the lexicon-author hooks.

## Pipeline context for agents

chant now exposes what `chant build` already computes about a pipeline — its jobs and run order, what it pulls in from outside, its security findings, where each job came from — as a set of **read-only MCP tools**. They give an agent a *before-it-runs* view of a pipeline change, complementary to the *after-it-ran* view live tooling provides. Every tool builds from source and never touches a live instance, reads run history, or writes anything — that boundary is what keeps chant a context *producer*, not a copy of the live tooling. See [Agent Integration](/chant/guide/agent-integration/#read-only-context-tools) for the full tool reference.

## Forgejo lexicon (Codeberg / Forgejo / Gitea)

A new lexicon for **[Forgejo Actions](/chant/lexicons/forgejo/)** — the CI behind Codeberg, self-hosted Forgejo, and Gitea — built as a **thin dialect of the github lexicon**. Forgejo runs GitHub-Actions-compatible YAML, so you author exactly as for GitHub (same entities and composites, imported from `@intentius/chant-lexicon-forgejo`) and the dialect applies on build. The differentiated value is the github->forgejo **compare**: what the move silently costs.

## CI/CD pipeline security audit

A workflow/pipeline security pass across the github and gitlab lexicons, split along chant's architectural boundary: deterministic checks run in the pure build, live-resolution checks run in the operational layer. Both lexicons were abstracted to the **same core problems** — pin & vet external references, least-privilege tokens, trust boundaries against untrusted input, secret containment, unsound expressions, artifact/cache hygiene — so the GitHub -> GitLab migration can map problem -> problem and carry the security invariant across the edge.

## Live import & the lifecycle dial

The follow-on to the observation thread: chant turned its single observational drift workflow into a full family — **observe -> reconcile -> authoritative**, chosen per environment. It gained *live import* (regenerate TypeScript from running cloud/cluster state) and *projection + cloud-side ownership* (a precise create/update/delete change set computed against live), **without** hosting an authoritative state file. The snapshot is never load-bearing — the projection reads ownership from the live resource only. The primitives need no runtime at all, and an Op only asks for a machine of its own when it has to run where nobody is watching.

## Cross-lexicon migration

A typed-compiler port of the upstream `gitlab-org/ci-cd/github-actions-to-gitlab-ci` Agent Skill (MIT). Translates `.github/workflows/*.yml` into `.gitlab-ci.yml` (or chant TypeScript) with per-key provenance recorded as SARIF, a curated mapping registry for the top 33 marketplace actions, and optional composite-pattern recognition for Node-shaped pipelines. The gitlab plugin exposes the same translation via a `gitlab:migrate` MCP tool and a `chant-gitlab-migrate` skill.
