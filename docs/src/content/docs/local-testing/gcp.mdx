GCP has no native deployment service — Deployment Manager is retired, and Config Connector needs a cluster running its operator. `gcpApply` applies chant's Config Connector output to a local emulator itself: it maps each resource to its underlying Google REST API and drives create, update, and delete itself against [floci-gcp](https://github.com/floci-io/floci).

<Aside type="tip">
This page is one cloud of [`examples/local-cloud-trio`](https://github.com/INTENTIUS/chant/tree/main/examples/local-cloud-trio). Start from [Local Testing](/chant/local-testing/overview/) for the cross-cloud picture.
</Aside>

## The resource

A GCS bucket, described as data. It synthesizes to a Config Connector manifest:

```typescript
// src/gcp/infra.ts
export const bucket = new StorageBucket({
  metadata: {
    name: "trio-bucket",
    labels: { "app.kubernetes.io/managed-by": "chant" },
  },
  location: "US",
  storageClass: "STANDARD",
  uniformBucketLevelAccess: true,
  versioning: { enabled: true },
});
```

## The op

`chant run gcp` boots floci-gcp, builds the manifest, applies it with `gcpApply`, verifies the bucket over the GCS REST API, and removes the container.

```typescript
// ops/gcp.op.ts
export default Op({
  name: "gcp",
  taskQueue: "trio-gcp",
  phases: [
    phase("Emulator", [flociGcpUp()]),
    phase("Build",    [build(".", { script: "build:gcp" })]),
    phase("Apply",    [gcpApply("dist/gcp.yaml", { endpoint: "http://localhost:4588", project: "local-project" })]),
    phase("Verify",   [httpCheck("http://localhost:4588/storage/v1/b/trio-bucket")]),
    phase("Teardown", [flociGcpDown()]),
  ],
});
```

## How gcpApply works

Config Connector normally reconciles a CRD on a cluster into Google API calls. `gcpApply` performs that reconciliation directly, no cluster involved:

- **Maps each kind** to its REST resource via a dispatch table (`MAPPERS` in `lexicons/gcp/src/op/activities/gcp-apply.ts`), which covers a VPC network and its subnetworks and the Cloud Run serverless load balancer beside the storage and IAM kinds.
- **Merges an IAM policy member** into its target's policy with `getIamPolicy` and then `setIamPolicy`, so the policy's other bindings stay as they were.
- **Orders resources** by their references so a dependency applies before its dependent.
- **Turns Config Connector refs into API fields** where the API takes something else: a Cloud Run service's `serviceAccountRef` becomes the account's email, and its `vpcAccess` `networkRef` and `subnetworkRef` become network and subnetwork paths.
- **Drives full CRUD**, following long-running operations to completion where the API returns one.
- **Prunes orphans** it owns — resources carrying the `managed-by: chant` label that are no longer in the manifest — and leaves everything else alone.

Every call is the real GCS/PubSub/IAM shape, pointed at the emulator.

## Run it

Requires Docker and `curl` on PATH.

```bash
cd examples/local-cloud-trio
npm install
chant run gcp
```

<Aside type="note">
floci-gcp emulates a subset of GCP services, and `gcpApply` maps fifteen resource kinds. A kind outside that set comes back as not attempted, though synthesis and lint still validate it. A mapped kind can still fail locally when floci-gcp lacks its API, and the load balancer kinds wait on [floci-gcp#27](https://github.com/lex00/floci-gcp/issues/27).
</Aside>

## From local to real cloud

Drop the `endpoint` override and `gcpApply` targets the real Google APIs for the same project. The manifest and the reconciliation logic are unchanged — this is the same code path a live apply takes.
