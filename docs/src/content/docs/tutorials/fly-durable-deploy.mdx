The [`fly-durable-deploy`](https://github.com/INTENTIUS/chant/tree/main/examples/fly-durable-deploy)
example runs a Fly Machines deploy that keeps running without anybody minding
it. The op is scheduled on a [fountain steward](/chant/lexicons/fountain/steward/):
one teammate, one persistent machine, one thread carrying every deploy this app
has had.

Where [`fly-deploy-rollback`](/chant/tutorials/fly-deploy-rollback/) uses a Sprite
checkpoint as its recovery boundary, durability here comes from two properties
that have nothing to do with a workflow engine.

**The machine persists.** The steward's sandbox is `sandbox_mode: persistent`,
so the checkout, the npm cache and the installed chant survive a turn ending. A
turn is a command on a computer that was already there, not a container booted
to run one deploy and thrown away.

**The op converges.** Build serializes `src/infra.ts` to the flaps plan; Deploy
applies that plan to the Machines API and waits each machine to `started`.
Applying it twice reaches the same App and the same Machine. So a turn that dies
halfway leaves the estate wherever it got to, and the next run walks the same
steps against that state and finishes. Nothing is resumed, because a convergent
op has the same shape from every starting point.

## The op

`ops/fly-durable-deploy.op.ts` is two phases and a cron:

```ts
import { Op, phase, build } from "@intentius/chant/op";
import { flyApplyStep } from "@intentius/chant-lexicon-fly";

export default Op({
  name: "fly-durable-deploy",
  overview: "Deploy the Fly App + Machine, convergently, on a cadence",
  schedule: { cron: "*/30 * * * *" },
  phases: [
    phase("Build", [build(".", { script: "build:fly" })]),
    phase("Deploy", [flyApplyStep("dist/fly.json")]),
  ],
});
```

`schedule` is data on the Op, not a resource. The flaps endpoint comes from
`FLY_FLAPS_BASE_URL`, which points at local mudflaps offline and at real Fly when unset.

## The steward

`ops/fountain.ts` declares the machine that runs it. Four documents come out of
the composite, plus one `Schedule` because the op carries a cron:

```ts
export const { agent, teammate, schedules } = Steward({
  name: "fly-steward",
  environment: toolchain,
  vault: flyCreds,
  ops: [flyDurableDeploy],
});
```

`toolchain` is the `Environment` the sandbox is provisioned from: the estate
repo mounted at `/workspace/estate`, a setup script that installs chant, and
`networking_type: "limited"` with an allowlist narrow enough to review
(`api.machines.dev`, `github.com`, `registry.npmjs.org`). `flyCreds` is the
`Vault` that holds `FLY_API_TOKEN`, which is set in fountain and never in the
repo. The `Steward` reads the op's name and its cron off the declaration, so the
cadence is written once, next to the op it paces.

`chant.config.ts` declares the fountain profile the CLI reads:

```ts
fountain: {
  profiles: { demo: { endpoint: "https://fountain.inevitable.fyi", token: { env: "FOUNTAIN_TOKEN" }, team: "fly-steward" } },
  defaultProfile: "demo",
}
```

## Prerequisites

- Node.js and `npm`.
- Docker (for the mudflaps emulator).
- A fountain instance and a token, for the steward half. The local half needs neither.

## Run it locally

The op runs here, in-process, with no fountain at all. Same steps, one
observation instead of a cadence:

```bash
docker run -d --rm -p 4280:4280 --name mudflaps ghcr.io/intentius/mudflaps:0.4.1

cd examples/fly-durable-deploy
npm install
export FLY_FLAPS_BASE_URL=http://localhost:4280

chant run fly-durable-deploy
```

```
[phase] Build
  ✓ chantBuild(script=build:fly)   3.1s
[phase] Deploy
  ✓ flyApply(plan=dist/fly.json)   6.8s
Op "fly-durable-deploy" completed in 9.9s
```

The App and Machine are now in mudflaps:

```bash
curl -s http://localhost:4280/v1/apps/fly-durable-demo/machines | jq '.[].state'
# "started"
```

Now run it a second time.

```bash
chant run fly-durable-deploy
```

The second run is the point. It reports the same steps and reaches the same App
and Machine rather than deploying a second one. That is the property the
schedule leans on, and it is why nothing here has to be resumed.

<Aside type="note">
In a dev checkout, run through the workspace CLI —
`npx tsx ../../packages/core/src/cli/main.ts run fly-durable-deploy`.
</Aside>

## Run it on the steward

```bash
npm run build:fountain             # dist/fountain.yaml
export FOUNTAIN_TOKEN=...          # the variable chant.config.ts names
npm run lint                       # FTN001, FTN010, FTN020..FTN023
chant run fly-durable-deploy --on fountain
```

`chant run … --on fountain` posts the command line `chant run fly-durable-deploy`
to the steward's thread, tails the conversation's event stream, and hands back a
record in the shape a local run would have written. Open the conversation in
fountain's UI and every turn is one command somebody could have typed, so
scrolling the thread is scrolling this app's deploy history.

If the steward is mid-turn the post is refused rather than queued:

```
fountain runtime: the steward "fly-steward" is running another op
(https://fountain.inevitable.fyi/conversations/c_01J…). A teammate runs one
turn at a time; wait for it to finish and run this again.
```

A teammate runs one turn at a time, which is what keeps two deploys off one
checkout, and it is also why the schedule is in-thread: a fire that lands
mid-turn is dropped, and the next one re-applies everything anyway.

Point the sandbox at your own estate with the build parameter:

```bash
chant build ops --lexicon fountain -o dist/fountain.yaml \
  --param repoUrl=https://github.com/you/your-estate
```

## Run it against real Fly

Drop the emulator override and give it a token. The op does not change:

```bash
docker rm -f mudflaps
unset FLY_FLAPS_BASE_URL       # flyApply falls through to real Fly
export FLY_API_TOKEN=...

chant run fly-durable-deploy
```

On the steward, the token lives in the `Vault` instead, and the op is unchanged.
