chant includes utilities for discovering infrastructure files in a project and resolving entity dependencies. This guide covers the complete discovery pipeline.

## File Discovery

### findInfraFiles

Recursively scans a directory for TypeScript infrastructure files:

```typescript
import { findInfraFiles } from "@intentius/chant";

const files = await findInfraFiles("./src");
// ["/project/src/resources.ts", "/project/src/config.ts"]
```

The function:
- Returns absolute paths to `.ts` files
- Excludes `node_modules/` directories
- Excludes test files (`*.test.ts`, `*.spec.ts`)
- Excludes files whose head carries chant's generated-file marker
- Reads the first child directory it meets that holds its own `chant.config.ts` as the project's own source, and skips every later one

### Discovery changes in the next release

chant has five discovery walks, and today they disagree. Source discovery (`findInfraFiles`, behind `build`, `graph`, `list` and `explain`), `chant lint`, component discovery, Op discovery and `chant audit` each have their own rules for dot-directories, git-ignored files, `dist` and child projects. The next release gives them one set of rules ([#2527](https://github.com/INTENTIUS/chant/issues/2527)):

| Rule | What changes |
|---|---|
| Dot-directories are skipped | source discovery stops reading `.ts` files under directories such as `.cache/`. `chant audit` still reads `.github/` and `.forgejo/` |
| Git-ignored files are skipped | every walk honours `.gitignore`, nested files included. Rules are applied only below the directory being scanned, so building or linting a directory that is itself ignored still reads it |
| `dist` is skipped | source and component discovery stop reading `dist/` |
| Child projects are boundaries | when the scanned directory is inside a project, a subdirectory holding a project config is not read. A `chant.config.json` holding only lint keys is not a project config and does not count. When the scanned directory is outside any project, every child project is read |
| Op discovery stops at child projects | the Op root is still found by walking up, but the walk down from it no longer enters child projects. A project with no config of its own, whose Op root is the git root, stops seeing its siblings' Ops |
| The first-config quirk goes | the first child project the walk meets is treated like any other child project |

This release reads exactly what it read before, and prints a warning on stderr for each file whose status will change. Each line of the warning names the affected files, grouped by directory when there are many, and ends with the glob that keeps today's behaviour:

```
warning: Source discovery (build, graph, list, explain) under the current directory changes in the next release (chant#2527):
  12 files under src/: src/ is a child project with its own chant.config, read today as this project's own source because the walk met it first. From the next release discovery stops there, as at any child project. To keep reading them after the change, add "src" to include in chant.config.ts, which the next release honours.
```

The glob goes in `include` in the project config when the next release would drop the file, and in `exclude` when it would start reading one that today's walk skips. Both keys come from [#2519](https://github.com/INTENTIUS/chant/issues/2519). Globs are relative to the directory holding the config, and a glob naming a directory covers everything under it. The warning stops once the glob is in the config, and there is no flag to silence it. Generated type stubs under `.chant/types/` never produce a warning.

### importModule

Dynamically imports a TypeScript module and returns its exports:

```typescript
import { importModule } from "@intentius/chant";

const exports = await importModule("./src/resources.ts");
```

On import failure, throws a `DiscoveryError` with type `"import"`.

### collectEntities

Collects all `Declarable` entities from imported modules:

```typescript
import { collectEntities } from "@intentius/chant";

const entities = collectEntities(modules);
// Map { "MyResource" => {...}, "MyFunction" => {...} }
```

## Dependency Analysis

### detectCycles

Detects circular dependencies in an entity graph using DFS:

```typescript
import { detectCycles } from "@intentius/chant";

const cycles = detectCycles(graph);
```

### topologicalSort

Orders entities so dependencies appear before dependents:

```typescript
import { topologicalSort } from "@intentius/chant";

const order = topologicalSort(deps);
// ["Database", "Cache", "App"]
```

### buildDependencyGraph

Builds a dependency graph from entity relationships, detecting dependencies from `AttrRef` references and direct `Declarable` property values.

## Reference Resolution

### resolveAttrRefs

Resolves all `AttrRef` instances by setting their logical names:

```typescript
import { resolveAttrRefs } from "@intentius/chant";

resolveAttrRefs(entities);
```

This enables `AttrRef.toJSON()` to work correctly during serialization.

## Complete Discovery Pipeline

### discover

The main discovery pipeline that orchestrates all steps:

```typescript
import { discover } from "@intentius/chant";

const result = await discover("./src/infra");
// result.entities: Map of entity name to Declarable
// result.dependencies: Map of entity to dependency set
// result.sourceFiles: Array of discovered file paths
// result.errors: Array of any errors encountered
```

The pipeline runs these steps in sequence:
1. **File scan** — find all infrastructure TypeScript files
2. **Import** — dynamically load modules
3. **Collect** — extract declarable entities from exports
4. **Resolve** — set logical names and resolve AttrRefs
5. **Graph** — build dependency graph

## Error Handling

Discovery operations can throw `DiscoveryError` with different types:

- `"import"` — module loading failed
- `"resolution"` — entity name conflicts or resolution issues
- `"circular"` — circular dependencies detected
