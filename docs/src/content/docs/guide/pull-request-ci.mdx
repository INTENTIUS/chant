import { Aside } from '@astrojs/starlight/components';

chant can generate a pull-request pipeline for a project whose components deploy Terraform roots, CloudFormation stacks or Kubernetes manifests, the three capabilities that can plan. A component built from other capabilities goes through the same pipeline, but its plan describes no changes. It does four things:

- On a pull request, it plans the components the change touches and the components that depend on them, and nothing else.
- It posts that plan on the pull request as one note, with a commit status.
- A reviewer approves the plan's digest.
- On merge, it plans the same components again and applies them only if the digest is the one the reviewer approved. If the plan moved, it refuses with both digests named and applies nothing.

The pipeline runs two commands, [`chant components pr-plan` and `pr-apply`](/chant/cli/components/#components-pr-plan-and-components-pr-apply). This page sets it up on each forge.

## A project to run it on

Each Terraform root is a component with one `terraform-apply` step. A root that reads another root's output names that component in `dependsOn` and reads the output through `stackOutput()`.

```json
// chant.config.json
{
  "lexicons": ["terraform"],
  "terraform": {
    "binary": "tofu",
    "roots": {
      "net": { "dir": "roots/net" },
      "a": { "dir": "roots/a" },
      "app": { "dir": "roots/app" }
    }
  }
}
```

```typescript
// estate.component.ts
import { phase, stackOutput, type Component } from "@intentius/chant/components";

export const net: Component = {
  name: "net",
  dependsOn: [],
  deploy: [phase("Apply", [{ kind: "terraform-apply", root: "net" }])],
};

export const a: Component = {
  name: "a",
  dependsOn: ["net"],
  deploy: [phase("Apply", [{ kind: "terraform-apply", root: "a", vars: { cidr: stackOutput("net", "cidr") } }])],
};

export const app: Component = {
  name: "app",
  dependsOn: ["a"],
  deploy: [phase("Apply", [{ kind: "terraform-apply", root: "app", vars: { subnet: stackOutput("a", "id") } }])],
};
```

A root is changed when a changed file sits in its directory, in a local module it calls, or is one of its var files. A pull request that edits `roots/a` plans `a` and `app`. It does not plan `net`.

`a` is still planned against `net`'s outputs. A dependency the change did not select is read like any other: the plan reads its outputs from the deployed estate, through the `outputs` of its `terraform-apply` or `cfn-deploy` step, and the apply plans against the same values. So a pull request that changes one cluster of [`examples/fan-out-estate`](https://github.com/INTENTIUS/chant/tree/main/examples/fan-out-estate) plans and applies it with `network`'s outputs, and the workflow needs no seed step. The report's `deployedOutputs` and a line of the note name each dependency read and the outputs it gave. `--seed-outputs <file>` supplies a component's outputs instead, and wins over a read. A dependency whose steps can't report outputs leaves its dependents' references unresolved, and their plans say so.

### CloudFormation stacks

A component whose step is `cfn-deploy` is planned with a CloudFormation change set. The plan creates one for the stack's template and resolved parameters, reads the changes it proposes and deletes it without executing it. The member is named after the stack. An `Add` counts as a create, a `Modify` as an update, or as a replace when CloudFormation says `Replacement: True` or `Conditional`, and a `Remove` as a delete. A change set with nothing to apply gives the member no changes. The proposed changes are part of the digest the gate binds, as every planner's are, so a change set that proposes something else at merge moves the digest and the apply refuses.

The apply plans again before it runs, and each `cfn-deploy` step then creates the change set it executes. It executes it only when that change set proposes the same changes as the plan the approval covers. When they differ, something moved after the plan was made. The step then deletes the change set without executing it and fails the member with `refusing to apply`. `pr-apply` exits 3 for it, as it does when the digest moved. A change set that replaces a resource (`Replacement: True`) fails the member's plan when `onReplace` is `"block"`, which is the default. The refusal names the resources and shows in the pull request's note. `Conditional` counts as a replace but is not blocked, which is also the apply's rule.

A template that declares an `AWS::CloudFormation::Stack` gets a change set with its nested stacks included, and each change inside a child is an entry of its own, addressed as `<child>/<logical id>`.

A stack that does not exist yet gets a CREATE change set, so every resource counts as a create. CloudFormation holds that change set in an empty stack in `REVIEW_IN_PROGRESS`, and the plan deletes that empty stack too. It never deletes a stack in any other status. The plan reads the stack outputs a dependent's `stackOutput()` names as they stand now. When the upstream stack does not exist yet, the dependent creates no change set: its row says `inputs from network; re-checked on apply`, with `?` for its counts, and the summary lists it under holes.

The plan job needs the same AWS credentials and region as the apply job, with permission to create, describe and delete change sets, and to delete a stack. Build the templates before `pr-plan`, as before the apply. Generate the pipeline with `--pr-build` and both jobs do it for you, as the next section shows.

### Kubernetes manifests

For a `kubectl-apply` step, the plan is a server-side dry run. It reads the manifest, sets the release attributes the apply would set, and sends each document as the apply does, with the same field manager `chant:<stack>`, but with `dryRun=All`, so the API server persists nothing. It reads each live object and compares it with what the dry run returned. A step without a `stack` gives its component's name to the member; otherwise the member takes the stack's name.

An object with no live counterpart counts as a create, with the fields the manifest declares. An object whose dry run equals the live object is a `no-op`, and one that differs is an update naming each changed field with its value before and after. Before comparing, the plan drops what the server writes on every request: `managedFields`, `resourceVersion`, `uid`, `creationTimestamp`, `generation` and `status`. A field the server defaults has the same value on both sides, so it does not show. A Secret's `data` and `stringData` are marked sensitive, and their values are left out of the note and the change set. An update under `spec.template` of a workload whose pods roll on such a change shows as a rolling change. Every other update shows as in place.

With `delete: "owned-only"` the plan also lists what the apply's prune would delete: objects carrying chant's marker and the step's stack label, in the namespaces the manifest touches, that the manifest no longer declares. Generated-once Secrets and effect receipts are never in that list, as the prune never deletes them. With the default `delete: "never"` the plan lists no deletes.

The apply never deletes and recreates an object. A change to an immutable field, such as a Deployment's `spec.selector`, is refused by the API server in the dry run as it would be in the apply. The plan shows that object as an update with unknown disruption, and a hole carrying the server's message, so the note says the apply would fail until someone deletes the object.

The gate's digest binds the documents sent. For each object it also binds the action and the new value of every changed field. A `kubectl-apply` step that receives the approved plan dry-runs those documents again before it applies them. If the digest moved, the step fails before the cluster changes, and its message names the approved digest beside the new one. `pr-apply` exits 3 for it, as for a `cfn-deploy` change set that moved. A live value that moved under a field the apply sets to the same value does not move the digest.

The plan job needs credentials that can read, list and dry-run apply the manifest's kinds in the cluster, and resolves the context the same way the apply does: the step's `context`, or `k8s.profiles.<env>.context`.

### Other capabilities

`cfn-deploy`, `kubectl-apply` and `terraform-apply` are the capabilities with `plan`. A component whose steps include none of them, such as one that runs `helm-upgrade`, is a member under its own name with a count of 0 in every column. Its digest covers the component's declaration and not the content of the files its steps deploy, so the reviewer reads that content in the diff. [Plan previews](/chant/components/plan-previews/) lists every capability and what the note shows for each, and says what to check for a component that cannot plan.

## Generate the pipeline

```bash
# GitHub
chant build --components --generate github --pr-loop --env prod --output .github/workflows/chant-pr.yml
# Forgejo
chant build --components --generate forgejo --pr-loop --env prod --output .forgejo/workflows/chant-pr.yml
# GitLab
chant build --components --generate gitlab --pr-loop --env prod --output .gitlab-ci.yml
```

`--gate <name>` renames the gate from `pr-apply`. `--branch <name>` names the branch pull requests target, `main` by default on GitHub and Forgejo and the project's default branch on GitLab.

`--pr-build` adds two steps to both jobs, before `pr-plan` and before `pr-apply`: `chant build --env <env>`, then `chant lint`. Either one failing fails the job. A project with a `cfn-deploy` step needs it, because the plan and the apply read the built template and an unbuilt one fails the member. When the templates come from several builds, `--pr-build-command '<line>'` names the line to run in place of `chant build`. The estate in `examples/fan-out-estate` builds one template per stack with `npm run build`:

```bash
chant build --components --generate forgejo --pr-loop --env local \
  --pr-build-command 'npm run build' \
  --output .forgejo/workflows/chant-pr.yml
```

The jobs need chant and the lexicons installed first, through `--image` or `--before-script` as below. Without `--pr-build` the output is unchanged.

Both commands measure the change with git, so the pipeline checks out the full history. The default image is `node:22`, which has git. The jobs install OpenTofu into it, but not chant. Pick an image that has git, chant and your Terraform binary with `--image`, or install them with `--before-script`, which every job runs before its command. With a `package.json` that pins `@intentius/chant` and the lexicons the project lists:

```bash
chant build --components --generate forgejo --pr-loop --env prod \
  --before-script 'npm ci --no-audit --no-fund' \
  --before-script 'echo "$PWD/node_modules/.bin" >> "$GITHUB_PATH"' \
  --output .forgejo/workflows/chant-pr.yml
```

On GitLab, put the `node_modules/.bin` directory on the path with `export PATH="$PWD/node_modules/.bin:$PATH"` instead, since a GitLab job's lines share one shell.

### GitHub

The workflow runs on `pull_request` and on `push` to the target branch.

- The `plan` job measures from `github.event.pull_request.base.sha`. It may comment and set statuses, and it cannot push, since it runs the pull request's code.
- The `apply` job measures from `github.event.before`, the commit the push replaced. That works for merge commits, squash merges and rebase merges. On a branch's first push GitHub sets it to forty zeros, so the job measures from the merge base of the target branch and the pushed commit, or from the pushed commit's parent when that merge base is the commit itself. A root commit is measured from the empty tree. A first push that changes a member and that no pull request merged is refused as `no-pull-request`, as any direct push is. It may push, to record a pending approval on `chant/lifecycle`. One apply runs at a time per environment, through `concurrency`.

Both use the job's own `github.token`. On a pull request from a fork that token is read-only, so the note and the status are not posted. The run says so and its outcome stands.

### Forgejo

The workflow is the GitHub one with the Forgejo dialect applied: the runner label, action references by URL, and no `permissions` block, which the Forgejo runner ignores. Its commands pass `--forge forgejo`, and Forgejo Actions supplies `GITHUB_SERVER_URL`, `GITHUB_API_URL` and `GITHUB_TOKEN`.

### GitLab

The pipeline runs `plan` in each merge request pipeline, measured from `CI_MERGE_REQUEST_DIFF_BASE_SHA`. It runs `apply` on each push to the target branch, measured from `CI_COMMIT_BEFORE_SHA`, which a first push settles as on GitHub, one at a time per environment through `resource_group`. `GIT_DEPTH` is `0`.

A CI job token cannot write merge request notes. Create a project access token with the `api` scope and set it as a masked CI/CD variable named `CHANT_FORGE_TOKEN`.

## Approve a plan

The note on the pull request lists each member with its creates, updates, replaces and deletes. The plan digest and the grouped plan summary follow, with every destroy named. The last block is the command that approves this plan:

```bash
chant approve pr-12 pr-apply --plan jcs1-sha256:3e43... --approver github:alice --sign
```

`chant approve` records it on `chant/lifecycle` under the op `pr-12`, so it answers this pull request and no other. It names one digest. A push that changes the plan changes the digest, and the note shows the new one.

By default the apply also asks the forge who approved the pull request. It counts a ledger record only when the person it names has a standing approving review there, named the way the [workspace names a forge identity](/chant/reference/workspace-declaration/#identity): `github:<login>`, `gitlab:<login>`, or `forgejo@<host>:<login>`. The generator option `requireReview: false` drops the check.

Under the same check, a person who wrote the change never counts. That is the pull request's author and the author and committer of each of its commits. When the ledger record names one of them, the apply refuses with `author-approved` and applies nothing. The note names the person. Their review on the forge does not help either. GitHub and Forgejo link each commit to the account its email belongs to. GitLab gives commits by email only, so chant looks each email up among the GitLab users, which finds an account by its public email. A committer whose email no GitLab account shows publicly is not found, so on GitLab also turn on "Prevent approvals by users who add commits" in the project's merge request approval settings.

To count only signed approvals, list the gate in the workspace declaration. An approval then has to be sealed with `--sign` by a key the signers file at base lists for its approver:

```json
"identity": {
  "gates": { "pr-apply": { "class": "human" } }
}
```

<Aside type="caution">
The apply job can push to `chant/lifecycle`, and so can anyone with write access to the repository. Protect the branch so that only the apply job's identity pushes to it, and list `pr-apply` under `identity.gates`, so a ledger line that claims to be a person counts only with that person's signature.
</Aside>

## When the plan changed after review

The apply plans every member before it applies any. When the digest is the approved one, it applies each member's plan in dependency order and updates the note and the `chant/apply` status. When an approval stands for another digest, something moved between review and merge. A later commit, a merge to the target branch that touched the same root, or a change in the live state each does it. Then the apply stops with exit 3:

```
The plan changed after review, so nothing was applied. approved: jcs1-sha256:d181...; planned now: jcs1-sha256:cef9.... Read the new plan, and if it is right, approve it: chant approve pr-2 pr-apply --plan jcs1-sha256:cef9... --approver <you> --sign; then run the apply again.
```

The note and the report carry the same message. Read the new plan in `.chant/pr/pr-apply.json`, which the job keeps as an artifact. If it is right, approve it and re-run the job.

The target can also move after that check, while the apply runs. A step that finds it moved applies nothing for its member and fails it: a `cfn-deploy` change set, a `kubectl-apply` dry run, or a choudoufu root's apply that differs from the approved plan. The apply then exits 3 as well, and the members before it stay applied. Plain terraform and tofu refuse a stale plan file too, but chant does not tell that error from others, so it exits 1.

## What each run keeps

Both jobs keep `.chant/pr` as an artifact:

| File | Holds |
|---|---|
| `pr-plan.json`, `pr-apply.json` | The report: the selection, every member's plan digest and counts, the digest the gate binds, where the approval stands and how the run ended. It follows the `pr-report` schema in the [workspace read contract](/chant/reference/workspace-read-contract/). |
| `change-set.json` | The [change-set document](/chant/reference/change-set/) over every member. [`chant change-set summary`](/chant/cli/change-set/) prints its grouped summary. |
| `pr-note.md` | The note as posted. |
| `run-events/<run id>.jsonl` | With `--events-json`: the stage's run events, the lines it printed on stdout. |

## Run a job without a forge runner

`chant ci run plan` and `chant ci run apply` run the same two jobs on your own machine, each in a fresh worktree of the commit with a clean environment ([#4094](https://github.com/INTENTIUS/chant/issues/4094)). Give them the generation flags and the values the forge would supply: `--base` for the base commit, `--pr` for the pull request and `--commit` for the commit to run. Each run is recorded as Op `pr-plan` or `pr-apply` on `chant/lifecycle`, signed with a runner key when you pass one, so `chant ci tick --source runs` can tag the commit green. [`chant ci run`](/chant/cli/ci/#ci-run) lists the flags and the variables a job gets.

`chant ci serve` runs both jobs from the forge's state, with no workflow file and no forge runner ([#4095](https://github.com/INTENTIUS/chant/issues/4095)). It polls the forge for open pull requests and the target branch's head, plans each new pull request head and applies each new commit on the branch. It runs one apply at a time per environment through a git-ref lease, and keeps each apply's resume record in its state directory in place of the CI cache, so `chant ci serve --once --rerun-failed` re-runs a failed apply and finishes it. Jobs run on its host as its user, so serve only repositories whose pull request authors you trust. [`chant ci serve`](/chant/cli/ci/#ci-serve) lists its flags and what it keeps.

Both commands take the values a forge job reads from repository secrets from a file on the host, `--secrets <file>` or the file `CHANT_CI_SECRETS` names, which must be readable by its owner alone ([#4096](https://github.com/INTENTIUS/chant/issues/4096)). Its values read `***` wherever chant writes about the run, in the events and the signed record as much as in the copied report and the console. See [Secrets](/chant/cli/ci/#secrets) for the format and the allowlist.

<Aside type="caution" title="What redaction does not cover">
Redaction keeps secrets out of what chant writes about a run. It does not keep them from the job. The plan runs the pull request's code with the secrets its job gets, so that code can read them and send them anywhere the host can reach. Give the plan only what planning needs with the file's `jobs` allowlist, such as read-only credentials, and keep the credentials that change the estate for the apply, which runs only after a reviewer approved the plan. A value under 4 characters is not redacted, and neither is a secret the job transforms before printing it, such as one it encodes in base64.
</Aside>

## Follow an apply while it runs

The apply job's log prints a line as each wave starts and as each component settles, so the waves read in order while the job runs. A component held back by a failed dependency reads `blocked by <dependency>, not run`.

Generate the pipeline with `--events-json` to have both jobs print the run-event stream on stdout. The jobs also set `CHANT_RUN_EVENTS_DIR` to `.chant/pr/run-events`, so the report artifact carries the stream too.

Add `--report-url <url>` to have each job copy its report and change set to `<url>/<pr>/<commit>/`. The events go there as well, and they go up again whenever a wave or a component settles. A viewer such as behold reads the apply from there while it runs and after the job is gone. The generator options are `events: true` and `reportUrl`.

```bash
chant build --components --generate github --pr-loop --env prod \
  --events-json --report-url 's3://acme-chant-reports/prod' \
  --output .github/workflows/chant-pr.yml
```

The AWS CLI uploads to an `s3://` URL with the credentials in the job's environment. Give the jobs an identity that can write only that prefix. The URL is passed in double quotes, so `$CHANT_REPORT_URL` names a CI variable the job expands. [Pull request reports](/chant/reference/workspace-read-contract/#pull-request-reports) gives the layout.

## Limits

A dependent is planned against the outputs its upstream has now. When the change moves an output a dependent reads, the dependent applies the plan it was approved with, which carries the old value. The apply marks it `inputsMoved`, and the next run plans it against the new value. To carry a moved output through every dependent in one rollout, add a [gate per wave on merge](#a-gate-per-wave-on-merge).

An apply that fails partway leaves the members it applied in place. The generated apply job runs `pr-apply` with [`--resume .chant/pr-resume/pr-apply.json`](/chant/cli/components/#finishing-an-apply-that-failed-partway) and keeps that record in the CI cache, saved even when the job fails. Re-run the failed apply job and it restores the record, skips the members that applied and applies the rest under the approval it already has. The record is not part of the report artifact, since it holds the outputs the members read.

The cache key names the environment, the member and the pushed commit: on GitHub and Forgejo `chant-apply-<env>-<commit>-<run>-<attempt>`, restored by the prefix up to the commit, and on GitLab `chant-apply-<env>-<commit>`. In a workspace member the key starts `chant-apply.<member>.<env>` instead. A push of another commit never restores it. The pull request and the gate digest are not in the key, because the job learns them only once it runs; `pr-apply` checks them against the record and refuses a record made for another pull request, gate, commit or digest, or one whose approval no longer stands. A refused record changes nothing: the apply plans every member, and the new digest needs a fresh approval.

The approved digest covers the change set's entries as well as each member's plan, so a record whose entries, holes or side effects are not the ones that were approved is refused like one for another digest. A member left to apply is checked against entries the approval binds, not against whatever the cache holds.

The record survives a re-run when the cache does:

- On GitHub, the Actions cache is per repository, and a run on the target branch reads only caches written from that branch or the default branch, so a pull request cannot write the record the apply reads.
- On GitLab, the cache is kept on the runner unless the runners share a distributed cache, as GitLab.com's hosted runners do. A retry that lands on another runner without one plans every member again. GitLab keeps protected branches' caches apart from the others by default; keep it that way.
- On Forgejo, the cache server runs with each runner unless the runners share one, with the same consequence. Run the apply on a runner the pull requests' jobs do not use, so no other job writes into the cache it reads.

A record that comes back from an older attempt of the same run still resumes correctly: what it lists as applied did apply, and a member that applied since plans no change, which the approved plan covers.

## A gate per wave on merge

Generate the pipeline with `--wave-gate <name>` beside `--pr-loop` when a later member reads an output an earlier one moves ([#4003](https://github.com/INTENTIUS/chant/issues/4003)). The pull request is planned and approved as before. On merge the apply runs a wave at a time, and plans each wave after the one before it applied.

```bash
chant build --components --generate github --pr-loop --wave-gate release --env prod \
  --output .github/workflows/chant-pr.yml
```

The apply job becomes one job per wave of the component graph, `apply-wave-1` to `apply-wave-<n>`, each after the one before it. Job `apply-wave-<k>` runs `pr-apply --wave-gate release --wave <k>`:

- Wave 1 plans every member, as the single apply does, and decides the pull request's gate against that digest. Approved, it applies wave 1. A moved plan refuses with both digests named, as before.
- Each later wave is planned again against the outputs the waves before it left. When the pull request's approved change set covers what it plans now, the wave applies under the pull request's approval. Coverage is the test a [resumed apply](/chant/cli/components/#finishing-an-apply-that-failed-partway) uses: each change the wave makes is one the approved plan made, and a value the approved plan knew only after apply may be any value now.
- A wave whose plan moved waits at `release-wave-<k>`, under the pull request's op, for an approval of its new plan. Nothing in that wave applies, and the job exits 3. Its new plan is kept as `change-set-wave-<k>.json` beside the report, and the note gives the approve command. Once it is approved, re-run the job; the waves after it follow.

```bash
chant approve pr-12 release-wave-2 --plan jcs1-sha256:9b1f... --approver github:alice --sign
```

`--require-review` holds a wave's approval to the same rules as the pull request's: the approver needs an approving review on the pull request, and whoever wrote the change never counts. The note and each wave job's report (`pr-apply.json`, kept as `chant-pr-apply-wave-<k>` on GitHub and Forgejo) carry a row per wave. Each row names the gate the wave applied or waits under and who approved it. The report's `waves` holds the same.

The waves hand the approved change set and what applied to each other through the apply's resume record. On GitHub and Forgejo each wave saves it under its own cache key and restores the newest one for the pushed commit. On GitLab every wave shares the commit's key. A wave job with no record of the waves before it refuses with exit 1 and applies nothing. So does a record whose pull-request approval no longer stands. `chant ci serve --wave-gate <name>` runs the one apply job with `--wave-gate` and no `--wave`. That job applies the waves in order and stops at the first that waits, and `--rerun-failed` carries on once the wave is approved.

## Inside a workspace member

Run the same command in a member of a [workspace](/chant/cli/workspace-init/) and the pipeline belongs to that member. Each member that wants the loop generates its own, and each runs on the same pull request without touching the others:

```bash
cd infra/network
chant build --components --generate github --pr-loop --env prod
# wrote .github/workflows/chant-pr.network.prod.yml for member network
```

The jobs run in the member's directory, so `.chant/pr` and every path in `chant.config.ts` read from there. The report artifact is kept from `<member dir>/.chant/pr`. On GitLab the file is `.gitlab/ci/chant-pr.<member>.<env>.gitlab-ci.yml`, its jobs are `<member>-plan` and `<member>-apply`, and each script starts with `cd <member dir>`.

A member's apply is serialized per environment by the concurrency group (GitLab: resource group) `chant-apply.<member>.<env>`. A member name has no `.`, so no two members' groups meet: member `a` in environment `b-c` and member `a-b` in environment `c` apply side by side.

The jobs pass `--member <name>` to `pr-plan` and `pr-apply`. The member's gate is recorded under `pr-<number>-<member>`, its note carries the member's name, and its statuses are `chant/plan/<member>` and `chant/apply/<member>`. A reviewer approves each member's plan on its own:

```bash
chant approve pr-42-network pr-apply --plan <digest> --approver github:<login> --sign
```

The gate name stays `pr-apply`, so one `identity.gates` entry covers every member.

The pipeline has no path filter. The plan measures the whole change, not only the files under the member, so a change outside the member that reaches one of its units selects it. A Terraform root that calls `../../modules/vpc`, a module another member keeps, is planned when that module changes. A member the change does not reach reports `nothing` and applies nothing.
