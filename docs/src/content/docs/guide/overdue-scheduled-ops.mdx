A scheduled [watch](/chant/guide/watching-lifecycle/) or [reconcile](/chant/guide/reconciling-lifecycle/) Op can stop running with no error anywhere. GitHub turns a scheduled workflow off after 60 days with no activity in the repository, and on GitLab the job runs only from a pipeline schedule that someone created. Since a stopped job cannot report itself, the [pull-request plan](/chant/guide/pull-request-ci/) reports it ([#4289](https://github.com/INTENTIUS/chant/issues/4289)).

## What the plan checks

`chant components pr-plan` with `--forge` checks every Op it discovers that has a `schedule` and the `Watch` or `Reconcile` label (`packages/core/src/op/schedule-overdue.ts:80`). `WatchOp` and `ReconcileOp` set those labels (`packages/core/src/op/composites/watch-op.ts:80`, `packages/core/src/op/composites/reconcile-op.ts:80`).

The plan skips an Op unless the checkout holds the file `chant run --generate` wrote for it (`packages/core/src/op/schedule-overdue.ts:297`), so Ops that `chant operator` or another scheduler runs are left alone.

| Forge | Pipeline file | What the forge is asked |
|---|---|---|
| GitHub | `.github/workflows/<op>.yml` (or `.yaml`), or `<member>-<op>.yml` in a workspace member; failing that, the workflow in that directory whose `name:` is the Op's | The workflow's state, and its newest `schedule` and `workflow_dispatch` runs |
| Forgejo | `.forgejo/workflows/<op>.yml`, or `<member>-<op>.yml`, found the same way | The repository's runs, kept to that workflow's `schedule` and `workflow_dispatch` events |
| GitLab | The first pipeline file whose rules test `$CHANT_SCHEDULED_OP == "<op>"` | The active pipeline schedules that set `CHANT_SCHEDULED_OP` to the Op, and their last pipelines |

On GitLab the pipeline files are read in this order ([#4789](https://github.com/INTENTIUS/chant/issues/4789), `gitlabPipelineFiles` in `packages/core/src/op/schedule-overdue.ts`): the root's `*.gitlab-ci.yml`, the local files `.gitlab-ci.yml` includes and the child pipelines they trigger with `trigger: include:`, every file under `.gitlab/`, then every `*.gitlab-ci.yml` further down. A workspace member's Op file in the member's directory is found through the root's include. An include with a wildcard or a variable is not followed, so its files are found only when they are under `.gitlab/` or named `*.gitlab-ci.yml`.

The lookup is `opPipelineFile` in `packages/core/src/op/schedule-overdue.ts`. The forge calls are `scheduledRuns` in `packages/core/src/pr-forge.ts`.

### A product's own pipeline files

A CI product that generates its own pipeline calls `checkOverdueOps` from `@intentius/chant/op/schedule-overdue` with one `ScheduledWatch` per job. `files` lists the files its generator wrote for the job, and the first one in the checkout is used. On GitLab, `schedule` is the job's selector when the job's rule is not `$CHANT_SCHEDULED_OP == "<op>"`, such as `{ variable: "TERRAGUCCI_SCHEDULE", not: ["comments", "resume"] }`. The check passes it to `scheduledRuns`, and when no schedule matches, the line names it. Both fields need chant `OVERDUE_PIPELINE_FILES_FLOOR` (`packages/core/src/release-floors.ts`).

A product passes its own words ([#4888](https://github.com/INTENTIUS/chant/issues/4888)): `logPrefix` goes before every line the check writes to `log`, such as `yodel plan: `, and `label` before each verdict's `message`, such as `Warning: `, so it does not wrap `log` or the messages itself. `overdueOpsAt` takes the same two.

A product whose plan runs on chant's product plan (`productPlan` in `@intentius/chant/ci-product`) lists its scheduled jobs as `watches`, each a `ScheduledWatch`. The plan job holds no token, so it cannot ask the forge for a private repository. The note job gets the watches from the pipeline as `CHANT_PLAN_WATCHES`, and its `pr-post` checks them with the job's token beside the Ops it discovers, in its checkout of the target branch's commit, and adds the line for each overdue job under the note's counts. A watch whose op is a discovered Op's takes its place. Both need chant `PRODUCT_PLAN_WATCHES_FLOOR`.

With the product plan's `targets`, every target's note checks every watch unless the watch names its own `targets` ([#4988](https://github.com/INTENTIUS/chant/issues/4988)). An environment's drift watch with `targets: ["prod"]` is checked by the `prod` note alone. The other notes check neither that watch nor a discovered Op of the same name, so the staging note does not warn about the prod watch. Each note job still gets the whole list, and its `pr-post --member <target>` picks its own (`watchesForTarget` in `@intentius/chant/op/schedule-overdue`). A target the plan does not have is refused, and so is `targets` on a plan with none. Needs chant `PRODUCT_PLAN_WATCH_TARGETS_FLOOR`.

## When it warns

The plan counts the fires of the Op's cron in UTC since the job last ran (`packages/core/src/op/cron.ts:158`). When no run is on record, it counts from the commit that added the pipeline file. Two fires or more is overdue (`packages/core/src/op/schedule-overdue.ts:312`), while one late or dropped run is not.

A CI checkout is often shallow, and its oldest commit lists every file as added. When the commit that added the pipeline file is that oldest commit, the check runs `git fetch --unshallow` once with the job's own credentials and then reads the commit again ([#4952](https://github.com/INTENTIUS/chant/issues/4952)). If the fetch fails, the check counts from the oldest commit and says so in the job log. That date is later than the real one, so the check can only warn late.

Each overdue Op adds a line to the plan note (`packages/core/src/pr-loop.ts:584`), such as:

```
Warning: Op `drift-watch` is overdue: its schedule `0 6 * * *` has fired at least twice and its last run was on 2026-10-18. GitHub has turned the workflow off (disabled_inactivity). Turn it on again under Actions.
```

The job log gets the same line. Chant `0.124.41` and newer also list the Ops in the report's `overdue` field (`packages/core/src/pr-loop.ts:393`). A workspace member's note is posted for an overdue Op even when the change reaches none of its components (`packages/core/src/cli/handlers/pr.ts:455`).

The warning never fails the plan, and when the forge refuses the call the job log says so and the Op gets no verdict (`packages/core/src/op/schedule-overdue.ts:303`).

## Give the note job read access

- GitHub: the generated `plan-note` job asks for `actions: read` (`lexicons/github/src/components/generate-pipeline.ts:356`). The plan job holds no forge token since [#4295](https://github.com/INTENTIUS/chant/issues/4295), so `pr-post` in the note job runs the check, with the Ops read at the target branch's commit. A pipeline generated before chant `0.124.41` lacks it, so regenerate it with the command in its header.
- Forgejo: the job token reads the repository's runs.
- GitLab: listing pipeline schedules needs an access token with the `read_api` scope, which the job token lacks. Set `CHANT_GITLAB_TOKEN` or `GITLAB_TOKEN`, which `--forge gitlab` reads before `CI_JOB_TOKEN` (`packages/core/src/pr-forge.ts:1232`).

`chant ci run plan`, on a host or in place, runs the check before it posts the note from the report, as `pr-post` does. It reads the Ops from a fresh checkout of `--base`, never from the change's ([#4328](https://github.com/INTENTIUS/chant/issues/4328), `overdueAtBase` in `packages/core/src/workspace/ci-run.ts:869`). That checkout imports packages from the `node_modules` the running chant is installed in.

## Fix an overdue Op

- GitHub: turn the workflow on again under Actions, or run it once by hand.
- GitLab: add a pipeline schedule with the Op's cron and the variable `CHANT_SCHEDULED_OP` set to the Op's name.
- Forgejo: check that Actions is on and a runner is up, then run the workflow by hand.

The next plan after a run sees it and drops the warning.
