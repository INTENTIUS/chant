This guide is for a workspace whose pull-request jobs must run a command of their own around the plan or the apply. A provider init before the plan is one such command. A backup before the apply is another. The jobs are `chant components pr-plan`, `pr-record` and `pr-apply` ([Generated CI for Pull Requests](/chant/guide/pull-request-ci/)). They run the same stage hooks an [Op waves](/chant/guide/op-waves/#stage-hooks) job runs ([#4288](https://github.com/INTENTIUS/chant/issues/4288)).

## Declare the hooks

Put them under `ci.hooks` in `chant.workspace.json`. The shape is the one an Op waves spec's `hooks` takes.

```json
{
  "ci": {
    "hooks": {
      "before": {
        "observe": [{ "name": "init", "command": ["./bin/init", "{target}"], "perRun": true }],
        "plan": [{ "name": "lint", "command": ["./bin/lint-config"] }],
        "apply": [{ "name": "backup", "command": ["./bin/backup", "{runs}"], "targets": ["db-*"] }]
      },
      "after": {
        "plan": [{ "name": "policy", "command": ["./bin/policy", "{target}", "{plan}"], "perRun": true, "onFailure": "approve" }],
        "apply": [{ "name": "smoke", "command": ["./bin/smoke", "{wave}"] }]
      }
    }
  }
}
```

A member can set its own `ci.hooks`. They run after the top level's (`packages/core/src/components/pr-hooks.ts:46`). Set `minReader` to 0.124.41 or newer with either.

## When each moment runs

| Moment | Runs in | When |
|---|---|---|
| `before.observe` | pr-plan, pr-record, pr-apply | before anything reads live state |
| `before.plan` | pr-plan, pr-record, pr-apply | after `before.observe`, before the plan |
| `after.plan` | pr-plan, pr-record, pr-apply | once every component planned |
| `after.gate` | pr-apply | once the pull request's gate decided, whatever it decided |
| `before.apply` | pr-apply | once the gate and the review let the apply through |
| `after.apply` | pr-apply | after the apply, for the components that applied |
| `check` | a product's check job, through `chant ci check` | before any plan, once, or once per target with `perRun` |

The plan-side moments wrap the plan in `hookedPlan` (`packages/core/src/cli/handlers/pr.ts:307`). The apply-side moments wrap `applyPrSet` (`packages/core/src/cli/handlers/pr.ts:715`, `:774`). With `--wave-gate`, each wave runs its own plan-side and apply-side hooks for its components.

`hooks.apply.runBy` is refused, since chant runs a pull request's apply (`packages/core/src/op/op-waves.ts`, `assertPrLoopHooks`). `onFailure: "approve"` on `after.gate` is refused as in an Op waves job, since the gate has already decided.

An `after.gate` hook runs in pr-apply right after the gate is decided (`runGateHook` in `packages/core/src/cli/handlers/pr.ts`). Its environment adds `CHANT_GATE_STATUS` (`approved`, or `waiting` when no approval of the digest stands), `CHANT_GATE_OP`, `CHANT_GATE` and `CHANT_GATE_DIGEST`. When the gate waits, the hooks still run, and the stage then ends as a refusal whatever they came to. pr-plan and pr-record decide no gate to act on, so they run no `after.gate` hook. A gate decided again for a later wave under `--wave-gate` runs none either.

## The check moment

`ci.hooks.check` runs the linters a repository already uses (tflint, checkov, trivy, pre-commit and the Pulumi side's equivalents) in the check job, the job that runs before any plan ([#4556](https://github.com/INTENTIUS/chant/issues/4556)). A hook takes the same shape as the other moments, with two limits: `onFailure` is `fail`, and a hook has no `{plan}`. A declaration that names `onFailure: "approve"` or `{plan}` on a check hook is refused, since nothing is planned yet to approve.

```json
{
  "ci": {
    "hooks": {
      "check": [
        { "name": "tflint", "command": ["tflint", "--chdir", "{target}"], "perRun": true },
        { "name": "pre-commit", "command": ["pre-commit", "run", "--all-files"] }
      ]
    }
  }
}
```

The check job runs `chant ci check --base <rev> [<target>...]`, or a product calls `runCheckHooks` from `@intentius/chant/components/check-hooks`. The hooks are read at base, as every moment is, so a change cannot remove a required check. The targets are the roots, stacks or components the change touches. A `perRun` hook runs once for each, with `{target}` and `CHANT_TARGET`, and `targets` matches their names as above.

A check hook's environment holds no forge token and no cloud credentials, and the OIDC request variables are dropped as well (`checkHookEnv`). It reads the change and nothing else. Its environment adds `CHANT_HOOK=check`, `CHANT_CHECK=1`, `CHANT_RUNS` and `CHANT_HOOKS_BASE`. The report is `check-hooks.json` under `--output` (default `.chant/check`). Each row names a hook call and its target and gives the call's result and exit code. The product copies the rows into its own check report. The command exits 1 when a hook failed and 0 when every hook passed or none is declared.

A product's `init` adds a hook with `writeCiHook(root, "check", hook)`, which writes `ci.hooks.check` in the declaration and keeps the file's formatting, replacing a hook of the same name so that `init` can run again. A declaration that uses `check` sets `minReader` to chant `0.124.55` or newer.

## What a hook sees

The runs are the components the change selects, in apply order. A `perRun` hook runs once per component, with `{target}` and `CHANT_TARGET`. After the plan, its `{plan}` is a JSON file with the component's members and the plans its steps hand the apply (`packages/core/src/components/pr-hooks.ts:130`).

`targets` limits a hook to the components whose names match. A name matches itself. In a pattern, `*` matches within one `/` segment and `**` across segments. A hook that runs once for the job runs when any component matches (`packages/core/src/op/op-waves-run.ts:914`).

`{op}` is the gate's op, such as `pr-12`, and `{wave}` is the environment. The environment adds `CHANT_HOOK`, `CHANT_RUNS`, `CHANT_ENV`, `CHANT_PR_STAGE` (`plan`, `record` or `apply`) and `CHANT_HOOKS_BASE`, the commit the hooks were read at (`packages/core/src/components/pr-hooks.ts:144`). The runs file and the plan files go under `<output>/hooks`, by default `.chant/pr/hooks`.

## Read at base

The jobs read `ci.hooks` from the declaration at the base the change is measured from (`packages/core/src/cli/handlers/pr.ts:253`). A pull request cannot add, edit or remove a hook its own jobs run. A hook it adds runs on the next pull request after it merges.

When the base has no declaration, no hook runs. When the declaration at base cannot be read and the checkout names hooks, the job refuses to start (`packages/core/src/components/pr-hooks.ts:81`).

## A hook that fails

With `onFailure: "fail"`, the default, a failure ends the stage as follows.

| Moment that failed | The stage ends | What applied |
|---|---|---|
| `before.observe` or `before.plan` | `plan-failed`, with no members | nothing |
| `after.plan` | `plan-failed` | nothing |
| `before.apply` | `failed` | nothing |
| `after.apply` | `failed` | the components that applied stay applied |

The report's `message` names the hook and its exit code. Every hook outcome goes in the report's `hooks` list, and the note counts those that passed and names the rest.

With `onFailure: "approve"`, a failure is recorded as `held` and the job goes on. The pull request's gate already waits for a person to approve the digest, so a hold asks for nothing more. A hook that writes `CHANT_HOLD` to name another gate is not a plain hold ([#4323](https://github.com/INTENTIUS/chant/issues/4323)). The job settles that gate as an Op waves job does (`settleHolds` in `packages/core/src/components/pr-hooks.ts`). If someone approved it at that digest under its `identity.gates` rule read at base, the hook runs again with `CHANT_HOLD_APPROVED` (JSON: `op`, `gate`, `digest`, `approvedBy`, `approvedAt`) and `CHANT_HOLDS_APPROVED`, the gates approved so far. The re-run passes, or holds on a further gate, settled the same way, up to ten gates per hook call. If nobody approved it, pr-apply records a pending fact for the gate and the stage ends as failed, with the command that approves it in the message. pr-plan only reads the ledger and records nothing. Approvals of the other gate are not spent.
