description: Generate the agent jobs that answer an agent comment on a pull request, follow a drift check, answer a production alert, a failed apply or a failed verify or soak, or run a task on a schedule, with a spend limit and the write token kept out of the model's job.
diataxis: how-to
prompt: |
  Read https://intentius.io/chant/guide/agent-jobs/.
  Add an agent to the scheduled Op spec I name, with the limit I give you, and regenerate its workflow with chant run --generate.
  Open a pull request with the change, and say in its description which secret holds the model's key and which holds the push token.
  Never deploy to a real cloud account or shared environment (with `chant run`, `chant components` or a platform's own CLI), approve (a pull request review, `chant approve` or `chant run approve`), override a policy denial (`chant approve policy-override`), or merge; never cut or publish a release (`chant release cut --yes` or `chant release publish`), push or delete a `ci/*` tag (`chant ci tick` pushes them), or change the value of an existing flag; never touch `.chant/allowed_signers` or `chant/lifecycle`.

This guide is for a repository that wants a coding agent to change code when someone asks, when a drift check finds the cloud has moved, when a production alert fires, when an apply fails, when a stage's verify or soak fails, or on a schedule. The agent runs as two generated jobs from a scheduled Op spec's `agent` ([#4616](https://github.com/INTENTIUS/chant/issues/4616)). The first runs the model with a read token. The second holds the write token and lands the change.

Nothing the agent does applies, approves or merges. A change it pushes plans like any other, and a person reviews it.

## Answer a comment

Add a spec whose `agent` has `on: "comment"`, and generate it with `chant run --generate github --spec <file>` (or `gitlab`, `forgejo`):

```json
{
  "ops": [
    {
      "name": "chant-agent",
      "agent": { "on": "comment", "comment": "/chant agent", "maxRuns": 10, "timeout": 30 },
      "runner": "ubuntu-latest"
    }
  ]
}
```

A comment such as `/chant agent add a cost-center tag to the bucket` on a pull request starts it. The ask is read with the product's comment grammar (`parseProductComment`, `packages/core/src/ci-product-words.ts:473`): one line, plain text, at most 2,000 characters. On GitHub the comment must come from an owner, member or collaborator. On Forgejo, which has no author association, `chant agent prepare` asks the forge whether the commenter can write (`packages/core/src/ci-agent.ts`). A pull request from a fork is refused, since the agent pushes only to this repository's branches.

The agent's change is one commit on the pull request's branch, pushed without force. Its message carries `Requested-by:` with the commenter's login.

A CI product gets the same spec from `productPipelineJobs(forge, env, { words, agent })`, which returns it as `agent.spec` beside the comment it answers, in the product's words.

## Follow a drift check

Set `agent` with `on: "drift"` on the drift check's own spec:

```json
{ "name": "drift-app", "trigger": { "kind": "cron", "schedule": "0 6 * * *" }, "findingMode": "issue", "agent": { "on": "drift", "maxRuns": 2 } }
```

The drift check's job keeps its output, and when its run exits with chant's `drift` code (2) the agent job runs with that output in the prompt. On GitHub and Forgejo the drift check's job ends green on drift, because Forgejo publishes a job's outputs only from a successful job. A job named `<drift-job>-found` follows it, runs when the drift check reported drift, and exits with the drift code, so a run that found drift still shows red on that job. The same job follows a drift check that has an `update`. The change goes to a branch of the agent's own, `<product>/agent/<name>` unless `branch` names another, and opens a pull request into the default branch. The next drift replaces the branch with a lease and updates the same pull request, as long as every tip on the branch is the agent's. A person's commit on it stops the agent there.

When the drift check keeps a drift issue with `keepDriftIssue`, the issue hears about the fix. The drift check's job sets `CHANT_DRIFT_ISSUE_FILE`, `keepDriftIssue` writes the issue's number to it, and the job hands the numbers to the push job through its outputs on GitHub and Forgejo and its dotenv on GitLab. Once the pull request exists, the push job comments its URL on each drift issue. A later drift that updates the same pull request adds no second comment to an issue that already has one, which the push job reads from the agent's run records on the ledger (`driftIssues`).

For a workspace member the drift check runs in the member's directory and the agent jobs run at the repository root. Each reads the member's own drift output. On GitHub and Forgejo the drift check hands its output to the agent job as job outputs. On GitLab the drift check keeps it in its artifact under `<member>/.chant/agent`, and both agent jobs use that directory.

## Answer a production alert

An alert agent opens a pull request when a production alert names something the code can fix. Add a spec whose `agent` has `on: "alert"`:

```json
{ "name": "chant-alert-agent", "agent": { "on": "alert", "maxRuns": 6, "maxCostUsd": 20 } }
```

The spec is a workflow of its own. [The relay](/chant/guide/notify/#take-production-alerts) checks each alert, writes it as a fact on `chant/lifecycle` signed with the relay key, and starts the workflow with no inputs. The workflow also runs every 15 minutes, or on the spec's own `cron` trigger, and picks up any fact whose start did not arrive. On GitLab the jobs run in the pipeline the relay's trigger token starts, and in a pipeline schedule with `CHANT_SCHEDULED_OP` set to the spec's name.

On GitLab the relay's trigger token starts a pipeline of the whole `.gitlab-ci.yml`. Every job in it that a trigger pipeline reaches runs, a deploy job too, so an alert would start it. Put this first in the `rules` of each job of your own:

```yaml
rules:
  - if: '$CI_PIPELINE_SOURCE == "trigger"'
    when: never
  # the job's own rules follow
```

A `$CI_PIPELINE_SOURCE != "trigger"` condition on each of its rules does the same. `chant run --generate gitlab` reads `.gitlab-ci.yml` when a spec sets an alert agent and warns about each job with no rules or with rules that have no condition on a trigger pipeline, the rule above in the warning. It warns as well about files the project includes, whose jobs it does not read, and when it cannot read the file at all. The generated file carries the same rule in its header.

`chant agent prepare` reads the facts from the ledger and checks each signature with the relay key: the `CHANT_RELAY_KEY` secret, or the one `relayKeyEnv` names. A fact the relay key did not sign starts nothing. The decision step and the push job hold the key, and the model's step does not. Facts older than a day start nothing.

One run answers one member's alerts. It takes the oldest new alert and every alert for the same member received within `window` minutes after it, 15 by default. An alert for that member that arrives later inside the same window joins that run and starts no other. Each alert reaches the prompt as JSON data: its source, the source's id, title, severity, member, time, link and details, cut to 20,000 characters in all. No header of the delivery reaches it.

The change goes to `<product>/agent/<name>-<member>` (`<product>/agent/<name>` for an alert with no member) and opens a pull request into the default branch, which plans and waits for a person like any other. The next alert for the member replaces the branch and updates the pull request, as long as every tip on it is the agent's. `maxRuns` and `maxCostUsd` limit the runs as for any agent, and alerts that arrive over the limit are recorded as `stopped` and start nothing later. A run with no new alert records nothing.

The push job reads the decision as data. Before it lands anything it checks that every fact the decision names is on the ledger, signed with the relay key, and taken by no other run. Each run record carries `trigger: "alert"`, the facts it took, the member, its window, and each alert's source and id.

A CI product gets the spec from `productAlertAgent(words, options)` in `@intentius/chant/ci-product`, and feature-detects on `AGENT_ALERT_FLOOR`.

## Answer a failed apply

A failed-apply agent opens a pull request when an apply fails for a reason the code can fix. It reads the same kind of fact as an alert agent, so the joining, the limits and the push job's checks are the same. Add a spec whose `agent` has `on: "apply-failed"`:

```json
{ "name": "chant-apply-failed-agent", "agent": { "on": "apply-failed", "maxRuns": 4, "maxCostUsd": 10 } }
```

The apply jobs record the facts. Give them `CHANT_AGENT_FACTS=apply-failed` and the relay key in `CHANT_RELAY_KEY`:

- chant's own wave jobs: the waves pipeline's `agentFacts` option, `{ "relayKeyEnv": "CHANT_RELAY_KEY" }`, puts both on each wave job's command step. A pipeline whose waves are split keeps its apply jobs without a token, so they record nothing.
- `chant components pr-apply`: set both variables on the apply job.
- a product's own apply job: run `chant agent apply-failed --op <name> --from <log> [--member <m>]` after the apply fails, with both variables set. The last 8,000 characters of the log are the error.

A failed apply records one fact per member that did not apply under `_alerts/apply-failed.jsonl` on `chant/lifecycle`, signed with the relay key, and pushes the ledger. The same member failing again at the same commit is the same fact. The triage comment posts as before.

The agent's workflow runs every 15 minutes, or on the spec's own `cron` trigger, and when started by hand on the default branch. On GitLab it runs in a pipeline schedule with `CHANT_SCHEDULED_OP` set to the spec's name, or in a pipeline of the default branch started by hand with the same variable. Each failure reaches the prompt as JSON data: the op, how the triage names the apply, the member, the exit code, the failed resources and the engine's error output, at most 8,000 characters per member and 20,000 in all. The change goes to `<product>/agent/<name>-<member>`. Each run record carries `trigger: "apply-failed"`, the facts it took, the member, its window, and the op and member of each failure.

A CI product gets the spec from `productApplyFailedAgent(words, options)`, and the wave jobs' variables from `opWavesAgentFactsEnv(forge, { relayKeyEnv })`.

## Answer a failed verify or soak

A failed-verify agent opens a pull request when a stage's verify step fails after a promote, or when one of its soak checks starts failing. It reads the same kind of fact as a failed-apply agent, so the joining, the limits and the push job's checks are the same. Add a spec whose `agent` has `on: "verify-failed"`:

```json
{ "name": "chant-verify-failed-agent", "agent": { "on": "verify-failed", "maxRuns": 4, "maxCostUsd": 10 } }
```

chant records the facts itself, so no webhook is involved. Give the pipeline's generator `agentFacts` with `verify-failed` among its triggers:

```ts
{ agentFacts: { relayKeyEnv: "CHANT_RELAY_KEY", triggers: ["apply-failed", "verify-failed"] } }
```

Each promote and recheck job's command step then holds `CHANT_AGENT_FACTS=verify-failed` and the relay key, and so does each wave job's. A job of your own that runs `chant components promote` records the same facts with both variables set.

- A soak check that starts failing records one fact per check and member, at the same moment the `soak` notify event goes out. A check that keeps failing records nothing more; a check whose reading is unknown records nothing.
- A promote or redeploy whose verify step failed records one fact per failed step. A verify step is a step in a phase named `Verify`, or a step of kind `health-gate`, `wait-endpoint`, `wait-cluster-healthy` or `http-check` (`VERIFY_STEP_KINDS`).

The facts go under `_alerts/verify-failed.jsonl` on `chant/lifecycle`, signed with the relay key. The same check failing again for the same release is the same fact. Recording one changes nothing else: the soak still holds, and the promote exits as it would have.

Each failure reaches the prompt as JSON data: the stage, whether a verify or a soak failed, the step or check and its kind, the member, the component, the release, and the step's error or the check's output, at most 8,000 characters per failure and 20,000 in all. The change goes to `<product>/agent/<name>-<member>`, or `<product>/agent/<name>` for a failure that names no member. Each run record carries `trigger: "verify-failed"`, the facts it took, the member, its window, and the stage, kind, check and member of each failure.

When the stage requests a rollback on the failure, that rollback stands. It waits at the stage's gate as before, and the agent's pull request goes forward as a new release once a person merges it. The prompt tells the model to leave the rollback alone, and the pull request says the same.

A CI product gets the spec from `productVerifyFailedAgent(words, options)`, and feature-detects on `VERIFY_FAILED_AGENT_FLOOR`.

## Run a task on a schedule

A scheduled agent does a recurring task, such as reviewing provider and module versions, and opens a pull request when the task changes something. Add a spec with `on: "schedule"`, the task, and a `cron` trigger:

```json
{
  "name": "chant-versions-agent",
  "trigger": { "kind": "cron", "schedule": "0 7 * * 1" },
  "agent": { "on": "schedule", "task": "Raise each provider and module version pin to the newest release that keeps the plan clean.", "maxRuns": 1 }
}
```

The task comes from the workflow file on the default branch and reaches the prompt as the maintainers' instruction. A scheduled run is its own fact: its key is the agent's name and the CI run's id, so a run started again (a retry, or a start by hand within `window` minutes) joins the run already made and starts nothing. The fact is never written to the ledger; the run record that takes it marks it spent. A scheduled agent holds no relay key. The change goes to `<product>/agent/<name>`, and each run record carries `trigger: "schedule"`.

A CI product gets the spec from `productScheduleAgent(words, { schedule, task, ... })`.

## Settings come from the default branch

Every agent reads its settings and caps from the default branch, whatever started it. The generated command lines carry a digest of the settings (`--digest sha256:...`), and `chant agent prepare`, `run` and `land` refuse variables that do not match it. On GitLab a pipeline variable can replace a job's variable, and the digest on the script line is what it cannot replace. `prepare` and `land` also refuse a job whose commit is not on the default branch, so a workflow that a pull request changed, started on the pull request's branch, does not run the agent. A pull request that raises `maxRuns` or `maxCostUsd` changes nothing until it merges. Both jobs note the remote's default branch as `origin/HEAD` in their checkout.

Products feature-detect the failed-apply and scheduled agents, and the settings check, on `AGENT_FACT_TRIGGERS_FLOOR`.

## The spend limit

`maxRuns` is the most runs a day. Each run leaves one run record on the workspace ledger, under op `<name>` in environment `env` (`local` by default). Its outcome names who asked and how the run ended. It also keeps the commit or pull request the run made, and the prompt's digest beside what the command said it cost. `chant agent prepare` counts the records of the last 24 hours before the model starts, and `chant agent land` counts them again before it pushes. A run over the limit is said on the pull request and recorded as `stopped`.

`maxCostUsd` is the most US dollars the agent's runs may cost a day. The cost of each run is the one its run record keeps, as the command reported it, and the sum covers the same 24 hours as `maxRuns`. A run whose command reported no cost adds nothing. The sum is checked before a run starts, so the run that passes the limit still finishes, and the next one is stopped. The two limits can be set together, and either one stops a run.

`timeout` is the minutes the model command may run, 30 by default. At the limit the command is stopped and the push job lands nothing. Each job's own timeout is 15 minutes longer, which leaves room for the checkout and the setup.

By default the command is Claude Code with the file tools alone, its turns limited by `maxTurns`. A command of your own reads the prompt on stdin and may write `{ model, cost_usd, input_tokens, output_tokens }` to `$CHANT_AGENT_USAGE`, which the run record keeps.

## Which job holds which token

Each job holds only what its own steps need.

| Job | Holds | Runs |
|---|---|---|
| agent | a read token in the checkout and the decision step; the model's key (`keyEnv`, `ANTHROPIC_API_KEY` by default) in its last step alone | `chant agent prepare`, then `chant agent run` in a worktree of the commit, with no forge token in its environment |
| push | the push token: the `tokenEnv` secret, else the job token | `chant agent land`, which applies the patch, refuses a guarded path, commits, pushes, opens or updates the pull request and records the run |

A push made with GitHub's job token starts no workflow, so the pull request is planned again only when `tokenEnv` names a token of a user or an app.

On GitLab the comment agent runs in a pipeline of the default branch started with `CHANT_AGENT_PR` set to the merge request's iid and `CHANT_AGENT_ASK` to the ask, since GitLab starts no pipeline on a note. The push job runs under environment `<name>-push`. Scope the push token (`CHANT_FORGE_TOKEN` unless `tokenEnv` names another) to that environment, protected and masked, so the agent job never holds it.

## Paths an agent may not change

The push job refuses a change that touches CI files, `.chant/`, `chant.workspace.json`, the chant config, code owners, `.claude/`, `.cursor/`, `.mcp.json`, or a `CLAUDE.md`, `AGENTS.md`, `.gitattributes` or `.gitmodules` in any directory. `guarded` adds a product's own files, and a trailing `/` names a directory. The prompt lists the same paths, and the push job enforces them either way.

## Where the jobs run

`runner` names where every job of the spec runs: a label, a list of labels, or on GitHub a runner group (`{ "group": "infra", "labels": ["linux"] }`). It is `runs-on` on GitHub and Forgejo and `tags` on GitLab. A runner group is refused on GitLab and Forgejo. The field works on any scheduled Op spec, with an agent or without one.

## Commit a command's result

A scheduled Op spec's `commit` ([#4722](https://github.com/INTENTIUS/chant/issues/4722)) has the same two jobs with a product's command in place of the model: a formatter after a failed format check, or `yodel rebase` on a forked migrations directory. `command` is an argv, run with no shell and no forge token in a worktree of the pull request's head, with the target branch's `node_modules/.bin` first on `PATH`. `allowed` lists the only paths the change may touch, and the paths above stay refused. The push job commits with a `Commit-run: <name>` trailer and pushes without force.

`on: "comment"` answers `/<product> <word>` from a workflow of its own, where the words map `<word>` onto `commit`. `on: "check"` follows the Op's own job on a pull request and runs when its run exits with one of `findings` (chant's drift code, 2, by default). The check trigger skips a head whose last commit is the job's own, refuses once the head's plan has an approval on the ledger, and says nothing when it changed nothing. A comment goes ahead on an approved head and says the new commit needs approval again. `maxRuns` (3 by default) caps the commits pushed to one pull request, counted on the ledger. A check that runs on push rather than on the pull request, as a product's own check job may, is matched to the branch's open pull request: the forge is asked on GitHub and Forgejo, and GitLab's `CI_OPEN_MERGE_REQUESTS` is read, this project's merge request only. A branch with no open pull request is skipped. A product that renders its own check job, one that runs on push, passes `onPush` to `githubCommitJobs` or `gitlabCommitJobs`, and both jobs then fetch the pushed commit (`github.sha`, `CI_COMMIT_SHA`) as the head ([#4749](https://github.com/INTENTIUS/chant/issues/4749)).

`allowedFiles` bounds the change by file name in any directory, `*.tf` or an exact name such as `terragrunt.hcl`, beside `allowed` ([#4758](https://github.com/INTENTIUS/chant/issues/4758)); a guarded path is still refused. A formatter that touches every file of a kind sets it in place of listing directories.

`tokenEnv` is required on GitHub and Forgejo, since a push with the job token starts no run and the new head would get no plan, unless the spec sets `jobToken: true`. The push job then pushes with the job's own token and runs the spec's `after` lines once it has pushed, with `CHANT_COMMIT_SHA` set to the new commit, for what the missing run would have done, such as taking the plan locks of the new head. GitLab refuses `jobToken`, since its job token cannot push. `CI_COMMIT_PUSH_FLOOR` is the first chant with `onPush`, `jobToken` and `after`. On GitLab a comment job runs in a pipeline of the default branch started with `CHANT_COMMIT_PR` and `CHANT_COMMIT` set to the word, and the check trigger is off unless `gitlabCheck` is set, because the push token is a protected variable. A product passes comment jobs as `commits` to `productPipelineJobs`, and a check's job with `productCheckCommit`. `CI_COMMIT_FLOOR` in `@intentius/chant/ci-commit` is the first chant with them.

`mergeBase: true` ([#4723](https://github.com/INTENTIUS/chant/issues/4723)) merges the base branch's tip into the head (`--no-ff`) before the command runs, since a forked migrations directory shows only on that merge. A conflict is refused and the command does not run. The push job makes the same merge without running code, refuses when the base tip moved, applies the change, checks it against `allowed`, and pushes one commit whose parents are the head and the base tip. GitLab refuses it on a comment job, whose pipeline cannot read the merge request's target branch.

`commandEnv` ([#4724](https://github.com/INTENTIUS/chant/issues/4724)) names variables of the job the command sees, such as a database reader's user and password; a forge token's name is refused. GitHub and Forgejo pass each from the secret of the same name to the step that runs the command, and on GitLab they are the project's CI/CD variables. The command also gets `CHANT_COMMIT_PR`, the pull request's number. A command that exits non-zero leaves the tail of its standard error to the push job, and a product's bin can set `setCommitRefusalReply` to turn what it printed into the reply; the run is then `refused`, and any other failure keeps chant's reply. `CI_COMMIT_REPLY_FLOOR` marks all three. The sql lexicon's `yodelCommitSpec` builds `/yodel new` and `/yodel rebase` on them.

`commentArg` ([#4820](https://github.com/INTENTIUS/chant/issues/4820)) lets a comment job's word take one argument, `/<product> <word> <arg>`. The spec gives a `pattern`, a regular expression anchored with `^` and `$`, and a `position` in the argv. `chant commit prepare` refuses an argument that misses the pattern or is not a plain name (letters, digits, `.`, `_` and `-`, no leading dash, at most 100 characters), records it in the decision, and `chant commit run` puts it into the argv at that index. On GitLab the pipeline's `CHANT_COMMIT_ARG` variable carries it. With no argument the argv is `command`. `/yodel new <name>` names the migration this way. `CI_COMMIT_ARG_FLOOR` marks it.

A comment for the job's word that chant refuses as it reads it, such as an argument off the pattern or a word after a command that takes none, is answered on the pull request ([#4838](https://github.com/INTENTIUS/chant/issues/4838)). The push job quotes the comment's first line and says why, for example `` plywood: `/plywood fmt now` was refused: `/plywood fmt` takes nothing after it. plywood-fmt did not run, and nothing was pushed. `` A comment for another word is left to that word's job. `CI_COMMIT_REFUSAL_REPLY_FLOOR` marks it.

A product's own comment job, one that reads every `/<product>` comment and replies to what it refuses, leaves the commit job's words alone with `parseProductComment(words, body, env, {}, { leaveCommit: true })` ([#4890](https://github.com/INTENTIUS/chant/issues/4890)). A comment whose first two words are `/<product> <word>`, where the words map `<word>` onto `commit` (`commitWordOf(words, body)`), is then not addressed to it, a malformed one included, so `/plywood fmt now` gets the commit job's reply and no other. The GitLab note poller answers a commit word's note before any pipeline starts, so it reads these as before. `COMMENT_LEAVES_COMMIT_FLOOR` marks it.

A product's e2e harness can prove that land's checks matter ([#4836](https://github.com/INTENTIUS/chant/issues/4836)). In a BREAK arm, `CHANT_COMMIT_HARNESS_BREAK` on the push job turns one check off: `paths` lands a change outside `allowed` and `allowedFiles` (a guarded path is still refused), and `moved-base` lands, under `mergeBase`, the merge of the base tip the command ran on after the base moved. Land reads it only with `BREAK=1` on the harness's Forgejo (`GITHUB_SERVER_URL` is `http://forgejo:3000`). Anywhere else land fails and pushes nothing. A land with a check off says so in its reason and reply. `CI_COMMIT_HARNESS_BREAK_FLOOR` marks it.
