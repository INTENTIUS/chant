Every security feature in chant is off until a workspace turns it on ([#4168](https://github.com/INTENTIUS/chant/issues/4168)). A group turns on a set of them at once, and each feature still turns on alone; the [security features reference](/chant/reference/security-features/) lists them all.

Under `supply-chain`:

- A publish target with no SBOM source is refused (`publish-sbom-missing`). Without the group it publishes without one.
- A publish with no OIDC token warns that what it publishes carries no provenance. Without the group, provenance is only a field in the plan. `--require-provenance` refuses instead, with or without the group.
- `chant release cut` refuses `release.green: "none"` (`release-green-none-refused`), so every release passed a [green gate](/chant/cli/release/cut/#the-green-gate).
- An `oci` or `forge` target signs what it publishes with Sigstore and adds SLSA provenance, keylessly with the CI job's OIDC token, or with a KMS key or a cosign key (`release.signing.kms`, `release.signing.key`) where there is none. A publish that can't sign is refused (`publish-signing-no-oidc`, `publish-signing-key-missing`, `publish-signing-tool-missing`). `release.signing: false` in `chant.config.ts` turns it off with a warning. [Sigstore signatures](/chant/reference/publish-targets/#sigstore-signatures) has the details.
- `chant release publish` scans what it would put out for known vulnerabilities before anything is pushed or signed, and stops with `publish-scan-failed` on a finding the policy blocks. `release.scan: false` turns it off with a warning. [The scan before the stage](#the-scan-before-the-stage) has the details.

An SBOM comes from the file a target's `sbom` names. With none named, an image's SBOM is the one the scan made from the image's layers, so it lists the OS packages in the image. Every other SBOM comes from the lockfile nearest the member: `package-lock.json`, `pom.xml` or `Cargo.lock`. A member whose directory holds a `Cargo.toml` reads `Cargo.lock` first.

## Opt in

Add the group to `security` in `chant.workspace.json`, at the top level for every member or on one member for that member only. A member's list adds to the top-level one.

```json
"security": ["supply-chain"]
```

A declaration that uses `security` sets `minReader` to `0.124.33` or newer.

`chant release init` does not add the group. It writes no `chant.workspace.json` for a single release, and under the group an npm package that carries no SBOM is refused, which a new project's packages usually don't yet. Add the group once the packages carry one.

## Fill the gaps

`chant workspace check` reports what the group still lacks as `WSP162` warnings:

| Code | What to do |
|---|---|
| `security-sbom-disabled` | Remove `sbom: false` from the publish target. |
| `security-sbom-unsourced` | Point `sbom` at the SPDX or CycloneDX file the build writes, or commit the member's lockfile. |
| `security-publish-no-provenance` | Pass `--require-provenance` in the publish job, which runs in CI with an OIDC token. |
| `security-component-no-sbom` | Add a `generateSbom` step to the member's components. |
| `security-component-no-verify` | Add a `verify` step before the deploy steps. |
| `security-image-base-unpinned` | Pin the `FROM` line it names by digest; see [Pin image bases by digest](#pin-image-bases-by-digest). |

## Pin image bases by digest

A base named by tag (`FROM node:22`) is whatever the registry serves under that tag on the day of the build, so a later build of the same commit can start from a different image. Named by digest (`FROM node:22@sha256:<digest>`) it is the same image every time; the tag beside the digest is for a reader.

Under the group, `chant workspace check` reads each Dockerfile a member's `release.images` names and reports a `FROM` that is not pinned (`security-image-base-unpinned`), and `chant release doctor` warns of the same (`image-base-pinned`), with the entry's `args` applied. A `FROM` passes when it names an earlier stage, `scratch`, or an `ARG` declared before the first `FROM` whose default is pinned and which the entry's `args` do not replace with a tag. The workspace check reads `chant.config.ts` as text, so it finds a `dockerfile:` written as a string, not one built at run time; the doctor loads the config and sees every entry.

### Pull bases from a private registry

A base from a registry that needs a login, such as a hardened image set served to an organization, is named with a `pull` entry on the `release.images` entry; [the release workflow](/chant/cli/release/workflow/) then logs in to it before each build. See there for the variables and secrets it reads.

### Hardened bases for a product's CI image

A CI product's image (plywood's, terragucci's, SQL Yodeler's) can be built on Chainguard's images in place of Debian. The product's own config has a key for it, which sets `base` in chant's image helper. No `security` group turns it on, and `supply-chain` does not check for it. See [the image's base](/chant/concepts/ci-products/#the-product-pipeline) for what it changes. A product's Chainguard bases are pinned by digest like any other, and `--repin` moves them.

### Move the pins

A pinned base stays where it was pinned while its tag moves on to patched images. `chant release images --repin` asks each image's registry what digest the tag names today and, when it moved, rewrites the digest in place, keeping the tag:

```
$ chant release images --repin
moved docker/Dockerfile:1 node:22-bookworm-slim sha256:c3de60bf2f9d... -> sha256:5e1d2c7a90b3...
1 reference(s) moved; 0 unchanged.
```

It reads the Dockerfiles `release.images` names, or the files given after `--repin`, and moves every `name:tag@sha256:<digest>` in them, `ARG` defaults included. A `FROM` by tag alone is left for a person to pin the first time. A run with nothing to move writes nothing and says so. `--check` writes nothing and exits 1 when a reference would move, and `--json` prints `moved`, `unchanged`, `failed` and `written`, so a scheduled job can open a pull request with the change. It reads with a pull-only token, using `OCI_USERNAME` and `OCI_PASSWORD` or the docker config's login for a private registry, and asks anonymously otherwise. A tag it can't resolve leaves its digest and exits 1.

Outside a release, the docker lexicon's [DKRD021](/chant/lexicons/docker/lint-rules/#dkrd021--from-names-a-base-by-tag-not-by-digest) runs the same rule on generated Dockerfiles once a project turns it on.

## The scan before the stage

A publish stages every target before it reveals any, but staging is not private: an `oci` target pushes the image's layers, manifest and referrers by digest, and anyone can pull it by digest from then on. So the scan runs first, before any target stages and before anything is signed, on what each target would put out:

- each `oci` target's image, from its local archive (which `chant release images` already checked against the release's digests), through an SBOM syft makes from the image's layers;
- the SBOM each `forge` target attaches beside its assets, goreleaser and nfpm files among them;
- the SBOM each npm package carries, or, for a package with none, one written from the member's lockfile.

Each SBOM goes through the gate a component's `vuln-gate` step runs, with the project's `vulnPolicy` in `chant.config.ts`: `failSeverity` (default `critical`), `fixableOnly`, `failOnKev`, the EPSS thresholds, and the VEX files `vexSources` names. A finding the policy blocks stops the publish with `publish-scan-failed` and the list of findings, and nothing reaches a registry: no layer, manifest or referrer. Fix the dependency or the base image and build the release again, or record a VEX statement when the finding is not exploitable.

The scanner is grype, or trivy with `vulnPolicy.scanner: "trivy"`, and syft makes an image's SBOM. A publish finds them in `CHANT_GRYPE`, `CHANT_TRIVY` and `CHANT_SYFT`, else on `PATH`, and is refused (`publish-scan-tool-missing`) without them. The workflow `chant release workflow` renders installs grype and syft at versions pinned by SHA-256, on GitHub, GitLab and Forgejo and in a train's jobs, with nothing to add to `release.workflow`. `chant release doctor` reports a missing scanner before a cut: a warning on a workstation, a failure in CI.

The scanner downloads its vulnerability database on first use, which needs the network. For a job without it, `release.scan: { db: "<dir>" }` names a directory that already holds the database, and the scan reads it there without updating it.

What the scan found stays with the release:

- the publish record, `_releases/publishes.jsonl` on `chant/lifecycle`, gets a `scanned` or `scan-failed` line with the scanner, its database's version and build time, and every finding with what the policy made of it;
- each image gets a `scan.json` referrer beside its SBOM (`application/vnd.intentius.chant.scan.v1+json`) with the same findings for that image, so `oras discover` or `cosign tree` lists it under the image's digest.

To scan images with Wiz, set `release.scan: { "imageScanner": "wiz" }` in `chant.config.ts`. Each image goes through `wizcli docker scan` in place of grype, and its findings go through the same `vulnPolicy`, VEX files, record and referrer. syft still makes the image's layer SBOM, and the SBOMs forge assets and packages carry still go to grype or trivy, since Wiz scans images. The job sets `WIZ_CLIENT_ID` and `WIZ_CLIENT_SECRET` and puts `wizcli` on `PATH` (or names it in `CHANT_WIZCLI`); without them the publish stops with `publish-scan-tool-missing` and does not fall back to another scanner. chant reads the results `wizcli` writes as SARIF: a finding's advisory is the rule id, its severity the `security-severity` property (else the SARIF level), and its package, version and fix the result's `packageName`, `packageVersion` and `fixedVersion` properties.

`release.scan: true` turns the scan on without the group.
