import { Aside } from '@astrojs/starlight/components';

Each open pull request can get an environment of its own, named `pr-<n>` after its number ([#4298](https://github.com/INTENTIUS/chant/issues/4298)). The environment is derived from a template environment you already declare, such as `staging`. A job applies the pull request's components to it once someone approves the plan, and another job tears it down when the pull request closes. The teardown removes only what carries that environment's ownership marker.

A pull request's environment is not a release target. Releases come from green commits (ws-104), and `chant components promote` refuses `pr-<n>` as the target or the source (`packages/core/src/cli/handlers/promote.ts:903`).

## Declare the template

Name the template in `chant.workspace.json`:

```json
"ci": {
  "prEnvironment": { "template": "staging", "ttl": "72h" }
}
```

`ttl` is how long an environment lives after its last apply, as `90m`, `72h` or `7d`. It is 72h when absent (`packages/core/src/workspace/declaration.ts:1301`). The jobs read the block from the declaration at the pull request's base, never from the pull request (`packages/core/src/cli/handlers/pr-env.ts:170`). A pull request cannot name another template or a longer TTL for itself, and one that adds the block gets no environment until it merges. Set `minReader` to 0.124.42 or newer with the block.

## Make the project's resources say which environment they belong to

The teardown selects on the ownership marker each lexicon stamps on what it creates, so the marker has to name `pr-<n>`. The `chant.config.ts` below does that.

```ts
export default {
  environments: ["local", { name: "staging", endpoint: "http://localhost:4566" }, "prod", "pr-*"],
  ownership: { stack: "shop", env: { param: "env" } },
  buildParams: { env: { type: "string", env: "CHANT_ENV", default: "local" } },
};
```

`pr-env up` refuses to run when the marker could not tell the environment's resources apart from any other (`packages/core/src/components/pr-environment.ts:175`):

- `ownership.stack` is unset, so nothing carries a marker.
- `ownership.env` is a literal. Every resource would carry that literal, so the build parameter form is required (`packages/core/src/components/pr-environment.ts:179`).
- The config declares environments and does not declare the template, or does not cover `pr-<n>`, which `"pr-*"` does (`packages/core/src/components/pr-environment.ts:191`).
- The config declares `pr-<n>` outright. That environment is the project's, not a pull request's (`packages/core/src/components/pr-environment.ts:198`).

The job sets the build parameter that `ownership.env` reads to `pr-<n>` (`packages/core/src/cli/handlers/pr-env.ts:188`). It also sets `CHANT_ENV` to `pr-<n>` and `CHANT_ENV_TEMPLATE` to the template's name, so a component that sizes itself by environment can read the template (`packages/core/src/cli/handlers/pr-env.ts:185`).

The environment takes the template's declared endpoint, unless a `pr-*` entry declares one of its own (`packages/core/src/components/pr-environment.ts:202`). Point the template at an emulator and every pull request's environment goes there too.

A component's site carries over as well ([#4330](https://github.com/INTENTIUS/chant/issues/4330)). `pr-<n>` takes the runtime and lifecycle remote of a component's site in the template, as its `environments` declare it. A URL or domain carries over only when it names the environment with `{env}`, which becomes `pr-<n>`. A literal URL or domain is the template's own release, so it is left out (`packages/core/src/components/pr-environment.ts:219`). An entry the component declares for `pr-<n>` itself wins. The note shows each component's URL or domain in a Where column.

```ts
environments: [{ name: "staging", runtime: "fly", url: "https://shop-{env}.example.test" }],
```

## Generate the jobs

Add `--pr-env` to the pull-request pipeline:

```sh
chant build --components --generate github --pr-loop --pr-env
```

On GitHub and Forgejo the workflow's `pull_request` trigger then fires on close too, and a schedule starts the sweep. The plan job skips the close event. The table lists the jobs the flag adds.

| Job | Runs on | Command |
|---|---|---|
| `env-up` | an opened, updated or reopened pull request | `chant components pr-env up --base "$BASE_SHA" --pr "$PR_NUMBER" --no-push` |
| `env-post` | after `env-up`, from the target branch's commit | `chant components pr-env post --pr "$PR_NUMBER" --head "$HEAD_SHA" --forge <forge>` |
| `env-down` | a closed pull request, from the base branch's checkout | `chant components pr-env down --pr "$PR_NUMBER" --reason closed --forge <forge>` |
| `env-sweep` | the schedule, hourly at minute 17 | `chant components pr-env sweep --forge <forge>` |

`env-up` runs the pull request's code, so it holds no forge token while it does, as the plan job holds none ([#4295](https://github.com/INTENTIUS/chant/issues/4295)). Its permissions are `contents: read` (`lexicons/github/src/components/generate-pipeline.ts:492`). A checkout script alone sees the job's token, every later step starts without the token variables, and the `pr-env up` step runs last and hands its report and record on as the job's outputs (`lexicons/github/src/components/generate-pipeline.ts:485`). On GitLab the job's script drops the tokens on its first line (`lexicons/gitlab/src/components/generate-pipeline.ts:515`). `env-post` runs none of the change's code. It takes the report and record back, keeps the record on `chant/lifecycle`, and posts the note and the `chant/pr-env` status with the token.

`env-up` and `env-down` share a concurrency group per pull request, so a close waits for an apply still running. `env-down` checks out the base branch, since a closed pull request's merge ref can be gone (`lexicons/github/src/components/generate-pipeline.ts:549`).

On GitLab, `env-up` starts a GitLab environment `pr-<iid>` whose stop job is `env-down`, so the environment's Stop button tears it down (`lexicons/gitlab/src/components/generate-pipeline.ts:510`). GitLab starts no pipeline when a merge request closes. Create a pipeline schedule for the project, and `env-sweep` then tears down a closed merge request's environment (`lexicons/gitlab/src/components/generate-pipeline.ts:542`).

### The environment's cloud identity

With `ci.identity.cloud` declared, the environment's jobs take a cloud identity through the OIDC trade the plan job uses ([#4296](https://github.com/INTENTIUS/chant/issues/4296), [#4330](https://github.com/INTENTIUS/chant/issues/4330)). `env-up` applies, and it runs the pull request's code, so it gets the apply identity of a rule that names the pull request environments. A rule with no `environments` covers every environment, and it is never the one `env-up` gets (`packages/core/src/ci-identity.ts:323`). Give the pull request environments a rule of their own:

```json
"identity": { "cloud": { "aws": { "rules": [
  { "environments": ["pr-*"], "plan": "arn:aws:iam::000000000000:role/pr-plan", "apply": "arn:aws:iam::000000000000:role/pr-env" },
  { "environments": ["prod"], "plan": "arn:aws:iam::000000000000:role/prod-plan", "apply": "arn:aws:iam::000000000000:role/prod-apply" }
] } } }
```

`chant build --pr-env` resolves it for the member, matching each rule's globs against `pr-1` (`packages/core/src/cli/handlers/build.ts:167`). On GitHub and Forgejo, `env-up` then has `id-token: write`, and its first step trades the token before the change is checked out (`lexicons/github/src/components/generate-pipeline.ts:495`). Every later step starts without the forge token and the token request variables, so the change's code can request no other token (`lexicons/github/src/components/generate-pipeline.ts:485`). On GitLab the trade is the job's first line, and the same unset drops the forge tokens (`lexicons/gitlab/src/components/generate-pipeline.ts:515`). `env-down` and `env-sweep` trade for the same identity, since a teardown deletes what `env-up` created (`lexicons/github/src/components/generate-pipeline.ts:536`). `env-post` holds no cloud identity. With no rule that names the pull request environments, the jobs request no OIDC token.

There is one note per environment on the pull request. Each job keeps its report under `.chant/pr-env` as an artifact.

## Approve the environment's plan

`env-up` plans the components the change reaches into `pr-<n>`. A plan with changes applies only once an approval of its digest stands under gate `pr-env`, on the pull request's op (`packages/core/src/components/pr-env-run.ts:234`). Until then the job exits 3, and the note names the command:

```sh
chant approve pr-42 pr-env --plan <digest> --approver github:<you> --sign
```

The `ci.hooks` the other pull-request jobs run go around the plan and the apply here too, read at base (`packages/core/src/cli/handlers/pr-env.ts:199`). A failed `before-apply` hook stops the apply, and no record is kept (`packages/core/src/components/pr-env-run.ts:254`).

Run the job again, or push, once it is approved. A push that moves the plan needs a new approval. An empty plan applies with no approval, by the rule ws-104 gives an empty change set (`packages/core/src/components/pr-env-run.ts:234`).

<Aside type="caution">
`env-up` runs the pull request's code with the credentials the job gives it. Give the job credentials that reach only what a pull request's environment may touch, such as an emulator or an account set aside for previews. With `ci.identity.cloud`, that is the identity of the `pr-*` rule. On GitHub a forked pull request's job gets no secrets, so it has nothing to apply with.
</Aside>

`env-up` writes the apply's record to `pr-env-record.json` under `--no-push` (`packages/core/src/cli/handlers/pr-env.ts:136`). `env-post` checks it as data before it appends the line to `_pr-envs/records.jsonl` on `chant/lifecycle` (`packages/core/src/cli/handlers/pr-env.ts:316`). The record must name this pull request's `pr-<n>`, that marker env and the template the base declares. The commit, the actor and the expiry are the post job's own, so a change cannot keep its environment past the base's TTL (`packages/core/src/components/pr-environment.ts:520`). The line names the marker the teardown will select on. An apply that failed part way is recorded too, so what did apply is torn down with the rest.

## Run it by hand

Against an emulator, from the pull request's checkout:

```sh
chant components pr-env up --base origin/main --pr 42
chant approve pr-42 pr-env --plan <digest> --approver <you> --sign
chant components pr-env up --base origin/main --pr 42
chant components pr-env down --pr 42
```

By hand, `up` appends its record and pushes it. With `--no-push` it writes the record to `.chant/pr-env/pr-env-record.json` for `pr-env post` instead.

`chant ci run` also runs the environment's jobs ([#4330](https://github.com/INTENTIUS/chant/issues/4330)). It takes `env-up`, `env-post`, `env-down` and `env-sweep` from the same job list the generators use (`packages/core/src/workspace/ci-run.ts:730`):

```sh
chant ci run env-up --base <sha> --pr 42 --forge github
chant ci run env-down --pr 42 --forge github
```

`env-up` runs with every forge token variable left out of its steps, as the plan does (`packages/core/src/workspace/ci-run.ts:754`). Its `CHANT_ENV` is `pr-<n>` (`packages/core/src/workspace/ci-run.ts:250`). Once its steps settle, the runner runs `env-post` itself in a fresh checkout of `--base` (`packages/core/src/workspace/ci-run.ts:781`). That job holds the token and takes the report `env-up` wrote. It skips that with `--local` or `--in-place`, and without a token. A standalone `ci run env-post` takes `--head <sha>` and, on GitHub and Forgejo, `--result`. Each job's report lands under `.chant/pr-env`. A secrets file can give each of the four jobs its own list (`packages/core/src/workspace/ci-secrets.ts:41`).

## What the teardown removes

`pr-env down` reads the environment's record and runs the ownership check before it reads anything live (`packages/core/src/components/pr-environment.ts:359`). It refuses when:

- the record names another pull request,
- the record's marker names an environment other than `pr-<n>`,
- the config declares `pr-<n>` outright.

Then it plans the teardown under the record's marker, `{ stack, env: "pr-<n>" }`, through each lexicon's teardown capability. `planTeardown` drops a candidate whose marker differs (`packages/core/src/lifecycle/teardown.ts:126`), and `pr-env down` drops it again before anything is deleted (`packages/core/src/components/pr-environment.ts:376`). The template's resources carry `env: "staging"`, so they are never in the set.

A teardown that left something stays live: a failure, a lexicon with no teardown execution, or a part the plan could not read (`packages/core/src/components/pr-environment.ts:491`). The record says `incomplete`, and the next sweep tries again. The aws, k8s and fly lexicons execute teardowns today. For other lexicons the candidates are reported as skipped, as `chant lifecycle teardown` reports them.

## Tear down what no lexicon does

chant runs no Terraform, so the terraform lexicon has no teardown execution. Name a command that tears down such a copy, and `pr-env down` and `pr-env sweep` run it after the ownership check ([#4330](https://github.com/INTENTIUS/chant/issues/4330)):

```json
"prEnvironment": {
  "template": "staging",
  "teardown": { "name": "roots", "command": ["./scripts/pr-env-teardown.sh", "{stage}"], "lexicons": ["terraform"] }
}
```

The jobs read it from the declaration at the commit they check out, the base branch's (`packages/core/src/cli/handlers/pr-env.ts:341`). Set `minReader` to 0.124.45 or newer with it. chant runs the command twice, each time without the forge token variables (`packages/core/src/components/pr-env-run.ts:530`):

| Stage | `CHANT_PR_ENV_STAGE` | What the command does |
|---|---|---|
| owned | `owned` | Writes `{ "candidates": [...] }` to `$CHANT_PR_ENV_RESULT`. Each candidate has a `name`, a `type` and the `marker` `{ stack, env }` read back from it. |
| teardown | `teardown` | Deletes the candidates in `$CHANT_PR_ENV_CANDIDATES`, and writes `{ "outcomes": [...] }`, one `deleted`, `failed`, `not-prunable` or `retained` per candidate. |

The command also gets the variables in the table below.

| Variable | Value |
|---|---|
| `CHANT_PR_ENV` | `pr-<n>` |
| `CHANT_PR_NUMBER` | `<n>` |
| `CHANT_PR_ENV_STACK` | the marker's stack |
| `CHANT_PR_ENV_TEMPLATE` | the template |
| `CHANT_PR_ENV_COMMIT` | the commit last applied |
| `CHANT_PR_ENV_LIVE` | a JSON file with the components and their locations from the records |
 A candidate whose marker is not exactly `{ stack, env: "pr-<n>" }` is dropped before the teardown stage sees it, as a lexicon's is. A failed owned stage is a hole, and a candidate the teardown stage leaves out counts as failed, so the environment stays live. `lexicons` names the lexicons the command covers. Their own candidates are left out, so the terraform lexicon's skip does not leave the environment incomplete (`packages/core/src/components/pr-environment.ts:454`).

The command runs in the down job, which holds the forge token for the note. Keep it to the base branch's code.

## Review stacks for Pulumi programs

A `pulumi-up` step gets a stack of its own in `pr-<n>`, its review stack ([#4609](https://github.com/INTENTIUS/chant/issues/4609)). The step's stack keeps its organization and project, and its last part becomes `pr-<n>`, so `acme/shop/dev` applies as `acme/shop/pr-12` (`lexicons/pulumi/src/review-stack.ts:130`). A step with `reviewSuffix: "web"` applies `pr-12-web` instead.

Before the first preview the step runs `stack init <pr-stack> --no-select --copy-config-from <stack>` (`lexicons/pulumi/src/pulumi-up.ts:635`). A stack that exists already is previewed and updated. The config comes from the template when it names a stack of the same project, and from the step's own stack otherwise (`lexicons/pulumi/src/review-stack.ts:160`).

The template can be a Pulumi stack, `<project>/<stack>`, as plywood's `review_stacks.template` is:

```json
"ci": {
  "prEnvironment": { "template": "shop/dev", "ttl": "72h" }
}
```

The pulumi lexicon takes that form as one of its own stacks, so `chant.config.ts` needs no environment named `shop/dev` (`lexicons/pulumi/src/plugin.ts:89`, `packages/core/src/components/pr-environment.ts:192`). The ownership checks above still hold, and `"pr-*"` still has to be declared when the config declares environments.

The plan names the review stack's location, `<engine>:<dir>#<stack>`, and `pr-env up` keeps it on the record under `locations` (`packages/core/src/cli/handlers/pr-env.ts:286`). `pr-env down` and the sweep read it back and run `destroy --yes --json --stack <pr-stack>`, then `stack rm --yes --stack <pr-stack>` without `--force` (`packages/core/src/cli/handlers/pr-env.ts:360`). The up job ran the change's code, so each location is checked first. One that names a directory outside the project, a stack that is not `pr-<n>` of this pull request, or a form that does not read becomes a hole, and the environment stays live (`lexicons/pulumi/src/review-stack.ts:215`).

## Run it from a product of your own

A product that plans and applies with a tool chant does not run can take the gate, the records, the TTL, the ownership check and the sweep from chant, and supply the plan, apply and teardown itself. terragucci does this for Terraform roots under suffixed state keys. The functions are in `@intentius/chant/components/pr-env-run`:

| Function | What it does |
|---|---|
| `prEnvUp({ pr, head, template, ttl, stack, adapter, ports })` | Plans through `adapter.plan`, decides gate `pr-env` through `ports.decideGate`, applies through `adapter.apply` and keeps the record (`packages/core/src/components/pr-env-run.ts:185`). |
| `prEnvDown({ pr, reason, adapters, ports, commit })` | The ownership check, then the lexicons' and adapters' teardown (`packages/core/src/components/pr-env-run.ts:324`). |
| `prEnvSweep({ adapters, ports, commit })` | Runs `prEnvDown` for each environment whose TTL passed or whose pull request closed (`packages/core/src/components/pr-env-run.ts:392`). |

The ports chant itself uses are in `@intentius/chant/components/pr-env-ports`. `lifecyclePrEnvPorts({ forge })` reads and appends the records on `chant/lifecycle`, decides the gate from the ledger there, and posts the forge's note and status (`packages/core/src/components/pr-env-ports.ts:53`). They load the gate, Ajv and js-yaml, so they sit apart. A product that passes its own ports bundles `pr-env-run` without them, about 32 KB (`packages/core/src/components/pr-env-run-bundle.test.ts`).

The adapter's `apply` returns `locations`, where each component's copy lives, and the record keeps them. A teardown adapter, `PrEnvTeardownAdapter`, reads them back from `live.locations` in its `owned` half and answers each candidate with the marker its copy carries.

No gate holds a teardown. Closing the pull request is the decision, and so is the TTL the base set.

## The sweep

`pr-env sweep` tears down each live environment whose TTL passed (`packages/core/src/components/pr-env-run.ts:403`). With `--forge` it also asks whether each pull request is still open, and tears down the environment of one that closed or merged (`packages/core/src/components/pr-env-run.ts:406`). A forge that cannot answer leaves the TTL in charge.
