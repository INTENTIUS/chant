Two pull requests that change the same component can each be approved against the estate as it is. Whichever applies second then applies a plan made before the first one landed. Target locks stop that ([#4293](https://github.com/INTENTIUS/chant/issues/4293)). The first pull request to plan a component holds it, and the second gets a failing `chant/lock` status until the first merges or closes. [`chant lock`](/chant/cli/lock/) is the reference for every flag below.

This page assumes the [generated pull-request pipeline](/chant/guide/pull-request-ci/) already runs.

## Turn locks on

Set `ci.locks` in `chant.workspace.json`:

```json
"ci": {
  "locks": "plan"
}
```

`plan` makes the plan take the locks, through the generated lock job. `apply` leaves the plan alone. Then only `chant lock` and an [apply before merge](/chant/guide/apply-before-merge/) take locks ([#4301](https://github.com/INTENTIUS/chant/issues/4301)). Under either value, `chant components pr-apply` refuses with `locked` when another open pull request holds a component it reaches, and applies nothing ([source](https://github.com/INTENTIUS/chant/blob/main/packages/core/src/cli/handlers/pr.ts#L791)). It reads the field at base ([source](https://github.com/INTENTIUS/chant/blob/main/packages/core/src/workspace/ci-locks.ts#L15)), so the pull request that adds it does not lock yet. Set `minReader` to `0.124.36` or newer.

## The generated jobs

With `ci.locks: plan` in the declaration, `chant build --components --pr-loop --generate github` (or `forgejo`) writes two more jobs into the pull-request workflow ([source](https://github.com/INTENTIUS/chant/blob/main/lexicons/github/src/components/generate-pipeline.ts)). Regenerate the workflow after you set the field. Without `ci.locks` the workflow is unchanged.

| Job | Runs | Command |
| --- | --- | --- |
| `lock` | After the plan job succeeds | `chant lock --from-report .chant/pr/pr-plan.json --stage plan` |
| `unlock` | When the pull request closes | `chant unlock --pr <n>` |

The plan job runs the pull request's code, so it writes nothing to `chant/lifecycle`. Both new jobs check out the target branch's commit instead, so they run the target branch's `chant` and none of the pull request's code. The `lock` job takes the plan's report from the plan job's outputs and locks the components it selected. The `unlock` job needs no report. The workflow now also fires on `closed`, and the plan job skips that event.

Each new push to the pull request plans again and locks again. A component the new head no longer reaches is released ([source](https://github.com/INTENTIUS/chant/blob/main/packages/core/src/lifecycle/target-lock.ts#L281)). The unlock job tidies the file. Without it, a lock whose pull request closed still reads as released, because `--forge` asks GitHub whether each holder is open ([source](https://github.com/INTENTIUS/chant/blob/main/packages/core/src/lifecycle/target-lock.ts#L285)).

A held pull request does not lock again on its own when the holder merges. Re-run its lock job, or push to it.

A fork's pull request gets a read-only token, so its lock job cannot push `chant/lifecycle` and fails. Locks work for branches of the repository.

To block the merge of a pull request whose components another one holds, make `chant/lock` a required status in the branch protection rule.

Forgejo gets the same jobs from the same generator. On GitLab the commands are the same, but the pipeline does not write the jobs yet. Run `chant lock` in a job that checks out the target branch and has the plan job's `.chant/pr` as an artifact, with `--forge gitlab`.

## See who holds what

```sh
npx chant lock --list
```

```
app	pull request 12	plan	alice	2026-10-22T10:00:00.000Z
net	pull request 12	plan	alice	2026-10-22T10:00:00.000Z
```

## Release a stuck lock

A pull request that is abandoned but left open keeps its locks until someone releases them with `chant unlock`.

```sh
npx chant unlock --pr 12
```

`chant unlock --pr 12 net` releases one target only. The next run of the other pull request's lock job then takes it.

## Lock by hand

`chant lock` also takes a lock with no plan behind it, for example to hold a component during an incident:

```sh
npx chant lock net --pr 31 --by alice
```

A later plan of pull request 31 keeps that lock as it is, so the plan job cannot drop it ([source](https://github.com/INTENTIUS/chant/blob/main/packages/core/src/lifecycle/target-lock.ts#L293)).
