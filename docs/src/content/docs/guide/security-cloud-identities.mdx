The plan job of a [pull-request pipeline](/chant/guide/pull-request-ci/) runs the pull request's code. If it holds the identity the apply uses, a pull request can change the cloud before anyone approves it. `ci.identity.cloud` gives the plan and the apply an identity each, per cloud ([#4296](https://github.com/INTENTIUS/chant/issues/4296)). The plan job trades its OIDC token for the plan identity before the change is checked out. After that no step of the job holds a token or can ask for one.

The three clouds AWS, GCP and Azure, and Pulumi Cloud's access tokens, are covered on the three forges. It is off until the block is in the declaration, and no security group turns it on.

## Declare the identities

Each cloud takes a list of rules. Each rule has `environments` and `members` globs and two identities, `plan` and `apply`. `chant build --pr-loop` takes the first rule that matches the pipeline's environment and member (`ruleFor` in `packages/core/src/ci-identity.ts:217`). Leave out `environments` to match every environment. Leave out `members` to match every member, and also a pipeline outside a member.

```json
"ci": {
  "identity": {
    "cloud": {
      "aws": {
        "region": "eu-west-1",
        "rules": [
          { "environments": ["prod"], "plan": "arn:aws:iam::111111111111:role/prod-plan", "apply": "arn:aws:iam::111111111111:role/prod-apply" },
          { "environments": ["staging-*"], "plan": "arn:aws:iam::222222222222:role/staging-plan", "apply": "arn:aws:iam::222222222222:role/staging-apply" }
        ]
      },
      "gcp": {
        "provider": "projects/123/locations/global/workloadIdentityPools/ci/providers/forge",
        "rules": [{ "plan": "plan@acme.iam.gserviceaccount.com", "apply": "apply@acme.iam.gserviceaccount.com" }]
      },
      "azure": {
        "tenantId": "<tenant id>",
        "rules": [{ "members": ["app"], "plan": "<plan client id>", "apply": "<apply client id>" }]
      }
    }
  }
}
```

A rule whose plan and apply are the same identity is refused with `declaration-invalid`. So is a rule that plans as an identity another rule applies as (`cloudIdentityProblems`, `ci-identity.ts:416`). Either would let the change's code act as an apply identity. chant 0.124.41 is the first reader, so set `minReader` to it.

Then regenerate each member's pipeline with the flags it was generated with:

```bash
chant build --components --generate github --pr-loop --env prod --output .github/workflows/chant-pr.yml
```

A workspace has one pull-request pipeline per member and environment. Each member's apply jobs hold that member's apply identity alone, so a rule per member keeps one member's apply from reaching another's state.

## Give targets inside a member their own identities

A member can hold several targets, such as Terraform roots or the runs of an Op wave. A rule with `targets` covers only the targets its globs match ([#4332](https://github.com/INTENTIUS/chant/issues/4332)). In a target glob `*` matches within one `/` segment, `**` across segments and `?` one character, as the terraform lexicon reads unit globs (`targetGlobMatch`, `ci-identity.ts:158`). A target takes the first rule that covers its environment, its member and the target (`ruleFor`, `ci-identity.ts:217`). Put the rules with `targets` before the member's own rule, since a rule with no `targets` covers every target. A Terraform root matches a target glob by its key in `terraform.roots` or by its directory relative to the project, and the first rule either name matches wins.

```json
"aws": {
  "rules": [
    { "members": ["infra"], "targets": ["envs/prod/**"], "plan": "arn:aws:iam::111111111111:role/prod-plan", "apply": "arn:aws:iam::111111111111:role/prod-apply" },
    { "members": ["infra"], "targets": ["envs/staging/**"], "name": "staging", "plan": "arn:aws:iam::222222222222:role/staging-plan", "apply": "arn:aws:iam::222222222222:role/staging-apply" },
    { "plan": "arn:aws:iam::333333333333:role/plan", "apply": "arn:aws:iam::333333333333:role/apply" }
  ]
}
```

The plan job's trade then lists the member's own plan role and, before it, each rule's plan role with its globs (`resolveCloudIdentity`, `ci-identity.ts:268`). The trade asks for one OIDC token per cloud and trades it for each of them (`ci-identity.ts:509`). The job's own credentials go in the job's environment as before. Each role's credentials also go in a file of mode 0600 under `RUNNER_TEMP` or `TMPDIR`. The variable `CHANT_CLOUD_TARGETS` holds the file's path (`ci-identity.ts:534`). The file holds plan credentials only, since no rule may plan as what a rule applies as.

A tool that runs one target calls `targetCloudEnv(process.env, target)` from `@intentius/chant/ci-identity` and runs with the environment it returns (`ci-identity.ts:583`). It swaps each cloud's variables for those the target's rule names. A target that no rule with `targets` covers keeps the job's own, and without the file the environment comes back unchanged. The module has no dependency and bundles to about 18 KB (`packages/core/src/ci-identity-targets.test.ts`).

An apply runs in one job per apply role, so no job holds the apply tokens of two targets that apply as different roles. `cloudIdentityGroups(decl, env, member, targets)` groups the targets that take the same roles in every cloud (`ci-identity.ts:329`). A group takes its rule's `name`, or a name from its first glob (`envs/prod/**` gives `envs-prod`). The targets no such rule covers are the group `default`. `cloudIdentityWave` turns the groups into an Op wave's `cloud` and `jobs` (`ci-identity.ts:365`):

```ts
import { cloudIdentityWave } from "@intentius/chant/ci-identity";

const roots = ["envs/prod/net", "envs/staging/net", "shared/dns"];
const wave = { name: "wave-1", runs: roots.map((target) => ({ target })), ...cloudIdentityWave(decl, "prod", "infra", roots) };
```

The deciding job trades for every plan role of the wave's targets, and each group's job for its own apply roles. On GitHub and Forgejo each such job gets `id-token: write` and starts with the trade, ahead of its checkout (`lexicons/github/src/components/generate-op-waves-pipeline.ts:98`). Each later run step starts with an `unset` of the token request variables (`generate-op-waves-pipeline.ts:183`). On GitLab the job takes an `id_tokens:` entry per cloud and its script starts with the trade (`lexicons/gitlab/src/components/generate-op-waves-pipeline.ts:121`). With one group the wave keeps its one job, which trades for that group's apply roles.

The pull-request pipeline applies a member in one job. With `--apply-on-merge` or `--apply-before-merge`, `chant build --pr-loop` refuses a member whose targets apply as more than one role in a cloud (`packages/core/src/cli/handlers/build.ts:156`). Apply such a member through Op waves; its plan and record jobs still trade for every plan role as above. A declaration whose rules set `targets` or `name` needs chant 0.124.45 or newer as its `minReader`.

## Preview and up with separate Pulumi Cloud tokens

A Pulumi program logs in to Pulumi Cloud with an access token. Under `ci.identity.cloud.pulumi` the plan and record jobs trade the job's OIDC token for a preview credential and the apply jobs for an up credential, through Pulumi Cloud's OAuth exchange ([#4549](https://github.com/INTENTIUS/chant/issues/4549)). The pull request's program previews with the preview credential and never sees the up one, and no long-lived Pulumi secret sits in the forge's secrets.

```json
"ci": {
  "identity": {
    "cloud": {
      "pulumi": {
        "organization": "acme",
        "rules": [
          { "environments": ["prod"], "plan": "team:prod-preview", "apply": "team:prod-deploy" }
        ]
      }
    }
  }
}
```

An identity names the access asked for. `team:<name>` asks for a team's, `user:<login>` for a person's, and `organization` or `organization:admin` for the organization's (`pulumiTokenRequest` in `packages/core/src/ci-identity.ts`). Any other value is refused with `declaration-invalid` at that rule. The OIDC audience defaults to `urn:pulumi:org:<organization>`; set `audience` to change it. `apiUrl` points the trade at a self-hosted Pulumi Cloud, and then the trade sets `PULUMI_BACKEND_URL` to it as well. Rules, targets and the job split work as they do for the clouds.

In Pulumi Cloud, register the forge as an OIDC issuer of the organization and give it two authorization policies: the pull request's subject may get the preview credential, and the protected branch's subject may get the up one. The trade only asks; those policies decide. A declaration that sets the block needs chant 0.124.55 or newer as its `minReader` (`PULUMI_CLOUD_IDENTITY_FLOOR`).

A SQL member on Azure Database for PostgreSQL signs in with an Entra token for the database's own scope, and the ARM token above is for another scope. With `"database": true` on `ci.identity.cloud.azure`, the trade makes a second grant per identity for that scope (`AZURE_DATABASE_SCOPE` in `packages/core/src/ci-identity.ts`) and sets the result as `AZURE_DATABASE_ACCESS_TOKEN`. The sql lexicon's `entra` token source reads that variable before it tries `az`, so the job's image needs no Azure CLI. AWS and GCP need no extra setting, because `rds-iam` signs its token with the traded AWS keys and `cloud-sql-iam` signs in with the traded Google access token. Older chant releases refuse the key, so a declaration that sets `database` also sets `minReader` to chant `0.124.55` or newer (`AZURE_DATABASE_TOKEN_FLOOR`).

## Which job takes which identity

| Job | Identity | Runs |
|---|---|---|
| `plan` | plan | the pull request's code |
| `plan-note` | none | the target branch's commit |
| `record` | plan | the merged commit |
| `apply`, `apply-wave-<k>` | apply | the newest green commit |
| `env-up` | apply, of a rule that names `pr-*` | the pull request's code |
| `env-down`, `env-sweep` | apply, of the same rule | the base branch's commit |
| `env-post` | none | the target branch's commit |

The environment jobs come with `--pr-env` ([#4330](https://github.com/INTENTIUS/chant/issues/4330)). A rule that names no `environments` is skipped for them (`packages/core/src/ci-identity.ts:323`), so a catch-all apply identity never reaches a pull request's code. See [an environment per pull request](/chant/guide/pr-environments/#the-environments-cloud-identity).

The plan, record and apply jobs get `id-token: write` on GitHub and Forgejo (`withIdToken` in `lexicons/github/src/components/generate-pipeline.ts:290`). Forgejo's dialect keeps that one permission. Each job's first step is the trade, ahead of its checkout (`generate-pipeline.ts:293` and `:362`). On GitLab the same jobs take an `id_tokens:` entry per cloud, and the trade is the first line of the script (`lexicons/gitlab/src/components/generate-pipeline.ts:384`).

## What the trade does

The trade is a script run with `node -e` from `/`, so it reads none of the checkout's files and needs nothing installed (`TRADE_JS`, `ci-identity.ts:487`). It gets one OIDC token per cloud with that cloud's audience. The token comes from the forge's request URL on GitHub and Forgejo, and from the `id_tokens` variable on GitLab (`ci-identity.ts:498`).

| Cloud | Trade | Variables it sets |
|---|---|---|
| AWS | STS `AssumeRoleWithWebIdentity` (`ci-identity.ts:509`) | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_REGION` |
| GCP | Google's STS token exchange, then IAM `generateAccessToken` for the service account (`ci-identity.ts:517`) | `GOOGLE_OAUTH_ACCESS_TOKEN`, `CLOUDSDK_AUTH_ACCESS_TOKEN` |
| Azure | Entra's client credentials grant with the token as the client assertion (`ci-identity.ts:526`) | `AZURE_ACCESS_TOKEN`, `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and the `ARM_` spellings |
| Pulumi Cloud | the OAuth exchange at `<apiUrl>/api/oauth/token`, asking for the identity's type and scope | `PULUMI_ACCESS_TOKEN`, and `PULUMI_BACKEND_URL` when `apiUrl` is set |

On GitHub and Forgejo the trade appends the variables to `GITHUB_ENV` and masks each secret in the job's log (`ci-identity.ts:539`). GitLab's script sources a file of `export` lines and then deletes it. The file sits outside the project directory with mode 0600. A value with a space, a newline or anything outside printable ASCII is refused, so a reply cannot add a variable of its own (`ci-identity.ts:493`). The minted token is written nowhere.

terragucci leaves Azure untraded, since the azurerm provider takes only the OIDC token. chant trades it, so the plan job holds an ARM access token and no token another client could be traded for. A tool that needs the OIDC token itself cannot plan under this block.

## What the change's code can reach

After the checkout, every step of the plan job starts again without the forge tokens and without the variables a token is requested with (`OIDC_REQUEST_VARS`, `ci-identity.ts:443`, dropped at `generate-pipeline.ts:358`). Those are `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, `ACTIONS_ID_TOKEN_REQUEST_URL` and GitLab's `CHANT_ID_TOKEN_<CLOUD>`. The way the step starts again is the forge token handover's ([Keep the Forge Token From the Plan](/chant/guide/security-forge-token-handover/)). On GitLab the same `unset` line covers both (`gitlabTradeLines`, `ci-identity.ts:562`). The plan job's file names no apply identity.

The tests run the generated jobs against a local emulator of the token URL and the three clouds (`packages/core/src/__fixtures__/oidc-emulator.ts`). `lexicons/github/src/components/generate-pr-pipeline.identity.test.ts` runs the GitHub plan job step by step. Each later step tries to request a token and prints what it sees. The plan credentials are there and the apply identity is not. No step holds a token or a request variable, and the emulator mints nothing after the trade. The GitLab test does the same with the plan script.

## Trust each identity to its job

The trade only asks. The cloud decides whom to answer, so each identity's trust has to name its job.

| Forge | Plan identity trusts | Apply identity trusts |
|---|---|---|
| GitHub | the subject `repo:<owner>/<repo>:pull_request` | the subject `repo:<owner>/<repo>:ref:refs/heads/<branch>`, which the push and green runs carry |
| GitLab | the merge request pipeline's claims | the protected target branch's `ref` and `ref_protected` claims |
| Forgejo | the pull request's ref | the target branch's ref, the one claim its token has |

Never trust an apply identity to the pull request's subject.

`chant ci forge-check` reads each identity's live trust and lists every subject it admits beyond its jobs ([chant ci](/chant/cli/ci/#ci-forge-check)). For Pulumi Cloud it reads the organization's OIDC issuers and their policies. The record job plans the merged commit with the plan identity, so the check expects the plan identity's trust to admit the default branch's subject as well as the pull request's.

<Aside type="caution" title="A pull request can edit its own workflow">
On every forge a pull request from the repository can change the workflow file. A changed plan job could skip the drop, but its token still carries the pull request's subject. The apply identity's trust is what refuses it, so check that trust before you rely on the split.
</Aside>

## What it does not cover

The plan job still holds `CHANT_RUNNER_KEY` when the pipeline signs its runs. `chant ci run` and `chant ci serve` use the host's own credentials and trade nothing. GitHub gives a pull request from a fork no OIDC token, so its plan job fails at the trade.
