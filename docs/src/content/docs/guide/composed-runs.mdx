A composed run is how chant handles a pull request that changes a component and one that reads its output. chant names the components the change reaches, plans them together, binds one digest, takes one approval and applies in one run, passing each new value on to the components that read it. It belongs to chant, not to a lexicon. Each lexicon takes part in the way its own plan and API allow ([ws-108](https://github.com/INTENTIUS/chant/blob/main/docs/design/decisions/ws-108-how-each-lexicon-composes.md)).

A value another component creates in the same run has no value when the plan is made. A reader of it is planned in one of three ways.

1. A group. The capability plans and applies several components in one call ([ws-107](https://github.com/INTENTIUS/chant/blob/main/docs/design/decisions/ws-107-a-capability-plans-and-applies-a-group.md)). The value reaches its readers inside the same apply, with no later round.
2. A preview. The capability plans the waiting component with stand-ins for the unknown values and keeps the plan's shape. After the upstream applies, the real plan is compared with that shape. If it matches, the round is covered by the first approval.
3. A hole. The component is not planned until its upstream has applied. The note shows `inputs from <component>; re-checked on apply`, and the round needs an approval of its own.

## Where a composed run applies

Groups form in the pull-request run (`pr-plan`, `pr-apply`, `pr-env`), and at promote too. Under the default `trunk-curated` workflow a merge deploys nothing, and `chant components promote --release` deploys, so the release gate's plan forms the same groups by the same rule ([#4465](https://github.com/INTENTIUS/chant/issues/4465)). Each group plans with one `planGroup` call, its digest is folded into each member's part of the release gate's change set, and the promote applies it with one `runGroup` call, with no round between its members. The promote prints a line per group with its members, its wave and its digest, then how each member ended. A promote that stopped part way through a group writes its resume record, and running the same promote again plans only the members that did not apply, as a smaller group where they still join.

`chant components fan-out` and `chant run --components` form the same groups. Neither plans before it applies, so each group plans in its wave against the outputs standing then, and applies at once.

Under `--wave-gate` no group forms, at promote or in a fan-out. Each wave is planned component by component, so every component that would have joined a group falls back with kind `wave-gate` and the run goes wave by wave as before.

A member of a group has one step, gates counted, so it has no gate of its own. At promote, the release gate is decided at the gates of the other components the promote deploys.

| `gcp-apply` | gcp | hole | none | no preview on the REST APIs `gcpApply` writes to; Config Connector and Infrastructure Manager preview through their own controllers, which chant does not use | `planGcpResources` reads each resource and decides it with `decideResource`. `GcpApplyStepInput` takes no values into resources: an upstream output can only fill `manifest`, `project`, `endpoint` or `stack`, all of which name the target. |
| `kubectl-apply` | k8s | hole | [#4467](https://github.com/INTENTIUS/chant/issues/4467) | server-side dry run (`dryRun=All`), which `plan` already uses against the live cluster | `KubectlApplyInput` takes no values into objects: an upstream output can only fill `manifest`, `stack`, `context` or `delete`, and a dry run needs a real cluster. `plan` does not read `unresolvedInputs` yet, so it plans against the missing value; #4467 makes it return a hole as the other two do. |

A hole becomes a preview when a step takes values into its resources. Until then none of the three is a group, since their applies write resource by resource and pass no value between members inside one call.

## A lexicon without a preview

A component whose capability has no preview, or no group, gets a hole. Its plan shows what is known and no more: the member lists `inputs from <component>; re-checked on apply` and the note shows `?` for its counts. Nothing the approval saw covers it, so no later plan of it is covered.

When the upstream has applied, the component is planned again against the real values. That plan needs an approval of its own, at the pull request's gate, or at `<gate>-round-<n>` in a promote. The first approval does not carry over. [Planned outputs and rounds](/chant/cli/components/#planned-outputs-and-rounds) states the round rule.

The other components of the change still plan together. A change can group the components that are eligible and plan the rest wave by wave, all under one approval through the covered rounds. The report's `groups` and `fallbacks` say which grouped and why the others did not. Components of another kind on a dependency path between two group members split the group, and only single-step deploys join one. [Groups planned and applied as one](/chant/cli/components/#groups-planned-and-applied-as-one) lists the fields.

A change set that looks empty while a group has reads it does not know yet is not passed without an approval.

## Nothing is atomic

A failure part way through a run leaves what applied, applied. chant rolls nothing back, and a lexicon's own locks stay the lexicon's. The report gives each member's outcome (`applied`, `partial`, `failed`, `not-started` or `no-changes`), and a resume plans only the members that did not apply, against the outputs the others applied with.
