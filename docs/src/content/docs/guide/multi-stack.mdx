A real estate outgrows one stack. chant's answer is **side-by-side stacks**: each stack is its own source directory, built by its own `chant build`, deployed on its own. You declare them once in `chant.config.ts` and the lifecycle commands treat them as the units they are.

There is a second, narrower mode — **child projects (nested stacks)** — where a parent template references a child it can deploy as a unit. That is lexicon-specific and comparatively rare. Reach for it only when you want the parent to own the child's deployment.

## Side-by-side stacks

Give each stack a directory. Build each one explicitly:

```
my-project/
├── chant.config.ts
├── src/
│   ├── networking/
│   │   ├── vpc.ts
│   │   └── subnets.ts
│   ├── compute/
│   │   ├── api-function.ts
│   │   └── worker-function.ts
│   └── storage/
│       ├── data-table.ts
│       └── assets-bucket.ts
└── dist/
    ├── networking.json
    ├── compute.json
    └── storage.json
```

```json
{
  "scripts": {
    "build:networking": "chant build src/networking --lexicon aws -o dist/networking.json",
    "build:compute": "chant build src/compute --lexicon aws -o dist/compute.json",
    "build:storage": "chant build src/storage --lexicon aws -o dist/storage.json"
  }
}
```

One `chant build` per stack, one output per stack. Nothing is inferred from the directory layout — the commands say what to build and where to put it, which is what makes each stack independently deployable and independently rebuildable.

### Declare them

Tell chant the set, so the lifecycle commands stop assuming one stack per environment:

```typescript
// chant.config.ts
import type { ChantConfig } from "@intentius/chant";

export default {
  lexicons: ["aws"],
  stacks: [
    { name: "networking", src: "src/networking" },
    { name: "compute", src: "src/compute" },
    { name: "storage", src: "src/storage" },
  ],
} satisfies ChantConfig;
```

Each entry names the deployed stack and the source it is built from. `region` is available too, for an estate spread across several.

With `stacks` set, `chant lifecycle snapshot` and `chant lifecycle diff` iterate every stack — building each `src` scoped so its logical ids match what that stack actually deploys, and observing each against its own live stack name. Without it, chant assumes a single stack named after the environment.

`chant graph` uses the same declaration: it builds each stack's source in isolation, qualifies node ids as `<stack>::<id>` so they line up with what observation reports, and groups them under `groups.byStack` so a viewer can draw one boundary box per stack.

### Cross-stack references

A resource in one stack refers to a resource in another through an ordinary TypeScript import. chant resolves it into the provider's own cross-stack mechanism — CloudFormation `Export`/`ImportValue`, and each lexicon's equivalent elsewhere.

The graph IR surfaces both halves so a viewer can draw the edge: `exports` carries what a stack publishes (name plus producing node), `imports` carries what it consumes. Match an import's `name` to another stack's export `name`.

For apply ordering, `chant graph --stacks` computes the dependency graph between stacks — every producer before its consumers.

## Child projects (nested stacks)

A **child project** is a subdirectory that builds to a separately-valid template and is referenced explicitly from a parent file. Unlike side-by-side stacks, the parent is aware of the child: it uses a lexicon-specific function like `nestedStack()`, passes parameters in, and reads outputs back. Cross-stack values are declared explicitly with `stackOutput()`.

Use this when you want one deployable unit that carries its children — not when you want independent stacks. For independent stacks, use side-by-side.

```
my-project/
├── src/
│   ├── app.ts            ← parent resources + nestedStack() call
│   └── network/          ← child project
│       ├── vpc.ts
│       ├── security.ts
│       └── outputs.ts    ← stackOutput() declarations
└── dist/
    ├── template.json             ← parent (AWS::CloudFormation::Stack)
    └── network.template.json     ← child (standalone template)
```

## A note on directory auto-partitioning

Earlier versions of this guide described a mode where a single `chant build src` detected subdirectories and emitted one stack per directory automatically, plus a `manifest.json`.

**`chant build` does not do that.** It partitions by *lexicon* — a project declaring `aws` and `k8s` produces one output per lexicon — and writes to the single path you give it with `-o`. Subdirectories carry no meaning to it. Every multi-stack example in this repository builds side by side, one explicit `chant build <dir>` per stack, which is why the guide now leads with that.

If you have a project written against the old description, nothing has changed underneath you: it was never auto-partitioning. Give each stack its own build command and add a `stacks` entry.

See [Multi-Stack Output](/chant/serialization/multi-stack/) for the serialization-level detail.
