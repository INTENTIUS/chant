The plan job of a [pull-request pipeline](/chant/guide/pull-request-ci/) runs the pull request's code. It synthesizes the components and runs their capabilities' plans. With `--pr-build` it builds and lints, and its hooks run too. A token that can post a note or set a status can also push. So since [#4295](https://github.com/INTENTIUS/chant/issues/4295) no step that runs that code holds a forge token, and a fresh job posts the plan. The order of the steps is terragucci's `handover.ts`.

This is on in every pipeline chant generates. It is in the [security features](/chant/reference/security-features/) table as a listed exception, like the environment allowlist, and no group turns it on.

## Regenerate the pipeline

Run the command the pipeline was generated with again, and commit the file:

```bash
chant build --components --generate github --pr-loop --env prod --output .github/workflows/chant-pr.yml
```

The plan job's report now reaches the forge through a second job, `plan-note`. The note job runs the chant of the target branch's commit, and that commit's `chant` has to have `components pr-post`. So on the pull request that brings the regenerated pipeline, the note job can fail where the target branch's chant is older. The next pull request posts.

A pipeline generated before #4295 still works. Its plan job holds the token, so `chant ci run plan --in-place` leaves every token out of the plan's steps. Once they settle it posts the note itself and warns to regenerate (`planPoster` in `packages/core/src/workspace/ci-run.ts:819`).

Since [#4328](https://github.com/INTENTIUS/chant/issues/4328) the plan job on GitHub and Forgejo no longer gets the `CHANT_RUNNER_KEY` secret (`packages/core/src/components/pr-pipeline.ts:364`), and on GitLab the plan note moves out of the merge request pipeline. Regenerate for both.

## What the plan job does on GitHub and Forgejo

1. It checks the change out with a script in place of `actions/checkout`, whose post step runs at the job's end with the token as its input. The job's token reaches the script's fetches through the environment and never the git config (`checkoutScript` in `packages/core/src/ci-handover.ts:205`). While it holds the token it also fetches `chant/lifecycle`, which the plan reads the approval from (`ci-handover.ts:229`).
2. Every later step starts by running its shell again without the token variables (`dropForgeTokens`, `ci-handover.ts:79`). Unsetting a variable leaves it in the shell's own starting environment, which a child process can read on Linux from `/proc/<pid>/environ`. A shell that cannot start again unsets them. The variables are those of `FORGE_TOKEN_VARS` (`ci-handover.ts:40`), from `GITHUB_TOKEN` and `ACTIONS_RUNTIME_TOKEN` to chant's own `CHANT_FORGE_TOKEN`.
3. The plan step is the job's last (`lexicons/github/src/components/generate-pipeline.ts:327`). A step after it would start beside whatever the change's code left running, with what it wrote to `GITHUB_ENV` and `GITHUB_PATH`. So there is no artifact upload, no cache save and no checkout post step. Lines the generator's `extraScript` option adds run inside the plan step. The step hands `.chant/pr` on as the job's outputs when it ends, failed or not (`handoverTrap`, `ci-handover.ts:162`). GitHub keeps a job's outputs to 1 MB and Forgejo each output to 1 MiB, so a report too large is cut to `pr-plan.json` and `pr-note.md` (`HANDOVER_LIMITS`, `ci-handover.ts:98`).
4. The job's token may only read: its `permissions` are `contents: read` (`generate-pipeline.ts:346`).

The `plan-note` job (`generate-pipeline.ts:350`) needs the plan job and runs when it passed or failed. It checks out the target branch's commit, `github.event.pull_request.base.sha` (`generate-pipeline.ts:335`), and runs your `--before-script` lines. Then it takes the report back from the plan job's outputs, keeps it as the `chant-pr-plan` artifact, and runs `chant components pr-post`. Its token may write pull requests and statuses, and read Actions runs. With that read `pr-post` asks when each scheduled watch or reconcile Op last ran, a check the plan job has no token for ([#4289](https://github.com/INTENTIUS/chant/issues/4289)). The Ops are read at the target branch's commit. Forgejo's dialect drops the `permissions` blocks, which its runner ignores.

## What the plan job does on GitLab

GitLab builds a merge request pipeline from the merge request's own `.gitlab-ci.yml`, so whatever the merge request wrote runs there, and nothing there may hold the token. Make `CHANT_FORGE_TOKEN` and `CHANT_RUNNER_KEY` protected CI/CD variables. GitLab then gives them only to pipelines of protected branches and tags, and never to a merge request pipeline.

In the merge request pipeline, the plan's script still starts by unsetting the token variables (`lexicons/gitlab/src/components/generate-pipeline.ts:426`), which drops `CI_JOB_TOKEN` and any token you left unprotected. The plan keeps `.chant/pr` as its artifact.

A pipeline of the target branch, which GitLab builds from that branch's files, runs the `plan-note` job (`generate-pipeline.ts:430`). Its rule is a pipeline that a schedule, a person or a trigger started with `CHANT_PLAN_NOTES` set to `1` (`gitlabPlanNotesRule`, `generate-pipeline.ts:357`). A merge request pipeline's own trigger job starts a pipeline whose source is `pipeline`, which the rule leaves out. The note job's command is `chant components pr-post --open`, which does this for each open merge request into the branch (`postOpenPlanReports` in `packages/core/src/pr-post.ts:202`):

1. GitLab names the merge request's head and the newest pipeline at that head in this project, and `pr-post` takes that pipeline's plan job (`mergeRequestJobs` in `packages/core/src/pr-forge.ts:1452`). A merge request whose pipeline ran in a fork's project is left out.
2. A plan job that has not settled waits for the next run. So does one whose result is already posted: the `chant/plan` status links to the plan job, and a status that links to it is that job's result (`pr-post.ts:219`).
3. For the rest, `pr-post` reads `pr-plan.json` from the plan job's artifacts (`pr-post.ts:225`) and posts the note and the status, as the note job does on GitHub.

Add a pipeline schedule to post the notes:

1. Under **Settings > CI/CD > Variables**, set `CHANT_FORGE_TOKEN` (and `CHANT_RUNNER_KEY` if the pipeline signs its runs) as protected and masked.
2. Under **Build > Pipeline schedules**, add a schedule of the target branch with the variable `CHANT_PLAN_NOTES` set to `1`. A merge request's note comes on the first run after its plan job settles, so pick a cron as often as you want notes, such as `*/5 * * * *`.

The pull request environment's `env-sweep` job runs on every schedule but this one (`generate-pipeline.ts:560`).

<Aside type="caution" title="What GitLab still gives the plan job">
GitLab's own checkout keeps `CI_JOB_TOKEN` in the remote's URL, and that token cannot write notes. An unprotected CI/CD variable still reaches the merge request pipeline. The plan's unset keeps it from the plan's later lines, but the value stays in the shell's starting environment on Linux.
</Aside>

## What the note job trusts

The pull request's code wrote the report, so the note job reads it as data (`packages/core/src/pr-post.ts`). The pull request, the head, the environment and the member come from the event, never the report. A report that names another fails the status and posts no note (`readPlanReport`, `pr-post.ts:66`). The note is rendered again from the report, and every `<!--` after its marker line becomes `&lt;!--`, so the note carries no hidden marker but its own (`planNoteFor`, `pr-post.ts:92`). A plan job that failed fails the status whatever the report says (`pr-post.ts:140`).

`chant ci run plan` on your own host keeps the same rule. No step of the plan gets a forge token from the host, `--pass-env`, a secret or the job (`packages/core/src/workspace/ci-run.ts:758`). The plan's `pr-plan` runs with `--no-status` (`packages/core/src/components/pr-pipeline.ts:360`), and `ci run` posts from the report once the steps settle. Like `pr-post`, it adds the scheduled Ops that stopped running to the note. It reads them from a fresh checkout of `--base`, not from the checkout the change ran in, in place or not (`overdueAtBase`, `ci-run.ts:869`). The steps run as the same user as `ci run`, which started with the token, so give a host runner only repositories whose authors you trust, as [`ci serve`](/chant/cli/ci/#ci-serve) says.

## What it does not cover

- The plan job holds no `CHANT_RUNNER_KEY`, so the plan's run record is unsigned. The record and apply jobs still sign theirs. The plan job's cloud credentials are its own unless `ci.identity.cloud` splits them, as [Plan and Apply as Separate Cloud Identities](/chant/guide/security-cloud-identities/) describes.
- The `chant` the plan job runs is whatever the image or your `--before-script` puts on the path. When that is the pull request's own `node_modules`, the pull request chooses it, as it chooses the rest of its code.
- On every forge a pull request from the repository can change the workflow file itself. A reviewer sees that change; the handover covers the code a reviewer is less likely to read.

The apply before merge (`--apply-before-merge`) runs the pull request's head with the job token and `CHANT_RUNNER_KEY`. A comment or a target branch pipeline starts it, and `pr-apply` checks the approval before any of the head's code loads. On GitLab the `env-post` job of a pull request environment still runs in the merge request pipeline and posts with `CHANT_FORGE_TOKEN`, so with the token protected it posts nothing.
