This guide is for a team that wants to hear when a wave waits for an approval or a run goes wrong, without watching the pipeline. chant posts one event, `chant.notify/v1`, to chat incoming webhooks (Slack and Microsoft Teams) and to a webhook of your own. The webhook's copy is signed so the receiver can check it came from your pipeline.

Op waves send these events when their spec says where. Products built on chant send the same event through `@intentius/chant/notify`, and each decides when to send.

## Name the webhooks

Add `notify` to the [Op waves](/chant/guide/op-waves/) spec. Each value is the name of an environment variable. The spec never holds a URL or a key, and chant never prints either.

```json
{
  "name": "migrations",
  "op": "migrate",
  "plan": ["./bin/plan", "{target}", "{plan}"],
  "waves": [{ "name": "prod", "runs": [{ "target": "prod" }] }],
  "notify": {
    "slack": "CHANT_SLACK_WEBHOOK",
    "teams": "CHANT_TEAMS_WEBHOOK",
    "webhook": "CHANT_WEBHOOK",
    "key": "CHANT_WEBHOOK_KEY",
    "events": ["waiting", "refused", "failed"]
  }
}
```

| Setting | The variable holds |
|---|---|
| `slack` | A Slack incoming webhook's URL |
| `teams` | A Teams incoming webhook's URL (a Workflows webhook that takes an Adaptive Card) |
| `webhook` | Your own receiver's URL. It needs `key` |
| `key` | The shared secret the webhook's events are signed with |
| `relay` | The key `chant notify relay` checks buttons with. Set, a waiting wave's Slack message has Approve and Decline buttons, and its Teams card the reply that approves |
| `events` | Not a variable: the events to send. Default: all of them |

A value that looks like a URL, a webhook without a key, or an unknown setting fails the spec before any wave runs.

## Put the secrets in the pipeline

On GitHub and Forgejo, `chant run --generate` maps each variable `notify` names from the repository secret of the same name. Create one secret per variable, with the same name. A value in the generator's `options.variables` takes precedence over that mapping. On GitLab, add them as masked CI/CD variables of the project; GitLab passes them to every job.

## What each wave job sends

| The job | Exit | Event |
|---|---|---|
| A wave waits for an approval of its digest | 3 | `waiting`, with the targets, the digest, the `chant approve` command and the run's link. Under `pr-review`, the pull request whose review would approve it |
| A share job refuses a run whose plan moved since the decision | 4 | `refused`, naming the runs it refused |
| A plan, an apply or a stage hook fails | 1 | `failed`, naming the runs or the hooks that failed, or the error |

A share job of a waiting wave sends nothing, because its deciding job already did. The exception is a share job that one of its own hooks holds, which sends `waiting` naming the hook. A wave that applies sends nothing.

A delivery that fails is logged on stderr, without its URL, and the job exits with the code the wave decided. A 5xx answer or a network error is tried three times; a 4xx is not retried. The webhook is never posted to unsigned: with `key` unset, the job logs that and skips it.

## What the tick sends

[`chant ci tick`](/chant/cli/ci/#ci-tick) sends three events of its own when `ci.green` in the workspace declaration has `notify` ([#4645](https://github.com/INTENTIUS/chant/issues/4645)). It takes the same settings, with `events` chosen from these three and `ci.quarantine-passed`:

```json
"green": {
  "branch": "main",
  "phases": { "lint": ["lint"], "test": ["test"] },
  "require": ["lint", "test"],
  "notify": { "webhook": "CHANT_WEBHOOK", "key": "CHANT_WEBHOOK_KEY", "slack": "CHANT_SLACK_WEBHOOK" }
}
```

| The tick finds | Event |
|---|---|
| The branch's newest decided commit is red, after the one retry of a failed run (a phase being retried is pending, not red), or its green tag was revoked | `ci.red`, with the phase and the run that failed |
| A bisect names the first red commit below that one | `ci.culprit`, with `ci.culprit` the commit found |
| The newest decided commit is green, and an older one in the window was told red | `ci.green`, with `ci.red` the commit it answers |

The quarantine's scheduled run sends a fourth through the same `notify` ([#4677](https://github.com/INTENTIUS/chant/issues/4677)): [`chant ci quarantine report`](/chant/cli/ci/#the-scheduled-run) sends `ci.quarantine-passed` for each quarantined test that passed there, with `ci.quarantine` naming the test, its issue and `until`, and `run.url` the scheduled run. It is sent on every scheduled run the test passes in, until its entry goes, and needs no records.

Each of the tick's three is sent once. The tick marks it in the commit's `_ci/<sha>.json` record (`notified`), so it needs `chant/lifecycle`, and a tick that can't read or write the records sends nothing rather than the same event again. A delivery that fails everywhere is a warning, and the next tick tries again. `--dry-run` reports what it would send. The events carry `ci`: the `branch` and `commit`, and `phase`, `failedRun`, `culprit` or `red`. `run.commit` is the commit, and `run.url` is left out, since the tick's own run says nothing about it. [`ci workflow`](/chant/cli/ci/#ci-workflow) gives the tick's step each variable `notify` names from the repository secret of the same name, so create one secret per variable and run it again.

## Check a delivery

The webhook gets the event as JSON. The body is signed with HMAC-SHA256 over `<timestamp>.<body>`, where the timestamp is in seconds since the epoch:

| Header | Value |
|---|---|
| `x-chant-signature` | `sha256=<hex>` |
| `x-chant-timestamp` | The seconds the signature covers |
| `x-chant-event` | `waiting`, `refused`, `failed`, `drift`, `ci.red`, `ci.culprit`, `ci.green` or `ci.quarantine-passed` |
| `x-chant-delivery` | The event's `id` |

`@intentius/chant/notify-verify` checks a delivery and needs nothing but `node:crypto`. The package ships it, and `@intentius/chant/notify`, as compiled JavaScript, so a receiver can import it under plain Node with no TypeScript loader, or bundle it alone:

```ts
import { verifyWebhook } from "@intentius/chant/notify-verify";

const checked = verifyWebhook({ body: rawBody, headers: req.headers, key: process.env.CHANT_WEBHOOK_KEY });
if (!checked.ok) return reply(401, checked.reason);
handle(checked.event);
```

Pass the body exactly as received, before parsing it. `verifyWebhook` compares the signature in constant time and refuses a timestamp more than five minutes from now (`toleranceSeconds` changes that), so a delivery recorded and replayed later fails. The event's `id` is the same for every send of one event about one digest, so a receiver can also drop a re-run's repeat.

## The event

The JSON Schema ships in the package as `@intentius/chant/notify.schema.json`, with `$id` `https://intentius.io/chant/schemas/notify/v1/notify.schema.json`. Readers ignore fields they do not know; a field is only ever added within a version.

| Field | Meaning |
|---|---|
| `schema` | `chant.notify/v1` |
| `id`, `event`, `at` | The delivery id, what happened, and when it was sent |
| `source`, `project`, `summary` | The product that sent it (`chant`), the repository, and one line a person can read |
| `wave` | `{ number, name, gate }` for a product that applies in waves |
| `environment` | For a product that applies per environment |
| `targets` | What the event concerns: a wave's runs or roots, an environment's migrations |
| `digest`, `approve` | The plan digest an approval binds, and on `waiting` the command that approves it (`approve.command`, and `approve.review` under `pr-review`) |
| `status`, `reason`, `exitCode` | The product's word for the outcome, why it was refused or failed, and the exit code |
| `drift` | On `drift`: `changed`, `missing`, `failed` and a `fingerprint` |
| `ci` | On the tick's events: `branch`, `commit`, and `phase` and `failedRun` on `ci.red`, `culprit` on `ci.culprit`, `red` on `ci.green`; on `ci.quarantine-passed`, `phase` and `quarantine` (`test`, `file`, `issue`, `until`) |
| `run` | The CI run's `url`, `forge`, `repository`, `commit` and `pr` |
| `reportUrl`, `detail` | A report page, and the product's own outcome record carried whole |

## Send from a product

A product builds the event and sends it. `sendNotify` reads the URLs and the key from the environment when it sends, never throws, and returns one result per target:

```ts
import { makeNotifyEvent, sendNotify } from "@intentius/chant/notify";

const event = makeNotifyEvent({
  source: "sql-yodeler",
  event: "drift",
  summary: "prod drifted: orders changed",
  environment: "prod",
  drift: { changed: ["orders"], missing: [], fingerprint },
});
await sendNotify({ slack: "SLACK_WEBHOOK_URL", webhook: "YODEL_WEBHOOK_URL", key: "YODEL_WEBHOOK_KEY" }, event, { prefix: "x-yodel" });
```

`prefix` keeps a product's existing header names (`x-yodel-signature`), and `verifyWebhook` takes the same `prefix`. `render.slack` and `render.teams` replace the default Slack text and Teams card, for a product that adds its own buttons. `@intentius/chant/notify` reaches only `node:crypto` and the verifier, so a product's bundled CLI stays small.

## Under a product's words

A wave job run through a product's bin sends in the product's words ([#4610](https://github.com/INTENTIUS/chant/issues/4610)). The event's `source` is the product's name, so a receiver can route on `plywood` or `terragucci`. The summary uses the product's apply verb, and the signed webhook's headers take the prefix `x-<product>`. A waiting wave's event carries the product's approve command, with chant's own command in `approve.chant`. The schema stays `chant.notify/v1`. Under chant's own words the event and the headers are as before.

The `notify` slot of the words changes three of these:

| Slot | Default | Use |
|---|---|---|
| `notify.source` | the product's name | sql-yodeler passes `sql-yodeler`, the name its receivers already filter on, while its product word is `yodel` |
| `notify.wave` | `wave {k} ({name}) of {spec}` | how a summary names a wave; `({name})` is dropped for a wave with no name |
| `notify.headers` | `x-<product>` | the header prefix the receiver verifies with |

A product that sends its own drift notice builds it with `driftNotifyFields(words, { changed, failed, fingerprint })` from `@intentius/chant/ci-product`, which gives `2 stacks drifted: shop-dev, shop-prod` under plywood's noun. `productSendOptions(words)` gives the header prefix to pass to `sendNotify`.

## Approve from chat

`chant notify relay` turns a click on a waiting wave's Approve button into an approval on the ledger ([#4611](https://github.com/INTENTIUS/chant/issues/4611)). Run it from a checkout of the repository, as a container or a function in your own cloud, with the same key the pipeline maps into the `relay` variable:

```bash
CHANT_RELAY_KEY=... SLACK_SIGNING_SECRET=... chant notify relay
```

The Slack app's interactivity requests go to the path `/slack` on the relay. A Teams outgoing webhook posts to `/teams` when a person mentions the relay and replies with the line the card shows. By default the relay listens on port 8787 of the loopback address, so only the proxy or function host in front of it reaches it; `CHANT_RELAY_HOST` and `CHANT_RELAY_PORT` change that.

Each click passes these checks before anything is written:

| Check | Refused when |
|---|---|
| The chat signature | Slack's `v0` signature or the Teams HMAC does not verify, or a Slack request is more than five minutes old |
| The button | The relay key did not sign it, or the event is older than `CHANT_RELAY_MAX_AGE` seconds (default a day) |
| The clicker | No line of the signers file at base lists `slack:<team>/<user>` or `teams:<aad object id>` beside a principal, the line names the relay, or the clicker made the gated request |
| The digest | No standing pending fact at the button's gate asks for that digest: the plan moved, or someone approved it already |

Then the relay records the approval as `chant approve <op> <gate> --plan <digest> --actor <principal> --relayed-by <relay>` would, with every rule that command applies. The relay holds no signing key, so a gate that `identity.gates` seals refuses it. A Decline click records nothing and says in the thread who declined. The approval is recorded as relayed by `CHANT_RELAY_PRINCIPAL`, by default `<product>-relay`, and the replies use the product's words. The relay starts no job, and the resume job applies the wave once the approval stands.
