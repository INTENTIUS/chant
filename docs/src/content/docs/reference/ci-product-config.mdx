terragucci, plywood and sql-yodeler each read a config file of their own (`terragucci.yml`, `plywood.yml`, `yodel.config.ts`) and map it onto the same chant mechanisms. This page holds the key for each setting, its value words, and the chant field it maps to, so a setting has one spelling in every product. The same table ships in code as `PRODUCT_CONFIG_WORDS` from `@intentius/chant/ci-product`, with `productConfigProblems`, which checks a product's config against it ([Checking a config](#checking-a-config)).

## How keys are spelled

- A key is written here in snake_case and dotted, as a YAML config spells it. A TypeScript config spells each part in camelCase: `approval_rules.<rule>.not_author` is `notAuthor`, `evidence.runner_key_secret` is `runnerKeySecret`. A hyphenated part keeps its hyphen in both, as `respond.wave-refused` does.
- `<name>` in a key stands for any key of a map, and `[]` for any item of a list.
- Value words are lower case and hyphenated: `on-destructive`, `pr-review`, `pull-request`.
- `off` turns a response off. A setting that is absent is off, and a key added to this page is off until a config sets it.
- A key ending in `_secret` names the forge secret (or GitLab CI/CD variable) holding a credential, such as a model key, OTLP headers or a webhook's URL. A key ending in `token_env` names the variable holding a forge token. The value is the name, and the credential itself is never written in the config.
- A duration is a whole number and a unit, `m`, `h` or `d`: `30m`, `48h`, `3d`. A schedule is a five-field cron line under a `schedule` key.
- Settings for one environment sit under `environments.<name>`, keyed by the environment's name.
- Where a value names a stage of the pull request pipeline, it takes the product's own stage word from its [words](#stage-words): terragucci and sql-yodeler say `plan` and `apply`, plywood says `preview` and `up`. So `locks.when` is `plan` in one product and `preview` in another, and `runner` takes a map of `default` and the stage words.

## Environments and stages

A stage is an environment in promotion order. A release cut from what the first environment applied moves through the rest in that order, each behind its own gate.

| Key | Sets | Value | chant |
|---|---|---|---|
| `environments.<name>` | an environment's settings, keyed by the environment's name | a map per environment | the names in `environments` of the member's `chant.config.ts` |
| `promotion` | the order a release moves through the environments, first to last | a list of environment names | `environments` in the member's `chant.config.ts`, in order, which `promotionOrder` reads and `chant components promote` follows |
| `forge_environments.<glob>`, `environments.<name>.forge_environment` | the forge deployment environment the jobs of the members a glob matches run in | a name, or `{ name, url }` | a wave's `environment` in the op-waves spec |

`promotion` is its own key in every product. It lists each environment once, with no patterns, and in a product with an `environments` map every name it lists is a key of that map. The product writes the list into the member's `chant.config.ts` `environments`, which is where `chant components promote` reads the step before `--to`. sql-yodeler's `waves` already lists one environment per wave in order, and sql-yodeler reads that order as its promotion order.

In plywood, `environments` maps a stack glob to a forge deployment environment. That map is `forge_environments` here, and the promotion order is `promotion`.

### Promote, roll back and redeploy

A product's bin passes these words to `chant components`, so each product's release commands read the same:

| Command | chant | Words |
|---|---|---|
| `<product> promote --to <env> [--release <label>]` | `chant components promote` | `--to` is the environment deployed to. `--from` defaults to the environment before it in `promotion`. `--release` is a release's label or digest, and the deploy reads that release's templates for `--to`. |
| `<product> rollback <env> --release <label>` | `chant components rollback` | the environment is the positional, and `--release` names the earlier release it goes back to |
| `<product> redeploy <env>` | `chant components redeploy` | deploys the release the environment runs now |
| `<product> reject <op> <gate> --plan <digest> --reason <text>` | `chant reject` | turns down the release a stage's gate waits on; `--reason` is one line, and `--sign` seals it |

Promote, roll back and redeploy take `--dry-run`, which prints the plan and changes nothing. A comment never records a rejection, as it never records an approval: a comment that types the product's `reject` word gets a reply with the reject line, `rejectLine` from `@intentius/chant/ci-product`, filled from the product's `reject` template. A promote that skips an environment of `promotion` is refused unless it passes `--allow-skip`. The words are `PRODUCT_RELEASE_WORDS` in code.

In plywood, `rollback --release <label> --env <env>` is the alias for the positional. The positional reads as an environment with `--release`, and names a stack without it, as in `plywood rollback <stack> --digest <d>`.

A product writes one component per member and puts each environment's target in its step's `environments` map, keyed by environment name. Before the step's capability sees its input, chant merges the entry for the run's environment over the step's own input, so `promote --to staging` applies the staging target and records it under staging, and `rollback` and `redeploy` pick the target of the environment they act on. An environment the map does not name is refused before anything runs, and the refusal lists the environments it names. A pull request's environment `pr-<n>` takes its template environment's entry.

```ts
{
  kind: "pulumi-up",
  dir: "infra/shop",
  environments: {
    dev: { stack: "acme/shop/dev" },
    staging: { stack: "acme/shop/staging" },
    prod: { stack: "acme/shop/prod" },
  },
}
```

A `terraform-apply` step sets `root` and `vars` the same way: `environments: { staging: { root: "envs/staging/network", vars: { region: "us-east-2" } } }`. The mechanism ships as `STEP_ENVIRONMENTS_KEY` and `componentsForEnvironment` from `@intentius/chant/components`, and a product feature-detects it on `STEP_ENVIRONMENTS_FLOOR`.

### Planning dependents again

When a member applies and an output another member reads comes out changed, that reader holds a value from before. Once a wave applied, its job runs the replan step for the runs it applied when `replanDependents` in the spec it read at base names one of them. The step digests each applied member's outputs and compares them with the digests the member's last apply recorded in `<env>/outputs.jsonl` on `chant/lifecycle`. Then it lists the members that read a changed output. Reads come from the places the waves are ordered by. A step's `stackOutput()` is one. A Terraform root's `terraform_remote_state` of another root is another, as is a Pulumi program's `StackReference`.

An output the engine marks sensitive (a Terraform output with `sensitive = true`) or secret (a Pulumi secret) gets no digest. The record names it, and it counts as changed every time its member applies, so its readers are listed on each apply. A digest of a short secret could be guessed back, and a Pulumi secret's value never reaches the job.

For a member that `replan_dependents` names, its dependents are planned as a pull request's members are planned. The plan waits at the gate `pr-apply-replan` under the op `replan-<env>`. The pending fact and the note both name the upstream member and the outputs that changed at that commit. The plan applies through the dependent's own pipeline once someone approves it at its gate, and the step itself applies nothing. When the key is unset, no step runs and the rendered jobs are the same files.

A pipeline whose applies run outside `chant run wave` runs the same step as a command after its apply: `chant components replan --env <env> --component <member>[,<member>]`, with `--gate` (default `pr-apply`) and `--op`. It reads `replanDependents` from `.chant/pipeline.ts` on the default branch.

```ts
stages: [{ name: "prod", waves: [/* ... */], replanDependents: ["network", "shared/*"] }]
```

The mechanism ships as `replanAfterApply` from `@intentius/chant/components`, and a product feature-detects it on `UPSTREAM_REPLAN_FLOOR`.

### Release artifacts

A stage names the values it publishes for each release under `environments.<name>.publish`, and a later stage names what it reads of them under `environments.<name>.reads`. The product maps both onto the stage's `publish` and `reads` in `.chant/pipeline.ts` with `pipelineFromConfig`, which renames a secret's snake_case keys (`aws_secrets_manager`, `json_key`) to the set's words. The [pipeline reference](/chant/reference/pipeline/#release-artifacts) gives the rules.

```yaml
environments:
  dev:
    publish:
      endpoint: { member: cluster, output: endpoint }
      db_password: { secret: { aws_secrets_manager: "arn:aws:secretsmanager:us-east-2:111111111111:secret:dev/db" } }
  staging:
    reads:
      TF_VAR_dev_endpoint: { stage: dev, artifact: endpoint }
control:
  repo: github.com/acme/control
  op: deploy
  release: true
```

### Cost estimate

The `cost` keys set one estimate for the plan note, the policy and the wave. A product writes them into the workspace declaration's `ci.cost`, which `pr-plan` and `pr-apply` read at base, and into the op-waves spec's `holds.cost`. The estimator runs once per member whose plan changes something, over the plan document its step wrote: `terraform show -json` for a `terraform-apply` member, the preview JSON for a `pulumi-up` member. `{planJson}` is that file and `{target}` the member. The note shows each member's monthly change and the sum, and the policy reads the same record as `input.cost`, with a wave's run's own figures as `input.cost.member`. `cost.approve_above` only adds approvals: a plan over it, or with a member the estimator could not price, needs an approval of its own digest, and a wave over it waits whatever its gate says. Nothing about the estimate lets a plan apply without an approval. With no `cost` keys, no estimate runs. The record and its note lines ship as `estimateCosts`, `costEstimateLines` and `policyCost` from `@intentius/chant/ci-product`, for a product that plans by itself and hands chant its own plan note (`PrPlanNote.cost`), and a product feature-detects them on `COST_ESTIMATE_FLOOR`.

### Change risk

The `risk` keys score each change from 0 to 1 and let the score ask for more approvals. A product writes `risk.approve_above` and `risk.questions` into the workspace declaration's `ci.risk`, which `pr-plan` and `pr-apply` read at base, and a stage's `risk` keys into its gate's `holds.risk` in `.chant/pipeline.ts`. The review agent answers each question on the pull request, and an answer over the question's `approve_above` asks for an approval as the score does. Over `approve_above`, a pull request's plan needs an approval of its own digest, and a stage's wave waits whatever its gate says and takes the stage's `risk.approval_rules` on top of its own: `{ count: 2 }` asks for a second approver, `{ count: 1, roles: [sre] }` for a named role. Below the score, the gate behaves as it does with no `risk` keys. With no `risk` keys, no score is made. How the score is made, reason by reason, is on [Change Risk](/chant/guide/change-risk/). The record and its note lines ship as `scoreChangeRisk` and `changeRiskLines` from `@intentius/chant/ci-product`, and a product feature-detects them on `CHANGE_RISK_FLOOR`.

A product that reads the hold, freeze, failure tolerance, stage approval rules and release keys writes them into the member's `.chant/pipeline.ts` with `pipelineFromConfig` and `pipelineSource` from `@intentius/chant/pipeline`, and its `ci --check` runs `checkPipelineFile`. See [Pipeline](/chant/reference/pipeline/).

#### Config and secret sets

Each environment has one set of config and secrets that its stage's jobs get as variables, under `environments.<name>` beside its targets. `config` holds plain values. `secrets` holds where each secret is kept, and the config file holds no secret: a forge secret's name (a GitLab CI/CD variable's on GitLab), or a map naming an AWS Secrets Manager secret (with `json_key` for one key of a JSON secret, and `region`), a Google Secret Manager secret (`projects/<project>/secrets/<secret>`, with `/versions/<version>` or the latest), or an Azure Key Vault secret's URL. Shared sets sit under `config_sets.<set>`, and `imports` lists the shared sets a set takes first, in order; the set's own values replace theirs. An environment's set imports shared sets, and no other environment's, so the staging set holds staging's values and the shared ones.

```yaml
config_sets:
  common:
    config: { LOG_LEVEL: info }
    secrets: { SENTRY_DSN: SENTRY_DSN }
environments:
  staging:
    imports: [common]
    config: { REGION: us-east-2 }
    secrets:
      DB_PASSWORD: STAGING_DB_PASSWORD
      API_KEY: { aws_secrets_manager: "arn:aws:secretsmanager:us-east-2:111111111111:secret:staging/api", json_key: key }
  prod:
    imports: [common]
    config: { REGION: us-east-1 }
    secrets: { DB_PASSWORD: PROD_DB_PASSWORD }
```

chant picks an environment's set with the lookup a step's `environments` uses, so a pull request's environment `pr-<n>` takes its template's set, and an environment the sets do not name is refused before anything runs. Each generator hands a stage's jobs that stage's set: the config as variables, the forge secrets as passed secrets, and the store secrets read in the job after its cloud login, with the identity `ci.identity` gives that stage, so a staging job reads what the staging identity may read.

- In a pipeline (`.chant/pipeline.ts`), `chant pipeline generate` gives the first stage's wave jobs the first stage's set and apply identity, and each later stage's promote job its own stage's.
- In an Op waves spec, each wave takes the set of the spec's `labels.Env`, or else of the wave's name. Before merge a wave's plan job runs the pull request's code with the wave's variables, so a set that holds secrets is refused there.
- In the pull request pipeline, the apply and record jobs take the set. The plan job runs the pull request's code and gets the config alone.

chant reads the sets from `ci.environmentSets` in the workspace declaration, beside `ci.identity`, in `chant build --pr-loop` and `chant pipeline generate`, and a product that calls the generators in process passes them as the `environmentSets` option. Each job also gets `CHANT_ENV_SET`, the set's record: every variable, the set it came from and the imports that led there, and for a secret the place it is kept, without its value. `chant ci run` redacts each secret the record names from the run's events, its record on the ledger, its report and the note posted from it, whatever the variable's name. On GitHub and Forgejo the store read masks each value before the runner prints a line.

The mechanism ships as `resolveEnvironmentSet` and `environmentSetJobInputs` from `@intentius/chant/components`, and a product feature-detects it on `ENVIRONMENT_SETS_FLOOR`.

### Refused wave summary

`respond.wave-refused: summary` turns the summary on, and the `agent.wave-refused` keys set the model it runs. The note holds the diff `diff` posts with a model's summary above it; a run past a limit, or one that fails, posts the diff alone and says the summary was skipped. Each summary is one run record under op `<product>-refused-wave` with its prompt digest and cost, and `max_runs` and `max_cost_usd` count those records over the last day. The command defaults to the review command with `--output-format json`, the key to `ANTHROPIC_API_KEY`, the timeout to 10 minutes. A product passes the keys as `waveSummary` of its op waves spec or pull request loop, and chant's generated apply and wave jobs carry them as `CHANT_WAVE_SUMMARY_*` variables with the model's key: on GitHub and Forgejo from the secret `key_secret` names, on GitLab as the CI/CD variable of that name. With `diff` or `off` the jobs carry none of them. The summary approves nothing and changes no exit code. A product feature-detects it on `WAVE_REFUSED_SUMMARY_FLOOR`.

## Checking a config

```ts
import { productConfigProblems, PRODUCT_CONFIG_WORDS_FLOOR } from "@intentius/chant/ci-product";

const problems = productConfigProblems(config, { product: "plywood" });
// [{ level: "warning", path: "respond.wave_refused", key: "respond.wave-refused",
//    message: "is accepted as respond.wave-refused, the vocabulary's key" }]
```

`productConfigProblems(config, { product, case, scopes })` reads the parsed config:

- each spelling of the table above that `product` accepts is a warning naming the key;
- a spelling set beside its key is an error;
- a value outside a key's words, or a secret name, URL, duration or cron line in the wrong form, is an error;
- `promotion` is an error unless it is a list of distinct environment names, each a key of `environments` when the config has that map.

`case: "camel"` reads a TypeScript config's camelCase keys, and `scopes: ["ci"]` also reads the keys under `ci`, as sql-yodeler keeps them. A key this page does not list is the product's own and is not read. `productConfigWord(key)` returns one row of the table. A product feature-detects all of this on `PRODUCT_CONFIG_WORDS_FLOOR`.
