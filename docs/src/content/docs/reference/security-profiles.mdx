A security profile is a name in the top-level `security` list of `chant.workspace.json`, beside the [security groups](/chant/reference/security-features/):

```json
{
  "name": "acme",
  "schema": 1,
  "security": ["fedramp-moderate"],
  "retention": { "changeSets": { "days": 90 }, "releases": { "days": 90 } }
}
```

A profile does not make a system compliant or authorised. It turns on chant's security features and reports what is missing from the records they produce, and those records are evidence toward the controls named below. The system owner implements the controls, and an assessor decides whether each is met.

A profile is named at the top level only, since its retention, gates and trust file cover the whole workspace. A member's own `security` list takes groups. A declaration that names a profile needs a chant that reads it, so it sets `minReader` to the release that carries `SECURITY_PROFILES_FLOOR`.

## Profiles

| Profile | Baseline | Groups it turns on | Retention at least | Scanner database at most | Check |
|---|---|---|---|---|---|
| `fedramp-moderate` | the FedRAMP Rev. 5 Moderate baseline (NIST SP 800-53 Rev. 5) | `verified-releases`, `supply-chain`, `who-ran-it`, `review-rules`, `isolated-runners` | 90 days | 24 hours | `WSP166` |
| `cccs-medium` | the CCCS Medium cloud profile (ITSG-33, which follows NIST SP 800-53 Rev. 4) | `verified-releases`, `supply-chain`, `who-ran-it`, `review-rules`, `isolated-runners` | 90 days | 24 hours | `WSP167` |

`fedramp-moderate` reads the FedRAMP Rev. 5 Moderate baseline, whose control ids are NIST SP 800-53 Rev. 5. `cccs-medium` reads the CCCS Medium cloud profile (ITSP.50.103 Annex B), whose ids come from ITSG-33 and follow SP 800-53 Rev. 4, so it has no SR family and no CM-14. The 90 days come from FedRAMP's AU-11 parameter (on-line for at least 90 days) and the 24 hours from its RA-5(2) parameter (within 24 hours prior to running scans). `cccs-medium` uses the same two numbers. Naming both profiles turns on the same groups, runs both checks, and takes the stricter number of each.

Each profile does three things.

- It turns on every security group. Each group's own check (`WSP161` to `WSP165`) reports what the group lacks, and every command that a group changes, such as `chant release publish` and `chant ci run`, behaves as it does under the group.
- `chant lifecycle gc` keeps change sets and releases for at least the profile's days. A longer `retention` is kept. A shorter one is not used, and gc says so. Run events are not covered, since they live in one clone.
- `chant release publish` and `chant workspace train publish` refuse a scan whose vulnerability database was built longer ago than the profile's hours, or whose build time the scanner does not report, with `publish-scan-db-stale`. The scan is recorded as `scan-failed` and nothing is staged. `release.scan.dbMaxAgeHours` in `chant.config.ts` sets a shorter bound, and sets one without a profile.

## Checks

`chant workspace check` reports each profile's findings under its own check: `WSP166` for `fedramp-moderate` and `WSP167` for `cccs-medium`, warnings by default. Each finding's message ends with the control ids it bears on, taken from the profile's baseline.

| Code | Reports | FedRAMP Moderate | CCCS Medium |
|---|---|---|---|
| `profile-retention-short` | `retention.changeSets.days` or `retention.releases.days` is unset or below the profile's days | AU-11 | AU-11 |
| `profile-gate-not-human` | `identity.gates.release`, or a gate an apply job names, is missing, names no class, names a class an agent, runner or service principal holds, or sets `agentPassesAlone: true` | AC-5, CM-3(4) | AC-5, CM-3(4) |
| `profile-scan-off` | a member's `chant.config.ts` sets `release.scan: false` | RA-5 | RA-5 |
| `profile-scan-db-unbounded` | `release.scan.db` is set with no `dbMaxAgeHours`, or `dbMaxAgeHours` is above the profile's hours | RA-5(2) | RA-5(2) |
| `profile-signing-off` | a member's `chant.config.ts` sets `release.signing: false` | SI-7, SR-11 | SA-10(1), SI-7 |
| `profile-signing-module` | a member signs images or forge assets keylessly or with `key`, and its `chant.config.ts` names no `CHANT_COSIGN`, so the upstream cosign build makes the signature | SC-13 | SC-13 |
| `profile-runner-key-eddsa` | `.chant/trust.json` lists an `ssh-ed25519` key under `runners` or `local.keys` | SC-13 | SC-13 |

`kms` mode passes `profile-signing-module`, since the KMS makes the signature and its own certificate is the one to read. So does a `CHANT_COSIGN` build named in the release config's `env` or `setup`. [Signatures and crypto modules](/chant/reference/crypto-modules/) lists what makes each signature.

Whether the forge refuses a force push to or a deletion of `chant/lifecycle` (AU-9) is a forge setting. `chant release doctor` reads it as `lifecycle-protected` under either profile, since a profile turns on `verified-releases` and `who-ran-it`.

## Controls

The table is printed from `SECURITY_CONTROLS` in `packages/core/src/workspace/security-controls.ts`, and a test compares the two. "yes" means the baseline selects the control, "-" that it does not, and "n/a" that the id is not in the catalogue the baseline uses. The Checks column names the `workspace check` codes, publish refusals and doctor checks that bear on the control.

| AC-5 | Separation of Duties | yes | yes | `ci.identity.cloud`, `_gates/<op>.jsonl`, `identity.gates.<gate>` with a `class`, `.chant/trust.json` | `profile-gate-not-human`, `security-review-not-required` |
