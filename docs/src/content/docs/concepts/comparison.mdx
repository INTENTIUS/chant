## What chant is

chant is typed infrastructure, end to end: a **compiler at its core** — TypeScript in, spec-native output out — with the lifecycle you choose built on top. You declare infrastructure as typed TypeScript objects, chant validates them against a lexicon's semantic rules, and emits the target format — CloudFormation, GitLab CI, or whatever the lexicon targets.

The build path is pure synthesis: parsing, type-checking, linting, and emitting artifacts, with no API calls and no state. Deployment and drift live one layer up, in the lifecycle you choose — observational diff, `cloud → code` reconcile, or gated `code → cloud` apply — built as durable Ops on that core rather than welded into it.

This isn't a reaction to other tools' failures — it's an approach that was always available. Nobody built it because the industry was racing to weld one lifecycle to the compiler. chant keeps the compiler deterministic and lets the lifecycle be yours.

For the model behind the rows below — the three axes of state and where each tool sits — see [Lifecycle Models](/chant/concepts/lifecycle-models/).

**The agentic angle:** the operational layer — deploying, monitoring, remediating — is increasingly handled by agents and automation. chant handles the part that should be deterministic and auditable: turning typed declarations into spec-native output. The two layers are complementary.

## Nobody sells you a lifecycle

Every infrastructure tool sells you a lifecycle. Synthesis, state, apply, drift, retire — owned end to end. A decade of investment goes into that lifecycle, into a better way to own it. The ownership is the product. That coupling is why a pure synthesis tool never existed. You could not get the compiler without the lifecycle welded to it.

chant sells nothing. Synthesis is pure and the output is native spec — standard CloudFormation, GitLab CI, whatever the lexicon targets. Walk away and there is nothing to unwind. That is the test the claim has to pass, and it is the one most tools fail. You can leave a thing you were never sold.

The lifecycle is still there when you want it. You write your own. Ops are declared as code in `*.op.ts` files and run on a local executor for one-shot work, or on [Temporal](/chant/concepts/durable-workflows/) when an apply needs to outlive a single process — approval gates, rollback, crash-resume. The durable version of what the others sell, for the lifecycle you chose rather than one chosen for you.

Decoupled first. Durable when you ask.

## Owning less

A pure synthesis core also owns less *machinery*. Because the build path makes no API calls, holds no state, and emits native spec, it needs little of the apparatus a full lifecycle pulls in at plan time — no provider SDKs, no state backend, no credentials, no network. What runs to turn source into output is a type-checker, an evaluator over a [static subset of TypeScript](/chant/concepts/typescript-as-data/), and the lexicon packages for the formats you target. That is the whole of it.

A smaller build-time surface is a smaller thing to audit, and a smaller blast radius if something upstream is compromised: fewer packages execute during synthesis, and none of them reach the network or your cloud credentials. This is a property of the architecture, not a security feature — it falls out of synthesis being side-effect-free. The same boundary is described value-by-value in [Where Values Come From](/chant/concepts/where-values-come-from/).

The scope is exact. This is the **build path**. The apply side is whatever lifecycle you brought — the CloudFormation CLI, a CI pipeline, an agent, [Temporal](/chant/concepts/durable-workflows/) — and it carries its own dependencies and its own surface. chant shrinks the build-time surface; it does not remove the apply-time one. Owning less is a build-time property, and only that.

## Paradigms

Configuration and infrastructure tools are grouped by several overlapping paradigms. Separating the terms makes the differences legible.

- **Infrastructure as Code (IaC)** — infrastructure managed from machine-readable definitions rather than manual steps.
- **Configuration as Code (CaC)** — configuration authored in a programming language, versioned and reviewed like code.
- **Configuration as Data (CaD)** — configuration represented as declarative data, separated from the code that transforms it, and inspectable without running a program.
- **Code as Data** — the source is statically evaluable: it has no side effects and yields the same result without being executed.

A tool can satisfy more than one.

| | IaC | Config as Code | Config as Data | Code as Data |
|---|---|---|---|---|
| **chant** | ✓ | ✓ | ✓ | ✓ |
| **ConfigHub** | ✓ | — | ✓ | — |
| **Formae** | ✓ | ✓ | ✓ | ✓ |
| **Terraform** | ✓ | ✓ | — | — |
| **CDK** | ✓ | ✓ | — | — |
| **Alchemy** | ✓ | ✓ | — | — |

chant is a static subset of TypeScript (code as data) that compiles to native spec (configuration as data). Because the source is not executed, it satisfies the code and data paradigms at once.

The other rows sit on one side of that line. **CDK** executes its source, so the configuration exists as the output of a program run rather than as data available beforehand. **Terraform** authors configuration in a DSL (HCL) that is evaluated with functions and applied against state, so it is code rather than inert data. **ConfigHub** keeps configuration as data in a store, which places it in the data paradigms and not the code ones. **Formae** reaches all four the way chant does, through Pkl, a dedicated configuration language that evaluates to data. Formae and chant differ on the language and the runtime model: chant compiles a subset of a general-purpose language (TypeScript) and you invoke the lifecycle you want, where Formae uses a purpose-built language and an always-on agent that observes and reconciles.

**[Alchemy](https://alchemy.run)** is the TypeScript-native tool on the executed side, and the one most worth naming explicitly: it is actively developed and its stated goal — infrastructure should feel like code, not configuration — is the same goal chant has. (Read against `alchemy@2.0.0-beta.74`, published under npm's `latest` tag as of this writing; the project ships fast pre-1.0 betas, so treat specifics as dated rather than fixed.) Its resources are [Effect](https://effect.website/) programs — Layers composed together and run inside a `Stack` — and the desired-state graph exists only once that program runs to produce it, which lands Alchemy in the same cell as CDK: code and configuration-as-code, not data. The disagreement with chant is narrower than "code vs. config": both agree infrastructure should feel like code; they disagree about whether that requires running it. Alchemy answers yes and gets composition, control flow, and Effect's type safety by executing resources as async programs. chant answers no and gets the same code-feel — autocomplete, go-to-definition, refactoring, cross-file references — from a statically evaluable subset, without executing anything. `typescript-as-data` is chant's answer to that question, not a rejection of Alchemy's.

The paradigms say where each tool sits. Underneath, the mechanics differ.

| | Authoring | Build model | Source of truth | Requires a store | Multi-cloud |
|---|---|---|---|---|---|
| **chant** | TypeScript (static subset) | Compiled | Source + live system | No | Yes |
| **AWS CDK** | TypeScript, Python, and others | Executed | CloudFormation | No (AWS-managed) | No |
| **Terraform** | HCL | Executed | State file | Yes (state file) | Yes |
| **ConfigHub** | YAML data | Stored | The store | Yes (database) | Yes |
| **Formae** | Pkl | Compiled | Source | No | Yes |
| **Alchemy** | TypeScript (Effect-based) | Executed | State store | Yes | Yes |

*Build model* is how source becomes the applied result: **compiled** (evaluated to data with no side effects), **executed** (run as a program, which can reach the environment and vary by run), or **stored** (configuration is already data in a store, applied by a worker). chant and Formae are the compiled, storeless pair, and differ in the authoring language: a subset of a general-purpose language versus a purpose-built one. ConfigHub keeps the data in a database. CDK, Terraform, and Alchemy execute their source. Alchemy's store is not a single mandatory backend — the default is a local `.alchemy/state/` directory, with a Cloudflare Durable Object/D1-backed store available for team or CI use — but a store is always required.

## Design decisions and their consequences

These tools make different design decisions. Each decision has consequences — some favorable for certain workflows, some not. This isn't a feature matrix; it's a comparison of architectural choices.

| Decision | Terraform | CDK | chant |
|---|---|---|---|
| **Language** | HCL (custom DSL) | TypeScript, Python, Java, Go, C# (executed) | TypeScript (static subset) |
| **Spec fidelity** | Provider-mapped | Abstracted (L2/L3) | Spec-true |
| **Output** | State + API calls | CloudFormation | Native spec output |
| **Lifecycle scope** | Full | Full (via CloudFormation) | Deterministic core + chosen lifecycle (observe / reconcile / apply) |
| **State model** | Authoritative | Authoritative (via CloudFormation) | No authoritative state file; precise change set via live projection + cloud-side ownership |
| **Reconciliation** | `code → cloud` | `code → cloud` | none / `code → cloud` / `cloud → code` (chosen per environment) |
| **Determinism** | Mostly | No (code executes) | Yes (for lint-conforming source) |
| **Walk-away cost** | High (state, HCL) | Medium (CloudFormation remains) | Zero (output is native) |
| **Semantic validation** | None built-in | None built-in | Built-in (lexicon rules) |
| **Drift detection** | Built-in (`plan` / `refresh`) | Via CloudFormation drift detection | Built-in (`lifecycle diff --live` against any of 5 cloud lexicons + 4 artifact lexicons) |

**Spec fidelity** means whether the tool's resource model matches the underlying spec 1:1. CDK's L2 and L3 constructs deliberately abstract away from CloudFormation — that's a feature for productivity and a cost for transparency. Terraform providers map closely but not identically to provider APIs. chant lexicons are generated directly from the target spec.

**Walk-away cost** is what happens if you stop using the tool. Terraform leaves you with a state file and tool-specific code. CDK leaves CloudFormation templates that continue to work. chant leaves native spec output — standard CloudFormation templates, GitLab CI files, whatever the lexicon targets. There's nothing chant-specific in the output.

## The execution model difference

The core architectural difference is what happens when you "run" each tool:

**Terraform:** HCL is parsed, a dependency graph is built, the provider checks current state against desired state, and changes are applied. The state file is the source of truth.

**CDK:** Your TypeScript *executes*. Constructors run, methods are called, side effects happen. The result is captured as a CloudFormation template, which is then deployed. The execution can be nondeterministic — same code, different environment, potentially different output.

**Alchemy:** Your TypeScript also executes, by design. Resources are Effect programs — Layers composed together and run inside a `Stack` — and the desired-state graph exists only once that run has produced it. Planning, applying, and destroying are separate CLI verbs, so there's a real preview step before anything changes; the graph the preview walks is still the output of a program run, not data that existed beforehand. This is an explicit design position, not an oversight — Alchemy's bet is that running the code is what buys composition, control flow, and Effect's type safety.

**chant:** by default, chant reduces your TypeScript directly from the AST to the resource objects it declares, executing none of it. Synthesis does nothing else. No API calls, no state, no deployment. Source outside that foldable subset falls back to being imported and run, per file; a separate evaluability lint pass (EVL) restricts source to literals, constants, and cross-resource references, so that executed result is equivalent to static data too. Same conforming source always produces the same output — see [Folded vs Run](/chant/concepts/typescript-as-data/#folded-vs-run).

This matters for:
- **Determinism** — chant's output is a pure function of its input. No environment variables, no network calls, no runtime state.
- **Auditability** — every value in the output traces to a specific line in the source.
- **Speed** — no interpreter, no runtime, no provider calls. Synthesis is fast.
- **IDE support** — because the API surface is defined by types (not runtime behavior), autocompletion, inline errors, and go-to-definition work without executing anything.
- **Agent-friendliness** — agents can generate chant source files and know exactly what output they'll produce. No surprises from execution-time behavior.

## State: authoritative vs. observational

The most consequential design difference after execution model is the lifecycle model.

**Terraform** treats state as authoritative — the state file IS the source of truth for what's deployed. This enables precise plan/apply workflows: the tool knows exactly what exists, what changed, and what to do. The cost is operational burden: state must be locked during operations, stored in a backend with access controls, and protected from corruption. Sensitive data (database passwords, API keys) ends up in state because the tool needs it for diffing.

**CDK** inherits CloudFormation's authoritative lifecycle model, which AWS manages as a service. Less operational burden, but the same architectural commitment: state is truth.

**Alchemy** looks the closest to chant's model on the surface — state defaults to local files in `.alchemy/state/`, in-repo, inspectable, no separate service (a Cloudflare-backed store is available for team or CI use) — but the role is different. Alchemy's `reconcile` step is documented as convergent: it reads live cloud state before deciding what to do, and can rediscover a resource by its deterministic physical name even without its prior state. Ownership is also read live — a provider returns `Unowned(attrs)` for a resource that carries someone else's tags, and by default that fails the run (`OwnedBySomeoneElse`) unless the operator opts in with `--adopt`. That narrows the gap with chant's live-projection model. What doesn't narrow: the stored state, not a live query, is still what tells Alchemy which resources exist and are eligible to be deleted on a plan — the same role a Terraform state file plays, with a lighter operational cost. Same storage mechanism as a chant snapshot; a different role. chant's snapshot is evidence that can be deleted between runs with no change in behavior. Alchemy's state store drives the plan.

**chant** is designed with an observational lifecycle model — snapshots record what was observed at a point in time, not what must be true now. It does not give up the precise change set, though: chant computes a create/update/delete plan against the live system using [cloud-side ownership markers](/chant/configuration/config-file/#ownership) rather than a hosted state file. What it drops is the *authoritative file*, and with it the costs:

- **No locking** — a stale snapshot is inconvenient, not dangerous
- **No sensitive data** — scrubbing is a design requirement, not a best-effort guideline
- **No corruption risk** — a bad snapshot doesn't break deployments. Agents verify against live APIs regardless
- **Minimal overhead** — state is designed to live in git alongside source code

**Trade-offs:**
- Ownership is answered by a live marker on the resource, so the projection must query live APIs; a resource with no marker is `foreign` and escalates to human review rather than being auto-deleted
- Git-based snapshots give versioning, portability, and offline access, but no locking, no encryption at rest, and no access control separation from source code

## What each tool optimizes for

**Terraform** optimizes for multi-cloud lifecycle management with a unified workflow. One tool, one language, one lifecycle model across AWS, Azure, GCP, and hundreds of providers. The trade-off: HCL is a custom DSL with limited expressiveness, and the state file creates operational overhead.

**CDK** optimizes for AWS-native development with familiar languages and high-level abstractions. L2/L3 constructs encode AWS best practices and reduce boilerplate. The trade-off: abstractions obscure what's actually deployed, and code execution means builds can be nondeterministic.

**chant** optimizes for typed, linted, deterministic synthesis that's true to the underlying spec, then lets you choose the lifecycle on top. The output is native to the target platform with zero lock-in. The trade-off: the build path itself doesn't apply — you deploy through a chant Op or hand the artifact to your own mechanism.

## Trade-offs

chant's design decisions have real consequences:

- **The build path doesn't apply.** Deployment runs one layer up — a chant Op (local or durable), the CloudFormation CLI, a CI pipeline, an agent. chant produces the artifact; an Op or your pipeline applies it. The build stays pure so that step is a choice, not a coupling.

- **Static evaluation means no runtime lookups at build time.** You can't call an API during synthesis to get a VPC ID or read a secret. Cross-resource references within a project work (via attribute references). For values that need to be resolved at deploy time, lexicons provide intrinsics. For values that need to be resolved before synthesis, agents or scripts can populate source files.

- **Lexicon ecosystem is young, but covering.** Twelve lexicons ship today (AWS CloudFormation, Azure ARM, GCP Config Connector, Kubernetes, Helm, Docker, GitHub Actions, GitLab CI, Forgejo Actions, Temporal, Fly Machines, and Fountain — Forgejo is a thin GitHub-Actions dialect). The architecture supports any spec-based operational domain — see [Lexicons](/chant/lexicons/overview/) for the current set and [Lexicon Authoring](/chant/lexicon-authoring/overview/) for adding new ones.

- **The static subset of TypeScript is a constraint.** No function calls, no control flow around resources, no dynamic property access. This is deliberate — it's what makes synthesis deterministic — but it means some patterns that work in CDK don't work in chant. See [TypeScript as Data](/chant/concepts/typescript-as-data/) for exactly what's supported.
