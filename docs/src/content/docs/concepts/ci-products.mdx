[terragucci](https://intentius.io/terragucci/) is pull-request automation for Terraform and OpenTofu, and [plywood](https://intentius.io/plywood/) is pull-request automation for Pulumi. Both run on chant's CI runtime and share its features as far as they can ([#4530](https://github.com/INTENTIUS/chant/issues/4530)). A team on either engine gets the same gates, approvals and records, in its own engine's words.

## Where a feature goes

A feature goes in the first of these homes that fits it:

1. chant CI core, when both products share it.
2. chant's [terraform](/chant/lexicons/terraform/) or [pulumi](/chant/lexicons/pulumi/) lexicon, when the capability belongs to one engine. Cone plans and Atmos reads live in the terraform lexicon and stack export in the pulumi lexicon, and each lexicon parses its engine's plans and drift and runs its apply.
3. The product. It holds its words and presets, its config defaults and init templates, and its docs.

Extending chant CI is the default. A feature stays inside one product only for a reason that belongs to its audience, such as a Terraform or Pulumi convention, and never for convenience.

Pulumi stacks plan and apply as components through the pulumi lexicon ([#4541](https://github.com/INTENTIUS/chant/issues/4541)), and Op waves plan and apply through chant's capabilities for both products ([#4545](https://github.com/INTENTIUS/chant/issues/4545)). The pulumi member reads its graph from the stack export the apply writes ([#4546](https://github.com/INTENTIUS/chant/issues/4546)) and follows StackReference targets between members ([#4547](https://github.com/INTENTIUS/chant/issues/4547)). The pull-request note and the exit codes are chant's too ([#4548](https://github.com/INTENTIUS/chant/issues/4548), [#4553](https://github.com/INTENTIUS/chant/issues/4553)), and so are the cloud identities ([#4549](https://github.com/INTENTIUS/chant/issues/4549)). One chant pipeline runs both products, and each product names its statuses and commands in its own words, `/terragucci apply` or `/plywood up` ([#4550](https://github.com/INTENTIUS/chant/issues/4550)).

## Records

Approvals and gate decisions go in the workspace [ledger](/chant/cli/ledger/), and so do overrides and the records of applies and runs ([#4551](https://github.com/INTENTIUS/chant/issues/4551)). A product keeps no record store of its own. Before a product adds storage for a record, check whether the ledger already holds it.

## The product pipeline

A product passes chant one object of words from `@intentius/chant/ci-product` and gets its pull request jobs from `productPipelineJobs`. terragucci's jobs and plywood's come from the same generator. The words fill fixed slots in chant's sentences.

| Slot | chant | terragucci | plywood |
|---|---|---|---|
| `product` | `chant` | `terragucci` | `plywood` |
| `stages.plan` and `stages.apply` | `plan` and `apply` | `plan` and `apply` | `preview` and `up` |
| `noun` | member | root | stack |
| `commands` | `apply` | `plan` `apply` `lock` `unlock` `agent` | `preview` `up` `lock` `unlock` |
| `approve` | `chant approve {op} {gate} --plan {digest} ...` | `terragucci approve {gate} --plan {digest} {sign}` | `plywood approve {gate} --plan {digest} {sign}` |
| `op` | the spec's | `tf-apply` | `pulumi-up` |
| `gateName` | `{gate}-wave-{k}` | `wave-{k}` | `wave-{k}` |
| `prGate` | `pr-apply` | unused | `up` |
| `approval` | `pull-request` | `per-wave` | `pull-request` |

Status contexts come out as `<product>/<stage>`, such as `plywood/preview`, with `/<member>` after it inside a workspace member. A job answers the comment `/<product> <command>`. Job names and note markers stay chant's, and so do ledger paths and artifact names: people never type them, and readers of the ledger key on them. `assertProductWords` refuses a word outside `[a-z0-9-]` or two stages with one word. It also refuses a command the pipeline has no job for.

The approve and override templates take `{op}`, `{gate}` and `{digest}` among their placeholders. `{target}` is the wave's run target. A product that approves by environment writes `approve {target} --plan {digest}`.

The plan side is the pull request loop's: `pr-plan`, then `pr-post` in a job that holds the forge token. The apply on merge runs on [Op waves](/chant/guide/op-waves/) with a job per wave. The spec is `.chant/op-waves/<op>.spec.json`, and chant reads it at the base commit. Under `approval: per-wave` each wave waits for an approval of its own digest. Under `approval: pull-request` the pull request's approval applies every wave whose plan its change set covers, and a wave whose plan moved waits at its own gate.

The generated jobs run the product's bin, named by `bin`. The bin calls chant in process with its words through `runChantInProcess`. The words live in the product package at its pinned version, and the repository holds no words file.

Through `prNoteDetail` a lexicon may add a section under a member's row in the note, such as a SQL member's statements with their class. chant leaves a section out, and names the member, when the note would pass the forge's comment limit. Install lines for the engine come from `ciSetup`. The terraform lexicon gives OpenTofu and adds choudoufu for a root that runs it. The pulumi lexicon gives Pulumi, or plunge when the member's engine is plunge.

## The control repo

A control repo runs the work that crosses repositories, for terragucci and plywood alike ([#4568](https://github.com/INTENTIUS/chant/issues/4568)). The pieces come from `@intentius/chant/ci-control`.

Set `control` on the pull request loop and each member's pipeline gets a `control-dispatch` job after its last apply on merge. The job tells the control repo the member applied: a `repository_dispatch` of `<product>-applied` on GitHub, a pipeline trigger on GitLab, and a workflow dispatch on Forgejo. The job maps the product's secret into `CHANT_CONTROL_TOKEN` for its one step, and curl reads the token on stdin, so it stays off every command line. On GitLab the plan job unsets that variable along with the forge tokens. A product's bin can send the same request in process with `dispatchControl`.

The control repo's own pipeline is `<product>-dependents.yml`, written by each forge lexicon's `generateControlPipeline`. It checks the member and Op names it was given, then runs `chant workspace run --dependents-of <member> --op <op>`, one member at a time.

The control repo's projects and its shared defaults are `control-entry` records on the control repo's ledger, in `_control/entries.jsonl`. Each line is one version of one entry and names the digest of the version it replaces, so a write that raced another is refused. A retired entry is no longer read. chant checks each record's shape, and the product passes a check for the settings it writes.

`reconcileProjects` brings each project's pipeline in line with the entries. It clones the project and runs the product's generator in the clone. A dry run reports what would change. An apply pushes `<product>/pipeline` and opens a pull request there, or updates the one already open. It never writes a default branch. Each project names the variable its token is in, and the default is `CHANT_<FORGE>_TOKEN` for its forge. git reads the token from its environment.
