[terragucci](https://intentius.io/terragucci/) is pull-request automation for Terraform and OpenTofu, and [plywood](https://intentius.io/plywood/) is pull-request automation for Pulumi. [SQL Yodeler](https://intentius.io/sql-yodeler/) does the same for SQL schema changes on ClickHouse and Postgres. All three run on chant's CI runtime and share the same pipeline core ([#4530](https://github.com/INTENTIUS/chant/issues/4530)): the gates, approvals and records are chant's, in each engine's own words. A product can still do more than chant does, such as terragucci's tips and its module registry.

| Changes to | chant entry point | CI product |
|---|---|---|
| Terraform and OpenTofu roots | the [terraform lexicon](/chant/lexicons/terraform/) | terragucci |
| Pulumi stacks | the [pulumi lexicon](/chant/lexicons/pulumi/) | plywood |
| SQL schemas | the [sql lexicon](/chant/lexicons/sql/) | SQL Yodeler |

## Where a feature goes

A feature goes in the first of these homes that fits it:

1. chant CI core, when both products share it.
2. chant's [terraform](/chant/lexicons/terraform/), [pulumi](/chant/lexicons/pulumi/) or [sql](/chant/lexicons/sql/) lexicon, when the capability belongs to one engine. Cone plans and Atmos reads live in the terraform lexicon, stack export in the pulumi lexicon and destructive classes in the sql lexicon, and each lexicon parses its engine's plans and drift and runs its apply.
3. The product. It holds its words and presets, its config defaults and init templates, and its docs.

Extending chant CI is the default. A feature stays inside one product only for a reason that belongs to its audience, such as a Terraform or Pulumi convention, and never for convenience.

Pulumi stacks plan and apply as components through the pulumi lexicon ([#4541](https://github.com/INTENTIUS/chant/issues/4541)), and Op waves plan and apply through chant's capabilities for both products ([#4545](https://github.com/INTENTIUS/chant/issues/4545)). The pulumi member reads its graph from the stack export the apply writes ([#4546](https://github.com/INTENTIUS/chant/issues/4546)) and follows StackReference targets between members ([#4547](https://github.com/INTENTIUS/chant/issues/4547)). The pull-request note and the exit codes are chant's too ([#4548](https://github.com/INTENTIUS/chant/issues/4548), [#4553](https://github.com/INTENTIUS/chant/issues/4553)), and so are the cloud identities ([#4549](https://github.com/INTENTIUS/chant/issues/4549)). One chant pipeline runs both products, and each product names its statuses and commands in its own words, `/terragucci apply` or `/plywood up` ([#4550](https://github.com/INTENTIUS/chant/issues/4550)).

## Records

Approvals and gate decisions go in the workspace [ledger](/chant/cli/ledger/), and so do overrides and the records of applies and runs ([#4551](https://github.com/INTENTIUS/chant/issues/4551)). A product keeps no record store of its own. Before a product adds storage for a record, check whether the ledger already holds it.

## The product pipeline

A product passes chant one object of words from `@intentius/chant/ci-product` and gets its pull request jobs from `productPipelineJobs`. terragucci's jobs and plywood's come from the same generator. The words fill fixed slots in chant's sentences.

| Slot | chant | terragucci | plywood | SQL Yodeler |
|---|---|---|---|---|
| `product` | `chant` | `terragucci` | `plywood` | `yodel` |
| `stages.plan` and `stages.apply` | `plan` and `apply` | `plan` and `apply` | `preview` and `up` | `plan` and `apply` |
| `noun` | member | root | stack | environment |
| `commands` | `apply` | `plan` `apply` `lock` `unlock` `agent` | `preview` `up` `lock` `unlock` | none |
| `approve` | `chant approve {op} {gate} --plan {digest} ...` | `terragucci approve {gate} --plan {digest} {sign}` | `plywood approve {gate} --plan {digest} {sign}` | `yodel approve {target} --plan {digest} {sign}` |
| `op` | the spec's | `tf-apply` | `pulumi-up` | `yodel-apply` |
| `gateName` | `{gate}-wave-{k}` | `wave-{k}` | `wave-{k}` | `yodel-apply-wave-{k}` |
| `prGate` | `pr-apply` | unused | `up` | unused |
| `approval` | `pull-request` | `per-wave` | `pull-request` | `per-wave` |
| `applyMode` | `release` | `on-merge` | `on-merge` | `on-merge` |
| `notify.source` | `chant` | `terragucci` | `plywood` | `yodel` |

SQL Yodeler names no comment command, since its migrations apply only after the merge, and no `/yodel` comment starts an apply. It keeps the op and gate names it recorded before it moved onto chant, so approvals already on `chant/lifecycle` still count.

Status contexts come out as `<product>/<stage>`, such as `plywood/preview`, with `/<member>` after it inside a workspace member. A job answers the comment `/<product> <command>`. Job names and note markers stay chant's, and so do ledger paths and artifact names: people never type them, and readers of the ledger key on them. `assertProductWords` refuses a word outside `[a-z0-9-]` or two stages with one word. It also refuses a command the pipeline has no job for.

The approve and override templates take `{op}`, `{gate}` and `{digest}` among their placeholders. `{target}` is the wave's run target. A product that approves by environment writes `approve {target} --plan {digest}`. The note then prints one approve line per member, each naming its own target.

The note's sentence on the merge follows `applyMode`. With `on-merge` the waves apply in order, each under its own gate for `per-wave` or under the pull request's approval for `pull-request`. A `release` product's merge records the plan for a release to deploy. For `before-merge`, the apply comment runs the plan on the open pull request and the merge records it. A product that names an `op` or approves per wave gets `on-merge` by default, and `productPipelineJobs` sets the mode from the jobs it builds.

The plan side is the pull request loop's: `pr-plan`, then `pr-post` in a job that holds the forge token. The apply on merge runs on [Op waves](/chant/guide/op-waves/) with a job per wave. The spec is `.chant/op-waves/<op>.spec.json`, and chant reads it at the base commit. Under `approval: per-wave` each wave waits for an approval of its own digest. Under `approval: pull-request` the pull request's approval applies every wave whose plan its change set covers, and a wave whose plan moved waits at its own gate. A product's approve verb can find the gate from the digest alone: `pendingGatesByPlan(digest)` and `chant run pending --plan <digest>` return each standing pending gate whose plan or change set is that digest, with the pull request a `pr-<n>` op names ([#4607](https://github.com/INTENTIUS/chant/issues/4607)).

The plan step is `pr-plan` or the product's plan verb ([#4799](https://github.com/INTENTIUS/chant/issues/4799), the 2026-11-09 amendment of the #4550 ruling on the pipeline path). A product with no component graph for `pr-plan`, such as SQL Yodeler planning an environment or terragucci planning its roots, passes `productPlan` to `productPipelineJobs`. `command` is the plan verb as one line, with `{target}` and `{output}` filled in. It writes `pr-plan.json`, a `PrReport`, or `pr-plan-note.json`, a plan note hand-off (`planNoteHandoff` in `@intentius/chant/pr-plan-note`), into `.chant/pr`. With `targets`, each target gets a plan job and a plan-note job: `plan-<target>` and `plan-note-<target>` on GitHub and Forgejo, and `<target>-plan` and `<target>-plan-note` on GitLab. A target's `variables`, `secrets` and `writeProbe` appear only in its own job. The probe runs before the plan, after the forge tokens are dropped. The target is the note's and the status's member, so each target gets its own note and its own `<product>/plan/<target>`. With `evidence`, a target's note job (on GitLab its `<target>-plan-evidence` job) signs `plan:<target>` and `policy:<target>` ([#4978](https://github.com/INTENTIUS/chant/issues/4978)), and the `refs` rule names each target's two checks: `refGateInitPlan(repo, { checks, targets })` expands `plan` and `policy`, and `productPlanEvidenceChecks(targets)` from `@intentius/chant/ci-evidence-jobs` lists them (floor `TARGET_SIGNED_CHECKS_FLOOR`). `pr-post` checks the hand-off's pull request, head, environment and target against its own flags. It renders the note with the pipeline's note words (`noteWords`, passed to the note job as `CHANT_PLAN_NOTE_WORDS`), defuses every hidden comment but its own marker and the waves marker it renders itself, and sets the status the hand-off gives. If the plan job failed, the status fails. `forks: "skip"` runs neither job for a pull request from a fork, and `artifact` names the report artifact. The forge lexicons render the workflow in process, with no component graph: `generateProductPlanPipeline` (github), `generateForgejoProductPlanPipeline` (forgejo) and `generateGitlabProductPlanPipeline` (gitlab), each under `components/product-plan-pipeline`. Each returns the YAML and the document, so a product can add its own jobs before writing it. The product plan takes none of the options that need `pr-plan`'s report or flags (the comment preview, stale notes, locks, the apply before merge, `build`, `identity`, `refresh` among them). Each one is refused by name. A product feature-detects it on `PRODUCT_PLAN_FLOOR`.

The product plan job carries the steps a product's plan needs beside the verb ([#4899](https://github.com/INTENTIUS/chant/issues/4899), [#4931](https://github.com/INTENTIUS/chant/issues/4931)), each switched on in `productPlan`:

| Option | What the jobs do |
|---|---|
| `login`, a target's `login` | chant's cloud login from the OIDC token file (`@intentius/chant/ci-login`), after the setup lines and before the write probe. The job asks for the token: `id-token: write` on GitHub, `enable-openid-connect` on Forgejo, `id_tokens` on GitLab. A target's login replaces the plan's. On GitHub and Forgejo the login's steps alone keep `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN` (Forgejo's request token is the run's own token); the setup, the probe and the plan step start without them, so the change's code cannot request a token ([#5021](https://github.com/INTENTIUS/chant/issues/5021)). GitLab's login unsets its `id_tokens` variables. `identity`, the trade before `pr-plan`'s checkout, is still refused; the product plan's own `trade` is below. Floor: `PRODUCT_PLAN_LOGIN_TOKENS_FLOOR`. |
| `idTokens`, a target's `idTokens` | OIDC tokens for a login the product's command does itself, `{ <variable>: <audience> }`. On GitHub and Forgejo the plan step keeps the token request variables for the command; the setup and the probe start without them. |
| `env` | Variables for the whole plan job, every step of it. A forge token's name is refused. |
| `pending` | On GitHub and Forgejo, a step before the checkout posts `<product>/plan[/<target>]` pending with the job's token, which no later step holds, on the pull request's head (`github.event.pull_request.head.sha`; GitHub's `github.sha` is the merge preview, [#5020](https://github.com/INTENTIUS/chant/issues/5020)). GitLab's plan job holds no token, so it posts none. |
| `controlRead` | chant's read-only fetch of the control repo's `chant/lifecycle` right after the checkout, which sets `CHANT_CONTROL_DIR`. |
| `setup` | Steps after the checkout and before the setup lines: a `run` line, or on GitHub and Forgejo a `uses` action such as a cache restore. GitLab leaves a `uses` step out; the GitLab generator's `cache` is its cache. |
| `report` | A line after the plan verb, in the plan step, run whatever the verb's exit. The step then exits with the verb's status. `{target}` and `{output}` are filled. |
| `concurrency` | A workflow-level group `<group>-<pull request>` (default group: the workflow's name), with `cancelInProgress`. A comment's run is in a group of its own comment. On GitLab `cancelInProgress` makes the plan jobs `interruptible`. |
| `replan` | `/<product> <plan word>` and the words' aliases for the plan command plan an open pull request again: `replan` and `replan-note` (`replan-<target>`, `<target>-replan` on GitLab). With targets, `/<product> plan <target>` plans that target alone; without, the one word after the command reaches the verb as `CHANT_PLAN_ARGUMENT`. A word that starts with `-`, such as `--target=x`, is a flag and never that word: the re-plan refuses it, with `replan.reply` in a reply ([#4984](https://github.com/INTENTIUS/chant/issues/4984)). On GitHub and Forgejo the first step reads the comment from the event file and asks the forge whether the pull request is open (and from this repository, with `forks: "skip"`); on GitHub the commenter must be an owner, member or collaborator, and on Forgejo the step asks whether the commenter can write. On GitLab the note-commands job (`noteCommands`, which the product plan takes only with `replan`) starts the comment preview's pipeline, and the re-plan jobs run for the target the comment names. |
| `watches` | The product's own scheduled jobs, each a `ScheduledWatch` (`op`, `cron`, the generator's `files`, GitLab's `schedule` selector), such as terragucci's drift job ([#4888](https://github.com/INTENTIUS/chant/issues/4888)). The note job gets them from the pipeline as `CHANT_PLAN_WATCHES`, and `pr-post` asks the forge with the job's token when each last ran and adds the line for an overdue one under the note's counts. A watch that is not one is refused when the pipeline is written. |
| `noteSteps` | On GitHub and Forgejo, lines the note job runs with its token, `before` and `after` `pr-post`. A `before` line may write notices, one a line, to `$CHANT_PLAN_NOTE_NOTICES`, a file outside the report the plan job handed on, and `pr-post` adds them under the note's counts. GitLab's note job posts every open merge request's note in one run, so it takes none. |

A hand-off may carry `marker`, the body of the product's own hidden line. When the note words name a `productMarker`, such as `terragucci:plan`, `pr-post` writes `<!-- terragucci:plan <marker> -->` on the note's second line, under chant's marker, and defuses every other hidden comment as before. The body holds letters, digits and `_.,/@+=:-`, words split by single spaces; any other body refuses the hand-off. `pr-post` also adds the overdue scheduled Ops it reads with the job's token, and the note job's notices, to a hand-off's notices, each once. A product feature-detects all of this on `PRODUCT_PLAN_STEPS_FLOOR`.

`record: true` gives the plan job a run record ([#4899](https://github.com/INTENTIUS/chant/issues/4899)), as `chant ci run plan --in-place` gives `pr-plan` one: Op `pr-plan` in `<env>/runs__pr-plan.jsonl` on `chant/lifecycle`, labelled with the target. The plan job holds no token, so its plan step writes the record into the hand-off, `.chant/pr/run-record.json`, after the verb and the report line, whatever the verb's exit. The note job holds the token: `pr-post --record-run <plan job>` appends the record once, by its id, and pushes `chant/lifecycle`; on GitHub and Forgejo the note job then asks for `contents: write`, and on GitLab `pr-post --open` reads the record from each plan job's artifacts. The record is the change's, so the note job keeps only its id, its times and the verb's exit code, and names the op, environment, target, commit, run and status itself; a record that names another environment, target or commit is refused with a warning, and a failed plan job records a failed run. The record is unsigned, as `pr-plan`'s is. A product feature-detects it on `PRODUCT_PLAN_RECORD_FLOOR`.

terragucci's and SQL Yodeler's plan jobs need a few more things of the product plan ([#4963](https://github.com/INTENTIUS/chant/issues/4963), [#4951](https://github.com/INTENTIUS/chant/issues/4951)). Each is off until the product sets it, and a pipeline without them is written as before:

| Option | What the jobs do |
|---|---|
| `trade`, a target's `trade` | chant's trade of the job's OIDC token for the plan identities' own credentials (`@intentius/chant/ci-identity`), before the change is checked out. On GitHub and Forgejo it is a step after the pending status (and in the re-plan, after the decision), before the checkout; on GitLab the script's first lines, before the re-plan checks out the head. Every later step starts without the variables a token is requested with, so the change's code holds the traded credentials and no OIDC token. A job gives one of `login` and `trade`; a target's own login or trade replaces both of the plan's. |
| `replan: { dispatch }` | On GitHub and Forgejo, `workflow_dispatch` with the inputs `pr` and `argument` (or the name `dispatch.argument` gives, such as `root`) plans that pull request again, as the comment does. Only a writer can dispatch, so no permission is asked. On GitLab, a web pipeline of the target branch with `CHANT_PREVIEW_PR` and `CHANT_PREVIEW_COMMENT` already is the dispatch. |
| `replan: { reply }` | On GitHub and Forgejo, the re-plan job (the first target's, with targets) also takes every `/<product>` comment that no other job takes, and replies with the reason: a word that is not the plan command (the reply names the commands), a target that is none of the plan's, a fork's pull request with `forks: "skip"`. `reply.others` names the comments the product's own jobs answer, such as `/terragucci apply`, which it leaves alone. A commenter who cannot write gets no reply. GitLab's note-commands job answers every comment already. |
| `replan: { notAffected }` | The re-plan's note job runs `pr-post --not-affected "$CHANT_PLAN_ARGUMENT"`. When the re-plan was narrowed to one argument and the hand-off's note says `nothing` (or a `PrReport` says `nothing`), the pull request gets `<product>: <argument> is not affected by this pull request, so nothing was planned.`, and the note and the status stay as they were. |
| `previousMarker` | Deprecated: hand the plan's `subject` instead (below), which works on every forge. On GitHub and Forgejo, a step before the checkout, which alone holds the job's token, finds the pull request's note by chant's marker and sets `CHANT_PLAN_PREVIOUS_MARKER` to the body of the product's own line (the note words' `productMarker`), empty when there is no note yet. GitLab's plan job holds no token to read a note with, so the option is refused there. |
| `noteSteps.pullRequest` | The note job's own lines also read `PR_NUMBER` and `HEAD_SHA`, the note's pull request and head (in a re-plan, the re-plan job's). On GitHub and Forgejo `HEAD_SHA` is the pull request's head, `github.event.pull_request.head.sha` ([#5020](https://github.com/INTENTIUS/chant/issues/5020)). The plan job checks out GitHub's merge preview, `github.sha`, and `pr-post` takes a plan note hand-off for either commit as the head's, so the plan verb may write it for `git rev-parse HEAD` or for the head. Floor: `PR_HEAD_SHA_FLOOR`. |

chant keeps a product's own names ([#5003](https://github.com/INTENTIUS/chant/issues/5003), the maintainer's decision of 2026-11-11), so the required checks and the artifact paths a product's branch protection and readers already name keep matching once its plan jobs move onto the product plan. Each name option is off until the product sets it, and a plan without them renders byte for byte as before:

| Option | What it names |
|---|---|
| `workflowFile` | The file the workflow goes in, from the repository root: directly under `.github/workflows/` on GitHub and `.forgejo/workflows/` on Forgejo, any `.yml` file on GitLab. The generators return it as `path`. By default it is the workflow's name (`workflow`, default `chant-pr-<env>`) in the forge's workflow directory, and `.gitlab/<name>.gitlab-ci.yml` on GitLab. |
| `jobNames` | `plan`, `note`, `replan` and `replanNote`: the plan job, its note job and the comment re-plan's two jobs. With `targets` each holds `{target}`. Left out, each is chant's (`plan`, `plan-note`, `replan`, `replan-note`, with a target's name after on GitHub and Forgejo and before on GitLab). Two jobs that share a name are refused. On GitLab the note job runs `pr-post --open --plan-job <name>` for a plan job of the product's name. |
| `statusContext` | The plan status, with `{target}` when there are targets. The note job posts it (`pr-post --context`), the pending step says it is pending, the stale job sets it back to pending, and the apply before merge asks that it passed. Default the words' `<product>/<plan stage>`. |
| `reportDir` | The directory the plan verb writes into (`{output}`), the plan job hands on, the note job keeps as the artifact's path and posts from (`pr-post --output`), and the evidence and lock jobs read. A path from the checkout's root that stays inside it. Default `.chant/pr`. `artifact` still names the artifact. |

terragucci renders its workflow with `workflow: "terragucci"`, `workflowFile: ".github/workflows/terragucci.yml"` (`.forgejo/workflows/terragucci.yml`, `.gitlab/terragucci.yml`), `artifact: "terragucci-report"` and `reportDir: "terragucci-report"`; its job names and `terragucci/plan` are chant's defaults under its words, and it may name them too. A product feature-detects these on `PRODUCT_PLAN_NAMES_FLOOR`.

The Op waves generators keep a product's names the same way ([#5022](https://github.com/INTENTIUS/chant/issues/5022)), so a product's apply jobs can render through them into the workflow its plan jobs are in:

| Option | What it names |
|---|---|
| `jobNames` | Every job the generators write, through a function of the job's role, wave, share and group: terragucci's `apply-wave-<k>`, `apply-wave-<k>-share-<n>`, `apply-wave-<k>-<group>`, `apply-rest`, `apply-done` and `pr-merge`. |
| `stageNames` | GitLab's stages, such as terragucci's one `apply` stage. |
| `artifactNames` | The outcome, decision, saved plan and check claims artifacts, and the pattern a later wave downloads the earlier outcomes with, such as `terragucci-report-apply-wave-*`. A `waveJobs` artifact's `{job}` is the product's job name, so terragucci's report stays `terragucci-report-apply-wave-<k>`. |
| `workflowFile`, `runIf`, `dispatchInputs` | The jobs go in the product's own workflow (`terragucci.yml`): each runs on a push `runIf` admits or a before-merge or follow-on dispatch, never on the product's `pull_request`, `issue_comment` or re-plan dispatch, and the dispatch inputs take names of the product's own. On GitLab `runIf` joins every rule. The product pipeline's `wavesBeforeMerge` takes the same `workflowFile` and `dispatchInputs`, which the comment job dispatches with. |

Every option is off until the product sets it, and the renders without them are byte for byte as before. A product feature-detects these on `OP_WAVES_NAMES_FLOOR`. The [Op waves guide](/chant/guide/op-waves/#keep-a-products-job-names) has the details.

A product that applies on the repository's default branch, whatever it is called, sets `defaultBranch: true` on its waves spec ([#5032](https://github.com/INTENTIUS/chant/issues/5032)), as terragucci does: the guards, the GitLab rules and the stand-down read the branch's name at run time (`github.event.repository.default_branch`, `$CI_DEFAULT_BRANCH`), and `branches` adds named ones beside it, such as terragucci's `apply.branches`. With `firstWaveNeeds: ["check"]` the first wave waits for the product's own check job, so a push that fails it applies nothing (floor `OP_WAVES_FIRST_WAVE_NEEDS_FLOOR`). Floor: `OP_WAVES_DEFAULT_BRANCH_FLOOR`; the [Op waves guide](/chant/guide/op-waves/#run-from-the-default-branch) has the details.

A product whose wave jobs post the spec's responses, or whose hooks read the forge, asks for the job's token with `commandToken: { permissions }` on GitHub and Forgejo ([#5044](https://github.com/INTENTIUS/chant/issues/5044)), as terragucci does with `pull-requests: write`. Only the jobs that run the default branch's code get it, never a split wave's plan or applying job. Floor: `OP_WAVES_COMMAND_TOKEN_FLOOR`; the [Op waves guide](/chant/guide/op-waves/#what-a-product-adds-to-the-jobs) has the details.

On GitLab each plan job keeps the product's own artifacts beside the report directory ([#5004](https://github.com/INTENTIUS/chant/issues/5004)), as the check job does: `productPlan.artifacts: { paths, reports }` puts `paths` after the report directory in `artifacts:paths` and `reports` under `artifacts:reports`, with `{target}` and `{output}` filled as in `command`. terragucci passes `reports: { terraform: "{output}/gitlab-terraform.json" }`, which feeds the merge request's widget. The re-plan jobs keep the report directory alone, since they run in a pipeline of the target branch and GitLab would read their reports as that branch's own. The rules are the check job's: paths stay inside the checkout, a report type is a lower-case word, and `coverage_report` is refused. GitHub and Forgejo refuse `artifacts`, as the plan verb is the plan job's last step there. A product feature-detects it on `PRODUCT_PLAN_ARTIFACTS_FLOOR`.

A `PrReport` may carry `marker` as a hand-off does: with the note words' `productMarker`, `pr-post` writes the product's line under chant's marker, so a per-member note keeps a line such as `<!-- yodel:plan env=prod -->`. A hand-off may carry `body`, the product's own note text, in place of `note` (`planBodyHandoff` in `@intentius/chant/pr-plan-note`), for a note chant's layout cannot carry yet, such as SQL Yodeler's tenant set note. `pr-post` checks it as any hand-off, defuses every hidden comment in it, writes chant's marker and the product's line above it and the notices under it, and cuts it to the forge's limit. A product feature-detects all of this on `PRODUCT_PLAN_REPLAN_FLOOR`.

The note job says what changed since the previous plan ([#4972](https://github.com/INTENTIUS/chant/issues/4972)), so the plan job reads no note on any forge. A hand-off (`planNoteHandoff` or `planBodyHandoff`) may carry `subject`: an `id`, such as SQL Yodeler's plan digest, and optional `parts`, each `<group>` or `<group>/<item>` to a word such as a checksum. `pr-post` keeps the subject in a hidden line of the note, `<!-- chant-pr-subject:... -->`. On the next post it reads the previous note of the same environment and member with the job's token (on GitLab, `pr-post --open` in the target branch's pipeline), and when the id differs it adds a line to the notices: the note words' `sinceLast`, by default ``Since the previous version of this note (`{previous}`): {changes}.``, where `{changes}` names the parts added, gone and changed group by group in the words' `subjectParts` (`added`, `gone`, `changed` over `{group}` and `{items}`, and `item` over `{item}`, `{before}` and `{after}`). With no parts to compare it uses `sinceLastOnly`. Ids, keys and values hold letters, digits and `_.,:+=-`, and a hand-off with any other subject is refused. A subject whose line would pass 16,384 characters is kept by its id alone. A product feature-detects this on `PRODUCT_PLAN_SUBJECT_FLOOR`.

```ts
planNoteHandoff(note, {
  pr, env: "default", member: "prod", state, description, marker: "env=prod",
  subject: { id: digest, parts: { "applied/001_init": "c1", "pending/002_users": "c2", live: "f1" } },
});
// note words, from the pipeline:
// subjectParts: { pending: { added: "new pending migrations: {items}", changed: "files changed: {items}" } }
```

The `plan` runner runs the plan and the comment preview. The `apply` runner runs the apply jobs, the record job and the waves on merge when the spec names no runner of its own. A waves spec with a capability `step` takes it as the number of runs a wave applies at once.

On GitHub and Forgejo the note job adds the note to the job summary, `GITHUB_STEP_SUMMARY`, in the product's words ([#4628](https://github.com/INTENTIUS/chant/issues/4628)). With `staleNotes` (`chant build --pr-loop --stale-notes`) the note carries, in a hidden line, the target branch's commit it was posted against. A `stale-notes` job runs on each push to the target branch, at the pushed commit, and runs `pr-post --stale`. It marks each open pull request's note posted against another commit stale with a line under the heading. The line names the comment that previews again (`/<product> <plan word>` with `previewComment`, else a push), and the job sets the plan status on the pull request's head back to pending. A note posted before this, with no such line, is left alone. `productPipelineJobs` returns the job as `stale`.

A day-2 action is asked for with `/<product> <action word> <member> <action>`, such as `/plywood action shop/prod-us rotate` ([#4654](https://github.com/INTENTIUS/chant/issues/4654)). Words that map a word onto `action` need a job that answers it. A product whose own workflow answers it, as terragucci's action workflow does, passes `actions: true` to `productPipelineJobs`; the command then counts as answered, `comments.action` names the comment, and the pipeline writes no job for it. A product with no workflow of its own passes `actionJob` (`chant build --pr-loop --action-job`), and on GitHub and Forgejo the pipeline writes an `action` job. It starts on the comment, from a commenter with write access on GitHub, and on a dispatch of the workflow with two inputs, the member (named after the words' noun, such as `stack`) and `action`. A dispatch that names an action starts no apply. The job checks out the target branch's commit, or the ref a dispatch names, and runs the product's action verb with `--from-event`, holding the apply identity. The comment and the inputs reach the verb as variables (`CHANT_ACTION_COMMENT`, `CHANT_ACTION_MEMBER`, `CHANT_ACTION`), and the verb reads them with `productActionFromEnv`, by the comment grammar's rules. A run that waits for its approval exits green. GitLab starts no pipeline on a note, and `--action-job` is refused there. `productPipelineJobs` returns the job as `action`, and a product feature-detects both on `PRODUCT_ACTIONS_FLOOR`.

A product that writes its pull request jobs with `chant build --pr-loop` passes the same settings on the build line. `--merge auto --merge-token-env <VAR>` is `applyMerge` ([#4636](https://github.com/INTENTIUS/chant/issues/4636)), `--respond`, `--decide-backend` and `--decide-model` are `respond` and `decide` ([#4629](https://github.com/INTENTIUS/chant/issues/4629)), and `--refresh` is `refresh` ([#4627](https://github.com/INTENTIUS/chant/issues/4627)). The generated apply and note jobs then match the ones `productPipelineJobs` returns. A product feature-detects the build's mapping on `PR_LOOP_BUILD_FLAGS_FLOOR`.

A repository's own jobs survive regeneration in one of two ways ([#4769](https://github.com/INTENTIUS/chant/issues/4769)). `chant build --components --generate <forge> --own-jobs <file>` reads a YAML map of job name to job, in the forge's own syntax, and writes the jobs after chant's under one comment line: inside `jobs:` on GitHub and Forgejo, at the top level on GitLab. A name chant's file already gives a job is refused, and on GitLab so is a top-level keyword or `pages`. `--keep-own-jobs` reads the file `--output` names before writing over it and keeps each job the new file lacks, as it was written, unless the job runs `chant` or the product's bin (the words' `bin`, and its last word). The library functions are `mergeOwnJobs` (with `readOwnJobsFile` or a map) and `keepOwnJobs` in `@intentius/chant/ci-product`, and a product feature-detects them on `OWN_JOBS_FLOOR`.

On Forgejo, a workflow with no workflow-level `concurrency:` gets a group per ref, workflow and event, and the run in progress is cancelled when a push starts another, so a second merge can cancel the first merge's wave jobs ([#4771](https://github.com/INTENTIUS/chant/issues/4771)). `runGroup` asks the Forgejo generators for a group. `pull-request` (`chant build --components --generate forgejo --run-group pull-request`) gives each run its own group, except that a pull request's runs share one and cancel each other. `commit` (an op waves spec's `options.runGroup`, or `chant run --generate forgejo --spec <file> --run-group commit`) gives one group per event and commit, which only queues. A workflow that has a group of its own, such as the resume and plans workflows, keeps it. GitHub cancels nothing without a group and GitLab's jobs are not `interruptible`, so their files are unchanged. A product feature-detects it on `FORGEJO_RUN_GROUP_FLOOR`.

The generated jobs run the product's bin, named by `bin`. The Op waves pipeline does too: `chant run --generate` run through the bin writes the bin into each wave job, the resume job and the plans job ([#4607](https://github.com/INTENTIUS/chant/issues/4607)). The bin calls chant in process with its words through `runChantInProcess`. The words live in the product package at its pinned version, and the repository holds no words file.

For the commands it runs as a child, a product runs the chant it is installed with through `@intentius/chant/chant-install` ([#4800](https://github.com/INTENTIUS/chant/issues/4800)). `bundledChant()` is that package, with its `bin`, `binDir` and `version`; `installedChant(dirs)` walks up each directory's `node_modules` for another; `chantArgv(args, { nodeArgs? })` is the argv that runs its `bin/chant` under the current node, which picks the compiled CLI or the source itself; `chantEnv(env)` puts its bin first on `PATH` for the Op activities that run `chant` again; and `chantCommand({ chant? })` is a `--chant` flag, else that bin, else `chant` on `PATH`. A product run from a global install calls `installChantResolveFallback(import.meta.url)` in its bin, so a repository's Op files that import `@intentius/chant` or a lexicon resolve them from the product's install when the repository has none. A note a product writes itself fits the forge with `noteLimit(kind)` and `fitNote(body, { limit, tail })` from `@intentius/chant/plan-summary`, and its forge flags go through `forgeTargetFromFlags` ([posting from your own tool](/chant/guide/ops/#posting-from-your-own-tool)). A product feature-detects all three on `PRODUCT_HELPERS_FLOOR`.

`runChant(args, options)` from the same module spawns that chant and resolves with `{ code, stdout, stderr, json }`, where `json` is the last `--json` document the command printed (`lastJsonLine(stdout)`) ([#4889](https://github.com/INTENTIUS/chant/issues/4889)). It takes `cwd`, `env`, `chant` (a `--chant` flag, run as it is), `from` (directories to look for an install from), `nodeArgs`, `noColor`, `stdio: "inherit"` for a job's log, and `onStdout` and `onStderr` for output a person watches. It rejects only when the child cannot start. A product's command can also run where nothing is installed, such as the git worktree chant's commit job makes outside the job's checkout: `installResolveFallback()` in the product's bin, and `resolveFallback: true` on `runChant` (or `fallbackImportArgs()` as `chantArgv`'s `nodeArgs`) for the children, resolve any bare specifier imported by a file with no `node_modules` above it from the product's own install. A file that has an install of its own resolves as before. A product feature-detects these on `CHANT_RUN_FLOOR`.

A product's CI image is config passed to `@intentius/chant/ci-image` ([#4784](https://github.com/INTENTIUS/chant/issues/4784)). `productImageStages({ name, product, description, source, tools, bundle, ... })` returns the stages for the docker lexicon's `new Dockerfile({ stages })`, and `productImageDockerfile` returns the same as text. Every product image has the same layers: a fetch stage on the pinned Debian base that downloads each engine in `tools` and checks it, then the pinned Node 22 base with git, CA certificates and `safe.directory '*'`, the engines under `/opt/<product>/<tool>-<version>/` linked into `/usr/local/bin`, the product's `steps`, its `bundle` and the OCI labels, the version label read from `CHANT_RELEASE_LABEL` or the product's `versionArg`. `derivedImageDockerfile({ from, header, steps })` writes an image a user builds FROM the product's, such as one with plugins or a provider mirror preinstalled. Each engine is checked against its release's checksums file and against a recorded sha256, chant's (`CI_TOOL_SHA256`) or one from the product's config (`sha256`), so a tampered checksums file fails the build as a tampered archive does. An image refuses an engine with no recorded sha256. The same check runs in a job (`ciToolInstallLine`, which skips when the versioned directory holds the binary) and at run time from Node (`installCiTool`, for a pin the image does not carry). A product feature-detects them on `CI_IMAGE_FLOOR`.

A job that is not root, such as one on GitHub's hosted runners, passes `sudo: true` to `ciToolInstallLine`, which writes the tool root and the link with `sudo` and leaves the download and the check to the job's user, or a `root` and a `binDir` it can write, which may start with a variable the job's shell expands: `ciToolInstallLine("aws-cli", "2.37.9", { root: "$RUNNER_TEMP/chant-tools", binDir: "$RUNNER_TEMP/chant-bin" })`, with the job putting `binDir` on its PATH ([#4908](https://github.com/INTENTIUS/chant/issues/4908)). `CI_TOOL_SHA256` records terraform 1.14.9, terragrunt 1.2.0 and the AWS CLI 2.37.9 beside OpenTofu, choudoufu, Pulumi and plunge. The pulumi lexicon's `ciFetchScript` and `PINNED_SHA256` are this module's script and sums under Pulumi's x64 and arm64 names. `productImageStages`'s stages type as the docker lexicon's `DockerfileStage[]` under `exactOptionalPropertyTypes` ([#4932](https://github.com/INTENTIUS/chant/issues/4932)). They gate on `CI_IMAGE_NON_ROOT_FLOOR` and `CI_IMAGE_DOCKER_STAGES_FLOOR`. squawk and sqlfluff have no install here: squawk's releases publish bare binaries with no checksums file and no product pins one, and sqlfluff is a pip package.

A job whose image carries node but neither curl nor unzip passes `download: "node"` to `ciToolInstallLine` or `ciToolFetchScript` ([#4952](https://github.com/INTENTIUS/chant/issues/4952)). The line downloads with node's `fetch` and unpacks a zip with node and keeps each entry's executable bit, so the AWS CLI's installer runs as it does after `unzip`. The checks are the ones curl's line makes. `CI_TOOL_SHA256` now records terragucci's pins of just and act, and each release is checked against the checksums file its project publishes (act's `checksums.txt`, and for just either `SHA256SUMS` or one `.sha256sum` file per archive, by version). The `download` option and these sums arrive with `CI_TOOL_NODE_DOWNLOAD_FLOOR`.

Through `prNoteDetail` a lexicon may add a section under a member's row in the note, such as a SQL member's statements with their class. chant leaves a section out, and names the member, when the note would pass the forge's comment limit. Install lines for the engine come from `ciSetup`. The terraform lexicon gives OpenTofu and adds choudoufu, checked against its recorded sha256, for a root that runs it. The pulumi lexicon gives Pulumi, or plunge when the member's engine is plunge.
A SQL project's setup checks for Node 22 and installs the project's packages, which carry the dialect's client. Through `ciServices` it adds the replay server for each dialect the project declares, on the image the lexicon's emulator runs.

SQL Yodeler keeps its versioned migration engine, which owns the migrations directory and its checksums and guards the history table with its own apply lock. The engine has an audience of its own in database teams, as choudoufu has for Terraform and plunge for Pulumi. chant's sql lexicon runs it from a wave through the `sql-migrate` capability, with a fixed list of `yodel` argv as the pulumi lexicon runs plunge ([#4569](https://github.com/INTENTIUS/chant/issues/4569), [SQL members](/chant/guide/op-waves/#sql-members)). The `sql-apply` capability applies a declarative build with the lexicon's own appliers. Both plan into a change-set part with the destructive classes that the `on-destructive` gate policy reads.

The sql lexicon maps the engine's outcomes onto the one [exit-code table](/chant/reference/exit-codes/) ([#4570](https://github.com/INTENTIUS/chant/issues/4570)). A wave that a newer commit will apply anyway stands down in core ([#4581](https://github.com/INTENTIUS/chant/issues/4581)), and `chant approve` at a terminal asks for the environment's name before it records the approval ([#4575](https://github.com/INTENTIUS/chant/issues/4575)). ## The control repo

A control repo runs the work that crosses repositories, for terragucci and plywood alike ([#4568](https://github.com/INTENTIUS/chant/issues/4568)). The pieces come from `@intentius/chant/ci-control`.

Set `control` on the pull request loop and each member's pipeline gets a `control-dispatch` job after its last apply on merge. The job tells the control repo the member applied: a `repository_dispatch` of `<product>-applied` on GitHub, a pipeline trigger on GitLab, and a workflow dispatch on Forgejo. The job maps the product's secret into `CHANT_CONTROL_TOKEN` for its one step, and curl reads the token on stdin, so it stays off every command line. On GitLab the plan job unsets that variable along with the forge tokens. A product's bin can send the same request in process with `dispatchControl`.

A product that applies on merge through op waves sets `control` on the spec instead. After the last wave, whatever it did, a `control-dispatch` job sends the dispatch with the outcome the wave jobs add up to: `applied`, `partial`, `unchanged`, `waiting` or `failed` ([#4617](https://github.com/INTENTIUS/chant/issues/4617), [Tell the control repo](/chant/guide/op-waves/#tell-the-control-repo)).

The control repo's own pipeline is `<product>-dependents.yml`, written by each forge lexicon's `generateControlPipeline`. It checks the member and Op names it was given, then runs `chant workspace run --dependents-of <member> --op <op>`, one member at a time. A dispatch that carries an outcome is recorded first, as a `control-applied` line of `_control/applied.jsonl` on the control repo's `chant/lifecycle`, and its dependents run only when something applied. The job pushes the record with its own token. A control repo whose chant predates `CONTROL_APPLIED_FLOOR` says so and records nothing.

The control repo's projects and its shared defaults are `control-entry` records on the control repo's ledger, in `_control/entries.jsonl`. Each line is one version of one entry and names the digest of the version it replaces, so a write that raced another is refused. A retired entry is no longer read. chant checks each record's shape, and the product passes a check for the settings it writes.

`reconcileProjects` brings each project's pipeline in line with the entries. It clones the project and runs the product's generator in the clone. A dry run reports what would change. An apply pushes `<product>/pipeline` and opens a pull request there, or updates the one already open. It never writes a default branch. Each project names the variable its token is in, and the default is `CHANT_<FORGE>_TOKEN` for its forge. git reads the token from its environment.

The release catalog lists the consumers of each version across every project the control repo names ([#4600](https://github.com/INTENTIUS/chant/issues/4600)). A `consumers.json` in each project lists the versions its roots pin and where each call sits. `consumersDocument` writes it from the product's scan, and the terraform lexicon's `moduleConsumers` fills it for terragucci. `readControlConsumers(entries, read)` reads each project entry's file through the product's reader and joins them with `joinControlConsumers`. The result has one consumer list per version, with each consumer named by its project, and it goes to `buildReleaseCatalog` as its `consumers`. A project with no file is listed as missing. A file with problems adds the entries it could read, and each problem names the project.

### Cross-stack edges

A member can read a stack that no member of its workspace applies, such as a Pulumi `StackReference` to a stack in another repository. The pull request note lists each such read in a table with the stack's owner and a mark ([#4617](https://github.com/INTENTIUS/chant/issues/4617)). The owner is the project whose control entry lists the stack among its `estates`. The mark compares the owner's newest apply on the control repo's record with the reader's last update, taken from its stack export:

| Mark | When |
|---|---|
| `stale` | The owner applied after the reader last updated, so the reader holds outputs that may have changed since |
| `current` | The reader updated after the owner's last apply |
| `unknown` | No entry claims the stack, two do, the owner has no apply on record, the reader has not updated, or the control repo was not read |

The plan job reads no control repo, so the report it writes marks every edge `unknown`. The job that posts the note marks them again from a checkout of the control repo named by `CHANT_CONTROL_DIR`, with its `chant/lifecycle` fetched. When the pull request loop's `control` or the waves spec's names a control repo, the generated note job does that fetch itself on GitHub, GitLab and Forgejo ([#4619](https://github.com/INTENTIUS/chant/issues/4619)). It fetches `chant/lifecycle` alone into a new directory outside the checkout, with the read secret (`readTokenSecret`) or else the job's token, and sets `CHANT_CONTROL_DIR` to it. A control repo it cannot read leaves a warning and every edge `unknown`. A product that writes its own note job takes the same step from `productPipelineJobs` as `post.control`. A product that writes its pipeline with `chant build --pr-loop` passes the control repo on the build line: `--control <repo>` with `--control-setting <key>=<value>` for `op`, `member`, `readTokenSecret` and the other settings ([#4772](https://github.com/INTENTIUS/chant/issues/4772)). `op` and `member` are needed, since the build has no repository name to default the member to. The generated note job then carries the fetch, and an apply on merge sends the dispatch. It feature-detects this on `PR_LOOP_CONTROL_FLOOR`. It takes only each edge's reader, stack and last update from the report. Only names and times are compared, never an output's value. An entry's `settings.member` names the owner's member in the control repo's workspace, and the default is the repository's name.

## Traces and agent tools

chant exports the traces for both products ([#4555](https://github.com/INTENTIUS/chant/issues/4555)). A `chant run wave` job writes run events on the [run-event contract](/chant/reference/workspace-read-contract/#run-events). Each wave is a phase of the job, and each run target is a step. When `OTEL_EXPORTER_OTLP_ENDPOINT` is set, the job sends one trace as OTLP/JSON over HTTP. The job is the trace's first span. Each wave is a span below it, each root or stack a span in its wave, and each resource the engine timed a span under its root or stack. Attributes carry the product's name as their namespace, `terragucci.root` or `plywood.stack`, taken from the words the product's bin set. A bin whose words are not set yet calls `configureOtlp({ prefix })` once. The lexicons add the engine's facts. The terraform lexicon names the root and its binary. The pulumi lexicon names the stack and its engine, and copies the counts from the summary of `up --json`. Core adds the plan's resource counts by action.

A product's agent tools run on chant's MCP server rather than a server of its own. Its bin passes them as a tool hook, `runChantInProcess(["serve", "mcp"], words, { mcp: hook })`, and chant registers each as `<product>:<name>`. A server started through the hook is read-only unless the hook says `readOnly: false`. On a read-only server a product tool is served only when it declares `readOnly: true`, and the server refuses to start with one whose name says it would approve, apply, override or write. The tools read the report store through `ctx.reports()` with the server's own credentials. The core [`report`](/chant/cli/mcp/#report) tool reads the files a pull request stage kept there.

## The estate page and delivery metrics

Both products build their estate page from the workspace ledger with `@intentius/chant/ci-estate` ([#4612](https://github.com/INTENTIUS/chant/issues/4612)). The page reads the `runs`, `gates`, `applies` and `pr_envs` tables of the [read contract](/chant/reference/workspace-read-contract/). A Terraform member and a Pulumi member both apply through `chant run wave`, and each wave job writes a run record, so one function reads both. `buildLedgerEstate` returns three things from one read of the ledger. The first is the page's data, with a section per member. Each section shows the waves of the newest commit and how long a waiting wave has waited. Below them come the newest drift check and the live pull request environments. The second is the delivery metrics, and the third lists the drift checks that are overdue.

A drift check is a run whose `Drift` outcome says whether it found drift, as a `WatchOp` records it. A check that names the drifted roots or stacks in a `DriftedRoots` outcome narrows the match to those. A scheduled check is overdue once its cron has fired twice since the member's newest check on the ledger. The plan note uses the same rule. The text names the product and uses its words for drift and for a member.

The delivery metrics are the four DORA numbers per member and for the estate, over the newest eight weeks. Deployment frequency counts applied waves, and the share jobs of one wave count once. Lead time starts at the first job that planned the wave's digest, or at the commit when the product passes `commitTime`. It is split at the gate by the pending fact and the approval the apply spent. Change failure rate counts failed waves and applied waves that drift followed within a week. Time to restore runs from a failure to the next apply of those targets, or from drift found to a clean check. The file is `dora.json` in terragucci's shape, with `<product>.dora/v1` as its schema. When `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` is set, the same numbers go out as OTLP gauges named `<product>_dora_*`.

A product whose applies are not all wave records, and a control repo that reads each project's report bucket, compute the same numbers from the product's own records with `buildRecordDelivery(sources, entries, { stages })` ([#4612](https://github.com/INTENTIUS/chant/issues/4612)). `sources` are each project's report index rows: plan rows give a change's first plan, its pull request and the set digests its waves bind, and drift rows give drift found (`drift_since`) and cleared (`drift_cleared`). `entries` is the audit trail: `apply`, `approval-requested` and `approval` lines split the lead time at the gate, or undefined when there is none, and then only drift counts. `stages` names the index's plan and drift stages, `tf-plan` and `tf-drift` for terragucci. The file is the same `dora.json`, without the `source` field the ledger's file adds. A product feature-detects it on `CI_ESTATE_RECORDS_FLOOR`.

`writeEstate` puts `estate.html`, `estate.json` and `dora.json` below the report URL, under `estate/` by default. A product adds its own sections through `sections`, such as terragucci's inventory and versions of each root. A product loads the module through a feature-detect until its chant floor reaches `CI_ESTATE_FLOOR`.

## The e2e harness

terragucci, plywood and SQL Yodeler prove their claims on one end-to-end harness in chant core, `@intentius/chant/e2e-harness` ([#4587](https://github.com/INTENTIUS/chant/issues/4587)). Each of them brings its own scenarios and words to it, and chant owns everything those run on.

The stack is one compose project, written as a chant project on the docker lexicon. Its network holds floci, Forgejo `16.0.5` and forgejo-runner `13.2.0`, whose docker executor puts each job's container on the same network. The sql emulator's servers wait behind the `sql` profile. `harnessStack({ project })` returns the properties of every service, which the product's own project hands to the lexicon's `Service`. Two benches can share a host: the project name is part of every name the stack gives out, and host ports bind to `127.0.0.1` behind variables such as `<prefix>_FLOCI_PORT`. All of its images are pinned in `e2e-harness/pins.ts`. That file holds floci at 5ec92ae8, the build choudoufu and plunge pin, until [lex00/floci#265](https://github.com/lex00/floci/issues/265) gives one image with the fixes of both floci lines.

Each scenario is an `e2e-scenario/v1` file with a repo tree, the pull request steps in order, and the outcomes each step must show. Its steps can open a pull request or a second one beside it, wait for the plan, approve, merge, wait for the apply, change something out of band, or kill a running job. Outcomes come from chant's own reports and run ledger rather than from a runner's logs. `lintScenario` refuses a scenario that has no claim id or no BREAK arm.

The driver plays every scenario twice. Its plain run must pass, and its run with `BREAK=1` must be caught, so that one of the outcomes fails to hold. When a step does not finish within its limit the run stalls, which counts as neither verdict. Both verdicts go into one `e2e-claim-row/v1` row. The row also names the product's commit and the engine binary with its version, and it carries the floci digest and date of the run. That row is recorded on the ledger under op `e2e-claim`, and `renderClaims` turns those records into the `e2e-claims/v1` file the product's page reads. An engine claim counts a row only at the engine version the row ran.

Every process a scenario starts goes through `SafeRun`, which follows plunge's rule. Cloud credential variables are unset, cloud config is empty, and the Pulumi backend is a `file://` directory. Nothing is recorded unless the scan of the run's logs says CLEAN. A product on an older chant imports the subpath lazily and uses it once `E2E_HARNESS_FLOOR` is exported.
