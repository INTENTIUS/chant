Teams keep state for governance, such as a known change set before apply. chant keeps that governance with markers on the cloud resources and snapshots in git.

[Lifecycle Models](/chant/concepts/lifecycle-models/) places chant on the three axes of state: where truth lives, reconciliation direction, and who answers "is this mine?". [Works with](/chant/concepts/comparison/) covers Terraform, OpenTofu and Pulumi estates in a chant workspace. [Drift Detection](/chant/concepts/drift-detection/) covers snapshots and diffs.

## State and governance

The properties a team relies on are governance:

- A known change set before apply
- A lock so two operators do not collide
- An audit trail that can be read later
- Blast-radius limits so one change cannot touch everything

Each tool provides them its own way.

| Model | State kept by | Ownership read from |
|---|---|---|
| Terraform, OpenTofu or Pulumi on its stock engine | The backend you choose | The state |
| CloudFormation and CDK | The cloud, as part of the stack | The stack |
| Terraform and OpenTofu on choudoufu, Pulumi on plunge | The backend you choose, with your existing roots and programs | Markers on the resources, read live |
| chant | A snapshot in git, kept as evidence | Markers on the resources, read live |

## How chant keeps it

Snapshots and diffs live in git, which gives audit and review. Linting runs on the static artifact before apply, which gives pre-apply validation. [`chant lifecycle plan`](/chant/cli/lifecycle/) computes a create/update/delete set against the live system from [ownership markers](/chant/configuration/config-file/#ownership) on the cloud resources. The marker on each resource makes a `delete` precise. See [Lifecycle Models](/chant/concepts/lifecycle-models/) for the full model.

## Plans without applying

chant computes the change set; it does not execute it. Two read-only commands sit on the observe side:

- [`chant lifecycle diff`](/chant/cli/lifecycle/) — the three-way comparison. The default mode builds and compares declarations against the last snapshot, offline; `--live` queries the cloud and compares the live result against both the snapshot and the current build.
- [`chant lifecycle plan`](/chant/cli/lifecycle/) — promotes the live diff to a typed create/update/delete change set you can act on.

Both stop at producing the artifact. The orchestration decides the next step, whether that is a CI job, an agent, a human, or a [scheduled WatchOp](/chant/guide/watching-lifecycle/). A team comfortable with the observational model wires the plan to automation. A team that wants a strict gate wires the same artifact into its own approval flow. chant does not force either, because it does not own the apply.

## Blast radius at scale

A common objection is that at scale a single change touches so many resources that verifying it means reading the whole estate.

The scope of a change is bounded by the change. A one-subnet change touches one subnet and its dependents whether the account holds a hundred resources or a hundred thousand. `chant lifecycle diff --live` queries the cloud for the declared resources through each lexicon's `describeResources()` method, not the entire account, so the read tracks what is declared rather than the size of the estate. The read is also bounded by the write already accepted, so reading the affected scope is less work than mutating it.

There is one case where the affected scope approaches the whole estate, such as rotating a root credential or re-tagging everything. That is the exact change a human or a policy should gate. A scope that large is a signal to split or stage the change.

## Where truth lives

In the observational model the live system is the source of truth. A snapshot is a baseline for the diff, and it is allowed to be stale, because a stale baseline is inconvenient while a stale source of truth is dangerous.
