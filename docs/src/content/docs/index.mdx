## Changes and approvals

A change gets one plan note. It covers the components the change touches and the components that depend on them, and nothing else. An approval covers the exact plan it was shown. [Changes and approvals](/chant/guide/pull-request-ci/).

## Your forge, your pipelines

chant writes the pipeline into your repository, in your forge's own format.

```bash
npx chant build --components --generate <forge> --pr-loop --env <env> --output <file>
```

| Where it runs | Page |
|---|---|
| GitHub, GitLab or Forgejo | [Changes and approvals](/chant/guide/pull-request-ci/) |
| A runner on your own host, with GitHub, Forgejo or plain git | [chant ci](/chant/cli/ci/) |

## Merges and releases

A merge records the plan and deploys nothing. A release that carries the commit deploys the change. [Apply on merge](/chant/guide/apply-on-merge/) is the opt-in for teams that want a merge to apply. [Trunk and releases](/chant/concepts/trunk-and-releases/).

## Ops with gates

A change that needs more than one step runs as an Op, with approval gates and rollback. A person or an agent can start one, and neither can hurry an approval. [Ops](/chant/guide/ops/).

## Drift

`chant lifecycle diff <env> --live` compares what you declared with what is running. [chant lifecycle](/chant/cli/lifecycle/).

## Native specs

chant writes each platform's own spec. Nothing sits between your code and the format the platform reads.

| Spec | Platform |
|---|---|
| CloudFormation | AWS |
| ARM | Azure |
| Config Connector | GCP |
| Kubernetes YAML | Kubernetes, EKS, GKE and AKS |

[Every platform](/chant/lexicons/overview/), and [the full docs](/chant/getting-started/introduction/) on defining infrastructure.
