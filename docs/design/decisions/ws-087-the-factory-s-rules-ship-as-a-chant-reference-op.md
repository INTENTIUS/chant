question: "Where do the rules every orchestrator of a factory must agree on live (which work items are ready, when the understand and slice-tier points are asked and what each answer does, which lease outcomes count as attempts, what done means, what happens to an unfinished attempt, when a failed build is retried and which decisions a build proposes it implements), and what does an orchestrator such as studio supply around them?"
options:
  - id: "a"
    label: "chant ships the factory loop as a reference Op with its rules declared and tested, and the orchestrator supplies typed execution hooks"
    how: "A composite in core, beside declareSteward, reads the factory from the box block (ws-077) and the work kind (#3147) and runs pick, lease, tier, understand, build, check, record and keep, then publish through the box's publisher (ws-088). The rules are its declared behaviour, with a test per rule: readiness on top of the work kind's ready (the intent decided, the contract approved and in force with a check, the tier known, under the attempt limit, not done and unapplied on its branch, not dropped there, no open question), the slice-tier and understand points asked through decide after the lease and what each answer does, the closed outcome vocabulary and which outcomes are attempts, done as every criterion evidenced and the item amended and committed on chant/work/<id> with chant's trailers, the kept-attempt ref for an unfinished attempt, a retry as a person's request keyed by the failed build's lease token (arugula-salad/studio#232), and implements proposed from the intent graph for the paths a done build changed (arugula-salad/studio#243). The orchestrator supplies hooks and nothing else: how a builder runs (Claude Code in the box, fountainRun, a stub), the prompt and context bundle, how a build is stood up and checked, and, when it is not the box's publisher, where it is published. An infra profile is the same loop with an estate builder and a plan as the check. The Op runs on a fountain steward or the steward's local form, with or without studio. Building it is #3406."
    tradeoff: "A second orchestrator, or studio's next version, gets the same rules by running the composite, and a harness with stub hooks can test any orchestrator against the factory tests. Studio's queue, ready, dispatch and record scripts shrink to hooks, which is a migration on studio's side. chant carries an Op whose behaviour studio relies on, so a rule change becomes a chant release, and the composite has to cover the infra profile from the start so ops work does not fork it."
  - id: "b"
    label: "keep the rules in studio's kit, as ws-056 and ws-057 placed the dispatch runtime"
    how: "Studio's queue.mjs, ready.mjs, dispatch.mjs and record.mjs keep the readiness, outcome and done rules; chant states the data they read (the work kind of #3147, the factory block of ws-077) and writer conformance (#3159) checks the writes."
    tradeoff: "Nothing moves. A second orchestrator reimplements every rule from studio's code, and writer conformance can show that its writes are well formed but not that it followed the same rules, so two factories over one repository can disagree about what is ready or done."
  - id: "c"
    label: "chant ships the rules as a conformance suite only"
    how: "A factory conformance suite in @intentius/chant/workspace/conformance runs scripted repositories through an orchestrator's runner and asserts which items it picks, what it records and when it stops; each orchestrator keeps its own implementation."
    tradeoff: "The rules are written down and checked without chant running a loop. Every orchestrator still writes the whole loop, and a suite that tests readiness, retries and kept attempts end to end is most of the work of writing the composite, without the composite to run."
  - id: "d"
    label: "chant ships the rules as functions, and the orchestrator keeps the loop"
    how: "Pure functions in core (readiness, attempts left, what an outcome means, whether an item is done, whether a retry is possible) that studio's scripts call, with the loop, leases and decide calls staying in studio."
    tradeoff: "Studio adopts them a function at a time. The order of the steps (lease before tier, understand before build, keep before release) is a rule too, and it stays in each orchestrator's loop, as do the decide calls and the run records around the builder."
choice:
  option: "a"
  reason: "The rules decide what a repository's work means, so they belong with the spec, the same reason the steward moved into chant (#2731): ws-074 makes every fact a file written through chant, and #3145 asks that the spec describe a studio repository without studio, yet today a second orchestrator could only learn what is ready or done by reading studio's scripts. A composite is the form chant already uses for a loop it owns (ApplyOp, declareSteward), and it carries the order of the steps, which function-level rules (option d) leave behind. ws-056 and ws-057 put the dispatch steps and the runner in the studio kit when the choice was between the kit and chud; this revises that part of both, and only that part: the builder declarations, the steward as the dispatcher's home, the evidence source block and everything else they decided stand. Execution stays the orchestrator's because it is runtime with credentials and a sandbox: which agent, which prompt, how an app is stood up. The data the rules read already ships (#3147's tiers, attempts, outcomes and kept refs; ws-077's factory; ws-088's publisher), so the composite adds behaviour, not schema. A conformance suite (option c) would test the same behaviour without giving anyone the loop."
rejected:
  - option: "b"
    why: "It leaves the rules in one orchestrator's code, so a second one reimplements them and nothing checks that the two agree, which is the gap #3162 was filed for."
  - option: "c"
    why: "The suite would cost about as much as the composite and still leave every orchestrator writing the loop; once the composite exists, its own tests with stub hooks are that suite."
  - option: "d"
    why: "The order of the steps and the decide and run-record calls around them are rules as much as readiness is, and they would stay in each orchestrator."
