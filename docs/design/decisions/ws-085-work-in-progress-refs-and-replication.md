question: "Under which refs does a box keep work in progress (checkpoints of a branch's working tree with its uncommitted records, work branches and kept attempts), who owns that namespace when hud and studio each take checkpoints, and where, when and what does the box replicate so that a lost box loses none of it?"
options:
  - id: "a"
    label: "chant owns one namespace, refs/chant/wip/<branch>, as a chain of snapshot commits, replicated under a replicate policy on the box block"
    how: "chant workspace wip save writes a commit whose tree is the whole working tree (staged, unstaged and untracked files, ignored files left out) through a temporary index, so the checkout's index, HEAD and branch never move. Its first parent is the snapshot before it on refs/chant/wip/<branch>, and its last parent is the commit HEAD named. Chant-Wip-Branch, -Head, -Kind, -Label and -By trailers carry the branch, the head, save or pre-restore, the caller's label (hud's turn) and who took it. The ref's first-parent chain is the branch's checkpoint history. wip restore puts the working tree back as a snapshot holds it, after a pre-restore snapshot of how it is, and resets the index to HEAD; the branch never moves. The box block's replicate { remote, refs, on, every } names the git remote (origin by default, or a mirror the host adds with its credential), which refs go (work for chant/work/..., kept for refs/chant/kept/..., wip, and ledger for chant/lifecycle; all four by default), when chant pushes on its own (save, release; both by default) and the interval at which the host runs wip push. Each ref is pushed under its own name and never forced, and chant records what reached the remote under refs/chant/replica/<remote>/, so status --json and wip --json say how far each ref is behind without fetching. wip fetch on a replacement box mirrors the remote into that namespace and creates or fast-forwards the local refs. At most one box block declares replicate."
    tradeoff: "hud, studio and any second tool take, list and restore checkpoints through one command and one document, and the work branch's own history never shows them. One ref per branch means one push carries every checkpoint of the branch and the branch's commits with it. The chain grows by one commit per checkpoint, and a ref nobody prunes keeps every one; pruning is left to a later change. A checkpoint is per branch, so a turn that edits two repositories is two snapshots, one in each, which the caller groups by label."
  - id: "b"
    label: "each tool keeps its own namespace, and chant replicates a list of ref prefixes"
    how: "hud keeps refs/hud/checkpoints/<who>/<session>/<turn> (hud#137) and studio keeps refs/chaff/checkpoints/<who>/<time> (studio#53). The policy lists the prefixes to push, and chant pushes whatever is under them."
    tradeoff: "No tool changes its layout. Two tools on one box write two histories of the same working tree, neither reads the other's, and each carries its own code to take, list and restore a checkpoint, the second implementation ws-052 and ws-074 rule out. A replacement box has to know every tool's layout to restore anything."
  - id: "c"
    label: "one ref per checkpoint in chant's namespace: refs/chant/wip/<who>/<session>/<turn>"
    how: "hud's layout under refs/chant/: each checkpoint is its own ref, named by who took it, the session and the turn."
    tradeoff: "A checkpoint is found by name without walking a chain. The identity and session segments are hud's model: studio has no sessions, a turn has no meaning outside hud, and every checkpoint is one more ref to push, list and prune. The segment hud wanted the identity for, worktrees and tabs sharing one ref namespace, is already separated by the branch, since git checks a branch out in one worktree at a time."
  - id: "d"
    label: "commit work in progress to the work branch and push the branch"
    how: "Each checkpoint is a commit on chant/work/<id>, pushed like any other, and applying squashes them."
    tradeoff: "Nothing new to replicate. The branch's history fills with checkpoint commits the tool made, which ws-074 rejected as its option e, and a person no longer chooses what goes into a commit."
  - id: "e"
    label: "replicate the box's disk or checkout outside git"
    how: "The substrate snapshots the volume, or the host copies the checkout to durable storage, on a schedule."
    tradeoff: "Works for any file. It ties durability to one substrate, copies caches and secrets with the work, and gives a reader nothing to list: no branch, head or label, and no way to tell which checkpoint holds which turn."
choice:
  option: "a"
  reason: "lex00 decided in the October burn-down (E4) that chant owns work in progress and checkpoints under refs/chant/wip/<branch>, one namespace, replicated per a spec policy, and that hud's turn checkpoints (hud#137), studio's staged, shipped and kept (studio#53) and pushing work off the box (studio#289) use it. ws-074 makes the repo the database and leaves uncommitted work on one disk until it is committed or replicated; this is the replication. Snapshots are commits so git carries them, push and fetch need nothing new, and a snapshot's tree is exactly what records --uncommitted reads after a restore. A temporary index keeps the checkout's index and branch as the person left them, so the history a person reviews has only the commits they made (ws-074, option e rejected). Keying the ref by branch rather than by person and session follows from git: a branch is checked out in one worktree at a time, so tabs and worktrees never contend for one snapshot ref, and who took a snapshot is a trailer anyone can read. The policy lives on the box block beside the factory (ws-077), because the box is where the disk that can be lost is, and the remote is named, not given as a URL, because a box holds no credential (#2726): the host adds the remote with the credential it brokers. chant pushes on save and on lease release, the two moments a tool or an executor hands work back; a record write never pushes, since chant's record writes never run git (ws-074). A schedule is the host's, so every is only stated. Pushes are never forced, so a box that lost a race never overwrites the remote, and the replica refs let status report how far behind each ref is without a fetch."
rejected:
  - option: "b"
    why: "Two tools would keep two histories of one working tree in two layouts, each with its own take, list and restore code, which is the second implementation ws-052 and ws-074 rule out, and a replacement box could restore only what it knew the layout of."
  - option: "c"
    why: "The identity and session segments are hud's model, which studio doesn't share, and the contention they guard against is already prevented by keying on the branch. A ref per checkpoint multiplies what is pushed and listed."
  - option: "d"
    why: "ws-074 already rejected committing per write: the tool, not the person, would author the branch's history."
  - option: "e"
    why: "It is one substrate's answer, it copies caches and secrets along with the work, and it gives a reader nothing to list or restore by turn."
