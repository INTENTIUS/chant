  issue: "INTENTIUS/chant#3165"
  row: "Studio owns publishing and the listing is a fact in the repo; remove hud's env-injected apply glue"
  revision: null
question: "How does a surface in a box, such as hud, ask for a built work item or the records it kept uncommitted to be published, who pushes the branch and opens the pull request, what record does each publish leave, and what does the surface read instead of the HUD_APPLY_CMD, HUD_APPLY_TO and HUD_ASK_CONSTRAINS variables the box's run script sets today?"
options:
  - id: "a"
    label: "the box block names its publisher, and chant workspace box publish runs it and checks what it did"
    how: "The box block takes publisher, a command run from the workspace root and split into words with no shell. Studio's kit names its own (the factory's apply step), and studio owns everything the command does: merging the item's branch into the box's checkout, pushing it to factory.publish's repo through the lobby's broker, opening the pull request, and sending the records a person kept. A surface asks with one call, chant workspace box publish <member> <item> --by <principal> [--head <owner/name>] [--dry-run], or chant workspace box publish <member> --records --by <principal> for the kept records (with --dry-run, which records would go). chant applies the identity rule to --by (ws-080), runs the publisher with a JSON request on stdin (the action, member, item, by, head, dryRun and the box's factory.publish as status prints it), reads the last JSON object the publisher prints, and checks the commit it names: an item's commit carries Chant-Applied-By naming --by, Chant-Applied-At, Chant-Applied-Commit and a Chant-Record for the item, and a records commit a Chant-Record for each record sent (ws-075). It prints box-publish.schema.json, with the commit, the pull request or the branch pushed, or why the work stayed in the box, and refuses with closed codes: publish-member-unknown, publish-none, publish-refused (the publisher exited 2), publish-failed, publish-answer-invalid and publish-unrecorded. chant runs no git push and no forge call itself. status --json prints the publisher under the member's box beside factory and listing, so a surface reads three facts from the declaration in place of the variables: whether to offer Apply (box.publisher), where an applied item goes (box.factory.publish, a pull request when it is set), and what an ask constrains (member:<box.factory.builds[0]>, as ws-077 already says). The listing stays where ws-077 put it, on the box block, written through chant workspace box listing set (#3308)."
    tradeoff: "hud and any other surface make one chant call and read one schema, and chant can hold every publisher to the apply record, so a publish that leaves no trailers is reported instead of passing silently. Studio rewrites its apply entry point to read the request from stdin and to write Chant-* trailers, and a declaration that names a publisher needs chant 0.103.0. chant spawns a command the declaration names, with the same trust as factory.check and a member's generators, and waits on it (ten minutes at most), so a slow push holds the call open."
  - id: "b"
    label: "the box block names its publisher, and each surface runs it"
    how: "The same publisher field, printed by status --json, but hud spawns it itself with studio's argv convention (<id> --by <who>, --records --list) and parses its answer, as it does with HUD_APPLY_CMD today."
    tradeoff: "No chant command to add or release. Every surface carries its own spawn, timeout and answer parsing, the argv convention lives in studio's script rather than a schema, and nothing checks that a publish left its apply record."
  - id: "c"
    label: "a publish request record that the orchestrator picks up"
    how: "hud writes a request through a chant command, onto chant/lifecycle or as a record, and studio's steward or a box process notices it, publishes, and writes the outcome back for hud to poll."
    tradeoff: "Publishing would survive a surface going away mid-call, and an agent could request one as easily as a person. The person pressing Apply waits on a loop that has to be running, the request needs a ledger or a record kind of its own, and a failure reaches them later, by polling."
  - id: "d"
    label: "chant pushes the branch and opens the pull request itself"
    how: "chant workspace box publish reads factory.publish and does the merge, the push and the GitHub call in core, with a token from the environment or a broker URL."
    tradeoff: "No publisher to write, and every orchestrator gets the same push. chant would hold or borrow a forge credential and make network writes in core, and would carry the merge, conflict and fork handling studio already has."
  - id: "e"
    label: "keep the environment variables, documented as a contract"
    how: "chant documents HUD_APPLY_CMD, HUD_APPLY_TO and HUD_ASK_CONSTRAINS as the names any box sets for any surface."
    tradeoff: "Nothing changes in any repository. A box's configuration stays in its run script instead of its declaration, and a surface in a box studio did not start has no way to learn the values."
choice:
  option: "a"
  reason: "#3165 asks that studio own publishing, that hud ask through one documented call, that hud read what it needs from the declaration, and that every publish leave an apply record. Naming the publisher on the box block moves the last piece of the env glue into the repo, where ws-074 puts a box's configuration, and status already prints the box block to every reader. Running it through chant makes the call one command with one output schema and closed codes, the way every other write a surface makes goes through chant, and gives chant the one place to check the apply record ws-075 defined: the trailers on the commit the publisher names. The work stays studio's: chant never pushes, never calls a forge and never commits, which ws-052 and ws-074 rule out for chant, and the lobby's egress broker that holds the GitHub credential is studio's runtime. HUD_APPLY_TO and HUD_ASK_CONSTRAINS need no call at all: both are already facts on the box block (factory.publish and factory.builds, #3146), so a surface reads them from status --json. The listing was already moved to the box block by ws-077 and is written through #3308, so this record only confirms it."
rejected:
  - option: "b"
    why: "Every surface would carry its own spawn, timeout, answer parsing and argv convention, and nothing would check that a publish left its apply record, so #3165's done-when would rest on each publisher's goodwill."
  - option: "c"
    why: "Apply is a person pressing a button and waiting for the pull request; a request and a poll add a ledger or a record kind, a loop that must be running, and a failure the person learns of later, for no gain over a call that answers."
  - option: "d"
    why: "chant would hold or borrow forge credentials and make network writes in core, which ws-052 keeps out of chant, and it would duplicate the merge, conflict and fork handling studio already has (arugula-salad/studio#242, #262)."
  - option: "e"
    why: "It keeps a box's configuration in its run script rather than its declaration, against ws-074, and leaves hud unable to tell where an item goes or what an ask constrains in a box that studio did not start."
