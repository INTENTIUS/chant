question: "Where does a durable fact about a workspace live, how does a tool such as hud, studio, behold or an agent write one, what may a tool keep outside the repository, and how is a writer held to that?"
options:
  - id: "a"
    label: "every durable fact is a file in the repo, written only through chant's write contract; a tool keeps only caches"
    how: "A fact is anything a person or agent decided, answered, reviewed, approved, wrote or was attributed with, and any configuration of a box or member. Facts live in the repo. Work in progress lives as files in the working tree of the active work branch (chant/work/<id>, or the box's checkout when nothing is leased), uncommitted until someone commits or applies it, so readable after a restart means re-read from the working tree through the read contract. Append-only history stays on the ledger branch, chant/lifecycle, with its leases, gates and runs (ws-068). Only four things may live outside the repo: secrets, held by a broker or vault the declaration names in box.capabilities; telemetry and other observations of a running system, which may be lossy; caches and indexes rebuildable from the repo; and runtime state of the substrate itself, such as a sprite's disk or a conversation transcript, which a record pins by hash and never copies. A tool writes only through chant's write contract: records new, amend, close and review, points ask and answer, work leases, the workEvidence activity and workspace upgrade. It never writes a record file itself and never keeps a fact elsewhere. A writer conformance suite holds a tool to this (#3159), with an amnesia test: delete every store the tool keeps, restart it, and every fact is still readable through the read contract."
    tradeoff: "A tool can lose its state and restart without losing anything a person did, and a second tool reads the same facts through the same contract. Each write costs a chant call, a fact a tool wants to query fast has to be indexed again from the repo, and chant has to carry a write command for every kind of fact a tool records. Uncommitted work sits on one disk until it is committed or replicated."
  - id: "b"
    label: "each tool keeps its own store and copies facts into the repo later"
    how: "hud keeps reviews, answers, attribution, spend, notes and the box listing in .hud/events.db, the lobby keeps apps, accounts and spend in JSON files, and each tool writes a record into the repo at turn end, on apply or on export."
    tradeoff: "Each tool queries its own store fast and writes in its own shape. The repo learns of a fact only when the tool copies it, so a lost box or a crash before the copy loses it, and nothing checks that the two copies agree."
  - id: "c"
    label: "a shared service is the source of truth, and the repo is a projection of it"
    how: "A database run beside the workspace, by chant or by a hosted service, holds the facts and serves queries. The repo gets record files written out of it for review."
    tradeoff: "Concurrent writers and queries become a database problem with known answers. chant becomes a service to run and secure, a workspace stops being readable from git alone, and the repo's copy can lag behind the service or differ from it."
  - id: "d"
    label: "tools write record files themselves, following the published schemas"
    how: "The facts are files in the repo, as in option a, but each tool parses and writes them with its own code against the kind schemas, without calling chant."
    tradeoff: "No chant call per write. Every tool carries its own validation, id allocation and scope checks, and they drift from chant's."
  - id: "e"
    label: "every write commits at once"
    how: "Each chant write makes a commit on the work branch, so there is no uncommitted work in progress and a restart reads HEAD."
    tradeoff: "A restart or a clone sees every write in git history, with nothing in the working tree to lose. History gets a commit per answer, made by the tool, and the caller can no longer group writes into the commit a person reviews."
choice:
  option: "a"
  reason: "The workspace spec exists so that the repository alone describes a workspace, and any tool built on it reads and writes the same facts. ws-052 already holds readers to the read contract and says hud writes only through chant commands, but nothing held writers to anything. So hud keeps reviews, intent-walk answers, turn attribution, spend, notes and a box's listing only in its own database, studio's lobby keeps apps, accounts and spend in JSON files, and studio's factory parses contracts and work files itself (#3154, arugula-salad/studio#287). Putting every fact in the repo makes it reviewable in a pull request, readable at any revision with --at, joinable to the commits made in answer to it (#3149), and kept when a box or a tool's state directory is lost. Writing only through chant keeps one implementation of ids, schemas, scope, approval and seals, the same reason ws-052 gives for one reader. The four exceptions are what a repo cannot or should not hold: secrets, a lossy stream, data derived from the repo, and the substrate's own runtime state, which records reach by hash. Leaving work in progress uncommitted keeps the chant write commands from running git, so the caller still chooses the commit and the pull request stays the unit of review. Keeping that working tree when a box is lost is #3172, and concurrent writers in one working tree are #3173. The amnesia test makes the rule mechanical: a tool that kept a fact only in its own store fails it."
rejected:
  - option: "b"
    why: "A fact kept in a tool's store is lost with the box before the copy happens, never joins the commits made in answer to it, and can disagree with the repo's copy. This is the state #3154 found and #3145 sets out to remove."
  - option: "c"
    why: "chant would have to run and secure a service, which ws-052 rules out, and reads at a revision, offline reads and review in a pull request would all go through that service instead of git."
  - option: "d"
    why: "It brings back the second implementation ws-052 rejected for readers: two writers of one kind can disagree about validity, hand out the same id and skip the write scope and approval rules that chant's write commands apply."
  - option: "e"
    why: "chant's write commands leave the commit to the caller so a person decides what goes into a commit and a pull request. Committing per write fills the history with one commit per answer and makes the tool, not the person, author of each one. Durability of uncommitted work against a lost box is handled by replicating it (#3172), not by committing it."
