plunge is a Pulumi fork with its own state backends. A Pulumi member can run
on it, and chant then runs `plunge` where it would run `pulumi`. The member
kind, the graph and the node ids are the same. The `plunge-member` example in
`lexicons/pulumi/examples/` is a workspace with one such member.

## How chant decides

| Source | Says plunge when | Read |
|---|---|---|
| `pulumi.member.engine` | it is `"plunge"` | first; when set, it decides |
| `Pulumi.yaml` `backend.url` | it starts with `plunge` (`plunge+file://...`, `plunge://...`) | when the config sets no engine |

Nothing else is read: not `PULUMI_BACKEND_URL`, not the CLI's login state.
Two checkouts of one repository therefore agree on the engine whatever their
environments hold. `PulumiWatchOp`'s `engine` field and the activities follow
the same rule.

A config that says `engine: "pulumi"` for a program whose backend URL is a
plunge URL runs stock `pulumi` against a backend it cannot open. PUL015
reports that at build time. The other way round, `engine: "plunge"` with a
stock backend, is not reported.

## What chant runs

| Read | Command | Changes the stack |
|---|---|---|
| graph | none; the export in the index store, else the checked-in `stack-export.json` | no |
| export after an apply | `plunge stack export --stack <name>`, from the `pulumi-up` apply only | no |
| change set | `plunge preview --json` | no |
| applied outputs | `plunge stack output --json --show-secrets=false` | no |
| drift | `plunge drift --resource <urn> --stream --stack <name>`, per resource | no |
| engine facts | `plunge graph --json --stack <name>`, once per member | no |

`runAllowedPlunge` refuses any other argv before it reaches the binary, as
ruled on [#4476](https://github.com/INTENTIUS/chant/issues/4476). For
`plunge graph` it lets through exactly four argv
([#4529](https://github.com/INTENTIUS/chant/issues/4529)):

```
plunge graph --json
plunge graph --json --stack <stack>
plunge graph --json --versions
plunge graph --json --stack <stack> --versions
```

Flags go in that order, each at most once. Any outputs or secrets flag is
refused, since chant never asks plunge for an output value.

## Engine facts

`plunge graph --json` prints the stack's graph from plunge's records, in the
engine graph document of [#4520](https://github.com/INTENTIUS/chant/issues/4520).
It reads no live object and makes no provider call. chant reads it two ways:

| Read | Source | What it adds |
|---|---|---|
| `describeResources` | `plunge graph --json --stack <name>` | each node as a resource, with plunge's `physicalId` and its facts on `ResourceMetadata.facts`; `ownership` is `unknown` and no marker is set |
| the graph | a checked-in `engine-graph.json` beside `stack-export.json` | `nodes[].facts`, and the `property` edges with `grain: "property"` |

The export's `dependencies` and `parent` edges carry `grain: "instance"`
on every member. The graph's provider edges are not taken, since providers
have no node. Facts are for people and for readers that show the graph:
nothing in chant decides from them. plunge's markers say `source: "record"`,
what its record says it wrote, and its ownership is only `bound` or
`pending`.

`describeResources` leaves `--versions` off: it costs one version listing
per record. Take the file with the same command the read runs:

```bash
plunge graph --json --stack dev > engine-graph.json
```

A stock member gets no facts, and chant runs nothing new for it. A plunge
older than `plunge graph` fails the read, and every entity is then
not-observed with `read-failed`.

## Drift

`plunge drift --stream` prints drift-record NDJSON, one record per line, so
chant decodes it rather than mapping a refresh's steps. Each record is placed
on a node by the same URN rule the graph uses (`@intentius/chant/pulumi-urn`).
A resource plunge cannot read, such as a component with no cloud object,
comes back not-observed with plunge's reason.

## The export

A stack chant applies with `pulumi-up` gets its export written to the index
store after each `plunge up`, as a stock stack does. A stack applied outside
chant checks in the same `stack-export.json` a stock member does, taken with
plunge:

```bash
plunge stack export --file stack-export.json
```

Every check on [The stack export](../stack-export/) applies to it.
