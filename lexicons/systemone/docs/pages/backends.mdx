## The config namespace

```ts
systemone: {
  backends: {
    systemone: { url: "https://api.typesafe.ai", key: { env: "TYPESAFE_API_KEY" } },
    local: { url: "http://127.0.0.1:8080" },
    studio: { url: "http://127.0.0.1:7071", key: { capability: "inference", member: "box" } },
  },
}
```

| Field | Meaning |
|---|---|
| `url` | The server's base URL. `/v1/systemone` is appended. |
| `key` | Where the bearer key comes from. Omitted for a server that takes none. |
| `timeoutMs` | How long to wait before the backend counts as unreachable. Default 30000. |

The backend's name is the `backend` a point's model decider writes. Each backend also joins the build as a `Systemone::Backend` entity, carrying its URL and where its key comes from, so SYS010 can read it.

## Keys

A key is never written into the config. SYS001 fails a string where a key goes, and so does the activity's contract.

| Form | Meaning |
|---|---|
| `{ env: "VARIABLE" }` | The key is read from the variable when the step runs. |
| `{ capability, member?, env? }` | The key is reached through a capability a box member declares as brokered (`box.capabilities` in `chant.workspace.json`). The capability must be declared and name a broker. With `env`, the broker sets that variable for the Op's process. Without it, the broker is the endpoint and adds the key itself, so none is sent. |

Without `member`, the one member whose box declares the capability is used. A capability declared by two members needs `member`.

## The wire format

```
POST <url>/v1/systemone          Authorization: Bearer <key>
{ "model": "jev-1.13.0", "state": { ...inputs }, "questions": { "<point>": { "type", "instructions", "criteria" } } }
```

The point's inputs are the state, and its question is the one question asked, under the point's name. The answer is read back from `answers["<point>"]`, the same place `chant workspace points ask --response` reads it. The response's `model` is compared with the pin by core, so a server that answers with another model is recorded as not observed.

## When the backend can't be reached

Each of these throws, and core reads the throw as the backend being unreachable: an unset key variable, a network error, a timeout, a status that is not 2xx (Jev's are 401, 422, 429 and 529), and a response without an answer to the question asked. The point's `unreachable` then decides whether the question escalates or the step fails.

## The stub

`startStubBackend()` starts a stub server on 127.0.0.1 for tests. It answers 401 to a wrong bearer when a key is set, 422 to a body outside the wire format, and a forced status when the test sets one. Otherwise it answers each question with what the test scripts, or with a confident answer of the question's own type. Every request it read is kept in `requests`.

## The live test

`decide.live.test.ts` runs against a real server when `TYPESAFE_API_KEY` is set, and is skipped otherwise. `TYPESAFE_BASE_URL` points it at another compatible server, and `TYPESAFE_MODEL` names another pinned model id.
