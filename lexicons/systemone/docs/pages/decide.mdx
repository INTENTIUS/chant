`decide` is the lexicon's one Op activity. It asks a decision point for one set of inputs and records the answer. `loadActivities(["systemone"])` resolves it by name, and the typed builder is `decide` from `@intentius/chant-lexicon-systemone`.

```ts
decide("slice-tier", { read: { "work-item": "W-002" }, subject: "W-002" })
```

## Arguments

| Argument | Meaning |
|---|---|
| `point` | The point's name, as its points file declares it. The builder takes it first. |
| `inputs` | Input values by the point's input names, such as `{ "work-item.fits_small": false }`. They win over values read with `read`. |
| `read` | What to read through the read contract, by output. `{ "work-item": "W-002" }` reads work item W-002 for every `work-item.*` input. |
| `subject` | What the question is about, such as a work item's id. It is written to the answer's `constrains`. |
| `kind` | The answer kind file, or a declared kind's name. Without it, the declared answer kind whose points file declares the point. |
| `cwd` | Where the workspace is found. Defaults to the working directory. |
| `backends` | Backends by name, in place of `systemone.backends` in `chant.config`. |
| `dryRun` | Ask, but write nothing, and return the question whatever its state. |

Core's OPS012 checks every step's arguments against the activity's contract at `chant build`, so a misspelled argument or a key written as a string fails the build.

## Reading inputs

A point names each input as a read-contract output, optionally with a dotted field. `read` reads these by id or name:

| Output | Read as |
|---|---|
| `record`, `decision`, `work-item` | a record by id, from the declared record kinds, as `records --json` lists it |
| `member` | a member by name, as `ls --json` lists it |

A record's field is looked up in its front matter first, then in the record as the read contract lists it. A field the record lacks is left out and listed in the result's `missing`, so no table row matches on it. The other outputs a point may name (finding, region, commit, gate, release, environment, component) go in `inputs`, as the read contract printed them.

## What the step does

1. It checks every backend the point's model deciders name: each is configured, and a key that names a brokered capability is declared on a box with a broker. A problem fails the step before anything is asked or written.
2. It reads the inputs.
3. It asks the point through core's `askPointInRun` ([#2749](https://github.com/INTENTIUS/chant/issues/2749)), with the backend call as the model decider. Core runs the chain: a table row answers, a model at or above its threshold proposes, and otherwise the question escalates to people. Core writes the answer record.

Because core writes the answer, the same point, declaration and inputs are answered once. Asking again finds the record that is there, and the backend is not called.

## An open question stops the run

An answered question is the step's result, and the Op goes on. A question that is escalated, or proposed by a model, is still open. The step then throws core's `PointWait`, and the run ends with status `waiting`, the way a gate ends it with `gated`. No later step runs, and `chant run` exits 3.

A person answers the question through hud or at a shell:

```bash
chant workspace points --open
chant workspace points answer <id> --answer <value> --by <name>
```

The next run asks the same point with the same inputs, reads the answer from its record, and goes on. Answering as the model proposed confirms the proposal, and the result then names the model as the decider and the person in `answeredBy`. A model's answer can route or report, and it never decides on its own.

## The result

| Field | Meaning |
|---|---|
| `id`, `path` | The answer record: the point's name and the first 12 hex digits of the inputs hash. |
| `state`, `open` | `answered`. A dry run returns the question in any state. |
| `answer` | The answer. |
| `decider`, `model`, `backend`, `confidence`, `threshold` | Who gave the answer: a table, a model a person confirmed, or the quorum. For a model, its pin, backend, confidence and threshold. |
| `answeredBy` | The people who answered, when people did. |
| `escalations` | Each decider asked that did not answer, and why. |
| `missing` | Declared inputs the read value did not have. |

A later step may read these through a step reference, such as `step.out.answer`.

## In a steward's turn

A steward runs unattended, so its model call goes through the broker. Core makes the call only through a capability the steward declares, and the capability is the one the backend's brokered key names, or `inference` when none does. A backend whose key is an environment variable is not called in a steward's turn, since the steward would hold that key. Either way the question is recorded with the reason and goes to people. The question names the steward and its run, and the steward never counts toward its answer.

## Failing closed

A model decider declares `unreachable`. With `"escalate"`, the default, a backend that can't be reached leaves the question open for people with the reason, and the run waits on it. With `"fail"`, nothing is written and the step fails with `point-decider-failed`.
