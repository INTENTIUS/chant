`chant import` turns an existing `docker-compose.yml` or `Dockerfile` into chant TypeScript.

## Import docker-compose.yml

```bash
chant import --lexicon docker docker-compose.yml -o src/compose/
```

Given:

```yaml
services:
  api:
    image: myapp:1.0
    ports:
      - "8080:8080"
    environment:
      NODE_ENV: production
volumes:
  pgdata: null
```

`-o` names a directory; the import writes `main.ts` in it. This produces `src/compose/main.ts`:

```typescript
import { Service, Volume } from "@intentius/chant-lexicon-docker";

export const api = new Service({
  image: "myapp:1.0",
  ports: ["8080:8080"],
  environment: {
    NODE_ENV: "production",
  },
});

export const pgdata = new Volume({});
```

Import keeps every field the Compose spec defines for a service, volume, network, config or secret, and `x-` extension fields. A field the spec does not define is dropped, and the import names it in a warning. A top-level key other than `services`, `volumes`, `networks`, `configs` and `secrets` (such as `name` or `include`) is not imported and is also named in a warning.

An export name is the compose key in camelCase. When the key is not a TypeScript identifier (`db-password`, `nginx.conf`), or two kinds share it, the import wraps the entity in `composeKey`, so the build writes the original key and references to it by name still match:

```typescript
export const dbPassword = composeKey("db-password", new DockerSecret({ environment: "DB_PASSWORD" }));
```

## Import a Dockerfile

```bash
chant import --lexicon docker Dockerfile -o src/web/
```

A Dockerfile imports as `steps`, one per instruction, in the order the file has them, so building the import writes the same instructions in the same order. `ARG` lines before the first `FROM` become `globalArgs`. Line continuations and heredocs are kept as written. Comments are dropped.

Given:

```dockerfile title="Dockerfile"
# Build stage
ARG NODE_VERSION=20
FROM node:${NODE_VERSION}-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build \
    && npm prune --omit=dev
FROM node:${NODE_VERSION}-alpine
WORKDIR /app
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]
```

Produces:

```typescript title="src/web/main.ts"
import { Dockerfile } from "@intentius/chant-lexicon-docker";

export const app = new Dockerfile({
  globalArgs: ["NODE_VERSION=20"],
  stages: [
    {
      from: "node:${NODE_VERSION}-alpine",
      as: "build",
      steps: [
        { workdir: "/app" },
        { copy: "package.json package-lock.json ./" },
        { run: "npm ci" },
        { copy: ". ." },
        { run: "npm run build \\\n    && npm prune --omit=dev" },
      ],
    },
    {
      from: "node:${NODE_VERSION}-alpine",
      steps: [
        { workdir: "/app" },
        { copy: "--from=build /app/node_modules ./node_modules" },
        { copy: "--from=build /app/dist ./dist" },
        { user: "node" },
        { expose: "3000" },
        { cmd: '["node", "dist/server.js"]' },
      ],
    },
  ],
});
```

The export is named `app`, so it builds `Dockerfile.app`. Rename the export to choose the file name, and point the Compose service at it by reference, which builds as the file name:

```typescript
import { app } from "../web/main";

export const web = new Service({
  build: { context: ".", dockerfile: app },  // dockerfile: Dockerfile.app
});
```

Exec-form values such as `CMD` stay strings; you can change them to lists (`{ cmd: ["node", "dist/server.js"] }`). See [Dockerfiles](/chant/lexicons/docker/dockerfiles/) for the step format.

## Import a running compose project

```bash
chant import --from <env> --lexicon docker -o src/compose/
```

`chant import --from` reads a compose project's containers from the Docker Engine API ([#4388](https://github.com/INTENTIUS/chant/issues/4388)) and writes the services they were created from. The Engine is the one `DOCKER_HOST` names (a `unix://` socket or a plain `tcp://` endpoint), else `/var/run/docker.sock`. The project is `COMPOSE_PROJECT_NAME` when it is set, else the environment name, and its containers are the ones labelled `com.docker.compose.project=<project>`. A scaled service is read from its first container, and `compose run` containers are skipped.

Each service gets its image, command, entrypoint, environment, labels, working directory, user, healthcheck, ports, restart policy, `depends_on`, volumes and networks. What the image already supplies (its command, environment, labels and so on) is left out, so the service reads as it was declared; `--verbatim` keeps it. Compose's own `com.docker.compose.*` labels are always left out. Volumes and networks named after the project become top-level entries; the others are declared `external`.

Outside swarm, a top-level config is not an Engine object, so its key and its `content` are not kept anywhere the Engine can return them. Import reads a config through the container instead: each absolute file path the service's command names (`--config=/etc/otel/config.yaml`) is read with `GET /containers/{id}/archive`, and one that holds a single text file becomes a config with that `content`, mounted at that path and named `<service>-<file name>`. A path inside a volume or a directory bind mount is left to that mount.

`--owned` exports only services labelled `app.kubernetes.io/managed-by: chant` (set with [`defaultLabels`](/chant/lexicons/docker/default-labels/)); the docker serializer stamps no ownership marker of its own.

## Workflow

Import is a one-time migration step, not an ongoing sync. After importing:

1. Review the generated TypeScript; complex fields may need edits by hand
2. Run `chant lint src/` to catch issues
3. Run `chant build src --lexicon docker -o build/docker-compose.yml` and diff the output (and the `Dockerfile.*` files beside it) against the originals
4. Delete the original file and commit the TypeScript source

## Limitations

- `extends:` (Compose file inheritance) is not supported
- Dockerfile comments and parser directives (`# syntax=...`, `# escape=...`) are dropped
- `MAINTAINER`, which has no step, is left as a comment with a warning; use a `label` step instead
- Build args with complex shell expressions may need cleanup by hand
- Environment variable syntax (`${VAR}`) is kept as written; replace it with `env()` by hand if you want
- A live import does not recover `deploy`, `build`, secrets, or a config the command does not name; a TLS Engine endpoint (`DOCKER_TLS_VERIFY`) is not supported
