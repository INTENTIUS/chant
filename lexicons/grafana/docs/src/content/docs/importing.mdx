`chant import` reads dashboard JSON and writes TypeScript that declares the same dashboard with this lexicon's classes. `chant build` on the result gives back the dashboard you started from. Anything the lexicon cannot express yet is printed as a warning, never dropped silently.

## Import a dashboard

Export the dashboard from Grafana (Export > Export as JSON, with the Classic model), then, from a chant project whose `chant.config.ts` lists `grafana`:

```bash
chant import checkout.json --output src
```

Outside a project, name the lexicon: `chant import checkout.json --lexicon grafana --output src`. Either export works, with or without "Export for sharing externally". The importer also reads a dashboard as `GET /api/dashboards/uid/<uid>` returns it, a `dashboard.grafana.app` v1 resource, and Grafana's datasource and dashboard provisioning files.

Each dashboard is written to a directory of its own, named after its uid, so a second import into the same `src` does not collide with the first:

| File | Holds |
|---|---|
| `variables.ts` | one variable per entry of the dashboard's variable list, datasource variables first |
| `datasources.ts` | an `ExternalDatasource` per datasource the panels name by uid |
| `plugins.ts` | a `definePanel` or `defineQuery` for each plugin chant has no class for |
| `panels.ts` | the panels above the first row, each with its queries |
| `row-<title>.ts` | one per row: the row and the panels under it |
| `dashboard.ts` | the `Dashboard`, listing the variables, panels and rows |

A module with more than eight declarations is split into `row-cpu-1.ts`, `row-cpu-2.ts` and so on, the limit COR009 sets, keeping each panel in the same file as its queries. Then build it:

```bash
chant build src --lexicon grafana -o dist/grafana/index.json
```

## What the generated source looks like

A panel becomes a constant named after its title, and its queries take the panel's name and their refId. Nested settings are lifted into named consts typed by the class's props, which is how COR001 wants a declaration written:

```ts title="checkout-service/panels.ts"
const requestRateEnvA = new PromQuery({
  editorMode: "code",
  expr: 'sum by (route) (rate(http_requests_total{job=~"$job", env=~"$env"}[$window]))',
  legendFormat: "{{route}}",
  range: true,
  refId: "A",
});

const requestRateEnvGridPos: PropsOf<typeof TimeSeriesPanel>["gridPos"] = { h: 8, w: 12, x: 0, y: 0 };
const requestRateEnvOptions: PropsOf<typeof TimeSeriesPanel>["options"] = {
  legend: { calcs: ["mean", "max"], displayMode: "table", placement: "bottom", showLegend: true },
  tooltip: { hideZeros: false, mode: "multi", sort: "desc" },
};
const requestRateEnv = new TimeSeriesPanel({
  id: 1,
  title: "Request rate ($env)",
  gridPos: requestRateEnvGridPos,
  options: requestRateEnvOptions,
  datasource,
  targets: [requestRateEnvA],
});
```

Panel ids, positions and query refIds are carried as they are, so the rebuilt dashboard keeps its layout and any links to `viewPanel=<id>`. A panel's `repeat` names the variable constant, and a panel or query that uses a datasource variable holds that variable. A key left at the value Grafana assumes when it is missing (`transparent: false`, an empty `options`) is not written.

A panel type chant has no class for yet (`piechart`, `bargauge`) is declared with `definePanel` in `plugins.ts`, and a query to a datasource type chant has no class for with `defineQuery`. Their options are carried as data, typed `Record<string, unknown>`; see [Other Panel and Datasource Plugins](../custom-plugins/) to type them.

## Datasources

A reference by uid (`{ "type": "prometheus", "uid": "prom" }`) becomes an `ExternalDatasource` in `datasources.ts`: the datasource as it exists in your Grafana, which the build does not provision but GRAF101 and GRAF102 check references against. To provision it from chant as well, replace it with a `Datasource` of the same uid. Grafana's own pseudo-datasources (`-- Grafana --`, `-- Dashboard --`) stay plain `{ type, uid }` refs. A datasource variable whose selected value is a uid adds an `ExternalDatasource` for it too.

GRAF101 fails a build in which a datasource variable's type has no declared datasource. So when the dashboard names some datasources by uid but none of a datasource variable's type, the importer writes those uids as plain refs instead, so the build passes, and its warning lists what to declare. A dashboard that names its datasources only through variables (a shared export) gets a GRAF101 warning after a build that it cannot check them, until you declare them.

An export made for sharing names its datasources through `__inputs` and `${DS_PROMETHEUS}`, which Grafana's import dialog fills in. The importer turns each such input into a `DatasourceVariable` of the same name, so every `${DS_PROMETHEUS}` in the dashboard still resolves, now to whatever the variable selects. A constant input (`${VAR_SERVICE}`) is replaced by its value, as the import dialog would. Both are reported.

## What is not carried

`chant import` prints a warning for each of these, and leaves it out:

- annotations other than Grafana's built-in one (#2953);
- library panels, and the `__elements` that carry their models;
- ad hoc filter, group by and switch variables, and anything but the query string of a query variable whose query is an object (#2952);
- a top-level dashboard or panel key no prop takes, such as `gnetId`, and the `__requires` plugin list;
- a textbox variable's current value when it differs from its default.

One is reported but not left out: a panel with no datasource inside a row that has one. A chant `Row` gives such a panel the row's datasource, which Grafana does not.

The stored copy's `id`, `version` and `iteration` are Grafana's bookkeeping, not part of the dashboard, and are dropped without a warning.

## Older dashboards

The dashboard's `schemaVersion` is carried, so Grafana still runs its migrations when it loads the rebuilt JSON. What the importer cannot carry is a panel from the AngularJS era (`graph`, `singlestat`), which keeps its settings as top-level panel keys: the panel is imported, its settings are reported and left out. To keep them, load the dashboard in Grafana 11 or later, which converts those panels, export it again and import that export. A dashboard saved before Grafana 5.0, with its panels inside a top-level `rows` list, is reported and not imported at all; the same re-export fixes it.

A v2 dashboard (Grafana 13's default "V2 Resource" export) is recognised and reported, and nothing is imported. Export it with the Classic model instead. Reading v2 is #2947.

## Keys outside the typed options

The panel and query types follow the schemas at the pin (see [Where the Types Come From](../schema-pin/)). A community dashboard can carry keys they do not list, such as the old `step` and `metric` fields on a Prometheus query. Such a key still imports and still builds back to the same JSON, but `tsc` reports it at the constructor or const that holds it, and GRAF107 warns about it after a build. Delete the key if Grafana no longer reads it, or keep it and mark the line with `// @ts-expect-error` and a reason.

## How the round trip is checked

`src/import/roundtrip.test.ts` imports every dashboard in the lexicon's corpus, builds it, and compares the result with the source: Grafana 12.4.11 and 13.2.2 UI exports, Node Exporter Full and other community dashboards from grafana.com (their sources and licenses are in `test/fixtures/community/README.md`), and what the lexicon's own examples build. The comparison applies the importer's edits to the source (each key left out, each value written in another form) and then puts both sides through `normalizeDashboard`, which removes the keys Grafana fills in or derives. A dashboard chant built comes back as the same text.
