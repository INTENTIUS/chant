`tsc` sees a tagged template's text as a plain string, so on its own it cannot tell that `${orders.columns.emial}` names no column. `chant sql types` closes the gap: it builds the project and writes the columns of every table, view and dictionary the build declares as TypeScript declarations. A tag that names its object as a type argument then returns typed columns.

## Name the declaration

Give the `table`, `view` or ClickHouse `dictionary` tag the object's qualified name as its type argument:

```ts
// src/schema.ts
import { schema, table } from "@intentius/chant-lexicon-sql/postgres";

export const shop = schema`CREATE SCHEMA shop`;

export const customers = table<"shop.customers">`
  CREATE TABLE ${shop}.customers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL
  )`;

export const orders = table<"shop.orders">`
  CREATE TABLE ${shop}.orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES ${customers} (${customers.columns.id}),
    refunded_at timestamptz
  )`;
```

The name is `schema.name` in Postgres and `database.name` in ClickHouse, unquoted, with Postgres's folding applied (`CREATE TABLE Shop.Orders` is `shop.orders`). An object the DDL does not qualify is its name alone. The type argument changes nothing at build time: the build output is the same with it or without it.

`chant import` and `chant import <file>.sql` write the type argument on every table, view and dictionary they declare.

## Generate the declarations

```sh
chant sql types
```

The command builds the project the way `chant build` does and writes `sql-types.d.ts` in the project's `sourceDir`, or in the project root when `sourceDir` is unset. Any tsconfig that includes the schema includes the file too. `--output <path>` writes it somewhere else. `chant build` never writes it.

The file starts with chant's generated-file marker, so source discovery skips it, and it is a module that augments the dialect's `SqlSchema` interface:

```ts
// Generated by chant — do not edit directly. `chant sql types` writes it from the build's entities.
import type { Column, KeyColumn } from "@intentius/chant-lexicon-sql/postgres";

declare module "@intentius/chant-lexicon-sql/postgres" {
  interface SqlSchema {
    /** src/schema.ts: orders */
    "shop.orders": {
      columns: {
        id: Column<"bigint", { ts: string; nullable: false; cmp: "N" }>;
        customer_id: Column<"bigint", { ts: string; nullable: false; cmp: "N" }>;
        refunded_at: Column<"timestamp with time zone", { ts: Date; nullable: true; cmp: "D" }>;
      };
      /** `${}` 3 is the column customer_id references. */
      slots: [unknown, unknown, KeyColumn<"N">];
    };
  }
}
```

Each column carries its type as the catalog spells it and its value in application code (`ts`). `nullable` says whether it can be NULL, and `cmp` is how it compares in a key. `slots` types the template's interpolations by position, up to the last one that is checked.

Commit the file, and run the command again after a schema change. The checks below are only as current as the file. If `order_ref` changes to `bigint` and nobody regenerates, tsc keeps checking the old type, and a `${}` inserted before a checked one shifts the positions until the next run.

The command refuses to write `sql-types.d.ts` when a `sql-types.ts` sits beside it, since tsc would read the `.ts` file and drop the declarations.

## What tsc checks

A column that does not exist is a compile error, with a suggestion:

```
error TS2551: Property 'emial' does not exist on type '{ id: Column<"bigint", ...>; ... }'. Did you mean 'email'?
```

A Postgres foreign key whose referenced column is interpolated is checked against the referencing column. Types compare by their catalog category, as Postgres compares them: `integer` to `bigint` passes and `text` to `bigint` does not. A domain compares as its base type and an enum as itself. The error lands on the `${}` that names the column:

```ts
order_ref text NOT NULL REFERENCES ${orders} (${orders.columns.id})
// error TS2345: Argument of type 'Column<"bigint", ...>' is not assignable to parameter of type 'KeyColumn<"S">'.
```

In ClickHouse, a `Nullable` column interpolated as an element of a materialized view's `ORDER BY` or `PRIMARY KEY` is a compile error (`NotNullColumn`).

Some things stay outside tsc, and the build and lint checks cover them instead:

- A key with no interpolated column has no slot. `REFERENCES ${customers}` with no column list, and a table named in text, are checked by SQLPG124 at build and lint.
- A ClickHouse table's own `ORDER BY (kind, country)` names its columns in text, since a table cannot interpolate itself. SQLCH002 reports a Nullable sort key there.
- A view's column is typed when it passes one column through (`${t.columns.c}` or `o.${t.columns.c}`, with or without an alias). A computed column (`count()`) is `Column<"unknown", ...>`.
- A composite's members get their entry in `SqlSchema`, so `RowOf<"name">` covers them, but the composite's return value keeps unchecked columns.

## Adopt it one declaration at a time

A tag with no type argument keeps unchecked columns: any name type-checks, as before. So does a name the generated file does not list yet. An unchecked column fits every slot, so a typed table can reference an untyped one's column. A typed table is still a `PostgresTable` (or `ClickHouseTable`), so it passes wherever one is expected, a composite's input included.

## Row types for application code

`RowOf` takes a typed declaration or a qualified name, which also covers an object declared only in a `.sql` file:

```ts
import type { RowOf } from "@intentius/chant-lexicon-sql/postgres";
import type { orders } from "./schema";

type Order = RowOf<typeof orders>;
// { id: string; customer_id: string; refunded_at: Date | null }
type User = RowOf<"shop.users">; // src/users.sql
```

`RowOf<"shop.ordrs">` is a compile error, and so is `RowOf<typeof t>` for a `t` declared without a type argument. A nullable column's type gets `| null`. A Postgres view's columns are always nullable, as Postgres's own catalog reports them.

## The type mapping

Postgres values are what node-postgres returns with its default type parsers:

| Postgres type | TypeScript |
|---|---|
| `smallint`, `integer`, `real`, `double precision`, `oid` | `number` |
| `bigint`, `numeric`, `money` | `string` (no JavaScript number holds every value) |
| `boolean` | `boolean` |
| `date`, `timestamp`, `timestamptz` | `Date` |
| `time`, `timetz` | `string` |
| `interval` | `{ years?: number; months?: number; days?: number; hours?: number; minutes?: number; seconds?: number; milliseconds?: number }` |
| `point` | `{ x: number; y: number }` |
| `circle` | `{ x: number; y: number; radius: number }` |
| `json`, `jsonb` | `unknown` |
| `bytea` | `Uint8Array` |
| an enum | the union of its labels |
| a domain | its base type's |
| `T[]` | the element type's array |
| every other built-in type (text types, `uuid`, network addresses, ranges, the `reg*` types, `xml`...) | `string` |
| a type outside the project | `unknown` |

The driver parses arrays of the built-in types it knows. An array of an enum or a domain arrives as its text form unless the application registers a parser for it.

ClickHouse values are what its JSON formats (`JSONEachRow`) write with the server's default settings:

| ClickHouse type | TypeScript |
|---|---|
| `UInt8` to `UInt32`, `Int8` to `Int32`, `Float32`, `Float64`, `BFloat16`, `Decimal*` | `number` |
| `UInt64` and wider, `Int64` and wider, `Interval*` | `string` (quoted by `output_format_json_quote_64bit_integers`) |
| `Bool` | `boolean` |
| `String`, `FixedString`, `UUID`, `IPv4`, `IPv6`, `Date`, `Date32`, `DateTime`, `DateTime64`, `Time`, `Time64` | `string` |
| `Enum8`, `Enum16` | the union of their labels |
| `Nullable(T)` | `T \| null` |
| `LowCardinality(T)`, `SimpleAggregateFunction(f, T)` | `T` |
| `Array(T)` | `T[]` |
| `Map(K, V)` | `Record<string, V>` |
| `Tuple(a T, b U)` | `{ a: T; b: U }` |
| `Tuple(T, U)` | `[T, U]` |
| `Point`, `Ring`, `LineString`, `Polygon`, `MultiLineString`, `MultiPolygon` | nested `[number, number]` arrays |
| `JSON`, `Dynamic`, `Variant`, `AggregateFunction`, `Nested`, `Geometry`, `QBit` | `unknown` |

The mapping covers every type in the pinned catalog of each dialect, and a test fails when a new catalog adds a type it does not cover.

## More than one project in a program

Two projects of the same dialect that declare the same qualified name both augment the one `SqlSchema`, and a single `tsc` program over both reports a duplicate property. Give each project its own tsconfig, as workspace members already have.
