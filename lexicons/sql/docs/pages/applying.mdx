`clickhouseApply` makes the ClickHouse server an environment is bound to hold what a `chant build` declares; `postgresApply` does the same for a Postgres server, and [Postgres](#postgres) below covers what differs. It is what `ApplyOp` runs for `target: "clickhouse"`, and an Op step of its own for a hand-written Op. It sends the statements for the changes [the classifier](../change-classifier/) puts in the metadata-only and background-rewrite classes, and nothing for a rebuild.

## Apply with ApplyOp

Build to `dist/schema.json`, the target's default output, and bind the environment as for [importing](../importing/) (`sql.profiles.<env>` in `chant.config.ts`, else `CLICKHOUSE_URL`):

```typescript
// ops/schema-apply.op.ts
import { ApplyOp } from "@intentius/chant/op";

const { op } = ApplyOp({
  name: "schema-apply",
  env: "prod",                 // selects sql.profiles.prod
  target: "clickhouse",
  delete: "gated",             // prune owned orphans and allow column drops, behind an approval gate
  gate: { gate: "approve-schema-apply" },
});

export default op;
```

`chant run schema-apply` stops at the gate before anything is written, and the next run after `chant approve schema-apply approve-schema-apply` applies. The run reports the counts every target reports: applied, pruned and not attempted.

## What each object gets

Every declared object comes back with one verdict.

| Verdict | When |
|---|---|
| applied, `created` | the server does not have it; its declared `CREATE` runs, with chant's marker in its comment |
| applied, `updated` | the server has it and the `ALTER`s for its changes ran |
| applied, `unchanged` | nothing to change and the marker in place; nothing is sent |
| not attempted, `unsupported-kind` | a change needs a rebuild (a sorting key, a partition key, an engine, a key column's type). Nothing is sent for the object. The detail names each rule, the `ALTER` restriction behind it and the ClickHouse page it is stated on, and the [`ClickHouseRebuildOp`](../rebuild/) declaration that runs it instead |
| not attempted, `filtered` | the change drops a column, which destroys its data, and the apply may not delete (`delete: "never"`, the default) |
| not attempted, `dependency-failed` | an object it references is not on the server because creating it failed or was not attempted |
| not attempted, `no-binding` / `no-credentials` | there is no server to apply to, or it refused the credentials |

A statement the server refuses fails the step. The objects after it are still applied, and the error lists what failed, what was applied and what was not attempted.

The SQL is the declaration's own text: an added column is sent as it is written, at its declared place (`ADD COLUMN ... AFTER`), and appending new columns to the sorting key goes in one `ALTER` with their `ADD COLUMN`, which is the only way ClickHouse allows it.

## Background rewrites

A column type change and a TTL change are mutations: the server records the `ALTER` and rewrites existing parts afterwards. The applier waits until `system.mutations` lists none unfinished for the table before it reports the table applied, ten minutes by default (`mutationTimeoutMs`). A mutation still running at the deadline fails the apply with its id, and one the server reports failing fails it at once with the server's reason; both messages say how to `KILL MUTATION`.

## The ownership marker

ClickHouse objects carry no tags, so chant's marker is a trailer on the object's own comment:

```sql
COMMENT 'Raw events [chant managed-by=chant stack=shop env=prod]'
```

The declared comment is kept and the trailer goes after it. It is set in the `CREATE`, so no object is created unmarked, and taken off again wherever chant reads a definition: a plan, the deep diff and an import compare and write the declared comment alone. `stack` and `env` are the project's `ownership.stack` and `ownership.env`. An object whose comment someone rewrites by hand loses the trailer and reads as not chant's, so it is never pruned; the next apply of its declaration stamps it again.

`chant lifecycle diff --live` reports a marked object `owned` and an unmarked one `foreign`, and `chant import --from <env> --owned` imports the marked ones.

## Prune

With `delete: "owned-only"` or `"gated"`, the apply drops the tables, views and databases in the declared databases that the build no longer declares, views before tables and databases last, but only those whose comment carries this project's marker, stack and env both. A table made by hand, or one another chant project stamped, is never touched. A database that still holds an object the prune does not drop is kept. A project with no `ownership.stack` cannot tell its objects from another project's, so a prune reports its candidates as `not-prunable` and drops nothing.

## A local server

`chant emulator up --lexicon sql` starts the pinned `clickhouse/clickhouse-server` (the image and digest the types come from) on port 8123; `--json` reports it as `CLICKHOUSE_URL`, which the binding reads when no profile names a server.

## Postgres

`postgresApply` is what `ApplyOp` runs for `target: "postgres"`. The build output and the binding are the same as for ClickHouse: `dist/schema.json`, and `sql.profiles.<env>` with a `postgres://` URL, else `POSTGRES_URL`, `POSTGRES_USER` and `POSTGRES_PASSWORD`. It sends the statements for every change [the Postgres classifier](../postgres-change-classifier/) does not refuse, and the verdicts are the ones in the table above, with three differences:

- An expand-and-contract change (a column rename, a type change across kinds, a `NOT NULL` column with no default, a view losing a column) is not attempted, `unsupported-kind`. The detail names each rule, its restriction and the Postgres 18 page, and for a column rename or a type change across kinds the `PostgresMigrationOp` declaration that makes it instead (see [below](#a-column-rename-or-type-change)); the other expand-and-contract changes have no Op yet.
- An object another tool keeps (an ORM's revision table, a managed provider's schema) is not attempted, `filtered`.
- When a statement fails, its transaction rolls back. Its own object fails the apply, and every other object whose statements were in that transaction is not attempted, `dependency-failed`, with the failing statement and the server's message in the detail.

### A column rename or type change

`chant sql plan` and `chant sql diff` print a `PostgresMigrationOp` declaration for each column they refuse as a rename (SQLPG205) or a type change across kinds (SQLPG208), and `--json` carries them as `migrationOps`. Put it in an `*.op.ts` file and run it until it is done; each run goes as far as the next gate:

```typescript
import { PostgresMigrationOp } from "@intentius/chant-lexicon-sql/postgres";

export const { op } = PostgresMigrationOp({ name: "migrate-app-users-login", env: "prod", table: "app.users", column: "login" });
```

The Op adds the new column, keeps it written with a trigger (both ways for a rename, from the old column for a type change, with `using` as the expression), fills the existing rows in batches of the primary key with a receipt per batch in `<schema>.__chant_receipts`, committed with the batch (ranges of the value for one integer column; for any other key, uuid, text or several columns, ranges between boundaries walked from the key's index once and recorded beside the receipts, so a resumed run finds the same batches), and pauses while a replica in `pg_stat_replication` is behind. What uses the column is carried over to the new one before the gate: each index, a primary key's or unique constraint's included, is built again on the new column with `CREATE INDEX CONCURRENTLY`, and each check and foreign key, another table's that references the column included, is added `NOT VALID` and then validated, all while writes go on. It verifies the new column against the old, stops at a gate bound to the plan, the carried objects and the verified column, then switches in one short transaction: a type change swaps the columns by name, and a rename sets the new column's `NOT NULL` and leaves both names written until the contract; the carried indexes and constraints take their names (a key with `ADD CONSTRAINT ... USING INDEX`), and each view that reads the column is dropped and created again from its declaration, with its grants and owner. A rename gives a name Postgres made from the old column (`users_email_key`) the one it makes from the new (`users_login_key`), or the name the build declares, and keeps the old column's unique constraints and indexes for readers of the old name until the contract. So `integer` to `bigint` on a primary key that other tables reference, or a rename of a uniquely indexed column, runs without a rewrite under `ACCESS EXCLUSIVE`. An identity column's type change moves the identity to the new column under its sequence's name, carrying on from the old sequence's position read under the switch's lock; a `serial` column's sequence is handed over with `OWNED BY`, widened to `bigint` for `bigserial`, and stays its default. A partitioned table is migrated as one: each partition takes the new column, the trigger, the check and the swap from it. The old column is kept for `retain` (default `7d`) and dropped at a second gate. A failed step runs onFailure, which drops what the Op added. A type change within a kind that would rewrite the table in place (SQLPG207) can run as the same Op.

The Op refuses, at its Plan phase and naming each object: a table a logical replication publication sends the column of; an exclusion constraint, a constraint trigger, a materialized view, a rule, a trigger, a policy or a statistics object on the column, a generated column computed from it, an `INVALID` index on it, and a view on it the build does not declare; a generated column itself (Postgres cannot make an existing column generated, so the applier changes it in place); on a partitioned table, an index, a key or a foreign key on the column (none can be built `CONCURRENTLY` there), and a column in the partition key; a partition (run it on its partitioned table) and an inheritance tree (a write to a child does not fire the parent's trigger); a rename of a column with a default, an identity or a serial sequence; and a table without a primary key.

### Transactions

Statements run in the build's order, each object's in the order its changes need, grouped like this:

| Statements | How they run |
|---|---|
| catalog-only: creates, comments, defaults, `NOT VALID` constraints, drops | consecutive ones share one transaction, across objects |
| ones that read or rewrite a table: a type change with a rewrite, `SET NOT NULL`, a validated `CHECK`, `VALIDATE CONSTRAINT`, an index built without `CONCURRENTLY` | a transaction of their own object, so the long statement holds locks on one table and what came before has committed |
| `CREATE INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY`, `ALTER TYPE ... ADD VALUE` | alone, outside any transaction |

A primary key or unique constraint added to a table that exists is two statements: its unique index built `CONCURRENTLY`, then `ADD CONSTRAINT ... USING INDEX`, which changes only the catalog. A `CONCURRENTLY` build that fails leaves an `INVALID` index behind; the applier drops it, and only an invalid one.

### Timeouts

Every statement runs with its own `lock_timeout` and `statement_timeout`, so a statement waiting on another session's lock fails after the lock timeout instead of queueing every later query behind it.

| Setting | Default | Applies to |
|---|---|---|
| `lockTimeoutMs` | 5000 | every statement |
| `statementTimeoutMs` | 60000 | catalog-only statements |
| `scanTimeoutMs` | 0 (no limit) | statements that read or rewrite rows, and `CONCURRENTLY` builds |

Set them per environment on the profile (`sql.profiles.prod.lockTimeoutMs`), or pass them to `postgresApply`. The result records the timeouts, every statement with the values it ran under and the transaction it was in, and how each transaction ended. A lock timeout reads `lock_timeout 5000ms: another session holds a lock this statement needs; SQLSTATE 55P03` in the failed object's error.

### The ownership marker

Postgres has a comment on every kind of object, so the marker is the same trailer, set with `COMMENT ON` in the transaction that runs the `CREATE` (right after it, for an index built `CONCURRENTLY`):

```sql
COMMENT ON TABLE app.users IS 'One row per account [chant managed-by=chant stack=shop env=prod]'
```

The declared `COMMENT ON` for the object is replaced by this one; comments on columns and constraints are sent as written. An extension with no declared comment keeps the comment its control file sets, with the trailer after it. A plan, the deep diff and an import read the comment with the trailer taken off.

### Prune

Prune drops the objects in the declared schemas that the build no longer declares and whose comment carries this project's marker: views first, then indexes (`CONCURRENTLY`), tables, sequences, types and extensions, and schemas last. It never uses `CASCADE`. An object something else still depends on is reported `not-prunable` with the server's message, and an object without the marker, or kept by another tool, is never touched.

### A local server

`chant emulator up --lexicon sql` starts the pinned `postgres:18.6` by digest beside ClickHouse; `--json` reports it as `POSTGRES_URL` with `POSTGRES_USER` and `POSTGRES_PASSWORD`, which the binding reads when no profile names a server.
