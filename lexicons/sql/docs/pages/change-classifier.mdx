Every change between two ClickHouse schemas is classified before anything runs:

| Class | Means |
|---|---|
| metadata only | the server records the change and touches no existing data |
| background rewrite | a mutation rewrites existing parts in the background, with no rollback |
| replace table | ClickHouse cannot alter a stream-engine table, and it stores no rows, so the applier drops and creates it around the views that read it |
| rebuild | ClickHouse cannot make the change to the existing table, and the data has to be copied into a new one; a plan refuses to make it in place |

Two commands report the classification, and `chant lifecycle plan` reports it as each update's disruption (metadata only is `in-place`, a rewrite `rolling`, a replacement or a rebuild `replace`):

```bash
chant sql diff base.json head.json     # two chant build outputs, offline
chant sql plan prod schema.json        # a build output against the prod server
```

Both exit 2 when a change needs a rebuild. `chant sql diff` compares a pull request's base and head builds with no server. `chant sql plan` reads the server `sql.profiles.<env>` binds, and asks that server's formatter about any expression the normalization rules leave different, so the server's own rewriting (`INTERVAL 1 DAY` as `toIntervalDay(1)`, `a+b*2` as `a + (b * 2)`) is not reported as a change.

`chant sql plan` also exits 2 when a declared database holds an object whose definition it cannot read. It names each one under `Refused` (`unreadable` in `--json`) instead of leaving it out. It exits 2 as well when the build names a named collection the server doesn't have, naming each under `Refused` (`namedCollections.missing` in `--json`); see [Named collections](../clickhouse-ddl/#named-collections). Dictionaries are read and planned like the other objects: any change but a comment replaces one (SQLCH245).

A clause chant's parser does not know ([Plain .sql Files](../sql-files/#clauses-chant-does-not-read)) is compared as text, and the rest of its object is planned as usual. A change to one is SQLCH290, refused for review with no rebuild Op suggested, since chant cannot tell what the change takes. A clause only the server prints is a hint, not a change: a newer server printing a clause with its default looks the same as a clause removed from the declaration.

## Stream tables

A table on Kafka, S3Queue, AzureQueue, RabbitMQ, NATS or FileLog stores no rows. It is the consumer that a materialized view reads through, and the position it has reached lives in the broker's committed offsets or in Keeper. There is no `ALTER` for its engine arguments, settings or columns, and there is nothing to copy, so a change to one is neither metadata nor a rebuild. It is SQLCH225, in the replace class (`diffStreamTable` in `src/clickhouse/plan/diff.ts`). The plan refuses nothing for it.

The applier makes the change in place, in this order (`replaceStreamSteps` in `src/clickhouse/apply/statements.ts`): `DETACH TABLE` for each materialized view on the server that reads the table, `DROP TABLE ... SYNC`, the declared `CREATE TABLE`, then `ATTACH TABLE` for the same views. The plan names the views in a hint. Messages wait in the broker, and files wait in the bucket, while the views are detached. A change that moves a table to or from a stream engine is still SQLCH223, a rebuild, and `ClickHouseRebuildOp` refuses a stream-engine table by name (`streamRefusal` in `src/clickhouse/rebuild/observe.ts`).

Two replacements lose the table's position, and the change carries a note saying so (`positionWarnings` in `src/clickhouse/plan/stream.ts`):

- A different `kafka_group_name`, as a setting or as the third engine argument, is a different consumer group. It starts from its own committed offsets, or from the start of the topic when it has none.
- A different S3Queue `keeper_path` is a different record of processed files. Every file already seen is processed again.

An apply killed between the detach and the attach leaves the views detached, and a detached view is not in `system.tables`. Nothing re-attaches it: run `ATTACH TABLE` for each view by hand, then plan again. This has not been run against a server.

The `StreamIngest` composite declares the stream table, the view and the MergeTree target together: see [Composites](../composites/#streamingest).

## After the plan

The plan only reports. [`clickhouseApply`](../applying/) makes the metadata-only, background-rewrite and stream-table changes, and refuses a rebuild the same way the plan does, sending nothing for that object. A rebuild runs as `ClickHouseRebuildOp`, a gated migration Op that creates the new table, backfills it, verifies it and swaps it in: see [Rebuilding a Table](../rebuild/). Both commands print the Op declaration to start from for each refused table.

`chant migrate` plays no part in any of this. It translates a file from one lexicon's format into another's, such as a GitHub Actions workflow into GitLab CI, and does not run schema migrations.

## Statements for a migration file

`chant sql diff base.json head.json --statements` prints the statements that take the base schema to the head one, offline: each one the applier would send for the same change, after a comment naming its object, rule and class. `--json` prints them as one document, which `diffStatements(before, after)` from `@intentius/chant-lexicon-sql` also returns:

```sql
-- events (analytics.events): SQLCH201 metadata
ALTER TABLE `analytics`.`events` ADD COLUMN region String DEFAULT 'eu' AFTER `user_id`;

-- events (analytics.events): SQLCH210 rewrite, waits for its mutation
ALTER TABLE `analytics`.`events` MODIFY COLUMN `kind` LowCardinality(String);

-- sessions (analytics.sessions): SQLCH220 made by ClickHouseRebuildOp, not a statement:
--   export const { op } = ClickHouseRebuildOp({ name: "rebuild-analytics-sessions", env: "<env>", table: "analytics.sessions", dualWrite: { mode: "materialized-view", cutoverColumn: "ts" } });
```

A rebuild is never DDL: it is a step naming `ClickHouseRebuildOp`, or for a view or a database, which the Op does not rebuild, a manual step. A column or object drop is a statement marked destructive. Each `CREATE` carries the project's ownership marker, as the applier stamps it. The command exits 2 when a step is not a statement. A migration runner's history table (`schema_migrations`, `goose_db_version`; see [Importing a Live Server](../importing/)) is never dropped: the report names it in a hint. Two things the applier asks the server are left out: whether a difference is formatting only, and whether a database is empty before it is dropped.

`--topology` renders the statements for where they will run: `single` (the default), `cluster:<name>`, `replicated` or `cloud`. On a cluster every statement carries `ON CLUSTER` and a MergeTree-family table becomes `Replicated*MergeTree` with its Keeper path; in a `Replicated` database the tables are `Replicated*MergeTree` with no path and no `ON CLUSTER`. `diffStatements(before, after, { topology })` takes the same choice; see [Applying to a Server](../applying/#topology).

## Migration files on a pull request

A workspace member that is a goose, golang-migrate, clickhouse-migrations or Flyway directory (see [Workspace kinds](/chant/reference/workspace-kinds/)) has no declaration to diff. On a pull request, `chant components pr-plan` lists each migration file the pull request adds to such a member, and the plan note gives every statement in it the class the rules below give the same change. This is the "check" level of adopting chant beside an existing migration tool: it reads files, applies nothing and contacts no server, so it needs no `--env`.

The up statements are the ones `chant sql replay` would run: goose's `-- +goose Up` section, the whole `.up.sql` file for golang-migrate, the whole file for clickhouse-migrations, and a Flyway file after placeholder substitution with the values in `flyway.toml` or `flyway.conf`. A file the base commit already has is not new, whatever the pull request does to it. Undo files are left out.

```text
`db/00002_orders.sql` (member `ledger`, postgres)
- 1. `CREATE INDEX orders_status_idx ON orders (status)`: needs CONCURRENTLY (SQLPG241, SHARE)
- 2. `ALTER TABLE orders ALTER COLUMN a TYPE bigint`: undecided between SQLPG206 metadata only and SQLPG207 ACCESS EXCLUSIVE rewrite or scan
```

Each statement is read with the dialect's parser (`CREATE`, `GRANT`, `COMMENT ON`) or word by word (`ALTER`, `DROP`, `RENAME`), and the lock on a Postgres statement is the one its rule's text names. The code is `lexicons/sql/src/postgres/plan/statements.ts` and `lexicons/sql/src/clickhouse/plan/statements.ts`.

A statement alone cannot always decide a rule, and then the note names the candidates and does not guess:

- `ALTER COLUMN ... TYPE` is SQLPG206 or SQLPG207 by the column's old type, and SQLPG208 as well with a `USING` expression.
- `MODIFY COLUMN <type>` is SQLCH210 or SQLCH211, `DROP COLUMN` SQLCH202 or SQLCH213, and `RENAME COLUMN` SQLCH212 or SQLCH213, by whether the column is in a key. When the same file creates the table, its keys are known and the statement is classified.
- `MODIFY ORDER BY` is SQLCH220, a rebuild. It is SQLCH216 or SQLCH220 when the same `ALTER` adds the columns the new key ends with, unless the file created the table and shows the old key is kept.
- `CREATE OR REPLACE VIEW` is SQLPG250 or SQLPG251 by whether the view keeps its columns.

A statement that reads or writes rows (`INSERT`, `UPDATE`, `TRUNCATE`) is listed as data. A schema change no rule covers, such as `ALTER TABLE ... OWNER TO` or a ClickHouse `DROP PARTITION`, is listed as having no class.

## Identity and renames

An object is identified by its export name between two builds, so a changed name in the SQL under the same export is a rename. Against a server, which has no export names, an object is identified by `database.name`; a declaration renamed since the server last saw it says so with `-- previously: <old name>` before its CREATE.

A column is identified by its name. A renamed column says so on its own line:

```sql
CREATE TABLE events (
  event_kind LowCardinality(String), -- previously: kind
  ...
```

Without the hint the change is a drop and an add, and the report points out a drop and an add with the same type in the same place.

## The rules

| Id | Class | Change | Restriction |
|---|---|---|---|
| SQLCH200 | create | Create an object | A new database, table, view, dictionary, function, user, role, row policy, quota or settings profile is created, or a grantee gets its first grants; nothing existing changes. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create) |
| SQLCH201 | metadata only | Add a column | ADD COLUMN only changes metadata: parts written before it read the column's default until they are merged or the column is materialized. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/column#add-column) |
| SQLCH202 | metadata only | Drop a column | DROP COLUMN removes the column's data from every part; it is not undone. A column in a key cannot be dropped (SQLCH213 covers that case). [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/column#drop-column) |
| SQLCH203 | metadata only | Change a comment | COMMENT COLUMN and MODIFY COMMENT change metadata only. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/comment) |
| SQLCH204 | metadata only | Add, drop or change a skip index | ADD INDEX and DROP INDEX change metadata; a new index covers parts written after it until MATERIALIZE INDEX rebuilds it for older parts. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/skipping-index) |
| SQLCH205 | background rewrite | Change a TTL | MODIFY TTL is recorded in metadata, and with materialize_ttl_after_modify (on by default) the server recalculates the TTL over existing data as a mutation. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/ttl) |
| SQLCH206 | metadata only | Change a table setting | MODIFY SETTING and RESET SETTING change metadata, for settings the server lets change after creation. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/setting) |
| SQLCH207 | metadata only | Change a column's default | MODIFY COLUMN with a new DEFAULT, MATERIALIZED or ALIAS expression changes metadata; values already written keep the old default until the column is materialized. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/column#modify-column) |
| SQLCH208 | metadata only | Change a column's codec | MODIFY COLUMN ... CODEC applies to parts written afterwards; existing parts keep their codec until they are merged or rewritten. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/column#modify-column) |
| SQLCH209 | metadata only | Move a column | MODIFY COLUMN ... FIRST \| AFTER changes the column order in metadata only. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/column#modify-column) |
| SQLCH210 | background rewrite | Change a column's type | Changing the type of a column outside the primary key is a mutation that rewrites the column in every part in the background, with no rollback. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/column#modify-column) |
| SQLCH211 | rebuild | Change the type of a key column | The type of a primary key column can change only when the change does not modify the data (for example adding values to an Enum); anything else needs a new table. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/column#modify-column) |
| SQLCH212 | metadata only | Rename a column | RENAME COLUMN changes metadata, for a column that is not in a key. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/column#rename-column) |
| SQLCH213 | rebuild | Rename or drop a key column | A column in the sorting key, the primary key or the partition key cannot be renamed or dropped. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/column#rename-column) |
| SQLCH214 | metadata only | Add, drop or change a projection | ADD PROJECTION and DROP PROJECTION change metadata; a new projection covers new parts until MATERIALIZE PROJECTION builds it for older ones. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/projection) |
| SQLCH215 | metadata only | Add or drop a constraint | ADD CONSTRAINT and DROP CONSTRAINT change metadata; existing rows are not checked. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/constraint) |
| SQLCH216 | metadata only | Append new columns to the sorting key | MODIFY ORDER BY can only append columns added by ADD COLUMN in the same ALTER, and leaves the primary key as it was; the declaration must keep the old key as PRIMARY KEY. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/order-by) |
| SQLCH217 | metadata only | Change the sampling key | MODIFY SAMPLE BY changes metadata; the new sampling expression must be part of the primary key, and the server refuses it otherwise. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/sample-by) |
| SQLCH218 | rebuild | Change a setting fixed at creation | A table setting the server marks read-only (such as index_granularity) is fixed when the table is created and needs a new table to change. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/setting) |
| SQLCH219 | metadata only | Replace a table over a table function | A table declared AS a table function (numbers, remote, s3, url) stores no data of its own and has no ALTER for its function; CREATE OR REPLACE TABLE replaces its call and columns, and queries read through the new one. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create/table#from-a-table-function) |
| SQLCH220 | rebuild | Change the sorting key | The sorting key is the on-disk order of every part (and in ReplacingMergeTree the deduplication identity); beyond appending new columns (SQLCH216) it cannot change in place. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/order-by) |
| SQLCH221 | rebuild | Change the primary key | The primary key cannot be changed by ALTER; MODIFY ORDER BY leaves it as it was. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/order-by) |
| SQLCH222 | rebuild | Change the partition key | There is no ALTER for the partition key; parts are laid out by it when they are written. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter) |
| SQLCH223 | rebuild | Change the table engine or its arguments | There is no ALTER for a table's engine or its arguments (a ReplacingMergeTree version column, a Distributed sharding key); a different engine is a different table. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter) |
| SQLCH224 | rebuild | Change what kind of object it is | A table cannot become a view or a view a table; the old object is dropped and the new one created. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create) |
| SQLCH225 | replace table | Change a stream table | A Kafka, S3Queue, AzureQueue, RabbitMQ, NATS or FileLog table stores no rows and has no ALTER for its engine arguments, settings or columns; the views that read it are detached, the table is dropped and created, and the views are attached again. Its position (a Kafka group's offsets, an S3Queue's record of processed files) is kept by the broker or Keeper, not by the table. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create/table) |
| SQLCH230 | metadata only | Rename or move a table or view | RENAME TABLE changes the name, or moves the object to another database, in metadata on an Atomic database. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/rename) |
| SQLCH231 | metadata only | Rename a database | RENAME DATABASE is metadata only, for an Atomic database. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/rename) |
| SQLCH232 | rebuild | Change a database's engine | A database's engine is fixed at creation; there is no ALTER for it. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create/database) |
| SQLCH240 | metadata only | Change a view's query | A plain view stores no data; CREATE OR REPLACE VIEW replaces its query. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create/view) |
| SQLCH241 | metadata only | Change a materialized view's query | ALTER TABLE ... MODIFY QUERY replaces the query without stopping inserts; rows already written are not recomputed. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/view) |
| SQLCH242 | rebuild | Change a materialized view's target | A materialized view's TO target is fixed at creation; the view is dropped and created again, and inserts into its source in between are not seen. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create/view) |
| SQLCH243 | rebuild | Change a materialized view's own storage | A materialized view without TO keeps its rows in an inner table whose engine and keys are fixed like any table's. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create/view) |
| SQLCH244 | metadata only | Change a refreshable view's schedule | ALTER TABLE ... MODIFY REFRESH changes the schedule of a refreshable materialized view. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/view) |
| SQLCH245 | metadata only | Change a dictionary | A dictionary stores no data of its own: CREATE OR REPLACE DICTIONARY replaces its attributes, key, source, layout, lifetime or range, and it loads again from its source. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create/dictionary) |
| SQLCH260 | metadata only | Change a function | A SQL user-defined function stores no data: CREATE OR REPLACE FUNCTION replaces its parameters and expression, and queries that call it use the new one. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create/function) |
| SQLCH270 | metadata only | Change a role | ALTER ROLE ... SETTINGS replaces a role's settings; its grants are untouched. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/role) |
| SQLCH271 | metadata only | Change a user | ALTER USER sets one clause (HOST, DEFAULT ROLE, DEFAULT DATABASE, GRANTEES, SETTINGS, VALID UNTIL, IDENTIFIED) and leaves the rest, the password and the grants untouched. Sessions already open keep the old settings. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/user) |
| SQLCH272 | metadata only | Change a row policy | CREATE ROW POLICY OR REPLACE replaces the policy's condition, kind and roles; queries started after it see the new one. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create/row-policy) |
| SQLCH273 | metadata only | Grant a privilege or a role | GRANT adds a privilege or a role to a user or role; it takes effect for new queries. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/grant) |
| SQLCH274 | metadata only | Revoke a privilege or a role | REVOKE takes a privilege or a role away, including one granted by hand to a grantee the build declares grants for; queries that relied on it fail from then on. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/revoke) |
| SQLCH275 | metadata only | Change a quota | ALTER QUOTA sets the quota's key, one interval's limits (NO LIMITS takes the interval away) or whom it applies to, on the quota that is there, so what names it still does. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/quota) |
| SQLCH276 | metadata only | Change a settings profile | ALTER SETTINGS PROFILE replaces the profile's settings, constraints and inherited profiles, or whom it applies to; the users, roles and profiles that name it keep it. Sessions already open keep the old settings. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/alter/settings-profile) |
| SQLCH290 | rebuild | Change a clause chant does not read | chant's parser does not know this clause, so it cannot tell whether ALTER can make the change in place; the plan refuses it rather than guess. Review it: make it by hand with the ALTER the server documents for the clause, or drop and create the object. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/create/table) |
| SQLCH250 | drop | Drop an object | DROP removes the object and, for a table, its data; it is not undone. [ClickHouse docs](https://clickhouse.com/docs/sql-reference/statements/drop) |
