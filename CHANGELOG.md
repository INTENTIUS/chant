# Changelog

This file records changes to what chant prints or writes for a plain project, the level-0 changes listed in [#2525](https://github.com/INTENTIUS/chant/issues/2525). The full list, with the release that warned about each one, is on the [level-0 exceptions](docs/src/content/docs/reference/level-0-exceptions.mdx) page.

## Unreleased

- [#3597](https://github.com/INTENTIUS/chant/issues/3597) `chant lifecycle diff --live` builds the project the way `chant build` does, so it folds unless `build.fold: false` or `--no-fold` says otherwise; it used to build on the run path, where every field a composite produced had an unknown origin. A drifted field a composite produced now prints one more line under its row, naming the composite call and argument with the file and line it was written on (`spec.replicas on K8s::Apps::Deployment webDeployment comes from WebApp({ replicas: 3 }) at src/app.ts:11`), or saying the composite fixes the field, or that its origin is unknown and why. The proposal line under it gives `at <file>:<line>` relative to the project where it used to give ` in <absolute file>`. A field declared directly prints as before. In `--json`, each `reconcile` row gains `summary`, and a composite origin gains `call` and `arguments` (file, line, column and the argument as written). `BuildResult.foldProvenance` entries gain `compositeCall` and the same origin fields.
- [#3555](https://github.com/INTENTIUS/chant/issues/3555) a workspace member's pull-request workflow is named `chant-pr.<member>.<env>` and its file is `chant-pr.<member>.<env>.yml` (`.gitlab/ci/chant-pr.<member>.<env>.gitlab-ci.yml` on GitLab), and a member's component pipeline workflow is named `chant-components.<member>.<env>` on GitHub, Forgejo and GitLab, so member `a` in environment `b-c` and member `a-b` in environment `c` no longer share a name. Regenerate a member's pipelines to move to the new names. The MCP `op-run` tool takes `env`, as `op-approve` does. The k8s CRD docs list the Grafana Operator's alerting kinds as generated, and the otel docs and skill name `sending_queue.block_on_overflow`.
- [#3555](https://github.com/INTENTIUS/chant/issues/3555) `chant build --lexicon-output` builds the project once and writes each file from that build, instead of building once per file. The "No serializer found for lexicon" warning now ends with "List the lexicon in chant.config.ts." The otel lexicon types `sending_queue.block_on_overflow` and reports the old `sending_queue.blocking` as OTEL107, since the collector reads only `block_on_overflow`.
- [#3555](https://github.com/INTENTIUS/chant/issues/3555) fountain: `chant run <op> --on fountain` posts `--work` and `--holder` on the command line it hands the sandbox, so an Op whose work lease leaves the item to the run can run on fountain, and `chant run approve ... --on fountain` carries the gated run's `--work` and `--holder` onto the re-run. A runtime says it carries them with the new optional `OpRuntimeProvider.carriesWork`; any other non-local runtime still refuses both flags by name. The fountain lexicon no longer exports `envOfPrompt`, which split a prompt on whitespace; `flagsOfPrompt` reads `--env` with the same quote-aware split `chant acp` uses. The MCP `op-approve` tool takes `env` and passes it to the runtime's `resolveGate`, as `chant run approve --env` does. A hosted run is still named by its conversation id, which every run on one teammate's thread shares: fountain exports no turn id to the command it spawns. Plain projects see no change.
- [#3555](https://github.com/INTENTIUS/chant/issues/3555) fountain: `chant acp` answers `session/resume` and advertises it in `initialize`, so a teammate's second and later turns run. Fountain spawns the agent afresh for every turn and resumes the conversation's session from the second turn on; an agent that offered no way to resume failed that turn before its prompt was sent (`acp_agent_cannot_resume`). Plain projects see no change.

Two level-0 changes that shipped in 0.81.0 without a warning release are now on the [level-0 exceptions](docs/src/content/docs/reference/level-0-exceptions.mdx) list, and so is a third, below. The maintainer accepted all three on 2026-09-30.

- [#3555](https://github.com/INTENTIUS/chant/issues/3555) generated Forgejo workflows carry no `permissions:` block, so the run page no longer shows a "Workflow warnings" box for it. The Forgejo dialect drops every scope Forgejo ignores, at the workflow and the job, and keeps `id-token` on a job that has it, which is what an OIDC role assumption needs ([#3500](https://github.com/INTENTIUS/chant/issues/3500)). `.forgejo/workflows/chant-pr.yml` from the pull-request pipeline loses its two job `permissions:` blocks, and `chant migrate --to forgejo` drops them from a GitHub workflow the same way. No build warning is printed for the dropped key.
- [#2550](https://github.com/INTENTIUS/chant/issues/2550) ledger reads and writes run `git ls-tree --full-tree`, so a project in a subdirectory of its repository appends to `chant/lifecycle` instead of having its second append refused. Ledger paths do not move. `level0-ledger.test.ts` now holds the subdirectory case ([#2610](https://github.com/INTENTIUS/chant/pull/2610)).
- [#3465](https://github.com/INTENTIUS/chant/issues/3465) `changedFilesBetween` lists every changed file in the repository, not only those under the project, so for a level-0 project in a subdirectory it now also returns `../` paths and a lexicon's `changedUnits` can select a module that sits outside the project. A GitLab member's pull-request pipeline file carries no `workflow:name`, so the files the root `.gitlab-ci.yml` includes no longer collide on it. With `--member`, `pr-plan` and `pr-apply` post no note on a pull request the change does not reach; the commit status is still set.
- [#2535](https://github.com/INTENTIUS/chant/issues/2535) `chant check-lexicon` prints a tier-1 row for the `./workspace-kinds` subpath for every lexicon, which passes when a lexicon has no such subpath ([#2631](https://github.com/INTENTIUS/chant/pull/2631)).
- [#2547](https://github.com/INTENTIUS/chant/issues/2547) plan digests are written as `jcs1-sha256:<hex>` instead of `sha256:<hex>`. The hex does not change, since the digest is still the SHA-256 of the RFC 8785 canonical JSON of the plan. The prefix shows in the `plan:` and `approve:` lines of a gated run, in `chant approve --plan`, in the pending facts and resolutions of `_gates/<name>.jsonl`, and in `chant workspace upgrade` output. A pending gate or an approval recorded as `sha256:<hex>` still matches the same plan, and `chant approve --plan` takes either prefix. No CLI golden moves.
- [#3365](https://github.com/INTENTIUS/chant/issues/3365) prometheus lexicon: `chant import` of a k8s manifest turns a `prometheus.yml` held as text in a ConfigMap into `ScrapeConfig`s, a `PrometheusConfig` and `prometheusConfigYaml([...])` in the ConfigMap, where it used to leave the value a string; the lexicon's `validate()` prints a `promtool-check-config` row (marked skipped when `promtool` is not installed); and `eventCount(selector, window?)` is a new export that builds the first-sample-aware event count for a sparse `Slo` SLI ([#3548](https://github.com/INTENTIUS/chant/issues/3548)).
- [#3555](https://github.com/INTENTIUS/chant/issues/3555) the change-set document's `digest` is `changeSetDocumentDigest`: the set digest over `{ member, planDigest }` as before, plus each member's status and holes, the entries and the side effects. A pull request's apply that resumes from its cached record now checks a re-planned member only against entries the approval binds, and refuses a record whose entries, holes or side effects were edited. Every change-set digest moves once, so a pull request planned under an earlier chant and applied under this one asks for approval again. A wave's set digest (`changeSetDigest`, `waveSetDigest`) does not move. The generated pull-request apply job's concurrency group, resource group and cache key for a workspace member are `chant-apply.<member>.<env>` instead of `chant-apply-<member>-<env>`, so member `a` in environment `b-c` and member `a-b` in environment `c` no longer share one; a single project's `chant-apply-<env>` does not change.

## 0.81.0

The level-1 workspace release: `chant.workspace.json`, `chant workspace init`, `ls`, `check`, `build`, `lint`, `audit`, `graph`, `status`, `records`, `verify` and `upgrade`, member ledgers, member links, template parameters at `chant init --from`, and the read contract. None of it runs for a project without a declaration. The level-0 changes below shipped their warnings in 0.80.0.

- [#2528](https://github.com/INTENTIUS/chant/issues/2528) audit reports a truncated scan: the JSON report carries `truncated: { limit, flag }` and the text reports name the limit and `--max-files`, and TF023 honours every `.gitignore` between a file and the scan root. The v0.80.0 warnings are removed. No level-0 golden moves ([#2607](https://github.com/INTENTIUS/chant/pull/2607)).
- [#2514](https://github.com/INTENTIUS/chant/issues/2514) real SHA-256 digests: `contentDigest` returns `"sha256:" + sha256(utf8(x))`, so every `manifestDigest` and every digest of a synthesized template or SBOM changes once for the same content. Release records and build manifests that hold old digests are never rewritten or re-keyed. They read back flagged `legacy-digest`, still resolve by their old digest, and are accepted through `0.89.x`. Plan digests and snapshot props hashes now sort keys by code unit rather than by locale, so a plan whose keys mix case can digest differently once, and a gate approved for it before the upgrade asks for approval again. No level-0 golden moves ([#2606](https://github.com/INTENTIUS/chant/pull/2606)).
- [#2574](https://github.com/INTENTIUS/chant/issues/2574) component gate approvals are bound to the environment and plan digest they were given for, and the binding is enforced. `chant run --components`, `chant components promote`, `chant components rollback` and `chant components redeploy` accept only an approval for their own environment and plan, and for a promote, rollback or redeploy the plan includes the recorded digest being deployed. An approval recorded before this change records neither, and it is refused: the run stops at the gate with exit 3 and prints `chant approve <component> <gate> --env <env>`. `chant approve` takes `--env` to pick which environment's pending fact to approve. The `v0.80.0` warning is removed. No level-0 golden moves ([#2594](https://github.com/INTENTIUS/chant/pull/2594)).
- [#2527](https://github.com/INTENTIUS/chant/issues/2527) one discovery walk: build, lint, component, Op and audit discovery share one walk. Every walk skips dot-directories (audit still reads `.github/` and `.forgejo/`), `dist` and git-ignored files, nested `.gitignore` files included and asked only below the scanned directory. Inside a project, a child directory with a project config is a boundary for every walk; a lint-only `chant.config.json` is not one, and a `chant.config.ts` always is. Outside every project, every child project is read, and the old rule that treated the first child project found as the project's own source is gone. Op discovery keeps its upward search for the Op root and stops at child projects on the way down. Op and audit discovery now read the project's `exclude` and `include` globs (audit from `chant.config.json` only), and `include` re-admits anything the walk skips apart from `node_modules` and `.git`. Workspace members and example-group matches leave the root project's walk only when a workspace declaration exists, read through the declaration reader from [#2593](https://github.com/INTENTIUS/chant/pull/2593). The v0.80.0 warnings go. The only golden that moves is the stderr of `adopt-alb-services/audit-format-json.golden`, which loses the warning ([#2617](https://github.com/INTENTIUS/chant/pull/2617)).
- [#2618](https://github.com/INTENTIUS/chant/issues/2618) `chant audit` never evaluates the audited repository's `chant.config.ts`. Through v0.80.0 it did: the CLI loaded the config before dispatching every command, audit included, and the #2528 warning path loaded it again. A lexicon the config declares by path is now read from the config's text and named in audit's messages, and its module is never imported. `chant workspace audit` runs no member's config either, including through the `workspace member-run` process. The fixes are [#2597](https://github.com/INTENTIUS/chant/pull/2597), [#2598](https://github.com/INTENTIUS/chant/pull/2598) and [#2617](https://github.com/INTENTIUS/chant/pull/2617).

## 0.80.0

Warning release for four listed level-0 changes. Nothing chant prints on stdout or writes changes in this release; each warning goes to stderr, and the change it warns about can land from the next release.

- [#2514](https://github.com/INTENTIUS/chant/issues/2514) real SHA-256 digests: one warning per project when a release ledger or build manifest holds an old 32-bit digest ([#2568](https://github.com/INTENTIUS/chant/pull/2568)).
- [#2527](https://github.com/INTENTIUS/chant/issues/2527) one discovery walker: each walker warns about the files the converged walker will read differently, and names the `include` or `exclude` glob that keeps today's behaviour ([#2571](https://github.com/INTENTIUS/chant/pull/2571)).
- [#2528](https://github.com/INTENTIUS/chant/issues/2528) audit: a warning when the local walk stops at its 1000-file limit, a new `--max-files <n>` flag, and a warning for each TF023 path that a nested `.gitignore` covers ([#2570](https://github.com/INTENTIUS/chant/pull/2570)).
- [#2574](https://github.com/INTENTIUS/chant/issues/2574) component gate approvals: a warning when a component gate passes on an approval that records no plan ([#2582](https://github.com/INTENTIUS/chant/pull/2582)).
