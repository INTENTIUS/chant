# Changelog

This file records changes to what chant prints or writes for a plain project, the level-0 changes listed in [#2525](https://github.com/INTENTIUS/chant/issues/2525). The full list, with the release that warned about each one, is on the [level-0 exceptions](docs/src/content/docs/reference/level-0-exceptions.mdx) page.

## Unreleased

- [#4553](https://github.com/INTENTIUS/chant/issues/4553) breaking: one exit-code table, `CHANT_EXIT` in `@intentius/chant/exit-codes`, documented on the [exit codes](docs/src/content/docs/reference/exit-codes.mdx) page: 0 done, 1 failed, 2 drift, 3 waiting, 4 moved, 5 held, 6 superseded, 7 denied, 8 declined. A moved plan exits 4 where it exited 3, from `pr-apply` and from every command that runs capability steps. `chant lock` and `pr-apply` under `ci.locks` exit 5 for a held target, where they exited 3. A policy denial exits 7 at `pr-plan` (was 1) and at `pr-apply` (was 3). `chant lifecycle drift` refuses a read with 1 (was 3). Gates and other waits keep 3, and op waves keep 3 to 8. Usage and config errors stay 1. The terraform lexicon maps choudoufu's refusals (`terraformExitOf`), and a choudoufu plan made against another estate is now a failure, not a moved plan. The pulumi lexicon maps Pulumi's codes and plunge's 40 (`pulumiExitOf`). No switch keeps the old codes.

- [#4473](https://github.com/INTENTIUS/chant/issues/4473) a new package, `@intentius/chant-lexicon-pulumi`, published with chant for the first time. It carries the `pulumi` member kind ([#4453](https://github.com/INTENTIUS/chant/issues/4453)), its preview change set, refresh drift and outputs ([#4455](https://github.com/INTENTIUS/chant/issues/4455)), and since [#4468](https://github.com/INTENTIUS/chant/issues/4468) the tier-1 lexicon checks: completion and hover over `Pulumi.yaml`, stack config and the member declaration, lint and post-synth rules, an example workspace, a docs page, and `dist/manifest.json`. `@intentius/chant/drift-record` and `@intentius/chant/pulumi-urn` are importable from the published chant, and `chant workspace drift`, `chant lifecycle drift` and `chant workspace promote --all` ship in it.

- [#4475](https://github.com/INTENTIUS/chant/issues/4475) drift records: a keyed array element in an attribute path, as the deep read writes it (`Tags[#api-token-owner].Value`), now counts as a key, the way a map key does. A drifted tag or environment entry whose key looks like a secret (`DB_PASSWORD`, a token) has its values redacted in the drift record; before, it kept them.

- [#4458](https://github.com/INTENTIUS/chant/issues/4458) terraform lexicon: `moved`, `import`, `removed` and `check` blocks are entities (`Terraform::Moved`, `Terraform::Import`, `Terraform::Removed`, `Terraform::Check`), with their references as graph edges. `chant graph` and `chant workspace graph` print nodes for them that they did not print before.

- [#4457](https://github.com/INTENTIUS/chant/issues/4457) terraform lexicon: a root's configuration is the files its binary reads. `.tf.json` is read for terraform, and `.tofu` and `.tofu.json` too for tofu and choudoufu, with `x.tofu` shadowing `x.tf`. A JSON file yields the entities its HCL twin does. Every reader (graph, compose, backend, changed roots, live detection, pin rollouts, audit discovery) uses the same list, so a root written in JSON or `.tofu` is no longer partly invisible.

- [#4486](https://github.com/INTENTIUS/chant/issues/4486) graph: instance nodes for `count = var.n`, `length(var.x)`, `for_each = var.m` and `toset(var.l)`, counted from the variable's default, the root's tfvars and varFiles, and a child module's call arguments, and for blocks under an expanded module call, as `<member>/<root>/module.app[0]/aws_eip.pool[1]` with `instanceScope` on the node. A plan address under an expanded call maps to that id.

- [#4463](https://github.com/INTENTIUS/chant/issues/4463) `terraform-apply` previews a root outside a composed group whose `vars` read an output not known yet, with a typed stand-in per such variable. What the stand-ins drive is marked unknown, the change-set member lists them under the new `placeholders` field, and the apply plans again with the real values and refuses a plan beyond the preview's shape (`PlanShapeMovedError`). A preview that cannot be made stays a hole whose reason says why.

- [#4467](https://github.com/INTENTIUS/chant/issues/4467) `kubectl-apply` plans one hole, `inputs from <component>; re-checked on apply`, when its inputs wait on another component, and reads or dry-runs nothing for it.

- [#4465](https://github.com/INTENTIUS/chant/issues/4465) `chant components promote`, `components fan-out` and `run --components` plan and apply a group of components one capability declares `planGroup` and `runGroup` for as one, as `pr-plan` and `pr-apply` do (ws-107), and print a line per group with each member's outcome. Under `--wave-gate` no group forms and each member falls back as `wave-gate`.

- [#4478](https://github.com/INTENTIUS/chant/issues/4478) terraform lexicon: the composition and the state store give one answer on where a root's state is and whether chant can lock it. The declared backend is read with the `-backend-config` flags of `TF_CLI_ARGS`, `TF_CLI_ARGS_init` and `backendConfig` over it, and a disagreement with what `init` recorded (another type, or a key with two values) is refused with a reason naming both.

- [#4459](https://github.com/INTENTIUS/chant/issues/4459) terraform lexicon: `terraform.roots.<name>.backendConfigFiles` lists backend-config files. Every `init` chant runs passes them as `-backend-config=<path>` before the key/value pairs, and the backend verdict reads them.

- [terragucci#1274](https://github.com/INTENTIUS/terragucci/issues/1274) terraform lexicon state: `takeSourceLocks` and `takeLocksWithSources` lock a workspace a state is read from (such as a Terraform Cloud workspace a migration moves from) before any state lock, and release it when a later lock cannot be taken (`SourceLockedError`). `takeLocks` takes any store with the lock methods.

- [#4484](https://github.com/INTENTIUS/chant/issues/4484) terraform lexicon: a root may set `signalOnly: true`. Change detection still counts it, and the build, the behaviour build, live root names and the drift read skip it.

- [#4483](https://github.com/INTENTIUS/chant/issues/4483) terraform lexicon: `choudoufuPlanSet` is an Op activity, with a contract and a step builder, so an Op can plan several live choudoufu roots and hand each root's change set to `composeChangeSet`.

- [#4482](https://github.com/INTENTIUS/chant/issues/4482) a TerraformApplyOp's Init step publishes `TerraformRootPath`, and `chant ledger runs` and `chant query` gain `root_member`, the member whose directory holds the root a run applied, so `--where root_member=<member>` finds the local applies of a root another member's Op ran.

- [#4485](https://github.com/INTENTIUS/chant/issues/4485) `chant workspace promote` keeps a stamp record when `live-import -approve` fails after the kind change is written, and a re-run (single member or `--all`) retries only the stamp instead of reporting `already-promoted`. A stamp that fails again stays `stamp-failed` with the command to run.

- [#4461](https://github.com/INTENTIUS/chant/issues/4461) `chant workspace promote` to `choudoufu` runs `choudoufu init -backend=false` in the staging worktree before `live-check`, and leaves what it installs under `.terraform/` out of the patch.

- [#4479](https://github.com/INTENTIUS/chant/issues/4479) `terraform-apply` reads each plan with one `show -json` and no text render.

- [#4455](https://github.com/INTENTIUS/chant/issues/4455) `chant workspace drift --member <m>` reads a member of kind `pulumi` (read `refresh`, `--resource <urn>` allowed) through the pulumi lexicon's `readDrift`; before, it answered `no-drift-read`. A Pulumi or plunge drift record is now placed on the member's graph. `member-outputs` reads a `pulumi` member's outputs through `pulumiOutputSource`, which runs `pulumi stack output --json --show-secrets=false` and `pulumi preview --json` (under `plunge` for a member on plunge).

- [#4453](https://github.com/INTENTIUS/chant/issues/4453) the `pulumi` member kind moved from `@intentius/chant-lexicon-terraform` to a new `@intentius/chant-lexicon-pulumi`, under the same name. A workspace that reads Pulumi members pins the pulumi lexicon. The graph's nodes keep their ids; their `lexicon` is now `pulumi`. The change set takes a `pulumi` planner, from `pulumi preview --json`, and entries may carry `mayAppear: true` for resources a preview cannot list. A Pulumi URN's drift record now gets its graph `node`, and so does a plunge one. A Pulumi member on plunge reads drift with `plunge drift --resource <urn> --stream`.

- [#4404](https://github.com/INTENTIUS/chant/issues/4404) an Op gate's `policy`, `mode` and `context` can no longer be changed by the change being run. `identity.gates.<gate>` in the workspace declaration takes `policy`, `mode` and `context` beside `quorum`, and a run reads each at base in place of the Op's own `approval` field. A `context` key the entry sets wins over the Op's key of that name, and a key only the Op sets still reaches the policy. A field the entry leaves out is read from the Op as before. A gate behaves differently only when its entry sets a field the Op sets to something else, for example `mode: "enforce"` over an Op in `log-only`, which now refuses approvals its policy denies; [Approval Rules](docs/src/content/docs/guide/approval-rules.mdx#migrating-a-gate-whose-op-sets-policy-or-mode) has the migration. New `chant workspace check` finding `WSP153` (`gate-approval-unbased`, a warning) names each gate in a built Op whose `approval` block sets a quorum, policy, mode or context that `identity.gates` does not set at base. `chant workspace upgrade` asks for the quorum `identity.gates.<gate>.quorum` sets at HEAD for a gate in a changed Op file, where it asked for the Op's own. `identityGatesAt` and `identityGateAdmissionAt` return the three fields. The new fields take floor 0.124.49.

- [#4324](https://github.com/INTENTIUS/chant/issues/4324) an Op gate's quorum can no longer be lowered by the change being run. `identity.gates.<gate>` in the workspace declaration takes `quorum` beside `class`, one rule or a list as in an Op's `approval.quorum`, and a run reads it at base in place of the Op's own. A gate whose entry sets no quorum keeps the Op's. A gate policy's `principal.roles` are now the roles `.chant/trust.json` at base gives an approver whose approval is sealed by a signer listed at base, never the roles claimed with `chant approve --role`; an unsealed approval reaches the policy with none. `--role` is still recorded, and `chant approve` notes a role the approver does not hold at base. `@intentius/chant/gate-decision`'s `identityGatesAt` and `identityGateAdmissionAt` return the entry's `quorum`. A policy that permitted on a claimed role now denies; [Approval Rules](docs/src/content/docs/guide/approval-rules.mdx#migrating-a-gate-policy-from-claimed-roles) has the migration. The new field takes floor 0.124.47.

- [#3179](https://github.com/INTENTIUS/chant/issues/3179) member kinds `helm-chart`, `kustomize`, `argo-app`, `flux-kustomization`, `cloudformation`, `cdk` and `pulumi`, shipped as data by the helm, k8s, aws and terraform lexicons. A kinds file may use a new probe, `anyDocument`, that reads YAML or JSON documents by pointer and value. `chant workspace init` proposes a typed member, and pins its package, for a directory a kind from an installed package claims, where it proposed `other` or nothing. Plain projects see no change.
- [#3179](https://github.com/INTENTIUS/chant/issues/3179) the `pulumi` member kind has a `graph` block. It reads the `pulumi stack export` JSON a member checks in as `stack-export.json` beside `Pulumi.yaml`: a node per resource, an edge per `dependencies` entry and `parent`. chant never runs the program; with no export the member has no nodes and `meta.pulumiMember` says `exported: false` and why.

- [#3179](https://github.com/INTENTIUS/chant/issues/3179) `chant workspace graph` now reads members of kind `argo-app`, `flux-kustomization`, `cloudformation`, `kustomize`, `helm-chart` and `cdk`, which were listed with `kind-not-run`. A kustomize or helm member that cannot be rendered because the binary is missing has no nodes and says `rendered: false` and why on the graph's `meta`. Plain projects see no change.

- [#3168](https://github.com/INTENTIUS/chant/issues/3168) org scope. A member of kind `repo` names another repository's workspace as `repo: { url, rev, workspace? }`, with no `dir`. `chant workspace graph` fetches the pinned revision into the user's cache (`$CHANT_CACHE_DIR/repos`) and reads it through that repository's own `chant workspace graph`, folded in the way a nested workspace is. A declaration with `scope: "org"` holds only `repo` members (`WSP013`). `chant workspace check --forge-repos <file>` reads a forge's repository list, as a warden writes it, and reports repositories the declaration lacks (`WSP014`) or names that the forge dropped (`WSP015`); `WSP016` fails a repo URL that carries a credential. `ls`, `graph`, `check` and `status` add `workspace.repo`, the `origin` URL of the repository a document came from, as a contract 1 field. Plain projects see no change.

- [#3672](https://github.com/INTENTIUS/chant/issues/3672) a member kind can name a file each member carries and a JSON Schema it must pass, as `memberFile: { path, schema }` in its kinds file. The schema is read as data from the supplying package; one that doesn't load is `WSP002`. `chant workspace check` fails a member whose file is missing or fails the schema with the new `WSP012`. A kinds file that uses `memberFile` needs this chant. Plain projects see no change.

- [#4300](https://github.com/INTENTIUS/chant/issues/4300) `chant components fan-out` and `chant run --components` take `--target <component>:<address>`, repeatable. `terraform-apply` passes each address as `-target`. `kubectl-apply` sends only the named objects and does not prune. `cfn-deploy`, `helm-upgrade` and any verb that does not say it accepts targets refuse by name. The targets join the digest a gate binds. A capability declares `targets: "accept"` or `{ refuse }`, a plan gives back `CapabilityPlan.targets`, and `DeployContext.targets` carries them. A run without `--target` sees no change. The new fields take floor 0.124.42.

- [#4294](https://github.com/INTENTIUS/chant/issues/4294) `ci.policy` in the workspace declaration runs conftest or OPA over a pull request's change set in `chant components pr-plan` and `pr-apply`, with the settings and the policy read at base. A deny rule refuses the apply (`policy-denied`, exit 3) unless an override on `_gates/policy-override.jsonl` counts; a hold rule needs a person's approval of the plan's own digest; a policy that cannot run refuses with `policy-error`. The report gains `policy`. An Op waves plan file takes `held`, which makes the wave wait for an approval whatever its gate. `@intentius/chant/gate-policy` is a new subpath. There is no unattended outcome. A workspace without `ci.policy` sees no change.

- [#4290](https://github.com/INTENTIUS/chant/issues/4290) a gate's `approval.quorum` no longer counts the roles an approver claims with `chant approve --role`. A role counts only when `.chant/trust.json` at base grants it and the approval is sealed by a signer listed at base. `--role` is still recorded and a gate policy still sees it. `quorum` may also be a list of rules, `{ targets, count, roles }`, with `targets` globs over the run's environment. An Op waves spec gains `approvals.quorum`, the same list read at base with `notAuthor`; under `pr-review` each approving reviewer is written to the ledger on their own line. A gate whose quorum names no roles sees no change. [Approval Rules](docs/src/content/docs/guide/approval-rules.mdx#migrating-from-claimed-roles) has the migration.

- [#3987](https://github.com/INTENTIUS/chant/pull/3987) follow-up: `chant workspace upgrade` has a new chant migration, `fountain-retired-kinds`. In each chant member it removes the `Teammate`, `Schedule` and `Webhook` declarations and `sandbox_mode: "persistent"` from files that import the fountain lexicon, so a repo made from chud's or the studio kit's template builds again. Each removed Schedule is listed as not moved, since its clock now lives outside Managoat. A removed name the file still uses is a conflict. Plain projects see no change.

- [managoat/managoat#2793](https://github.com/managoat/managoat/issues/2793) fountain lexicon: generated from Managoat v0.29.0 (`managoat/managoat`) instead of fountain v0.21.0, so it follows Managoat's removal of the team, its schedules, webhooks and persistent sandboxes, whose routes answer 404 or 422. `Teammate`, `Schedule` and `Webhook` are deprecated stubs: the serializer leaves them out of the manifest, `chant import` skips them in an old manifest, and a build that declares one fails with the new FTN025, which names the replacement. FTN025 also fails an Agent with `sandbox_mode: "persistent"`, a `daytona` or `runner` sandbox provider, or the `opencode` runtime. FTN020, FTN021 and FTN022, which checked only the removed kinds, are gone. The `Steward` composite returns `agent` and `declaration` only, and its Agent names no `sandbox_mode`. `chant run <op> --on fountain` sends a steward's runs to one long-lived conversation, opened and resumed with `channel_id` `chant:steward:<name>`, whose sandbox keeps its disk across park and wake. A profile's `team` is renamed `steward`; `team` still works and warns. The generated types also lose `inference_credential_id`, `allowed_inference_credential_ids` and `permission_policy.ask_timeout`, and gain `session_config`. Plain projects see no change.

  | Removed | Replacement |
  |---|---|
  | `Teammate` and its `fountain:team` thread | One conversation per steward, resumed by `channel_id`; `chant run --on fountain` opens and resumes it |
  | `Schedule` | The Op's own `schedule`, fired by a clock outside Managoat: a CI schedule or a CronJob running `chant run <op> --on fountain`, or `chant operator --steward` where the steward's form is `local` |
  | `Webhook` | None. Read a run's outcome from `chant run status` or `log`, or the conversation's event stream |
  | `sandbox_mode: "persistent"` | Drop it; the steward's conversation keeps its sandbox's disk |
  | `sandbox_provider: "daytona"` or `"runner"` | `"sprites"` or `"e2b"`, or unset |
  | `runtime: "opencode"` | `claude`, `codex`, `gemini` or `acp` |
  | `fountain.profiles.<name>.team` | `fountain.profiles.<name>.steward` |
  | `{ agent, teammate, schedules, webhook } = Steward(...)` | `{ agent, declaration } = Steward(...)` |

  The [fountain steward tutorial](docs/src/content/docs/tutorials/fountain-steward.mdx#coming-from-teammate-schedule-and-webhook) has the same table with the reasons.

- [#4049](https://github.com/INTENTIUS/chant/issues/4049) `chant release publish` refuses a release with no signature that verifies against `.chant/allowed_signers` at base (`release-unsigned`, `release-signature-unverified`), where it refused one only under a `release` gate; `--allow-unsigned` publishes it with a warning, and never overrides the gate. `--require-provenance` refuses a run with no OIDC token (`publish-provenance-missing`). Every target attaches an SBOM and the release's provenance statement, an in-toto statement that carries the cut's signature: an npm package must carry its SBOM at its root (`publish-sbom-missing` otherwise, unless `sbom: false`), an image gets both as OCI referrers, and a forge release gets both as assets, `sbom.spdx.json` written from the member's lockfile unless `sbom` names a file. In CI the npm target runs `npm audit signatures` over what it published (`publish-npm-audit-failed`). The dry run and the published lines name each attachment and the SBOM a package carries. New: `chant release verify <label|digest>` checks a release's signature offline against `.chant/allowed_signers` at the release's commit.
- [#4047](https://github.com/INTENTIUS/chant/issues/4047) `chant release publish` publishes to the targets `release.publish` in `chant.config.ts` declares: npm packages in order (with `--provenance` when the run has an OIDC token), an OCI image layout pushed by digest to a registry such as GHCR or Docker Hub, and release assets on GitHub, GitLab or Forgejo. It is a dry run without `--yes`, and `--json` gains `dryRun`. With a target, it refuses a checkout that is not the release's commit or has changes. Credentials are read from the environment and masked in all output. The `release cut` dry run lists the declared targets. A `release.publish` value that is not a list of targets now fails config loading.
- [#4027](https://github.com/INTENTIUS/chant/issues/4027) `chant release cut` is a dry run without `--yes`: it refuses a dirty tree (an untracked file git does not ignore counts), a commit not on `origin/<trunk>`, and one that isn't green, compiles every environment, and prints what the cut would record and tag and what publishes where, writing nothing. With `--yes` it cuts, records the actor (the signer, the CI's actor, then git's `user.email`) and a run id (`local-<epoch ms>` outside CI, with `runOrigin: { "forge": "local" }` where it wrote `null`), tags the commit `release/<label>` locally, and prints the next command. A cut line gains `runId`. `chant release publish <label|digest>` is new: it refuses a revoked release and, under `identity.gates.release`, an unsigned one, warns when the run has no OIDC token, and publishes nothing until #4047 gives it targets.
- [#4039](https://github.com/INTENTIUS/chant/issues/4039) `chant workspace metrics` reports the four DORA metrics per member and environment: deployment frequency, lead time from commit to running release, change failure rate and time to restore. It computes them from the deploy records, the releases, the release gate's resolutions and the `ci/revoked` tags, and never fetches. A deploy fails when its commit is revoked, or the environment is rolled back from it, within `metrics.failureWindowDays` of it (7 by default), a new declaration field. `--json` prints the read contract's new `delivery-metrics` document. `chant --help` lists the command. A project that never runs it sees no change.
- [#4036](https://github.com/INTENTIUS/chant/issues/4036) `chant lifecycle gc` prunes stored change sets, releases and their templates from `chant/lifecycle`, and old run event files from this host, by a retention policy with defaults that a workspace's `retention` block overrides. It is a dry run without `--yes`. A prune is one new commit that removes files, and never rewrites history; the ledgers are never pruned. It pushes only with `--push`. `chant --help` lists it, and `--push` is a new flag. A project that never runs it sees no change.
- [#3733](https://github.com/INTENTIUS/chant/issues/3733) sql lexicon: with a ClickHouse profile's `access: true`, `chant lifecycle diff --live` lists the grants and revokes an apply would make under PENDING, one row per declared grantee with its GRANT and REVOKE statements, the same changes `chant sql plan` reports (SQLCH273, SQLCH274). They count as drift. A gated `ApplyOp` binds its approval to that diff, so a privilege granted or revoked by hand after the approval moves the plan digest and the apply stops at the gate. Before, an approved apply revoked a hand grant (or restored a hand revoke) that nobody approved. Users, roles and row policies were already compared property by property. Plain projects see no change.
- [#3706](https://github.com/INTENTIUS/chant/issues/3706) sql lexicon: with a Postgres profile's `access: true`, `chant lifecycle diff --live` lists the privilege changes an apply would make under a new PENDING section, one row per object and grantee with its GRANT, REVOKE or ALTER DEFAULT PRIVILEGES statements, the same changes `chant sql plan` reports. They count as drift. A gated `ApplyOp` binds its approval to that diff, so a privilege granted or revoked by hand after the approval moves the plan digest and the apply stops at the gate. Before, an approved apply revoked a hand grant (or restored a hand revoke) that nobody approved. A deep reader may return `pending` changes in its `DeepObservationResult`, and `DeepDiffResult` carries them. Plain projects see no change.
- [#3716](https://github.com/INTENTIUS/chant/issues/3716) sql lexicon: ClickHouse users, roles, row policies and grants are planned, applied and observed only where `sql.profiles.<env>.access` is `true`, as on Postgres. Off by default: `chant sql plan` leaves them out with a hint counting them, the applier reports each as `filtered`, and `chant lifecycle diff --live` reports each as unobserved, `filtered`, without reading the server's access. A server bound by `CLICKHOUSE_URL` has no profile, so access is off there. A project that declares ClickHouse access sets `access: true` on each profile that should manage it. Plain projects see no change.
- [#3717](https://github.com/INTENTIUS/chant/issues/3717) sql lexicon: on the versioned path (`chant sql diff --statements`, `diffStatements`), a ClickHouse user declared without `IDENTIFIED` gets one `ALTER USER` per declared clause (`HOST`, `VALID UNTIL`, `DEFAULT DATABASE`, `GRANTEES`, `SETTINGS`, then `DEFAULT ROLE` after the grants it names), with rule SQLCH271 and no password. Before, its whole declaration was left out, so nothing ever set those clauses. The environment still creates the user with its password before the statements run, as the grants to it already required. Plain projects see no change.
- [#3718](https://github.com/INTENTIUS/chant/issues/3718) sql lexicon: `chant import --from <env>` of a ClickHouse server adopts only the SQL functions the imported objects call (and the functions those call), plus those `sql.profiles.<env>.importFunctions` names by name or by a prefix ending in `*`. Before, it adopted every user-defined function on the server, other projects' included. The import prints a warning naming the functions it left out. A selector (`--type`, `--name`) picks functions as before. Plain projects see no change.
- [#3707](https://github.com/INTENTIUS/chant/issues/3707) sql lexicon: a Postgres `grant` that interpolates a function or procedure (`GRANT EXECUTE ON FUNCTION ${fn} TO r`) builds its statement with the routine's parameter types (`app.total(integer)`), where it used to write the bare name. A plan or apply that reads the build output (`chant sql diff`, `chant sql plan`, the applier) failed on it with "name the parameter types". Plain projects see no change.
- [#3711](https://github.com/INTENTIUS/chant/issues/3711) sql lexicon: `.sql` files (in a build, and `chant import <file>.sql`) read ClickHouse `CREATE USER`, `CREATE ROLE`, `CREATE ROW POLICY` and `GRANT` into the declarations the `user`, `role`, `policy` and `grant` tags make. A password (`IDENTIFIED BY`) or a `REVOKE` is refused with the tag's message, where the file reader used to refuse every access statement. A file with a `CREATE ROW POLICY` is read as ClickHouse. Plain projects see no change.
- [#3713](https://github.com/INTENTIUS/chant/issues/3713) sql lexicon: a build leaves out `.sql` files under a directory named `migrations`, at any depth. Before, a build of the project root (`chant lifecycle diff` or an `ApplyOp`'s plan with no `sourceDir`) read versioned migrations and an ORM's generated migrations as schema and failed. The `.sql` files page says to set `sourceDir` in `chant.config.ts` when other SQL sits beside the schema. Plain projects see no change.
- [#3712](https://github.com/INTENTIUS/chant/issues/3712) the `lifecycleDiff` activity fails its step when `chant lifecycle diff` exits non-zero, a build error among them, instead of returning the error output with a plan digest over it. An `ApplyOp` whose diff cannot build the project now stops at its Plan phase. Before, every such run had the same digest, so an approval of one passed the gate on the next whatever the declarations had become. `exitCode` in the result is always 0. Plain projects see no change.
- [#3703](https://github.com/INTENTIUS/chant/issues/3703) sql lexicon: a `CHECK` or a foreign key added to a Postgres table that exists is planned as `ADD CONSTRAINT ... NOT VALID` (SQLPG217, metadata) followed by `VALIDATE CONSTRAINT` (SQLPG220, validate) in a transaction of its own, so writes go on while the rows are read. ## 0.81.0

The level-1 workspace release: `chant.workspace.json`, `chant workspace init`, `ls`, `check`, `build`, `lint`, `audit`, `graph`, `status`, `records`, `verify` and `upgrade`, member ledgers, member links, template parameters at `chant init --from`, and the read contract. None of it runs for a project without a declaration. The level-0 changes below shipped their warnings in 0.80.0.

- [#2528](https://github.com/INTENTIUS/chant/issues/2528) audit reports a truncated scan: the JSON report carries `truncated: { limit, flag }` and the text reports name the limit and `--max-files`, and TF023 honours every `.gitignore` between a file and the scan root. The v0.80.0 warnings are removed. No level-0 golden moves ([#2607](https://github.com/INTENTIUS/chant/pull/2607)).
- [#2514](https://github.com/INTENTIUS/chant/issues/2514) real SHA-256 digests: `contentDigest` returns `"sha256:" + sha256(utf8(x))`, so every `manifestDigest` and every digest of a synthesized template or SBOM changes once for the same content. Release records and build manifests that hold old digests are never rewritten or re-keyed. They read back flagged `legacy-digest`, still resolve by their old digest, and are accepted through `0.89.x`. Plan digests and snapshot props hashes now sort keys by code unit rather than by locale, so a plan whose keys mix case can digest differently once, and a gate approved for it before the upgrade asks for approval again. No level-0 golden moves ([#2606](https://github.com/INTENTIUS/chant/pull/2606)).
- [#2574](https://github.com/INTENTIUS/chant/issues/2574) component gate approvals are bound to the environment and plan digest they were given for, and the binding is enforced. `chant run --components`, `chant components promote`, `chant components rollback` and `chant components redeploy` accept only an approval for their own environment and plan, and for a promote, rollback or redeploy the plan includes the recorded digest being deployed. An approval recorded before this change records neither, and it is refused: the run stops at the gate with exit 3 and prints `chant approve <component> <gate> --env <env>`. `chant approve` takes `--env` to pick which environment's pending fact to approve. The `v0.80.0` warning is removed. No level-0 golden moves ([#2594](https://github.com/INTENTIUS/chant/pull/2594)).
- [#2527](https://github.com/INTENTIUS/chant/issues/2527) one discovery walk: build, lint, component, Op and audit discovery share one walk. Every walk skips dot-directories (audit still reads `.github/` and `.forgejo/`), `dist` and git-ignored files, nested `.gitignore` files included and asked only below the scanned directory. Inside a project, a child directory with a project config is a boundary for every walk; a lint-only `chant.config.json` is not one, and a `chant.config.ts` always is. Outside every project, every child project is read, and the old rule that treated the first child project found as the project's own source is gone. Op discovery keeps its upward search for the Op root and stops at child projects on the way down. Op and audit discovery now read the project's `exclude` and `include` globs (audit from `chant.config.json` only), and `include` re-admits anything the walk skips apart from `node_modules` and `.git`. Workspace members and example-group matches leave the root project's walk only when a workspace declaration exists, read through the declaration reader from [#2593](https://github.com/INTENTIUS/chant/pull/2593). The v0.80.0 warnings go. The only golden that moves is the stderr of `adopt-alb-services/audit-format-json.golden`, which loses the warning ([#2617](https://github.com/INTENTIUS/chant/pull/2617)).
- [#2618](https://github.com/INTENTIUS/chant/issues/2618) `chant audit` never evaluates the audited repository's `chant.config.ts`. Through v0.80.0 it did: the CLI loaded the config before dispatching every command, audit included, and the #2528 warning path loaded it again. A lexicon the config declares by path is now read from the config's text and named in audit's messages, and its module is never imported. `chant workspace audit` runs no member's config either, including through the `workspace member-run` process. The fixes are [#2597](https://github.com/INTENTIUS/chant/pull/2597), [#2598](https://github.com/INTENTIUS/chant/pull/2598) and [#2617](https://github.com/INTENTIUS/chant/pull/2617).
